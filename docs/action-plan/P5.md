## 0. 执行背景与目标

P0-P4 已经把 monorepo、`core.db + workflow kernel`、control plane、clean pipeline、rag pipeline 依次冻结下来。尤其 P4 已经把 `chunks`、`vec.db.vector_records`、`chunk_embedding_index`、`chunks.vec_status` 的写入与 purge-aware 语义落成了稳定输入（`docs/action-plan/P4.md:37-71`, `docs/refactor/core.sql:226-249`, `docs/refactor/vec.sql:35-99`）。现在进入 P5，目标不再是“让向量能被写进去”，而是要把这些向量真正变成 **query -> candidate hits -> core hydration -> secure assembled results** 的可消费检索面。

依据 `docs/refactor/todo-list.md:408-438`，P5 必须同时交付 `query embedding`、`vec.db` top-k search、`core.db` hydration、文档状态过滤、team / permission 过滤、search result assembly、debug 检索视图，并且以 `VectorStore.search`、search service、search API / CLI、检索日志与命中调试能力作为阶段产出。`docs/refactor/index.md:696-704` 也已经把查询主链明确写成：`query -> embed query -> search vec.db -> hydrate results from core.db -> assemble response`。因此 P5 的本质不是“补一个 API handler”，而是要把 **向量候选层** 与 **业务/权限真相层** 正式接起来。

本计划继续沿用 `todo-list.md` 的当前阶段编号，把本轮定义为 **P5 检索与查询面**。`docs/refactor/index.md` 仍保留一版较早的阶段编号残留，其中向量内核和基础 search 被放在 `P2`，rag pipeline 被放在 `P5`（`docs/refactor/index.md:94-102,883-899,925-939`）；本计划以 `todo-list.md + P0/P1/P2/P3/P4` 的现行链路为准，只吸收 `index.md` 中关于包边界、查询主链和 `rag_vectorizer/search.py` 模块归属的冻结结论（`docs/refactor/index.md:539-543,696-704,791-799`）。

- **服务业务簇**：`smind-family / retrieval-surface`
- **计划对象**：`P5 检索与查询面`
- **本次计划解决的问题**：

## 1. 执行综述

### 1.1 总体执行方式

本计划采用**先冻结 query contract 与 ownership，再落 vec candidate retrieval，然后建立 core truth hydration / policy filtering，随后完成 result assembly / debug surface，最后做 adversarial integration 收口**的执行方式。关键顺序判断有四件：

1. **Phase 1 必须拿到“可工作的 query embed call”，而不是只定义一个 adapter 接口。** 否则 Phase 2 的 top-k search 只能用假向量或 stub 测试，embedding model / dimension mismatch 会被拖到最后才暴露。
2. **Phase 2 必须把 sqlite-vec 明确当成“KNN 候选层”，而不是 metadata filter 引擎。** 当前 `chunk_embedding_index` 没有 team / status / ACL 级别的 server-side filter 能力，因此所有 team、document status、`vec_status`、purge-aware 过滤都必须留给 Phase 3。
3. **Phase 2 必须定义 candidate over-fetch / k-expansion 策略。** 多租户环境下，global top-k 经过 team/status 过滤后可能严重掉量；如果不提前定义 over-fetch 规则，P5 会在生产中频繁出现“明明有数据却返回不足 k 条”的假阴性。
4. **Phase 3 必须显式冻结“当前 SSOT 只支持 team-based isolation”的事实。** legacy 的 owner-private ACL 只能作为参考锚点，不能在当前 schema 没有落点时被暗渡陈仓地借进来。

### 1.2 Phase 总览

| Phase | 名称 | 规模 | 目标摘要 | 依赖前序 |
|------|------|------|----------|----------|
| Phase 1 | query contract 与 ingress 基线 | `M` | 冻结 query DTO、namespace 选择、embedding model guard、实现归属与 northbound ingress 契约 | `-` |
| Phase 2 | vec candidate retrieval 与 over-fetch 基线 | `L` | 落 `VectorStore.search`、namespace 激活校验、score 语义、candidate expansion 与 top-k 候选检索 | `Phase 1`, `P4` |
| Phase 3 | core hydration 与 policy filtering | `L` | 把 vec hits 回收到 `core.db`，完成 chunk/document/source/workflow hydrate、team/status/purge-aware 过滤与 filter reason 归类 | `Phase 1`, `Phase 2` |
| Phase 4 | result assembly、API/CLI 与 debug surface | `M` | 组装最终 search result、统一 API / CLI 响应形状、落 gated debug retrieval view 与检索日志 | `Phase 2`, `Phase 3` |
| Phase 5 | 集成验收、回归与 handoff 收口 | `M` | 用 adversarial fixtures 验证 cross-team、deleted/purged、pending_purge、partial-vectorized、k-depletion 等关键边界，并完成文档 handoff | `Phase 4` |

### 1.3 Phase 说明

1. **Phase 1 — query contract 与 ingress 基线**
   - **核心目标**：先把 query request / response、namespace 选择、embedding model 一致性、northbound API/CLI surface 和模块所有权写死，避免实施期再发明第二套 search 内核。
   - **为什么先做**：如果 Phase 1 只给出 handler 外壳，不明确 `rag_vectorizer.search` 与 `VectorStore.search` 的边界，后续很容易把“业务过滤”“KNN 检索”“DTO 组装”混写进 northbound handler。
2. **Phase 2 — vec candidate retrieval 与 over-fetch 基线**
   - **核心目标**：把 query embedding 真正送进 `VectorStore.search`，得到可追溯的 rowid / chunk 候选、score、namespace 命中结果，并明确 top-k 之外的 over-fetch 策略。
   - **为什么放在这里**：P5 的第一性能力是“从 query 得到候选 chunk”；没有真实 KNN 候选，Phase 3 的 hydrate / filter 都只能空转。
3. **Phase 3 — core hydration 与 policy filtering**
   - **核心目标**：在 `core.db` 上完成 chunk / document / source / workflow 上下文复水，并把 team、document status、`vec_status`、`pending_purge` 等所有安全/状态约束集中到一个 post-filter 层。
   - **为什么放在这里**：`vec.db` 无法承担 ACL / business status 真相层；如果不在一个独立 Phase 里写清楚，过滤逻辑最终会散落到 API、service、debug view 多个地方。
4. **Phase 4 — result assembly、API/CLI 与 debug surface**
   - **核心目标**：把候选命中变成稳定结果对象，暴露 northbound API/CLI，并提供“为什么命中 / 为什么被过滤”的 debug retrieval 视图与日志。
   - **为什么放在这里**：只有 Phase 2/3 把命中与过滤边界稳定下来，Phase 4 才能避免把 debug payload 和正式响应体绑死在一起。
5. **Phase 5 — 集成验收、回归与 handoff 收口**
   - **核心目标**：用对抗式夹具验证 P5 的安全与一致性，并把 P5 交接给 P6 运维面与 P7 cutover。
   - **为什么放在最后**：P5 最大风险不是“结果格式不好看”，而是**返回了不该返回的数据**；这类问题只能在跨 team、mid-purge、partial-vectorized 等对抗场景里暴露出来。

### 1.4 执行策略说明

- **执行顺序原则**：先真实 query embedding，再 vec candidate retrieval，再 core truth filtering，最后 result assembly；不允许先做 northbound response 再回头补 ACL / purge-aware 逻辑。
- **安全边界原则**：`vec.db` 只负责找候选，`core.db` 才负责判定“这条候选是否真能返回”；team isolation、document status、`chunks.vec_status` 一律以后者为准。
- **过筛策略原则**：P5 默认采用 candidate over-fetch，再在 Phase 3 做 post-filter 和最终截断；不把 sqlite-vec 假想成带 metadata pre-filter 的托管向量库。
- **测试推进原则**：每个 Phase 都要有自己的 exit criterion；Phase 5 必须额外覆盖 adversarial fixtures，包括 cross-team 高相似数据、`pending_purge` 窗口、deleted/purged 文档、partial-vectorized 文档和 top-k 掉量场景。
- **文档同步原则**：若实施中发现 `namespace` 选择、query DTO、search result contract、`core.sql / vec.sql` 视图或状态定义需要变化，必须先回写 SSOT 文档，再修改实现与 action-plan。
- **回滚 / 降级原则**：若 debug surface 风险过高，允许先把 debug retrieval 置于内部/受保护入口之后，但不允许把正式响应和 debug 说明混成同一 payload；若 CLI 进度晚于 API，可在 Phase 4 末期补齐，但不能被最终 DoD 省略。

## 2. In-Scope / Out-of-Scope

### 2.1 In-Scope（本次 action-plan 明确要做）

- **[S1]** 冻结 query DTO、namespace 选择规则、score 语义、API / CLI surface、debug 开关与 `rag_vectorizer.search` 的模块归属。
- **[S2]** 复用 P4 的 embedding adapter / model 配置，提供真正可工作的 query embedding 路径，并在 ingress 阶段以 `(team_id, namespace_key)` 解析目标 namespace，校验 query embed model / dimension 与 namespace 的 `embedding_model`、`embedding_dimension`、`distance_metric` 一致。
- **[S3]** 落 `VectorStore.search`，完成 `vec.db` top-k candidate retrieval、active namespace gating、candidate over-fetch / k-expansion 策略与 rowid/chunk candidate 映射，并把 sqlite-vec 查询冻结为“先 KNN rowid scan，再 post-KNN join/filter”的两段式执行合同。
- **[S4]** 在 `core.db` 上完成 chunk/document/source/workflow/artifact hydration，并统一执行 `team_id`、`documents.status='active'`、`chunks.vec_status='vectorized'`、`vector_records.deleted_at IS NULL` 的 post-filter。
- **[S5]** 组装正式 search result 与 gated debug retrieval 结果，解释 raw hits、filtered hits、filter reasons、最终排序与返回条数。
- **[S6]** 提供 search API / CLI、检索日志与对抗式集成测试，覆盖 cross-team、archived、deleted/purged、`pending_purge`、partial-vectorized、top-k 掉量等边界场景。

### 2.2 Out-of-Scope（本次 action-plan 明确不做）

- **[O1]** rerank、hybrid lexical search、BM25、graph retrieval、多阶段召回融合。
- **[O2]** schema 级的 document-level `private / access_level` 重设计；当前 P5 只消费现行 SSOT 中已存在的 `team_id` 与状态字段。
- **[O3]** 替换 sqlite-vec、为 `vec.db` 增加托管向量库式 metadata pre-filter 能力，或直接暴露 sqlite-vec 方言给业务模块。
- **[O4]** restart / purge / replay / inspect 的运维写面、operator CLI、恢复编排（属于 P6）。
- **[O5]** 面向前端的完整检索体验、分页 UI、收藏/反馈等产品层能力。
- **[O6]** 兼容 legacy 的 Cloudflare Vectorize / DO / WAL / D1 查询面。

## 5. Phase 详情

### 5.1 Phase 1 — query contract 与 ingress 基线

- **Phase 目标**：冻结 query/search 的外部合同与内部所有权，确保 P5 从第一天起就沿着 `northbound -> rag_vectorizer.search -> VectorStore.search -> storage_sqlite hydration` 这一条链路落实现。
- **本 Phase 对应编号**：
  - `P1-01`
  - `P1-02`
  - `P1-03`
- **本 Phase 新增文件**：
  - `packages/contracts/**/search*.py`
  - `packages/management/**/search.py`
  - `apps/api/**/search*.py`
  - `apps/cli/**/search*.py`
- **本 Phase 修改文件**：
  - `packages/rag_vectorizer/src/rag_vectorizer/search.py`
  - `packages/rag_vectorizer/src/rag_vectorizer/embedder.py`
  - `packages/vector_sqlite_vec/**`
- **具体功能预期**：
  1. query request 能唯一确定：query 文本、requested_k、candidate_k 策略、namespace 选择、debug 开关。
  2. Phase 1 结束时已经能拿到真实 query embedding，而不是只写出一个尚未接线的 adapter 抽象。
  3. namespace 解析必须使用 `(team_id, namespace_key)` 唯一得到 `namespace_id + distance_metric + embedding_model + embedding_dimension`，不能把裸 `namespace_key` 直接传进 vec 检索。
  4. API / CLI 只负责 auth、team context、trace、输入校验与调用 search service，不复制检索逻辑。
- **具体测试安排**：
  - **单测**：search DTO、`(team_id, namespace_key)` 解析、distance metric 读取、embedding model guard、handler -> service contract。
  - **集成测试**：query ingress 能真实拿到 embedding 向量。
  - **回归测试**：model mismatch、namespace disabled、missing auth/team context。
  - **手动验证**：API / CLI 输入同一 query，能打印相同 trace / request contract。
- **收口标准**：
  - search contract 被唯一冻结，不再存在第二套 northbound / service payload。
  - query embed 与 `namespace_id / distance_metric / model` 选择能真实跑通。
  - `rag_vectorizer.search` 的 ownership 已冻结，API / CLI 不再承担业务核心逻辑。
- **本 Phase 风险提醒**：
  - 若 Phase 1 只完成“接口设计”而没有真实 embedding，Phase 2 的所有 KNN 测试都会变成假成功。

### 5.2 Phase 2 — vec candidate retrieval 与 over-fetch 基线

- **Phase 目标**：把 query embedding 送进 vec 层，拿到真实 candidate hits，并把 candidate expansion / over-fetch 作为 P5 的显式能力而不是隐含假设。
- **本 Phase 对应编号**：
  - `P2-01`
  - `P2-02`
  - `P2-03`
- **本 Phase 新增文件**：
  - `packages/vector_sqlite_vec/**/store.py`
  - `packages/vector_sqlite_vec/**/engine.py`
- **本 Phase 修改文件**：
  - `packages/rag_vectorizer/src/rag_vectorizer/search.py`
  - `packages/vector_sqlite_vec/**`
- **具体功能预期**：
  1. `VectorStore.search` 必须显式拆成两步：先在 `chunk_embedding_index` 上做纯 KNN rowid scan，再基于 `embedding_rowid` 回连 `vector_records` / `v_active_vector_records`。
  2. `VectorStore.search` 能输出 `chunk_id + score + namespace_id` 候选，并且只消费 active namespace / non-deleted vector record / 正确的 `distance_metric`。
  3. candidate over-fetch / k-expansion 规则被冻结，例如 `requested_k -> candidate_k` 的倍数、下限、上限与“仍不足 k 时如何降级”的策略。
  4. vec 层不会承担 team/status/purge-aware 过滤，只承担 candidate retrieval。
- **具体测试安排**：
  - **单测**：KNN rowid scan、rowid -> `vector_records` 映射、`namespace_id` gating、distance metric 读取、score 排序。
  - **集成测试**：已向量化 chunk 能被 query 命中；多 namespace 情况下命中行为稳定。
  - **回归测试**：disabled namespace、deleted vector record、空结果、requested_k 变化、`namespace_key` 重名但 team 不同。
  - **手动验证**：在 debug 模式下能看到 raw candidate 数量与 score 分布。
- **收口标准**：
  - `VectorStore.search` 已可独立以“两段式 KNN”返回候选 chunk hits。
  - candidate over-fetch / k-expansion 已被写成明确策略，而不是“实现时自己判断”。
  - vec 层职责被清楚限制在 KNN candidate retrieval。
- **本 Phase 风险提醒**：
  - 如果把 sqlite-vec 当成 metadata filter 引擎，Phase 3 的安全/状态过滤会被做散甚至直接漏掉。

### 5.3 Phase 3 — core hydration 与 policy filtering

- **Phase 目标**：让所有 vec hits 回到 `core.db` 真相层完成 hydrate 与过滤，并把安全/状态判定集中到一个单独阶段。
- **本 Phase 对应编号**：
  - `P3-01`
  - `P3-02`
  - `P3-03`
- **本 Phase 新增文件**：
  - `packages/storage_sqlite/**/search_queries.py`
  - `packages/storage_sqlite/**/chunk_repository.py`
  - `packages/storage_sqlite/**/document_repository.py`
- **本 Phase 修改文件**：
  - `packages/rag_vectorizer/src/rag_vectorizer/search.py`
  - `packages/storage_sqlite/**`
- **具体功能预期**：
  1. search service 能批量 hydrate `chunks / documents / sources / workflow_runs / artifacts`，而不是逐条查库。
  2. team isolation、`documents.status='active'`、`chunks.vec_status`、`vector_records.deleted_at`、active namespace 等过滤全部在同一层执行，并为每次丢弃记录 filter reason。
  3. partial-vectorized / `pending_purge` 文档有明确可见性策略，并在 debug output 中可解释。
- **具体测试安排**：
  - **单测**：hydration query、filter reason 分类、`vec_status` / `document status` 判定。
  - **集成测试**：cross-team、archived、deleted、purged、`pending_purge`、non-vectorized、partial-vectorized。
  - **回归测试**：候选 hit 对应 `core.db` 行缺失、namespace 已失效、候选全部被过滤。
  - **手动验证**：debug retrieval 能解释“为什么命中了 vec.db 但最终没返回”。
- **收口标准**：
  - 所有最终结果都来自通过 core truth filtering 的 hydrated hit。
  - `chunks.vec_status != 'vectorized'` 的候选永不返回。
  - 只有 `documents.status='active'` 的文档可被检索；`archived / deleted / purged` 全部不进入正式结果。
  - cross-team / archived / deleted / purged / pending-purge 不会泄漏到正式结果。
- **本 Phase 风险提醒**：
  - P5 最大安全风险集中在本 Phase；任何把过滤逻辑拆散到 API / assembler / debug handler 的做法都应视为失败。

## 7. 风险、依赖与完成后状态

### 7.1 风险与依赖

| 风险 / 依赖 | 描述 | 当前判断 | 应对方式 |
|-------------|------|----------|----------|
| sqlite-vec 无 metadata pre-filter，且 `vec0` KNN 不能与 join 混写 | vec 层不能直接按 team/status 过滤，post-KNN join/filter 也必须走两段式执行 | `high` | 在 Phase 2 显式引入“两段式 KNN + candidate over-fetch / k-expansion”，并把所有安全过滤集中到 Phase 3 |
| `pending_purge` / `purged` 跨库一致性窗口 | `vec.db` 仍可有 live record，但 `core.db` 已标记不可检索 | `high` | 以 `chunks.vec_status='vectorized'` 作为最终可见性权威，并在集成测试覆盖 mid-purge |
| 当前 schema 无 document-level private ACL | legacy 语义与新 SSOT 不对齐，容易被误搬 | `high` | 在 P5 明确冻结 team-based isolation；若要引入更细 ACL，先回设计阶段 |
| 没有现成 legacy search API | P5 的 northbound 检索面需要净新设计 | `medium` | 借 legacy 的 hydration/log/guard 模式，不借“已有搜索 API”的错觉 |
| embedding model / namespace / distance metric 漂移 | query embed model、target namespace、distance metric 任一不一致都会产生伪命中 | `medium` | 在 Phase 1 冻结 `(team_id, namespace_key) -> namespace_id + distance_metric + model` 解析，并在 Phase 5 覆盖 mismatch regression |
| hydration 路径可能出现批量查询与 DTO 组装耦合 | 若 hydrate 与 assemble 混写，debug 与安全测试会变复杂 | `medium` | 保持 repository hydrate 与 assembler 分层，filter reason 也不放在 northbound |

### 7.2 约束与前提

- **技术前提**：P4 已经稳定写入 `chunks`、`vector_records`、`chunk_embedding_index`，并且 query embedding 复用同一 embedding model 体系。
- **运行时前提**：API / CLI / debug surface 共享同一 search service，不允许各自复制 KNN / filter / hydrate 逻辑。
- **组织协作前提**：若要在 P5 引入 document-level ACL、新 namespace 语义或新的查询主链，必须先冻结 design / SSOT，再推进实现。
- **上线 / 合并前提**：至少具备 cross-team、archived、deleted/purged、`pending_purge`、partial-vectorized、model mismatch 的对抗式集成覆盖。

  - `docs/refactor/index.md`（仅当 query contract / package ownership 被改写）
  - `docs/refactor/database.md`（仅当 search/hydration/filtering 边界被改写）

2. 所有 search hits 都先经 vec 候选检索，再经 core truth hydration / filtering，安全边界不再分散。

### 8.1 Action-Plan 整体测试方法

  - API 与 CLI 输入同一 query 时返回一致结果
  - debug mode 能解释 raw hits、filtered hits、final hits、candidate shortfall

  - cross-team 高相似内容不串出

  - `pending_purge` 窗口不返回结果

4. debug retrieval 视图可以解释 raw hits、filter reasons 与最终返回条数。

## A5. Substrate-fit / 技术路线（TR）过滤复核

本节使用四条固定技术路线过滤 legacy 参考：

- `TR-1`：运行时从 Cloudflare Worker / D1 / Vectorize / DO / WAL 迁移到 Python monolith + `core.db` + `vec.db` + `VectorStore`。
- `TR-2`：`vec.db` 只负责 candidate retrieval，`core.db` 才是权限、状态、hydrate 的真相层。
- `TR-3`：当前 SSOT 只冻结 `team_id + document/chunk status`，没有 document-level private ACL。
- `TR-4`：sqlite-vec `vec0` 没有 metadata pre-filter，P5 必须显式 over-fetch 并做 post-filter。

| 借鉴点 | 原机制 | 与本项目技术路线（TR）是否冲突 | 过滤后落地形态（降级/重映射/直采） |
|--------|--------|-------------------------------------|-------------------------------------|
| northbound 先建 auth/team context 再进入查询 handler | RPC 入口 + JWT/team guard | `TR-1: 部分冲突`, `TR-2: 兼容` | 直采“先建 auth/team context”的顺序，入口载体改成 FastAPI/CLI handler |
| 向量 metadata packing 与 flush 后回填 | Vectorize metadata + D1 task row backfill | `TR-1: 部分冲突`, `TR-2: 兼容`, `TR-4: 部分冲突` | 直采 metadata discipline 与 backfill 顺序，不把 metadata 当 vec-side ACL filter |
| hydrate-then-map 的 DTO 组装 | 单库 D1 join + DTO mapper | `TR-1: 部分冲突`, `TR-2: 兼容` | 直采分层方式，重映射成 `vec hits -> core hydrate -> assembler` |
| deleted 状态在查询面被默认排除 | management list/status filter | `TR-2: 兼容`, `TR-3: 兼容` | 直采“查询面先排除 deleted/purged”的原则，状态字段改成新 schema |
| owner-private ACL | D1 查询里的 `access_level/private` 过滤 | `TR-3: 冲突` | 不采；当前 P5 不假设该 ACL 已存在 |
| 向量 delete 先于本地状态 reset | Vectorize delete + DO/WAL cleanup | `TR-1: 部分冲突`, `TR-2: 兼容` | 直采 delete ordering 的思想，查询面则保守依赖 `core.db` 状态来隐藏结果 |

- **substrate-fit 总结（对 HEAD）**：legacy 最值得借的是 northbound guard、hydrate-then-map、metadata discipline、deleted/purge-aware 查询意识与 delete ordering；最不该借的是“管理查询即搜索”“metadata 可在 vec 层直接做 ACL filter”“owner-private ACL 已天然存在”“Cloudflare Vectorize/DO/WAL 机制可以直接延续”。P5 应把这些旧经验全部重映射到 `rag_vectorizer.search + VectorStore.search + storage_sqlite hydration + core.db/vec.db` 的显式检索链路上。
