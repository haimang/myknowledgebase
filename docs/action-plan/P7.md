## 0. 执行背景与目标

P0-P6 已经把新系统的骨架、workflow kernel、ingestion、clean/rag 主链路、retrieval surface 与 operator / detector 基底逐步冻结出来；`todo-list` 也明确把 **“让新实现成为默认主路径”** 放到 P7，而不是更早阶段（`docs/refactor/todo-list.md:516-539,547-556`）。这意味着 P7 不是继续“把功能做出来”，而是把前六个阶段交付的 Python 路线真正收敛成默认运行路径，并把 `legacy-family/` 从运行依赖降格成历史参考。

`index.md` 与 `database.md` 已经冻结了两条本阶段不能反悔的路线：一方面，新系统必须是 `apps/api` + `apps/worker` + `apps/cli` 驱动的 Python 模块化单体，围绕 `core.db` / `vec.db` / object store 运行；另一方面，queue / callback / service binding / Durable Object 不再是运行时真相层（`docs/refactor/index.md:26-37,45-74,617-740`, `docs/refactor/database.md:24-30,78-114`）。因此，P7 的任务不是把 legacy substrate “兼容下来”，而是把 legacy 的**合同、产出形状、运维边界**转译成新主路径可接管的实现与切换步骤。

本轮追回的 legacy 依据进一步说明了 cutover 的难点：`smind-admin` 仍是旧体系的默认入口，clean universal / dedicated APIs 的返回结构并不相同，RAG 的 layered JSON、vector identity 与 finalizer 状态推进都带有强合同色彩，而 file/static-file/admin management surface 本身也是验收对象，不只是 pipeline 能不能跑通的问题（见附录 A）。同时，P6 已经明确交出 ops API/CLI、health jobs、runbook 与 detector 结果供 P7 直接消费（`docs/action-plan/P6.md:396-399,452-456`）。因此，P7 必须采用 **先冻结 parity matrix 与 rollback gate，再补齐缺口，再做回归与 shadow diff，最后切默认路径并冻结 legacy** 的执行方式。

- **服务业务簇**：`smind-family / convergence-and-cutover`
- **计划对象**：`P7 收敛与替换`
- **本次计划解决的问题**：
  - P6 之前的阶段已经证明新实现能承载主能力，但仍未证明它已经覆盖 legacy 的全部 provider / cleaner / rag actions，以及 admin / management 命令面的关键入口。
  - legacy clean / rag / management surface 的产出结构存在多条高风险回归面：clean callback payload、file/static-file confirm 语义、layered JSON、vec identity、admin DTO 与 finalizer 状态推进；若没有专门的 golden fixture 与 shadow diff，默认切换会失去可靠验证基线。
  - 当前默认入口与生产职责仍停留在 legacy `smind-admin` + queue / RPC 体系上；若没有明确 rollback gate、legacy freeze 执行面与 cutover 文档，P7 很容易退化成“名义上切换，实际上双主路径长期并存”。
- **本次计划的直接产出**：
  - 一条把 parity 补齐、结构回归、默认入口切换、legacy freeze 和 cutover 文档连成闭环的分阶段执行序列。
  - 面向 `apps/api`、`apps/worker`、`apps/cli`、`packages/management`、`packages/workflow_clean`、`packages/workflow_rag` 与 `tests/**` 的实施边界、回归基线与回滚门槛。
  - 一份追加在本文底部的 legacy reference-anchor，明确旧代码中哪些合同要借、哪些机制只能部分借、哪些 legacy substrate 必须在 P7 明确冻结。
- **本计划不重新讨论的设计结论**：
  - 新系统的目标不是“翻译 TypeScript”，而是把 Cloudflare 分布式 Worker 流水线收敛成 Python 模块化单体；保留状态机、阶段边界与 action registry，但不保留 queue / service binding / callback / DO 作为运行时真相层（来源：`docs/refactor/index.md:26-37,58-74`, `docs/refactor/database.md:24-30,78-114`）。
  - `core.db` 是 workflow kernel，`vec.db` 是向量索引层；任何异步推进、restart / purge / claim / heartbeat / 补偿都必须在数据库真相层留痕（来源：`docs/refactor/database.md:78-114,150-184,397-406`）。
  - `legacy-family/` 在迁移完成前保持只读参照，P7 的完成态是“new implementation 成为默认主路径，legacy 不再承担生产职责”，不是删库式移除历史代码（来源：`docs/refactor/index.md:385-407,577-581`, `docs/refactor/todo-list.md:516-539,547-556`）。
  - P7 必须直接消费 P6 已经建立的 ops API/CLI、health jobs、runbook 与 detector 结果，不另起一套平行切换/回滚工具（来源：`docs/action-plan/P6.md:396-399,452-456`）。

## 1. 执行综述

### 1.1 总体执行方式

本计划采用**先冻结 parity matrix、contract normalization、rollback/freeze gate，再补齐缺失 actions 与 management parity，然后建立 legacy-vs-new 的 golden fixture / shadow diff，随后执行 processing plane + management plane 的默认切换，最后用机械化 freeze 与文档收口把 legacy-family 退化成只读参考**的执行方式。这个顺序吸收了本轮 critique 的两点修正：其一，不能把“盘点缺口”和“补齐缺口”混成一个 phase，否则后续回归没有稳定目标；其二，admin / management command parity 必须单列，而不能被 pipeline cutover 一笔带过。

### 1.2 Phase 总览

| Phase | 名称 | 规模 | 目标摘要 | 依赖前序 |
|------|------|------|----------|----------|
| Phase 1 | parity matrix 与 cutover guard baseline | `M` | 冻结 capability matrix、artifact/DTO 合同、rollback gate、legacy freeze 策略与 management parity 清单 | `P0-P6` |
| Phase 2 | parity closure implementation | `XL` | 补齐缺失 provider / cleaner / rag actions，并补齐 admin / management 命令面的新实现缺口 | `Phase 1` |
| Phase 3 | regression corpus 与 shadow diff | `L` | 建立 legacy-vs-new golden fixtures、端到端回归、artifact/output/admin DTO diff 与 cutover readiness gate | `Phase 1`, `Phase 2`, `P3-P6` |
| Phase 4 | default entrypoint cutover | `L` | 把默认 processing plane 与 management plane 切换到 `apps/api` / `apps/worker` / `apps/cli`，并通过 rollback gate、canary 与 drill 验证 | `Phase 1`, `Phase 2`, `Phase 3`, `P6` |
| Phase 5 | legacy freeze、cutover 文档与债务收口 | `M` | 机械化冻结 legacy 运行路径、完成 cutover 文档/总结/剩余债务列表，并把 legacy-family 固化为只读参考 | `Phase 3`, `Phase 4` |

### 1.3 Phase 说明

1. **Phase 1 — parity matrix 与 cutover guard baseline**
   - **核心目标**：先把 P7 的目标面说清楚：缺哪些 action、哪些 admin / management surface 必须 parity、哪些 output / DTO / callback shape 是必须保持的、rollback gate 与 legacy freeze 的控制面分别是什么。
   - **为什么先做**：如果不先冻结 capability matrix 和 rollback/freeze gate，Phase 2 的“补齐”会失去清单，Phase 4 的“切换”也会失去可执行的回滚锚点。
2. **Phase 2 — parity closure implementation**
   - **核心目标**：真正补齐 Phase 1 清单中的 provider / cleaner / rag actions，以及 workflow/file/static/API ingestion / inspect / update 等 management parity 缺口。
   - **为什么放在这里**：P7 的回归与 cutover 必须针对“完整候选主路径”进行；如果缺口仍未补齐，后面的 golden fixture 只能测到“未完成版本”。
3. **Phase 3 — regression corpus 与 shadow diff**
   - **核心目标**：围绕 clean callback、artifact shape、layered JSON、vec identity、file/static confirm、workflow/file management DTO 与 finalizer 状态推进建立 legacy-vs-new 的基准对照。
   - **为什么放在这里**：P7 最大风险不是“切不过去”，而是“切过去以后静默偏离 legacy 合同”；shadow diff 必须在默认切换前完成，而不能事后补。
4. **Phase 4 — default entrypoint cutover**
   - **核心目标**：分离 processing plane cutover 与 management plane cutover，把默认入口切到 `apps/api` / `apps/worker` / `apps/cli`，并保留受控 rollback gate 与 drill。
   - **为什么放在这里**：只有在 parity implementation 与 regression diff 已经稳定后，才有资格触碰默认入口；且 processing plane 与 admin plane 需要分别验证，不能一刀切。
5. **Phase 5 — legacy freeze、cutover 文档与债务收口**
   - **核心目标**：把 legacy 从“可运行备用路径”变成“只读参考”，交付完整 cutover 文档、执行总结与剩余债务台账。
   - **为什么放在最后**：freeze 是切换成功后的强制收口动作；如果前面没有稳定 default path 与 rollback drill，冻结只会让系统失去安全网。

### 1.4 执行策略说明

- **执行顺序原则**：先 parity matrix / contract / rollback guard，再 parity implementation，再 regression diff，再 default switch，最后 legacy freeze；不允许跳过 regression gate 直接切默认路径。
- **风险控制原则**：把 processing plane 与 management plane 分开建 gate；把 rollback gate 定义成显式控制面，而不是口头约定；把 legacy freeze 做成机械化限制，而不是文档声明。
- **测试推进原则**：Phase 2 以前以 unit/integration 为主，Phase 3 开始必须以 legacy-vs-new golden fixture、end-to-end regression、shadow diff 和 rollback drill 为主；P7 的最终验收必须覆盖“主要业务链路”和“关键管理命令”两条线。
- **文档同步原则**：若实施中发现 P7 需要改变 `todo-list`、`index.md`、`database.md` 中已冻结的 cutover / contract 结论，必须先回写 SSOT，再继续推进代码与 runbook。
- **回滚 / 降级原则**：Phase 4 的 default switch 必须建立显式 rollback anchor；若 processing plane 已可切换但 management plane 尚未收口，可延后默认 management cutover，但不得宣称 P7 完成；若 regression 未通过，只能回退，不得用“已知差异”替代正式 gate。

## 2. In-Scope / Out-of-Scope

### 2.1 In-Scope（本次 action-plan 明确要做）

- **[S1]** 建立完整的 P7 capability / parity matrix：覆盖 provider / cleaner / rag actions，以及 workflow/file/static/API ingestion / inspect / update / delete 等 management surface。
- **[S2]** 冻结 clean callback、artifact shape、layered JSON、vec identity、file confirm、static-file DTO、workflow management DTO、rollback anchor 与 legacy freeze contract。
- **[S3]** 按 parity matrix 补齐 Phase 1 列出的缺失实现，包括 processing plane 与 management plane 的新实现缺口。
- **[S4]** 建立 legacy-vs-new golden fixtures、end-to-end regression、shadow diff 与 cutover readiness gate，且显式消费 P6 的 detector / ops surface 做 rollout 与 rollback 验证。
- **[S5]** 将默认入口切换到 `apps/api` / `apps/worker` / `apps/cli`，完成 processing plane 与 management plane 的分层 cutover、canary 与 rollback drill。
- **[S6]** 冻结 legacy 运行路径，机械化阻断新代码继续依赖 legacy runtime，并交付 cutover 文档、收敛总结与剩余债务列表。

### 2.2 Out-of-Scope（本次 action-plan 明确不做）

- **[O1]** 重新设计 `core.db` / `vec.db`、claim / lease / heartbeat / restart / purge 的基础语义；这些已在 `database.md` 与 P6 中冻结。
- **[O2]** 新增超出 legacy parity 的业务能力、模型策略、provider 扩展或全新产品功能；P7 关注“补齐与切换”，不是继续扩 scope。
- **[O3]** 把 Cloudflare queue / callback / service binding / Durable Object 复刻成新系统兼容层；P7 只借 legacy 合同，不延续 legacy substrate。
- **[O4]** 面向前端用户的完整管理 UI 改造；P7 的控制面最小闭环仍是 API / CLI / operator surface。
- **[O5]** 从仓库中删除 `legacy-family/` 源码或改写其历史；P7 的完成态是“只读参考 + 不再承担生产职责”，不是清空历史实现。

### 2.3 边界判定表

| 项目 | 判定 | 理由 | 重评条件 |
|------|------|------|----------|
| provider / cleaner / rag missing actions parity matrix | `in-scope` | `todo-list` 明确要求 P7 先补齐缺失 actions | 若上游把某些 action 明确降级为永久不支持 |
| admin / management command parity（workflow/file/static/API ingestion） | `in-scope` | P7 验收标准包含“关键管理命令全部走新实现” | 仅当 product scope 先冻结删减某类管理面 |
| clean / rag artifact、callback、DTO 的 golden fixture 与 shadow diff | `in-scope` | 这是默认切换前的唯一可靠回归基线 | 若上游显式放弃 legacy shape 兼容并重开设计 |
| rollback gate / canary / switchback drill | `in-scope` | 没有显式回滚锚点，P7 的默认切换不可执行 | 仅当运行环境改成零停机双活路由并有更高层治理 |
| legacy freeze 的机械化 enforcement | `in-scope` | 仅写文档不足以阻止新实现重新依赖 legacy | 若仓库策略改成物理拆仓并由外层 CI 替代本仓 enforcement |

| 新前端管理台 | `out-of-scope` | 与 P7 最小闭环无关，会稀释 cutover 资源 | 后续如另开 P7.x / post-cutover 计划 |
| 物理删除 legacy-family | `out-of-scope` | `index.md` 已冻结 legacy 作为迁移参考的角色 | 只有在 post-cutover 历史归档策略单独冻结后再议 |

## 7. 风险、依赖与完成后状态

### 7.1 风险与依赖

| 风险 / 依赖 | 描述 | 当前判断 | 应对方式 |
|-------------|------|----------|----------|
| parity matrix 漏项 | 若漏掉某个 provider/action 或 management command，P7 可能在默认切换后才发现“仍需 legacy” | `high` | Phase 1 必须把 processing plane 与 management plane 放进同一张 matrix，并以 legacy 锚点逐项核对 |
| output / DTO 合同静默漂移 | clean callback、layered JSON、vec identity、file/static confirm、admin DTO 任一偏差都可能导致后续链路问题 | `high` | Phase 3 建 golden fixture + shadow diff，并要求所有关键偏差可解释 |
| admin plane 与 processing plane 风险耦合 | 若把两者一并切换，排障会失去定位能力 | `high` | Phase 4 分离 processing cutover 与 management cutover，分开 gate / drill / rollback |
| rollback gate 不可执行 | 若 rollback anchor 只是纸面约定，切换失败时无法真正回退 | `high` | Phase 1 定义显式 gate，Phase 4 做真实 switchback drill |
| legacy freeze 只停留在文档 | 新实现可能在后续开发中重新引入对 legacy runtime 的依赖 | `medium` | Phase 5 增加 import-boundary / CI / lint 级 enforcement，并做 repo audit |
| P6 handoff 不稳定 | 若 inspect / detector / ops surface 自身不稳定，P7 的 shadow diff 与 cutover watch 会失去支点 | `medium` | Phase 3 先把 P6 surface 纳入 readiness 检查；不满足则先修复再切换 |

### 7.2 约束与前提

- **技术前提**：必须继续遵循 `core.db` / `vec.db` 双库、显式状态机、显式 request / claim / heartbeat / detector 的路线，不允许在 P7 回退到 legacy queue / RPC / DO substrate。
- **运行时前提**：P6 的 ops API/CLI、health jobs、runbook 与 detector 已达到可作为 cutover / rollback / inspect 工具面的最低可用状态。
- **组织协作前提**：任何涉及 P7 验收项、contract baseline、cutover gate 或 legacy freeze 角色的变化，都必须先回写 refactor SSOT 文档。
- **上线 / 合并前提**：默认切换前必须有 regression evidence、shadow diff 结果、rollback drill 记录与已知差异台账；缺任一项都不能宣称 P7 完成。

### 7.3 文档同步要求

- 需要同步更新的设计文档：
  - `docs/refactor/index.md`
  - `docs/refactor/todo-list.md`
  - 如 contract baseline 变化触及数据库真相层，则同步 `docs/refactor/database.md`
- 需要同步更新的说明文档 / runbook：
  - `apps/api/` cutover / rollback 说明
  - `apps/worker/` processing plane 切换与 switchback 说明
  - `apps/cli/` management command cutover 说明
  - `docs/cutover/**`（执行顺序、回滚顺序、watchlist、已知差异）
- 需要同步更新的测试说明：
  - `tests/integration/p7_cutover/**` 的 regression / shadow diff / drill 说明

### 7.4 完成后的预期状态

1. 主要业务链路默认走新实现：ingestion -> clean -> rag -> retrieval / inspect 的正式主路径不再依赖 legacy runtime。
2. 关键管理命令默认走新实现：workflow/file/static/API ingestion / inspect / update / delete / confirm 等关键命令面不再依赖 `smind-admin`。
3. rollback gate、canary、switchback drill 都已经被真实演练，而不是停留在设计文档。
4. `legacy-family/` 不再承担生产职责，只保留为只读参考；新代码也无法静默重新依赖 legacy runtime。
5. P7 的 cutover 文档、执行总结与剩余债务列表完整，可作为 post-cutover 持续收口的交接面。

## A5. Substrate-fit / 技术路线（TR）过滤复核

本节使用五条固定技术路线过滤 legacy 参考：

- `TR-1`：运行时必须收敛到 Python monolith + `apps/api` + `apps/worker` + `apps/cli` + `core.db` / `vec.db`。
- `TR-2`：P7 要消费 P6 的 ops API/CLI、health jobs、detector 与 runbook，而不是另造平行 cutover/rollback 面。
- `TR-3`：默认切换前必须先证明 contract parity，不能把 substrate parity 当目标。
- `TR-4`：`legacy-family/` 的完成态是只读参考，不是长期双主路径或影子运行时依赖。
- `TR-5`：management surface 必须是 typed API/CLI，不是 generic RPC proxy。

| 借鉴点 | 原机制 | 与本项目技术路线（TR）是否冲突 | 过滤后落地形态（降级/重映射/直采） |
|--------|--------|-------------------------------------|-------------------------------------|
| clean / dedicated cleaner 的结果结构与 callback payload | queue callback 上报 artifact key / child_files / `_written_slots` | `TR-1: 部分冲突`, `TR-3: 兼容` | 直采 payload key / artifact contract；发送机制改为新 worker/state transition 路线 |
| layered JSON 与 vec identity 合同 | constructor / structurizer / vectorizer 以 R2 key + `vec_uuid` 上报 | `TR-1: 部分冲突`, `TR-3: 兼容` | 直采 schema 与 identity 规则，I/O substrate 改成新 object store / worker flow |
| admin auth/team guard 顺序 | giant RPC switchboard 先 guard 后 handler | `TR-1: 部分冲突`, `TR-5: 兼容` | 直采 guard 顺序；入口重映射到 FastAPI / CLI |
| file/static confirm 双分支 | 同一 admin worker 中动态区分 static 与 RAG | `TR-3: 兼容`, `TR-5: 兼容` | 直采 branching semantics，改由 typed API/management service 承载 |
| queue producer 作为默认 workflow start 发送面 | `CLEAN_DISPATCHER_INTAKE_QUEUE` + wrangler worker default entry | `TR-1: 冲突`, `TR-4: 冲突` | 不采；P7 只保留 rollback / read-only freeze 语义，不延续旧默认入口 |
| `/rpc` proxy + direct POST binding 双入口 | generic transport proxy | `TR-5: 冲突` | 不采；P7 只允许 typed API/CLI 作为正式入口 |
| D1/DO/WAL restart/purge substrate | queue + DO + internal task loop | `TR-1: 冲突`, `TR-2: 冲突` | 不采 substrate；只借 mode taxonomy / status expectation，执行依赖 P6 交接面 |

- **substrate-fit 总结（对 HEAD）**：P7 最值得借的是 capability matrix 组织方式、clean/rag artifact/callback contract、management guard 顺序、static-vs-rag confirm 语义与 final state expectation；最不该借的是 queue producer、`/rpc` 代理、giant switch router、D1/DO/WAL substrate 与 provider/action 硬编码。P7 的真实工作不是“复刻 legacy”，而是把这些合同压缩进 `apps/api` / `apps/worker` / `apps/cli` + P6 ops surface 组成的新主路径，并在切换后机械化冻结 legacy runtime。
