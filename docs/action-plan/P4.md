## 0. 执行背景与目标

P0 已冻结 monorepo 与 package 边界，P1 已冻结 `core.db + workflow kernel`，P2 已把 northbound 输入桥接到 `source / document / workflow_run / workflow_steps`，P3 已把 clean pipeline 真正跑成 **clean artifact -> rag step seed** 的稳定闭环，并把 downstream rag steps 显式回收到 `core.db`（`docs/action-plan/P3.md:218-225,447-453`）。现在进入 P4，目标不再是“能创建 rag step”，而是要把这些 rag steps 真的消费成 **structured artifact -> constructed artifact -> chunks -> vec.db -> workflow completed** 的完整知识加工闭环。

依据 `docs/refactor/todo-list.md:342-404`，P4 必须同时交付四条主线：`workflow_rag`、`rag_structurizer`、`rag_constructor`、`rag_vectorizer`。其中验收门槛已经写死：clean artifact 必须能进入 structurizer；constructor 必须能产出 chunk 与 summary；vectorizer 必须能把 chunk upsert 到 `vec.db`；`chunks.vec_status` 必须从 `pending_vectorize` 推进到 `vectorized`；整个 `workflow_run` 必须进入 `completed`。同时，`todo-list` 也明确把 P4 定义为当前风险最高的阶段，要求把 **幂等性与状态推进正确性** 放在第一优先级（`docs/refactor/todo-list.md:389-404`）。

本计划继续沿用 `todo-list.md` 的当前阶段编号，把本轮定义为 **P4 RAG Pipeline**。`docs/refactor/index.md` 里仍保留一版较早的编号残留，其中 rag pipeline 出现在 `P5`（`docs/refactor/index.md:925-939`）；本计划以 `todo-list.md + P0/P1/P2/P3` 的现行链路为准，只吸收 `index.md` 中关于包边界、运行拓扑、workflow kernel 和 rag 模块职责划分的冻结结论。

- **服务业务簇**：`smind-family / rag-pipeline`
- **计划对象**：`P4 RAG Pipeline`
- **本次计划解决的问题**：
  - P3 已经能创建第一批 rag steps，但 `workflow_rag` 的 planner / finalizer、step dependency control、restart / purge-aware 状态推进仍未冻结。
  - legacy RAG 逻辑分散在 `smind-rag-dispatcher`、`smind-skill-rag-structurizer`、`smind-skill-rag-constructor`、`smind-skill-rag-vectorizer` 四个 Worker 包里，强耦合 Cloudflare Queue / R2 / DO / Vectorize / callback roundtrip，不能直接照抄。

## 1. 执行综述

### 1.1 总体执行方式

本计划采用**先冻结 rag contract 与 step graph，再做 structurizer，随后落 constructor/chunk fan-out，再完成 vectorizer/vec consistency，最后做 end-to-end 收口**的执行方式。关键顺序调整点有三件：

1. **`context_meta_update` 双输入合同必须前置冻结**。legacy `orchestrator.ts` 里 `context_meta_update` 会跳过 structurizer，直接把既有 layered artifact 送给 constructor；这不是“后面再兼容”的实现细节，而是 planner 在 Phase 1 就必须冻结的 payload contract（`legacy-family/smind-rag-dispatcher/flows/orchestrator.ts:50-65`）。
2. **constructor 必须承担“写 chunk + 建 vectorize workflow_steps”的原子 fan-out 责任**。legacy `recorder.ts` 通过单独的 vec process 表隐式扇出；新系统没有这张表，因此 P4 必须把这份责任显式收回到 `core.db.chunks + workflow_steps(stage='vectorize')`（`legacy-family/smind-skill-rag-constructor/services/recorder.ts:126-239`, `docs/refactor/core.sql:226-280`）。
3. **purge-aware 行为不能只停在状态字段上**。本计划在 P4 内落一个最小 purge consumer：只负责 vector 侧领取 `purge_requests`、推进 `chunks.vec_status`、调用 `VectorStore.delete_chunks`，对象层清理与更高层运维编排仍留给 P6（`docs/refactor/database.md:397-406,516-523`）。

### 1.2 Phase 总览

| Phase | 名称 | 规模 | 目标摘要 | 依赖前序 |
|------|------|------|----------|----------|
| Phase 1 | rag contract 与 planner/finalizer 基线 | `M` | 冻结 rag step payload/result、step dependency control、`context_meta_update` 双输入路径、minimal finalizer 与 restart/purge-aware contract | `-` |
| Phase 2 | structurizer 与 structured artifact 基线 | `M` | 跑通 clean artifact -> structured JSON artifact 的结构化抽取、schema normalization、prompt binding、result artifact 写回 | `Phase 1`, `P3` |

### 1.3 Phase 说明

1. **Phase 1 — rag contract 与 planner/finalizer 基线**
   - **核心目标**：先冻结 `workflow_rag` 里最容易漂移的几件事：rag step payload/result contract、step dependency graph、`context_meta_update` 路由、minimal finalizer、restart / purge-aware 状态语义。
   - **为什么先做**：如果 Phase 1 没把 dual-input contract 和 vectorize fan-out 责任写死，Phase 2/3 会分别按单一路径和隐式扇出假设开发，最后只能返工。
2. **Phase 2 — structurizer 与 structured artifact 基线**
   - **核心目标**：交付 `rag_structurizer` 的 raw text -> structured JSON 最小闭环，并让 `workflow_rag` 真正能消费 P3 的 clean artifact。
   - **为什么放在这里**：todo-list 的第一条验收就是“clean artifact 能进入 structurizer”；没有 structurizer，后续 constructor / vectorizer 都无从谈起。
3. **Phase 3 — constructor、chunk identity 与 vectorize fan-out**
   - **核心目标**：交付 layered/constructed artifact、chunker、summarizer、metadata enrichment、chunk persistence，以及 constructor -> vectorize 的显式下游扇出。
   - **为什么放在这里**：constructor 是 P4 的状态分叉点；一旦 chunk_id、summary/original channel 和 vectorize step creation 没冻结，Phase 4 的向量一致性就无法定义。
4. **Phase 4 — vectorizer、vec consistency 与 purge-aware delete**
   - **核心目标**：交付 embedding / upsert / delete / vec_status / purge consumer 的完整执行与重试语义。
   - **为什么放在这里**：vectorizer 是唯一跨 `core.db + vec.db` 的阶段，必须建立在 chunk identity 和 workflow step fan-out 已经稳定之后。
5. **Phase 5 — 集成验收、full finalizer 收口与文档 handoff**
   - **核心目标**：把 standard 与 `context_meta_update` 两条闭环、retry/purge 分支、workflow completed 全部落成自动化资产与 handoff 文档。
   - **为什么放在最后**：只有 structurizer / constructor / vectorizer 都到位后，P4 的五项验收标准才有资格被完整验证。

### 1.4 执行策略说明

- **执行顺序原则**：先 contract / planner，再 structurizer，再 constructor/chunk fan-out，再 vectorizer/vec consistency，最后 integration；不允许先写 constructor/vectorizer 再回头猜 planner contract。
- **状态推进原则**：所有 rag 下游 handoff 都必须回收到 `workflow_steps / workflow_events / chunks / vector_records`；不再继续使用 legacy queue callback roundtrip 作为业务主语义。
- **幂等性原则**：idempotency 不是 Phase 5 补丁，而是每个 Phase 的 exit criterion。尤其 Phase 3 必须保证重复 constructor 不会生成冲突 chunk_id，Phase 4 必须保证重复 vectorize 不会生成重复向量。
- **purge 边界原则**：P4 只交付 vector 侧最小 purge consumer 与 `pending_purge -> purged` 状态推进；对象层删除、文档级 purge 编排、运维命令面继续留给 P6。
- **legacy 借鉴原则**：借 legacy 的步骤顺序、I/O contract、metadata enrichment、persist-then-fanout、delete ordering；不借 Queue / DO / R2 binding / Vectorize / WAL 的 substrate 机制。
- **文档同步原则**：若实施中发现 `chunk_id`、vectorize step payload、`metadata_json`、`purge_requests` 的边界需要调整，必须先回写 `index.md / database.md / core.sql / vec.sql / todo-list.md`，再改实现和 action-plan。

## 2. In-Scope / Out-of-Scope

### 2.1 In-Scope（本次 action-plan 明确要做）

- **[S1]** 冻结 `workflow_rag` 的 planner / finalizer / step expansion / dependency control / dual-input contract / restart-purge-aware 语义。
- **[S2]** 落 `rag_structurizer`，覆盖 structured extraction、schema normalization、prompt binding、result artifact 写回。
- **[S3]** 落 `rag_constructor`，覆盖 chunker、summarizer、layered/constructed artifact、metadata enrichment、chunk identity。
- **[S4]** 在 constructor 阶段原子创建 `chunks` 与 `workflow_steps(stage='vectorize')`，不再依赖 legacy 的隐式 vec process 表。
- **[S5]** 落 `rag_vectorizer + vector_sqlite_vec`，覆盖 embedding adapter、`upsert_chunks`、`delete_chunks`、`chunks.vec_status` 推进、最小 purge consumer。
- **[S6]** 建 standard 路径、`context_meta_update` 路径、retry / purge 分支的自动化验收与文档 handoff。

### 2.2 Out-of-Scope（本次 action-plan 明确不做）

- **[O1]** search / hydration / query API / ranking / reranking（属于 P5）。
- **[O2]** 北向 document-level purge/restart 入口、operator CLI、inspect / replay / 运维写面（属于 P6）。
- **[O3]** embedding provider 的底层供应商切换策略、auth/team 体系、northbound API 接入层。
- **[O4]** 兼容 legacy Cloudflare Queue / Durable Object / R2 / Vectorize / callback runtime。
- **[O5]** 多租户 search filtering 的完整消费面；P4 只负责把 filter metadata 正确写进 chunk/vector 侧，为 P5 提供稳定输入。

## 5. Phase 详情

### 5.1 Phase 1 — rag contract 与 planner/finalizer 基线

- **Phase 目标**：把 P4 最容易漂移的几件事先冻结：rag step payload/result、step graph、`context_meta_update` 双输入、minimal finalizer、purge/restart-aware 状态解释。
- **本 Phase 对应编号**：
  - `P1-01`
  - `P1-02`
  - `P1-03`
- **本 Phase 新增文件**：
  - `packages/workflow_rag/src/workflow_rag/planner.py`
  - `packages/workflow_rag/src/workflow_rag/steps.py`
  - `packages/workflow_rag/src/workflow_rag/registry.py`
  - `packages/workflow_rag/src/workflow_rag/finalizer.py`
  - `packages/contracts/src/contracts/rag.py`
- **本 Phase 修改文件**：
  - `packages/workflow_core/**`
  - `packages/storage_sqlite/**`
  - `apps/worker/**`
- **具体功能预期**：
  1. `workflow_rag.planner` 能区分 standard 与 `context_meta_update` 两类 rag workflow，并生成各自唯一的 step graph。
  2. constructor step payload 明确支持两种输入：standard 路径读取 `structured_artifact_ref`，meta-update 路径读取既有 `layered_artifact_ref`；不能再像 legacy 那样只靠 step 名称隐式跳转（参考：`legacy-family/smind-rag-dispatcher/flows/orchestrator.ts:50-65`）。
  3. rag step result 明确区分 structured artifact、constructed artifact、chunk refs、vectorize refs、completion summary，避免后续阶段各自发明字段。
  4. finalizer 是 rag 阶段唯一的 workflow 收口点：负责判断 step graph 是否已完成、是否存在失败/取消/待 purge 项，以及何时把 `workflow_run` 写成 `completed` 或 `failed`。
- **具体测试安排**：
  - **单测**：planner dual-route、step dependency graph、contract schema、finalizer completion rule。
  - **集成测试**：P3 rag seed -> Phase 1 planner -> 标准 graph / meta-update graph。
  - **回归测试**：重复规划同一 rag run 不会生成互相冲突的 step refs。
  - **手动验证**：查看 planned steps、artifact refs、dependency edges 是否都可读可追踪。
- **收口标准**：
  - standard / meta-update 两类 rag path 都能得到唯一、可解释的 step graph。
  - constructor dual-input contract 已冻结，不再依赖后续模块补猜。
  - finalizer 对 completed / failed / pending_purge 的语义有唯一解释。
- **本 Phase 风险提醒**：
  - 如果 dual-input contract 没冻结，Phase 2/3 很快会形成互不兼容的 artifact 命名与读取规则。
  - 如果 finalizer 语义不先冻结，Phase 4/5 会把 workflow completed 条件散落到 executor 内，导致状态无法推理。

- **本 Phase 对应编号**：
  - `P2-01`
  - `P2-02`
- **本 Phase 新增文件**：

- **本 Phase 修改文件**：
  - `packages/storage_objects/**`
  - `packages/contracts/**`
  - `packages/workflow_rag/**`
- **具体功能预期**：
  1. `rag_structurizer.service` 能从 clean artifact 读取 raw text，并结合 prompt alias / schema profile 生成 structured JSON。
  2. schema normalization、JSON repair、metadata 补全都在 structurizer 内完成，不把“修坏 JSON”留给 constructor 兜底（参考：`legacy-family/smind-skill-rag-structurizer/flows/structurizer.ts:170-303`）。
  3. structured output 以 artifact/object ref 的方式写回，并通过 step result 告知 `workflow_rag`，而不是继续沿用 legacy callbacker 的 authority/control roundtrip。
- **具体测试安排**：
  - **单测**：prompt binding、schema normalization、artifact writer。
  - **集成测试**：clean artifact -> structurizer -> structured artifact。
  - **回归测试**：同一 clean artifact 重跑 structurizer 不会生成互相冲突的 result schema。

- **本 Phase 风险提醒**：
  - 如果 schema normalization 漂移，constructor 会被迫承担上游清洗与结构理解两份职责。
  - 如果 structured artifact 不回收到统一 artifact contract，P4 后半段会重新长出“对象层路径就是业务 contract”的旧耦合。

### 5.3 Phase 3 — constructor、chunk identity 与 vectorize fan-out

- **Phase 目标**：把 structured / layered 输入真正推进成 constructed artifact、chunks 和显式 vectorize work。
- **本 Phase 对应编号**：
  - `P3-01`
  - `P3-02`
  - `P3-03`
- **本 Phase 新增文件**：
  - `packages/rag_constructor/src/rag_constructor/service.py`
  - `packages/rag_constructor/src/rag_constructor/chunker.py`
  - `packages/rag_constructor/src/rag_constructor/summarizer.py`
  - `packages/rag_constructor/src/rag_constructor/metadata.py`
  - `packages/rag_constructor/src/rag_constructor/recorder.py`
  - `tests/integration/p4_rag_pipeline/test_constructor.py`
- **本 Phase 修改文件**：
  - `packages/storage_sqlite/**`
  - `packages/contracts/**`
  - `packages/workflow_rag/**`
- **具体功能预期**：
  1. constructor 能处理 standard 与 `context_meta_update` 两条输入：standard 读取 structurizer output；meta-update 直接读取已有 layered artifact，并按模式决定是否跳过 summarizer（参考：`legacy-family/smind-skill-rag-constructor/flows/constructor.ts:116-149`）。
  2. metadata enrichment 需要把 `team / realm / source / is_active / workflow_run_id` 等 filter metadata 注入 `chunks.metadata_json` 或 vectorize payload，而不是只保留结构信息；否则 P5 的过滤能力会失去依据（参考：`legacy-family/smind-skill-rag-constructor/services/meta_fuser.ts:167-243`）。
  3. constructor 必须在同一事务内完成三件事：写 layered/constructed artifact、写 `chunks(vec_status='pending_vectorize')`、并创建每个 chunk/channel 对应的 vectorize step。新系统不能把“谁去建 vectorize work”留成隐式副作用（参考：`legacy-family/smind-skill-rag-constructor/services/recorder.ts:126-239`, `docs/refactor/database.md:389-393`）。
  4. chunk identity 以稳定的 `chunk_id` 为核心，summary/original channel 规则必须在本 Phase 冻结，而不是等 P4 再决定。
- **具体测试安排**：
  - **单测**：chunker、summarizer、metadata enrichment、chunk_id builder。
  - **集成测试**：structured artifact -> constructor -> constructed artifact / chunks / vectorize steps。
  - **回归测试**：重复 constructor 不会生成冲突 chunk_id，不会重复 fan-out 额外 vectorize steps。
  - **手动验证**：检查 chunk rows、metadata_json、vectorize step payload 是否一一对应。
- **收口标准**：
  - standard / meta-update 两条路径都能产出 constructed artifact。
  - `chunks` 与 `workflow_steps(stage='vectorize')` 已一一对应，且都锚定同一个 `chunk_id`。
  - metadata enrichment 足够支撑后续 vector filter / purge / search。
- **本 Phase 风险提醒**：
  - 如果 vectorize steps 不是由 constructor 原子创建，Phase 4 会陷入“谁负责发现下游工作”的设计空洞。
  - 如果 chunk_id 规则后置到 Phase 4，vector_records 的幂等性将无法验证。

### 5.4 Phase 4 — vectorizer、vec consistency 与 purge-aware delete

- **Phase 目标**：让 `pending_vectorize` 的 chunk 真正进入 `vec.db`，并在失败重试与 purge 分支下保持一致性。
- **本 Phase 对应编号**：
  - `P4-01`
  - `P4-02`
  - `P4-03`
- **本 Phase 新增文件**：
  - `packages/rag_vectorizer/src/rag_vectorizer/embedder.py`
  - `packages/rag_vectorizer/src/rag_vectorizer/executor.py`
  - `packages/rag_vectorizer/src/rag_vectorizer/purger.py`
  - `packages/vector_sqlite_vec/src/vector_sqlite_vec/store.py`
  - `tests/integration/p4_rag_pipeline/test_vectorizer.py`
- **本 Phase 修改文件**：
  - `packages/storage_sqlite/**`
  - `packages/workflow_rag/**`
  - `apps/worker/**`
- **具体功能预期**：
  1. vectorize executor 只消费 Phase 3 显式创建的 vectorize steps，不扫描全表推断工作。
  2. `VectorStore.upsert_chunks` 以 `chunk_id` 为唯一锚点写 `vec.db.vector_records` 与向量索引，并能在 already-vectorized / retry 情况下做幂等短路（依据：`docs/refactor/database.md:162-165,389-393`, `docs/refactor/vec.sql:35-115`）。
  3. 最小 purge consumer 领取 `purge_requests` 后，先将 chunks 置为 `pending_purge`，再调用 `delete_chunks`，成功后写回 `purged`；对象层清理仍不在本 Phase 内（依据：`docs/refactor/database.md:169-172,397-406`）。
  4. legacy 的 WAL / DO lock / alarm 只借“先 upsert/delete 再清本地状态”的顺序，不借其 substrate 机制（参考：`legacy-family/smind-skill-rag-vectorizer/vectorizer/engine.ts:216-246`, `src/purger_logic.ts:107-148`, `src/vectorizer_do.ts:118-149`）。
- **具体测试安排**：
  - **单测**：embedder、vector store upsert/delete、already-vectorized 短路。
  - **集成测试**：vectorize step -> vec.db record + chunk_embedding_index + `chunks.vec_status='vectorized'`。
  - **回归测试**：重试不会新增冲突 vector records；purge 顺序与状态推进可重复执行。
  - **手动验证**：检查 `core.db.chunks`、`vec.db.vector_records`、向量索引三者是否一致。
- **收口标准**：
  - `pending_vectorize -> vectorized` 与 `pending_purge -> purged` 两条状态推进都可验证。
  - `chunk_id` 成为唯一 upsert/delete 锚点，重复 vectorize 不会产生重复向量。
  - vectorizer 不再依赖 legacy callback / DO / WAL 语义来解释完成状态。
- **本 Phase 风险提醒**：
  - `core.db` 与 `vec.db` 没有强事务；若不显式定义 retry/short-circuit 语义，很容易出现“向量已写、状态未回”的中间态。
  - 如果 purge consumer 边界不在本 Phase 冻结，P4 的 purge-aware 要求将只能停留在文档里。

  2. `context_meta_update` 路径跳过 structurizer，直接复用 layered artifact 进入 constructor，并同样闭环到 completed。
  3. retry / already-vectorized / purge 分支都能给出可解释、可追踪的状态轨迹，而不是“看上去好了但 DB 对不上”。
  4. P5 / P6 能直接消费 P4 交付的 artifacts、chunks、vector records、workflow events、purge request 语义。
- **具体测试安排**：

## 7. 风险、依赖与完成后状态

### 7.1 风险与依赖

| 风险 / 依赖 | 描述 | 当前判断 | 应对方式 |
|-------------|------|----------|----------|
| dual-input contract 漂移 | 如果 `context_meta_update` 的 layered-input 路径不在 Phase 1 冻结，Phase 2/3 会按单一路径各自长出 contract | `high` | 在 Phase 1 明确 constructor 的双输入 payload，并用 integration fixture 固定 |
| constructor 不负责 vectorize fan-out | 若 chunks 写入与 vectorize step 创建分离，Phase 4 会没有 claimable work 或产生重复下游步骤 | `high` | 在 Phase 3 明确“写 chunk + 建 vectorize step”必须同事务完成 |
| `core.db` / `vec.db` 跨库中间态 | embedding 已生成、vector 已写、`vec_status` 未回写等中间态会破坏幂等性 | `high` | 以 `chunk_id` 建幂等 upsert/delete，定义 already-vectorized 短路与失败重试语义 |
| purge consumer 边界模糊 | 如果 P4 只写状态不落 consumer，`pending_purge` 将无法被验证，P6 也难以承接 | `high` | 在 P4 内交付 vector 侧最小 purge consumer，对象层 delete 保持 defer |

## 8. Action-Plan 整体测试与整体收口

### 8.1 Action-Plan 整体测试方法

- **基础校验**：
  - planner 能同时覆盖 standard 与 `context_meta_update` 两条 rag path。
  - constructor 完成后，`chunks` 与 `workflow_steps(stage='vectorize')` 一一对应。
  - vectorizer 完成后，`core.db.chunks`、`vec.db.vector_records`、向量索引三者状态一致。
- **单元测试**：
  - `workflow_rag` planner / finalizer / dependency graph unit tests
  - `rag_structurizer` prompt binding / schema normalization / artifact writer unit tests
  - `rag_constructor` chunker / summarizer / metadata enrichment / recorder unit tests
  - `rag_vectorizer` embedder / executor / purger unit tests
  - `vector_sqlite_vec` store upsert/delete / idempotency unit tests
- **集成测试**：
  - clean artifact -> structurizer -> constructor -> vectorizer -> workflow completed
  - `context_meta_update` -> constructor -> vectorizer -> workflow completed
  - purge request -> `pending_purge` -> vector delete -> `purged`
- **端到端 / 手动验证**：
  - 通过 P3 入口创建 clean artifact 与 meta-update fixture，检查 object refs、`core.db`、`vec.db`、worker event trail 四者一致。
- **回归测试**：
  - 已 vectorized 的 chunk 重试不会新增重复向量
  - purge 删除后重新规划 / 重建能够得到可解释结果
  - 失败重试不会生成冲突 chunk_id、冲突 vector records 或遗失 workflow completed 条件
- **文档校验**：
  - P4 输出契约与 P5 / P6 handoff 描述一致
  - `index.md / database.md / core.sql / vec.sql` 与 action-plan 对 `chunk_id / vec_status / purge` 的叙述一致

### 8.2 Action-Plan 整体收口标准

所有 Phase 完成后，至少应满足以下条件：

1. clean artifact 能稳定进入 structurizer，并产出 structured artifact。
2. constructor 能稳定创建 constructed artifact、chunks、summary，并原子创建 vectorize workflow_steps。
3. vectorizer 能把 chunk upsert 到 `vec.db`，且 `chunks.vec_status` 能从 `pending_vectorize` 推进到 `vectorized`。
4. standard 与 `context_meta_update` 两条路径都能把 `workflow_run` 推进到 `completed`。
5. 最小 purge consumer 已可验证地把 `pending_purge` 推进到 `purged`，同时不越权承担对象层 purge 编排。

## A5. Substrate-fit / 技术路线（TR）过滤复核

本节使用四条固定技术路线过滤 legacy 参考：

- `TR-1`：运行时从 Cloudflare Worker/Queue/DO/R2/Vectorize 迁移到 Python monolith + local apps/packages + object store + sqlite。
- `TR-2`：`core.db` 是唯一 workflow kernel，rag handoff 必须回收到 `workflow_steps / workflow_events / finalizer`。
- `TR-3`：`core.db.chunks` 是 chunk 身份 SSOT，`vec.db.vector_records.chunk_id` 是唯一跨库锚点。
- `TR-4`：每个阶段都要有独立验收闭环，因此 dual-input、fan-out、purge-aware 行为必须尽早显式化，不能等集成阶段“自然长出来”。

| 借鉴点 | 原机制 | 与本项目技术路线（TR）是否冲突 | 过滤后落地形态（降级/重映射/直采） |
|--------|--------|-------------------------------------|-------------------------------------|
| dispatcher 的 step graph / finalizer 顺序 | Queue consumer + callback roundtrip | `TR-1: 部分冲突`, `TR-2: 兼容` | 直采步骤顺序与 finalizer 责任，重映射到 worker lane + DB state |
| structurizer 的 raw-text -> structured-artifact contract | Cloudflare AI + R2 write-back + callback | `TR-1: 部分冲突`, `TR-2: 兼容` | 直采输入/输出 contract，artifact 写回改到 `storage_objects`，回报改到 step result |
| constructor 的 persist-then-fanout 与 block × channel 扩张 | Worker service + vec process table | `TR-2: 兼容`, `TR-3: 部分冲突` | 直采顺序与 fan-out 语义，重映射到 `chunks + workflow_steps(stage='vectorize')` |
| vectorizer 的 upsert/delete 顺序 | DO/WAL + Vectorize | `TR-1: 冲突`, `TR-3: 兼容` | 借 delete/upsert ordering 与 recovery 思路，具体实现改成 `chunk_id + vec_status + vector_records` |
| purge 的 delete ordering | purge instruction + DO-local state reset | `TR-1: 部分冲突`, `TR-4: 兼容` | 直采“先删向量，再回写状态”的顺序，consumer 改成显式 `purge_requests` lane |
| callback envelope 中的 authority/control/workflow context | callback payload | `TR-1: 冲突`, `TR-2: 部分兼容` | 只保留上下文完整性的原则，具体载体改成 repositories / step result / workflow events |

- **substrate-fit 总结（对 HEAD）**：legacy 最值得借的是 rag pipeline 的阶段顺序、persist-then-fanout、metadata enrichment、upsert/delete ordering、purge/delete 的先后关系；最不该借的是 Queue / DO / R2 / Vectorize / callback / WAL 这些平台耦合机制。P4 应把这些旧行为全部重映射到 `workflow_rag + rag_structurizer + rag_constructor + rag_vectorizer + vector_sqlite_vec + core.db/vec.db` 的显式状态机上。
