## 1. 总体执行策略

### 1.1 总体思路

P2 不应该被做成“把 legacy admin worker 搬到 FastAPI”；正确路线是：

1. 先建立 **身份/租户/控制面契约**，让 API 层有稳定的 auth context、team gating、workflow config lookup。
2. 再建立 **本地对象存储 + 上传状态机**，把 file/static 的 object 生命周期先从 R2 语义映射到新 ObjectStore。
3. 随后建立 **ingestion 实体化桥**，把 file/url/api 三条入口统一收敛到 `uploads/sources/documents/workflow_runs`。
4. 再补 **management 读面**，把 workflow run / document / static file 这些新实体暴露成稳定查询接口。
5. 最后做 **集成验收与文档收口**，把 P2 对 P3/P5/P6 的 handoff 明确下来。

### 1.2 阶段划分

| 阶段 | 名称 | 目标摘要 | 规模 |
| --- | --- | --- | --- |
| Phase 1 | 身份、租户与入口契约 | 落 session / API key / team / profile / workflow-config lookup 的控制面基线 | `M` |
| Phase 2 | 本地对象存储与上传状态基线 | 落 `packages/storage_objects`、file/static initiate/confirm 以及 upload 状态约束 | `L` |
| Phase 3 | ingestion 实体化与 workflow-start bridge | 把 file/url/api 统一转成 `source/document/workflow_run`，并创建首批 clean steps | `L` |
| Phase 4 | management 读面与运行态查询 | 暴露 workflow runs / documents / static files 的 list/detail 查询面 | `M` |
| Phase 5 | 集成验收与文档收口 | 补齐测试、文档、风险闭环与下游 handoff | `M` |

### 1.3 为什么这样分

1. **先控制面后 ingestion**：P2 的所有北向入口都依赖稳定的 team/user/session 语义；否则 file/url/api 入口无法定义 ACL、quota、ownership。
2. **先对象层后实体化**：file upload 的 object key、checksum、mime、status 校验应先冻结，否则 `source/document` 的创建条件会漂移。
3. **file 与 URL/API 必须分开建模**：legacy 把 URL/API 也塞进 file payload；新 schema 已经把它们抽象成 `source_kind`，P2 不能继续沿用 file-centered 视角。
4. **static upload 要单独对待**：`static_files` 在新 schema 是一等实体，但不必自动创建 `workflow_run`；这条分支要在 P2 明确。
5. **management 要基于新实体，而不是 legacy DTO**：legacy 只有 file/static；新架构多了 document/source/workflow_run，所以查询面必须重写，而不是简单改壳。

### 1.4 执行原则

#### 1.4.1 契约优先

先定义 session / API key / team / workflow-config / ingestion request DTO，再落 repository 和 object store；避免 API contract 跟着 storage 细节飘。

#### 1.4.2 schema 优先于 legacy DTO

只要 legacy 行为和 `core.sql` 冲突，一律以新 schema 为准。最典型的三处是：

1. legacy 只有 `file/static_file`，新架构必须拆 `upload/source/document/static_file`
2. legacy 运行时读取 workflow config，新架构必须在 run 创建时固化 `config_snapshot_json`
3. legacy static file 与 source/document 无关联，新架构必须按 `static_files.source_id/document_id` 建好关系

#### 1.4.3 无队列验收

P2 的“workflow start 成功”不以消息入队为验收，而以以下事实为验收：

1. `uploads/sources/documents/workflow_runs/workflow_steps` 记录齐全
2. `workflow_runs.config_snapshot_json` 已固化
3. P1 的 ready-step 视图中能看到首批待执行 step

#### 1.4.4 读写边界清晰

P2 只负责：

- auth/team/profile/session/api-key 的必要写面
- ingestion 入口写面
- management 读面

P2 不负责：

- workflow config admin write
- restart/purge/replay write
- clean/rag 实际执行

#### 1.4.5 文档同步

若 P2 实施中需要调整 `core.sql`、包边界或 phase 编号说明，应先更新 SSOT 文档，再更新 action-plan；禁止只在代码或局部实现里偷偷变更。

## 2. 范围定义

### 2.1 In scope

1. **身份与租户控制面**
   - login / register / session create / session validate / logout
   - API key validate / rotate
   - `/me` profile read/update
   - current team / team bootstrap / team list-select 的最小闭环
2. **workflow config lookup**
   - 供 ingestion 入口选择处理方式的 workflow config list/read-only surface
   - 不含 config admin write
3. **本地对象存储与上传管理**
   - `packages/storage_objects` 的 put/head/get/delete/list 抽象
   - file/static object key 规范、checksum / size / mime 元数据落库
   - `uploads` 的 initiate / confirm / failure / abandon 语义
4. **三条 ingestion 入口**
   - file initiate / confirm
   - URL submit
   - API submit
5. **ingestion 实体化**
   - `upload -> source -> document` 创建逻辑
   - static upload 的 `static_file + source/document` 关联
   - `workflow_run + workflow_steps` 首次创建与 ready-step 暴露
6. **management 读面**
   - workflow run list/detail
   - document list/detail
   - static file list/detail
7. **P2 级测试与文档**
   - 单测 / 集成测试 / schema 断言
   - 下游 handoff 与风险文档化

### 2.2 Out of scope

1. **clean pipeline 内部实现**：包括 planner、executor、artifact 产出、step finalizer 等，属于 P3。
2. **rag / vector / search / hydration**：包括 scatter、vector store、search/hydration，属于 P4/P5。
3. **运维写面**：restart / purge / replay / force-run 等，属于 P6。
4. **workflow config 管理后台**：包括新增/编辑/发布 workflow config，不属于 P2。
5. **前端/UI 落地**：P2 只定义与提供后端北向接口。
6. **Cloudflare infra 兼容层**：不保留 Queue / R2 / Durable Object / Service Binding 适配。
7. **复杂团队协作写面**：invite、approve、role mutation 等多成员协作写面不在 P2；P2 只保留最小 team bootstrap / list-select。

### 2.3 范围边界表

| 事项 | 结论 | 说明 |
| --- | --- | --- |
| login / register / session / API key | `in scope` | `todo-list` 已明确要求 auth / session / API key |
| team bootstrap / current team / team list-select | `in scope` | P2 需要形成最小多租户控制面，但不扩成邀请审批系统 |
| workflow config list / read-only detail | `in scope` | ingestion 入口需要“选择处理方式”能力 |
| workflow config admin write | `out of scope` | legacy 有 admin update，但新架构不在 P2 实现 |
| file/static initiate-confirm | `in scope` | 对应 `uploads + storage_objects + static_files` |
| URL/API submit | `in scope` | 明确列在 `todo-list` |
| `source/document/workflow_run/step` 初次创建 | `in scope` | P2 是 P1 内核对北向入口的首次接线 |
| static upload 自动起 workflow run | `defer / depends-on-design` | 默认不做自动起 run；只在 action-plan 中冻结为“先建关系，不自动跑 clean” |
| management read（workflow run / document / static file） | `in scope` | todo-list 明确点名 |
| management write（restart/purge/delete admin） | `out of scope` | 下放到 P6 |

## 4. 分阶段执行计划

### 4.1 Phase 1：身份、租户与入口契约

**阶段目标**

让 API 层先具备稳定的 user/team/session/api-key 基础语义，并提供 ingestion 前必需的 workflow-config lookup。P2 后续所有入口都依赖这个 auth context。

**工作项**

| 编号 | 工作项 | 主要内容 | 依赖 |
| --- | --- | --- | --- |
| P1-01 | 鉴权与会话基线 | 基于 `sessions/api_keys` 表落 login/register/session validate/logout、API key validate、auth context 注入、teamless gating | P0, P1 |
| P1-02 | team/profile/workflow-config 入口 | 落 `/me` profile read/update、team bootstrap/current/list-select、workflow config list/read-only | P1-01 |

**拟新增文件**

- `apps/api/src/api/routes/auth.py`
- `apps/api/src/api/routes/team.py`
- `packages/auth/src/auth/**`
- `packages/team/src/team/**`

**拟修改文件**

- `apps/api/src/api/app.py`
- `packages/contracts/**`
- `packages/storage_sqlite/src/storage_sqlite/**`
- `packages/common/**`

**功能预期**

1. **session 模型以新 schema 为准**：不复刻 legacy 的 JWT-only 模式；session 必须可在 `sessions` 表中落地与失效。
2. **API key 仍保留 hash-then-lookup 语义**：借用 legacy `validate_api_key` 行为，但返回结构与错误码要按新 API 规范整理。
3. **team gating 继承 legacy setup-required 思路**：没有 team 的用户只能访问 team bootstrap / session / profile 等必要入口。
4. **workflow-config lookup 必须在本阶段就可用**：因为 file/url/api 三条 ingestion 入口都要依赖“选择哪个 workflow config”。

**测试安排**

- `auth/session/api_key` 单测
- `team bootstrap/current/list-select` 集成测试
- teamless 用户访问 ingestion API 的鉴权回归

**阶段退出条件**

1. `login/register/session validate/logout` 全部可用，且 session 生命周期可落库与回收。
2. API key validate / rotate 可用，team 级隔离成立。
3. `/me`、`team bootstrap/current/list-select`、workflow config list/read-only 可用。
4. teamless gating 明确，后续 Phase 2/3 可直接复用 auth context。

### 4.2 Phase 2：本地对象存储与上传状态基线

**阶段目标**

用 `packages/storage_objects` 和 `uploads/static_files` 新 schema 替换 legacy 的 R2 file/static_file 双轨实现，先把 object 生命周期与 upload 状态机冻结下来。

**工作项**

| 编号 | 工作项 | 主要内容 | 依赖 |
| --- | --- | --- | --- |
| P2-01 | 本地对象存储基线 | 定义 local object store adapter、object key 规范、head/get/delete 语义、错误模型 | Phase 1 |
| P2-02 | file/static initiate-confirm | 建立 `uploads` initiate/confirm/fail/abandon 流程，支持 file/static 两条 upload 路径 | P2-01 |

**拟新增文件**

- `packages/storage_objects/src/storage_objects/**`
- `packages/ingestion/src/ingestion/files.py`
- `apps/api/src/api/routes/ingestion.py`

**拟修改文件**

- `packages/config/**`
- `packages/common/**`
- `packages/storage_sqlite/src/storage_sqlite/**`
- `packages/contracts/**`

**功能预期**

1. **object key 规则要稳定**：至少区分 uploaded file 与 static file 的 key 空间，避免未来 artifact/export 与原始上传冲突。
2. **initiate 只保留“预留 upload + object key + metadata contract”职责**：不在此阶段偷跑 `source/document/run`。
3. **confirm 先做 object existence / metadata 校验，再交给 Phase 3 的实体化逻辑**。
4. **static upload 先视为独立分支**：其 confirm 成功应能创建/更新 `static_files` 相关记录，但默认不自动起 workflow run。

**测试安排**

- object store adapter 的 put/head/get/delete 单测
- file/static initiate-confirm 集成测试
- checksum / mime / size mismatch 的错误路径测试

**阶段退出条件**

1. `packages/storage_objects` 抽象可在本地文件系统上稳定读写对象。
2. `uploads` 状态能稳定走到 `initiated/uploaded/confirmed/failed/abandoned`。
3. file/static 的 initiate/confirm 契约已冻结，可供 Phase 3 复用。
4. 不出现任何 Cloudflare R2 / presigned URL / HEAD API 的硬依赖。

### 4.3 Phase 3：ingestion 实体化与 workflow-start bridge

**阶段目标**

把 file/url/api 三条入口统一收敛到 `upload/source/document/workflow_run/workflow_steps`，并让 workflow start 在 P1 内核上真正生效。

**工作项**

## 5. 关键设计与验收细化

### 5.1 auth/session/team 的设计抓手

1. **session 以新库表为真相**：不要把 legacy JWT payload 结构原封不动带过来；legacy 只提供 gating 语义，不提供存储模型。
2. **API key 仍然 team-scoped**：延续 legacy 的 `hash-then-lookup + one-time display` 语义，但要补明确的错误类型和 revoke/rotate 生命周期。
3. **team list-select 只做最小闭环**：P2 只需要让用户在已有 membership 中选择 current team，不扩展成邀请/审批系统。
4. **workflow config lookup 前置**：它是 ingestion 的前置依赖，而不是 management 的附属功能。

### 5.2 ingestion 的设计抓手

1. **file/url/api 三条入口共用同一套下游 command**。
2. **file 与 static upload 的 object 空间隔离**。
3. **URL/API 不再伪装成 file payload**：legacy 的做法只作为行为线索；新架构必须显式写 `source_kind = url/api`。
4. **confirm/submit 的成功标准不再是“消息已发出”**：而是 `source/document/run/step` 实体是否已经落地。

### 5.3 workflow-start bridge 的设计抓手

1. **run 创建时写 snapshot**：P2 需要从 workflow config 读取可执行配置，并在 `workflow_runs.config_snapshot_json` 冻结。
2. **桥接只负责创建首批 steps，不负责执行完成**：执行责任仍属于 P3/P4 下游。
3. **static upload 默认不自动起 run**：否则会把对象管理与处理管线耦死。

### 5.4 management 读面的设计抓手

1. **workflow run / document / static file 是三个独立读面**，不要继续用 legacy `files` 一把梭。
2. **跨 tenant 一律 not found**，延续 legacy 安全策略。
3. **path filter 只适用于 static file 语义**，不要泛化到所有 document。

### 5.5 P2 完成判定

以下条件同时满足，P2 才算真正完成：

1. auth/team/session/api-key/profile/workflow-config lookup 可用；
2. file/url/api 三条入口可用；
3. local object store 可用；
4. file/url/api 至少一种 clean workflow start 已能创建 run + first steps；
5. static upload 可稳定落到 `static_files`，且关系字段正确；
6. workflow run / document / static file management read APIs 可用；
7. 自动化测试覆盖关键成功/失败路径；
8. 文档与下游 handoff 已同步。

## 6. 风险、缓解与文档同步

### 6.1 主要风险

| 风险 | 触发方式 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 把 legacy JWT/R2/Queue 直接搬进新实现 | 过度追求“兼容旧代码” | 与 P0/P1 冻结方向冲突，后续 P3/P6 难落地 | 严格以 `core.sql + P0/P1` 为真相，legacy 只借语义 |
| 把 URL/API 继续建模成 file payload | 延续 legacy file-centered 视角 | 新 schema 被架空，document/source 无法成为主对象 | 在 Phase 3 明确 `source_kind` 三分支 |
| static upload 被错误地自动接到 clean run | 复用 file confirm 逻辑时偷懒 | 对象管理与处理管线耦合，管理面难定义 | 在 P2 明确“先建关系、不自动起 run” |
| workflow config 仍在运行时动态读取 | 复刻 legacy dispatcher 流程 | 重跑不可追溯，P6 restart/replay 无法成立 | run 创建时固化 `config_snapshot_json` |
| phase 编号说明继续漂移 | `index.md` 旧表述未收敛 | 后续 P3/P5/P6 计划串联混乱 | 在 Phase 5 做文档同步收口 |

### 6.2 文档同步要求

1. 若 P2 实施中改动了对象层命名、包边界或 workflow-config 读取方式，需同步更新：
   - `docs/refactor/index.md`
   - `docs/refactor/database.md`
   - `docs/refactor/todo-list.md`
2. 若 P2 最终确认 static upload 要自动起 workflow run，则必须先更新 schema 与行动计划，再进入实现。
3. 若 team list-select 的最小模型与后续协作模型冲突，则只允许在 P6 或后续计划中扩展，不在 P2 内部临时放大范围。

### 6.3 完成后项目状态

P2 完成后，项目应达到以下状态：

1. `apps/api` 已经具备真实可用的 auth/team/ingestion/management 北向入口；
2. `packages/storage_objects` 已成为 object 层唯一入口；
3. `packages/ingestion` 已能把 file/url/api 转成 `source/document/workflow_run`；
4. `packages/management` 已经围绕 workflow run / document / static file 建立查询面；
5. P3 可以直接在 P2 产出的 `workflow_runs/workflow_steps/static_files/documents` 上继续清洗执行与 artifact 生产。
