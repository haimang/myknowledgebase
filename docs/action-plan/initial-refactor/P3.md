## 0. 执行背景与目标

P0 已冻结 monorepo 结构与包边界，P1 已冻结 `core.db + workflow kernel`，P2 已把 file / url / api 三类输入桥接到 `source / document / workflow_run / workflow_steps`。现在进入 P3，目标不再是“能创建 clean steps”，而是要把这些 steps 真的跑成 **clean artifact -> child / derived artifact -> downstream rag steps** 的稳定闭环。依据 `docs/refactor/todo-list.md:278-339`，本阶段必须同时交付 `workflow_clean`、`cleaners_universal`、`providers_dedicated`、`browser_runtime` 四条线；缺任何一条，P2 产出的 clean steps 都只能停留在“待执行”。

本计划继续沿用 `todo-list.md` 的当前阶段编号，把本轮定义为 **P3 Clean Pipeline**。`docs/refactor/index.md` 仍保留一版较早的编号残留，其中 clean pipeline 出现在 `P4`；本计划以 `todo-list.md + P0/P1/P2` 的现行链路为准，同时只吸收 `index.md` 中关于包边界、运行拓扑和 clean/rag 职责划分的冻结结论。

- **服务业务簇**：`smind-family / clean-pipeline`
- **计划对象**：`P3 Clean Pipeline`
- **本次计划解决的问题**：
  - P2 已经能创建第一批 clean steps，但 clean step 的输入归一化、执行契约、artifact 写回和下游 rag handoff 仍未冻结。

## 1. 执行综述

### 1.1 总体执行方式

本计划采用**先冻结 clean contract、再做最小闭环、再扩 provider / scatter、最后全量收口**的执行方式。关键顺序调整点是：**最小 finalizer 不能拖到最后**。如果没有“写 `cleaned_text` artifact + 创建 rag step”的最小 finalizer，Phase 2 的 universal cleaner 和 Phase 3 的 provider 迁移都无法形成可独立验收的 clean 闭环；因此本计划把“最小 finalizer 路径”提前到 Phase 2，而把 scatter diff、child identity、derived artifact 规则留到 Phase 4 完成。

### 1.2 Phase 总览

| Phase | 名称 | 规模 | 目标摘要 | 依赖前序 |
|------|------|------|----------|----------|
| Phase 1 | clean contract 与 planner 基线 | `M` | 冻结 clean step 输入、clean result、artifact/object ref、action registry 与 source->step 归一化契约 | `-` |
| Phase 2 | universal runtime 与最小 clean 闭环 | `L` | 落 `browser_runtime`、`cleaners_universal`，并补上“写 `cleaned_text` + 创建 rag step”的最小 finalizer | `Phase 1` |
| Phase 3 | dedicated provider 框架与首批迁移 | `L` | 建 `providers_dedicated` adapter / registry，先迁 `ChinaTax + Domain` 两个代表性 provider | `Phase 1, Phase 2` |
| Phase 4 | full finalizer、child fan-out 与 rag handoff | `L` | 完成 child / derived artifact 规则、diff/idempotency、scatter 模式和下游 rag steps 扩展创建 | `Phase 2, Phase 3` |
| Phase 5 | 集成验收与文档收口 | `M` | 通过 file / url / api 三类输入验收 P3，补齐测试、观测、运行手册与下游 handoff | `Phase 4` |

### 1.3 Phase 说明

1. **Phase 1 — clean contract 与 planner 基线**
   - **核心目标**：先冻结 clean step 的输入归一化、result schema、artifact key 语义、action registry / routing contract，以及 `workflow_clean.planner` 该负责什么。
   - **为什么先做**：如果 contract 不先冻结，Phase 2 的 universal cleaner 与 Phase 3 的 dedicated provider 一定会各自长出不同输出结构，最后只能在 finalizer 硬补兼容层。
2. **Phase 2 — universal runtime 与最小 clean 闭环**
   - **核心目标**：把 URL / file 路径上的通用清洗能力跑通，包括 HTML crawl、browser fetch、browser PDF、doc understanding，以及“cleaned_text artifact + rag step”最小闭环。
   - **为什么放在这里**：todo-list 的最小闭环是 `source -> clean artifact -> rag steps`；只有先让 universal 路径闭环，P3 才有一条最低成本的验收线。
3. **Phase 3 — dedicated provider 框架与首批迁移**
   - **核心目标**：交付 provider registry / adapter / unified clean result，并迁 `ChinaTax + Domain` 两类代表性 API provider。
   - **为什么放在这里**：dedicated provider 的复杂度主要在 ETL / scatter，不应该在 universal 闭环尚未成立时就一起放进锅里调试。
4. **Phase 4 — full finalizer、child fan-out 与 rag handoff**
   - **核心目标**：把 scatter child、`content_hash / meta_hash`、derived artifact、idempotent update、rag downstream step expansion 全部做完整。
   - **为什么放在这里**：这一步要同时理解 universal 与 provider 输出形态，必须建立在前两类 cleaner 的 contract 已被验证之后。
5. **Phase 5 — 集成验收与文档收口**
   - **核心目标**：把 file / url / api 三条 clean 闭环全部跑通，形成 P3 对 P4 / P6 的明确 handoff。
   - **为什么放在最后**：只有 planner、runtime、providers、finalizer 都到位后，P3 的验收标准才有资格被完整验证。

### 1.4 执行策略说明

- **执行顺序原则**：先 contract / planner，再 universal 最小闭环，再 provider，最后 full finalizer 与验收；不允许先迁 provider 再回头发明 clean result contract。
- **风险控制原则**：只借 legacy 的行为与状态推进，不借 Cloudflare Queue / Worker fetch / R2 binding / Browser Rendering API / HTMLRewriter 的 substrate 机制。
- **测试推进原则**：每个 Phase 都要有自己的可验证闭环，其中 Phase 2 必须第一次满足 `cleaned_text artifact + rag step`，Phase 4 才补完 child / scatter / diff。
- **文档同步原则**：如果 P3 实施中发现 `clean artifact`、`child file`、`derived artifact` 与 `core.sql` / `database.md` 的边界需要调整，必须先回写 SSOT 文档，再调整实现和 action-plan。
- **回滚 / 降级原则**：P3 只要求迁移 1-2 个核心 provider；首轮默认 `ChinaTax + Domain`，`REA` 不作为 P3 最小闭环阻塞项。若 runtime 风险过高，优先保住 universal clean 与两个 provider，而不是追求 provider 全量覆盖。

## 2. In-Scope / Out-of-Scope

### 2.1 In-Scope（本次 action-plan 明确要做）

- **[S1]** 冻结 clean step 输入归一化、clean result schema、artifact/object ref 约定、child fan-out DTO 与 `workflow_clean` planner 边界。
- **[S2]** 落 `packages/browser_runtime` 与 `packages/cleaners_universal`，覆盖 `html_crawl`、`browser_fetch`、`browser_pdf`、`llm_clean`、`gemini_understanding`（或等价实现）。
- **[S3]** 为 universal 路径落地最小 finalizer：写 `cleaned_text` / `raw_snapshot` artifact、更新 workflow 事件、创建第一批 rag steps。
- **[S4]** 落 `packages/providers_dedicated` 的 provider registry / adapter abstraction / unified clean result，先迁 `ChinaTax + Domain` 两个 provider。
- **[S5]** 完成 child / derived artifact、`content_hash / meta_hash`、scatter diff、idempotent relation persistence 与 rag handoff 扩展逻辑。
- **[S6]** 建立 file / url / api 三条 clean 闭环的集成测试与 Phase 收口文档。

### 2.2 Out-of-Scope（本次 action-plan 明确不做）

- **[O1]** RAG 内部执行（`structurizer / constructor / vectorizer / workflow_rag`），P3 只负责创建 rag steps，不负责消费它们。
- **[O2]** search / hydration / query API（属于 P5）。
- **[O3]** restart / purge / replay / inspect CLI 与完整运维写面（属于 P6）。
- **[O4]** 全量 dedicated provider 覆盖；`REA` 与更多 provider 仅作为后续扩展，不阻塞 P3 最小闭环。
- **[O5]** Cloudflare RPC discovery、Queue binding、Worker fetch/queue handler 的兼容层保留。

### 2.3 边界判定表

| 项目 | 判定 | 理由 | 重评条件 |
|------|------|------|----------|
| `workflow_clean` planner / registry / finalizer | `in-scope` | `todo-list` 已将其列为 P3 核心 | 仅当 `todo-list` 改写 P3 范围 |
| `browser_runtime` + `cleaners_universal` | `in-scope` | URL/file clean 闭环依赖这两层 | 若 runtime 设计上移或拆分 |
| `llm_clean.py` 独立模块 | `in-scope` | `todo-list` 已显式要求 `llm_clean`；legacy 仅提供嵌入式 Gemini rewrite 语义，需在新结构中抽出 | 若设计文档明确改成别的命名/归属 |
| `ChinaTax + Domain` provider 首迁 | `in-scope` | 两者分别覆盖 proxy/public API 与 API key ETL；更适合作为 P3 首轮 provider 基线 | 若上游业务优先级明确要求换成别的 provider |
| `REA` provider | `defer` | 依赖 cookie / user-agent / query payload，风险高于 `ChinaTax + Domain`，不适合阻塞 P3 最小闭环 | P3 最小闭环稳定后，或明确要求第三个 provider |
| scatter child diff / relation persistence | `in-scope` | `todo-list` 明确要求 child files / derived artifacts 可记录 | 若 `database.md` 明确把 child fan-out 模型改成别的表设计 |
| Cloudflare Queue/RPC/R2 compatibility layer | `out-of-scope` | 与 Python monolith 路线冲突，只能借语义 | 永不重评，除非架构路线整体逆转 |

## 5. Phase 详情

### 5.1 Phase 1 — clean contract 与 planner 基线

- **Phase 目标**：把 P3 最容易漂移的几件事先冻结：source -> clean step 的归一化、`action_branch` 与 registry 的关系、clean result / artifact / child DTO 的统一协议。
- **本 Phase 对应编号**：
  - `P1-01`
  - `P1-02`
  - `P1-03`
- **本 Phase 新增文件**：
  - `packages/workflow_clean/src/workflow_clean/planner.py`
  - `packages/workflow_clean/src/workflow_clean/steps.py`
  - `packages/workflow_clean/src/workflow_clean/registry.py`
  - `packages/contracts/src/contracts/clean.py`
- **本 Phase 修改文件**：
  - `packages/ingestion/**`
  - `packages/storage_objects/**`
  - `packages/workflow_core/**`
- **具体功能预期**：
  1. `workflow_clean.planner` 能根据 `source_kind`、mime、provider hints、workflow config 解析出唯一的 clean action 与 runtime hints。
  2. clean result 明确区分 `cleaned_text`、`raw_snapshot`、`child_files`、`derived artifacts`、`metadata`、`hashes`，并为 finalizer 提供稳定输入。
  3. `workflow_clean`、`cleaners_universal`、`providers_dedicated` 三层 registry 的职责边界清晰：前者做 action routing，总后两者做 branch capability 暴露。
- **具体测试安排**：
  - **单测**：planner 路由、contract schema、registry capability 暴露。
  - **集成测试**：source fixture -> clean step payload normalization。
  - **回归测试**：同一 source 重复规划不会生成互相冲突的 action route。
  - **手动验证**：审查 file/url/api 三类 source 的 planner 输出是否都可读、可解释、可追踪。
- **收口标准**：
  - file / url / api 三类 source 都有统一 clean step payload。
  - universal 与 dedicated provider 共用同一 clean result schema。
  - planner / registry 的职责不再依赖 legacy SMCP/Queue 术语。
- **本 Phase 风险提醒**：
  - 如果 contract 仍含糊，Phase 2/3 的 cleaner 很快会长出不兼容输出。
  - 如果 planner 直接嵌入 provider-specific 判断，后续 provider 会反向污染 `workflow_clean`。

### 5.2 Phase 2 — universal runtime 与最小 clean 闭环

- **Phase 目标**：跑通 URL/file 的通用 clean 路径，并尽早形成第一次 `cleaned_text artifact -> rag step` 闭环。
- **本 Phase 对应编号**：
  - `P2-01`
  - `P2-02`
  - `P2-03`
- **本 Phase 新增文件**：
  - `packages/browser_runtime/src/browser_runtime/playwright_runner.py`
  - `packages/browser_runtime/src/browser_runtime/extractors.py`
  - `packages/cleaners_universal/src/cleaners_universal/html_crawl.py`
  - `packages/cleaners_universal/src/cleaners_universal/browser_fetch.py`
  - `packages/cleaners_universal/src/cleaners_universal/browser_pdf.py`
  - `packages/cleaners_universal/src/cleaners_universal/llm_clean.py`
  - `packages/cleaners_universal/src/cleaners_universal/registry.py`
- **本 Phase 修改文件**：
  - `packages/llm_adapters/**`
  - `packages/workflow_clean/src/workflow_clean/finalizer.py`
  - `packages/storage_sqlite/**`
  - `packages/workflow_core/**`
- **具体功能预期**：
  1. `html_crawl`、`browser_fetch`、`browser_pdf` 共享 `browser_runtime`，而不是分别自己创建抓取逻辑。
  2. `llm_clean.py` 从 legacy `*-geminiClean` 行为中抽出独立文本重写能力，避免把 LLM 清洗硬嵌在 web cleaner 内部。
  3. `gemini_understanding` 或等价实现能处理 file-based clean，并复用统一 artifact/result contract。
  4. universal clean 完成后，最小 finalizer 立刻写出 `cleaned_text` artifact 并创建 rag steps，而不是等到 full finalizer 才第一次闭环。
- **具体测试安排**：
  - **单测**：extractor、runtime timeout / retry、cleaner result schema。
  - **集成测试**：URL -> universal cleaner -> artifact/object ref -> rag step。
  - **回归测试**：browser/html/pdf 三条 universal 路径不会互相污染 output slots。
  - **手动验证**：查看对象层中 `cleaned_text` / `raw_snapshot` 的实际产物是否可读。
- **收口标准**：
  - 至少一条 URL 路径和一条 file 路径可以完成 `cleaned_text` artifact 写回。
  - universal clean 完成后已有 rag steps 可被 P4 消费。
  - browser runtime 的 retry / timeout 不散落在业务 cleaner 内部。
- **本 Phase 风险提醒**：
  - Cloudflare Browser Rendering API 与 HTMLRewriter 的旧能力不能一比一照抄；必须显式 remap 到 Playwright + extractor。
  - 若最小 finalizer 不在本 Phase 落地，P3 会失去第一条可独立验收闭环。

### 5.3 Phase 3 — dedicated provider 框架与首批迁移

- **Phase 目标**：在 universal 闭环稳定后，交付 provider-specific clean 的框架和首批代表性迁移。
- **本 Phase 对应编号**：
  - `P3-01`
  - `P3-02`
  - `P3-03`
- **本 Phase 新增文件**：
  - `packages/providers_dedicated/src/providers_dedicated/base.py`
  - `packages/providers_dedicated/src/providers_dedicated/registry.py`
  - `packages/providers_dedicated/src/providers_dedicated/provider_chinatax.py`
  - `packages/providers_dedicated/src/providers_dedicated/provider_domain.py`
- **本 Phase 修改文件**：
  - `packages/workflow_clean/**`
  - `packages/storage_sqlite/**`
  - `tests/integration/providers_dedicated/**`
- **具体功能预期**：
  1. provider adapter 抽象统一管理 fetch、parse、hash、child metadata、summary bundle 生成。
  2. `ChinaTax` 作为 public/proxy API 型 provider 首先迁移，覆盖法规列表 / JSON ETL / atomic child 输出。
  3. `Domain` 作为 API-key 授权型 provider 第二个迁移，覆盖 agency listings / JSON ETL / child fan-out。
  4. `REA` 不作为 P3 最小闭环阻塞项，因为它依赖 cookie / user-agent / query payload，风险更高，适合作为 P3 后续扩面。
- **具体测试安排**：
  - **单测**：provider adapter / parser / hash / child metadata builder。
  - **集成测试**：ChinaTax / Domain 两条 dedicated clean 路径。
  - **回归测试**：provider-specific metadata 不会破坏统一 clean result schema。
  - **手动验证**：child JSON / summary bundle 的 object keys、mime、size、hash 是否与 contract 对齐。
- **收口标准**：
  - `ChinaTax + Domain` 都可返回统一 clean result，并产生 child / derived outputs。
  - provider-specific ETL 不需要修改 `workflow_clean` 主流程即可接入。
  - `REA` 已被明确标为 defer，而不是隐形半成品。
- **本 Phase 风险提醒**：
  - 一次性追求全 provider 覆盖会拖垮 P3 节奏。
  - 如果 provider adapter 没有冻结，child fan-out 规则会在不同 provider 中分叉。

### 5.4 Phase 4 — full finalizer、child fan-out 与 rag handoff

- **Phase 目标**：把 clean 输出真正纳入新系统的数据模型和 downstream workflow kernel，补齐散射模式与幂等更新。
- **本 Phase 对应编号**：
  - `P4-01`
  - `P4-02`
  - `P4-03`
- **本 Phase 新增文件**：
  - `packages/workflow_clean/src/workflow_clean/finalizer.py`

- **本 Phase 修改文件**：
  - `packages/storage_sqlite/**`
  - `packages/workflow_core/**`
  - `packages/contracts/**`
- **具体功能预期**：
  1. child / derived artifacts 能稳定映射到新 `artifacts / documents / static_files` 结构，而不是简单复刻 legacy `smind_files_relations`。
  2. `content_hash / meta_hash` 可用于判定 unchanged / full_update / context_meta_update，并阻止重复创建 downstream rag steps。
  3. finalizer 不再向下游发送 queue `WORKFLOW_START`，而是直接通过 `workflow_core` 在 `core.db` 中创建 downstream rag steps。
  4. scatter 与标准 handoff 都能保持可解释、可重放的 workflow events。
- **具体测试安排**：
  - **单测**：diff decision、artifact relation builder、rag step expansion planner。
  - **集成测试**：scatter provider -> finalizer -> rag steps；standard clean -> finalizer -> rag step。
  - **回归测试**：重复 clean 不重复创建 child / rag；meta update 只触发必要重建。
  - **手动验证**：检查 child / derived artifact 与 workflow events 的可读性和可追踪性。
- **收口标准**：
  - child / derived artifacts 已稳定落到新数据模型。
  - scatter 与标准 handoff 都能创建正确的 downstream rag steps。
  - finalizer 完成后不再需要 legacy queue callback 思维来解释 clean 状态推进。
- **本 Phase 风险提醒**：
  - 如果直接照搬 legacy `payload_artifacts` / `file_relations`，会把旧表结构耦合带进新系统。
  - 若 rag handoff 仍被做成“黑盒消息发送”，P4 会失去对下游 steps 的显式控制。

## 8. Action-Plan 整体测试与整体收口

### 8.1 Action-Plan 整体测试方法

- **基础校验**：
  - planner / registry / contract schema 能覆盖 file / url / api 三类 source。
  - `cleaned_text`、`raw_snapshot`、`child_files`、rag steps 都有明确可观察落点。
- **单元测试**：
  - `workflow_clean` planner / registry / diff / finalizer unit tests
  - `browser_runtime` / `cleaners_universal` / `providers_dedicated` unit tests
- **集成测试**：
  - file -> universal clean -> `cleaned_text` artifact -> rag steps
  - url -> browser/runtime clean -> `cleaned_text` artifact -> rag steps
  - api -> dedicated provider -> child fan-out -> rag steps
- **端到端 / 手动验证**：
  - 通过 P2 的入口创建 file / url / api 三类 source，检查对象层、`core.db`、worker 事件轨迹三者一致。
- **回归测试**：
  - 重复 clean 不重复创建 child / rag steps
  - timeout / retry 分支不会破坏 artifact consistency
- **文档校验**：
  - P3 输出契约与 P4 / P6 handoff 描述一致

### 8.2 Action-Plan 整体收口标准

所有 Phase 完成后，至少应满足以下条件：

1. file / url / api 三类输入至少各有一条 clean 闭环成功。
2. 每条闭环都能产出可持久化、可查询的 `cleaned_text` artifact。
3. child / derived artifacts 能被稳定记录，且 scatter 场景具备幂等更新能力。

## A5. Substrate-fit / 技术路线（TR）过滤复核

本节使用四条固定技术路线过滤 legacy 参考：

- `TR-1`：运行时从 Cloudflare Worker/Queue/R2/Browser Rendering API 迁移到 Python monolith + local apps/packages + object store。
- `TR-2`：`core.db` 是唯一 workflow kernel，clean -> rag handoff 必须回收到 `workflow_core` / `workflow_steps`。
- `TR-3`：数据库只保留 refs / hash / metadata，大对象必须落对象层。
- `TR-4`：每个阶段必须有可独立验收的闭环，因此最小 finalizer 需要早于 full scatter finalizer。

| 借鉴点 | 原机制 | 与本项目技术路线（TR）是否冲突 | 过滤后落地形态（降级/重映射/直采） |
|--------|--------|-------------------------------------|-------------------------------------|
| dispatcher 的 hydrate -> orchestrate -> finalize 主流程 | Queue consumer + callback roundtrip | `TR-1: 部分冲突` | 直采 clean workflow 分层，重映射到 worker lane + direct service calls + `core.db` 状态推进 |
| registry-driven branch routing | Worker RPC discovery + registry metadata | `TR-1: 部分冲突` | 直采 registry / metadata / validation；RPC discovery 降级为应用内 capability registry |
| universal web/doc cleaner | Browser Rendering API + HTMLRewriter + Gemini | `TR-1: 冲突`, `TR-3: 兼容` | 借 pipeline 结构与输出 contract，底层改成 Playwright / extractor / llm_adapters |
| provider scatter ETL | provider processor + `atomic_bundle` + child hash | `TR-2: 兼容`, `TR-3: 兼容` | 基本直采 child/hash/summarize 思路，object refs 改由 `storage_objects` 管理 |
| finalizer 的 diff + child persistence + RAG dispatch | `smind_files_relations` + queue `WORKFLOW_START` | `TR-2: 冲突`, `TR-4: 部分冲突` | 借 hash/diff/child identity 原则；重映射为 new artifact model + `workflow_core` downstream step creation，并把最小 finalizer 提前到 Phase 2 |

- **substrate-fit 总结（对 HEAD）**：legacy 最值得借的是 clean pipeline 的分层、显式 registry、child/hash fan-out 与 clean->rag 的状态推进顺序；最不该借的是 Queue / R2 / Browser Rendering API / HTMLRewriter / queue callback roundtrip。P3 应把这些旧行为全部重映射到 `workflow_clean + workflow_core + storage_objects + core.db artifacts/events`。
