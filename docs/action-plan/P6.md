## 0. 执行背景与目标

P0-P5 已经把 `smind-family` 的代码骨架、双库状态内核、control plane、clean/rag pipeline 与 retrieval surface 依次冻结下来。尤其 P5 已经把 query/search/debug retrieval 收口为正式 northbound 能力，因此从 P6 开始，目标不再是“证明系统能跑通主链路”，而是把系统推进到 **可长期运行、可恢复、可清理、可调试、可操作** 的状态（`docs/action-plan/P5.md:53-57,117-122,503-507`）。

依据 `docs/refactor/todo-list.md:445-510`，P6 必须同时交付 restart/replay、purge、observability、ops CLI 与 health jobs；而 `docs/refactor/database.md:167-184,253-425` 又进一步冻结了几条不可绕开的底线：`task_claims` 是唯一 lease 权威记录，heartbeat 是长任务安全执行的必要条件，`restart_requests/purge_requests` 必须有独立状态机，`chunks.vec_status='pending_purge'` 长时间滞留必须被检测/告警，`v_active_claims`、`v_workflow_run_summary`、`v_restart_backlog`、`v_purge_backlog` 等视图应成为运维面基底。也就是说，P6 不是补几条管理命令，而是把 **P1 的状态机** 变成 **可运维的状态机**。

本轮追回的 legacy 事实依据也说明了这一点：`legacy-family/smind-clean-dispatcher/services/restarter.ts:96-175,177-231,533-673,785-995` 已经给出 `KICKSTART / RECOVERY / FORCE_RECOVERY` 的恢复语义和 `debug_context` 回传形状，`legacy-family/smind-rag-dispatcher/services/purger.ts:75-260` 与 `legacy-family/smind-skill-rag-vectorizer/src/purger_logic.ts:56-162` 给出了 purge 请求、锁冲突和删除顺序，`legacy-family/smind-skill-rag-vectorizer/core/db.ts:44-136` 给出了 claim/release stranded task 的旧实现轮廓，`legacy-family/smind-admin/src/index.ts:146-225` 与 `legacy-family/smind-rag-dispatcher/src/index.ts:150-215` 则给出了 northbound admin/restart/purge surface 的入口形状。它们都可借，但必须全部重映射到 Python monolith + `core.db/vec.db` + 本地 API/CLI 的新基底上。

- **服务业务簇**：`smind-family / operability-and-recovery`
- **计划对象**：`P6 运维与恢复能力`
- **本次计划解决的问题**：
  - P1-P5 已经能执行 workflow、写入向量、完成检索，但 operator 仍缺少一条正式的 restart / purge / inspect / retry / debug 操作面，系统还不具备持续运行时的恢复抓手。
  - `database.md` 已经冻结了 heartbeat、lease timeout、`restart_requests/purge_requests`、`pending_purge` 与 backlog views 等核心运维语义，但还没有把这些冻结结论分解成真正的实施顺序、模块归属和验收闭环。
  - purge 既跨 `core.db` 又跨 `vec.db`，还可能清理 object store；在“不依赖跨库强事务”的前提下，如果没有前置 detector、重试与补偿路径，P6 实施很容易留下“半清理、不可见、不可恢复”的脏状态。
  - legacy 只有 RPC / queue / DO 时代的 restart/purge/admin 形状，没有本地 CLI、没有真正 heartbeat TTL、也没有统一的 vec/core mismatch detector；这些都必须在 P6 中净新建立。
- **本次计划的直接产出**：
  - `packages/workflow_core`、`packages/storage_sqlite`、`packages/storage_objects`、`packages/management`、`apps/api`、`apps/cli` 在 P6 范围内的执行拆分、阶段边界与测试收口标准。
  - 围绕 `restart_requests`、`purge_requests`、`task_claims`、`step_attempts`、`chunks.vec_status`、`vector_records.deleted_at` 的统一运维合同，包括 dispatch、幂等、TTL、detector、审计与 CLI/API surface。
  - 一条“先 contracts 与 detector baseline，再落 restart/purge 写路径，再交付 operator API/CLI 与 recovery drills”的安全执行顺序，避免把高风险清理逻辑先落地后补救。
  - 一份追加在本文底部的 legacy reference-anchor，明确旧代码哪些运维机制可借、哪些只能部分借、哪些在 P6 必须净新实现。
- **本计划不重新讨论的设计结论**：
  - `core.db` 是 workflow kernel，`vec.db` 是向量索引层；P6 不能把任何关键恢复语义放回队列、DO 或隐式内存状态中（来源：`docs/refactor/index.md:47-55,58-74`, `docs/refactor/database.md:78-115`）。
  - `task_claims` 是唯一 lease 权威记录，heartbeat 与 `lease_timeout` 是长任务恢复的正式机制；`workflow_steps.status='running'` 不能替代 claim 真相层（来源：`docs/refactor/database.md:150-159,253-276,343-383`）。
  - `restart_requests` 与 `purge_requests` 必须作为显式数据库请求来执行，而不是无状态管理动作或隐藏 side effect（来源：`docs/refactor/database.md:174-184,397-406,559`）。
  - `chunks.vec_status='pending_purge'` 的长时间滞留必须被检测；`vector_records.deleted_at` 只是 purge 窗口辅助手段，不能替代 `core.db` 的状态真相（来源：`docs/refactor/database.md:167-172,317-324,397-406`）。
  - P6 的 observability/ops surface 必须复用并扩展 P5 已经建立的 debug/log/query surface，而不是平行再造第二套调试面（来源：`docs/action-plan/P5.md:117-122,503-507`）。

## 1. 执行综述

### 1.1 总体执行方式

本计划采用**先冻结运维合同与 request dispatch，再建立 read-model / detector baseline，随后实现 restart/replay，接着实现 purge 与双清理，最后交付 operator API/CLI、定时健康任务与 recovery drills** 的执行方式。这个顺序与 P5 的“先建立可观测/debug surface，再推进复杂状态机”的经验保持一致，也吸收了本轮 critique 的关键修正：`pending_purge` detector 和 vec/core mismatch detector 不能等 purge 引擎落地后再补，否则 P6 会在最危险的阶段失去最基本的自我观测能力。

### 1.2 Phase 总览

| Phase | 名称 | 规模 | 目标摘要 | 依赖前序 |
|------|------|------|----------|----------|
| Phase 1 | ops contracts 与 dispatch baseline | `M` | 冻结 request/command contract、lease TTL、幂等规则、dispatch 责任归属与 audit contract | `-` |
| Phase 2 | ops read-model 与 detector baseline | `M` | 先把 workflow summary、claims、restart/purge backlog、pending_purge 与 vec/core mismatch 的读面做出来 | `Phase 1`, `P1`, `P5` |
| Phase 3 | restart / replay / stale-claim recovery | `L` | 实现 workflow restart、step restart、downstream replay、kickstart/force recovery、lease-timeout takeover | `Phase 1`, `Phase 2`, `P1-P4` |
| Phase 4 | purge engine 与 dual-cleanup compensations | `L` | 实现 document/workflow/chunk purge、vector + object 双清理、resume/retry 与异常补偿 | `Phase 1`, `Phase 2`, `Phase 3`, `P4-P5` |
| Phase 5 | operator API/CLI、health jobs 与 drills | `M` | 暴露 ops API/CLI、定时健康任务、审计/debug surface、恢复演练与 P7 handoff | `Phase 2`, `Phase 3`, `Phase 4` |

### 1.3 Phase 说明

1. **Phase 1 — ops contracts 与 dispatch baseline**
   - **核心目标**：先把 `restart_requests/purge_requests` 的 dispatch、lease TTL、幂等/去重、force 模式语义、审计字段和 northbound 命令合同冻结下来。
   - **为什么先做**：如果不先冻结这些合同，后续 restart/purge/CLI/health job 都会各自假设不同的 TTL、状态迁移和 request ownership。
2. **Phase 2 — ops read-model 与 detector baseline**
   - **核心目标**：在写任何高风险恢复逻辑之前，先把 `v_workflow_run_summary`、`v_active_claims`、`v_restart_backlog`、`v_purge_backlog`、pending-purge detector、vec/core mismatch detector 这些观察面建立起来。
   - **为什么放在这里**：P6 最危险的逻辑是 restart 与 purge；没有前置 detector/read-model，它们一旦卡住就没有可解释性。
3. **Phase 3 — restart / replay / stale-claim recovery**
   - **核心目标**：把 workflow/step/downstream restart 与 `kickstart / recovery / force recovery` 模式真正映射到 `core.db` 请求状态机，并把 stale claim takeover / `lease_timeout` 的收口逻辑跑通。
   - **为什么放在这里**：restart 主要消费 `core.db` 状态与 claim 语义，对 `vec.db` 的依赖较 purge 更轻，适合先落成第一条 operator 写路径。
4. **Phase 4 — purge engine 与 dual-cleanup compensations**
   - **核心目标**：在 detector baseline 已存在的前提下，实现 `pending_purge -> vector soft delete -> physical delete -> object cleanup -> completed` 的完整 purge 流程。
   - **为什么放在这里**：purge 是 P6 中最容易制造跨库半失败状态的部分，必须在 read-model、restart 收口和 detector 已存在的前提下再做。
5. **Phase 5 — operator API/CLI、health jobs 与 drills**
   - **核心目标**：统一 ops API/CLI 的 read/write surface，交付 lease reaper、heartbeat monitor、pending_purge detector、vec/core mismatch detector 的定时执行路径，并用对抗式 drills 验证整个恢复面。
   - **为什么放在最后**：CLI 与定时任务必须站在稳定的 restart/purge state machine 之上，否则只是把不稳定实现暴露给操作员。

### 1.4 执行策略说明

- **执行顺序原则**：先 contract，再 read-model/detector，再 write-path；不允许先做 purge/restart 的 destructive path，再回头补观测和补偿。
- **风险控制原则**：所有 operator 写操作都必须落到显式 request row；force 模式默认受保护，不允许把“直接改状态”当常规运维手段。
- **测试推进原则**：每个 Phase 都要有独立 exit criterion；Phase 5 必须额外覆盖 recovery drills，包括 stale claim takeover、mid-purge crash、vec/core mismatch、force recovery、downstream replay。
- **文档同步原则**：如果实施中发现 TTL、request 状态、backlog view、`chunks.vec_status`、`vector_records.deleted_at`、audit 字段或 CLI 命令合同需要变化，必须先回写 `database.md` / `core.sql` / `vec.sql` / action-plan，再改代码。
- **回滚 / 降级原则**：若 CLI 写命令晚于 API 完成，可先以内部 API + 手动脚本做过渡，但不得把最终 DoD 降成“只有 API 没有 CLI”；若 purge 的 object cleanup 风险过高，可先把删除动作做成显式 retriable sub-step，但不能省略 request 状态与 detector。

## 2. In-Scope / Out-of-Scope

### 2.1 In-Scope（本次 action-plan 明确要做）

- **[S1]** 冻结 `restart_requests`、`purge_requests`、ops command/result DTO、force/recovery/kickstart 模式语义、request dispatch 责任归属与幂等/去重规则。
- **[S2]** 冻结并实现 heartbeat / lease TTL 合同、stale claim 判定方式、`lease_timeout` 的 `step_attempts` 落账语义与 claim takeover 路径。
- **[S3]** 建立 workflow summary、active claims、stale claims、failed steps、pending restart、pending purge、pending_purge 异常与 vec/core mismatch 的统一 read-model / detector baseline。
- **[S4]** 实现 workflow restart、step restart、downstream replay、force recovery、kickstart、document/workflow/chunk purge、vector + object 双清理与 resume/retry。
- **[S5]** 暴露 ops API 与 ops CLI，覆盖 workflow list/inspect/restart/purge、step inspect/retry、detector inspect、request inspect。
- **[S6]** 建立 health jobs / reaper / monitor / detector 的调度入口、审计日志写入与 recovery drills。

### 2.2 Out-of-Scope（本次 action-plan 明确不做）

- **[O1]** 新增 clean/rag 业务 action、本体业务算法升级、provider/embedding 模型切换。
- **[O2]** 面向前端用户的完整运维 UI；P6 只负责 API / CLI / debug surface。
- **[O3]** 改写 P5 的 query/search contract；P6 只消费并扩展 P5 已有 debug/log/search surface。
- **[O4]** 重新设计更细粒度 ACL 或跨 team 权限模型；P6 只在现有 auth/team 边界内交付 operator surface。
- **[O5]** 切换默认生产入口、冻结 legacy 运行路径或执行 cutover；这属于 P7。
- **[O6]** 兼容 Cloudflare queue / Durable Object / Worker RPC 作为新系统运行时；P6 只借鉴 legacy 形状，不延续 legacy substrate。

### 2.3 边界判定表

## 7. 风险、依赖与完成后状态

### 7.1 风险与依赖

| 风险 / 依赖 | 描述 | 当前判断 | 应对方式 |
|-------------|------|----------|----------|
| purge 跨 `core.db` / `vec.db` / object store 无强事务 | 任一子步骤失败都会留下半清理状态 | `high` | detector baseline 前置；所有 purge 通过 request row、resume/retry、idempotent delete 收口 |
| restart/replay 幂等性 | workflow/step/downstream restart 很容易重复 fan-out 或重复 attempt | `high` | 在 Phase 1 冻结 dedupe key、active request 去重、mode 语义；Phase 3 做 matrix tests |
| heartbeat TTL 与 stale 判定不合理 | TTL 太短会误杀长任务，太长会延误恢复 | `high` | 把 TTL 合同写成显式参数与测试矩阵，不让不同组件各自猜测 |
| object cleanup 失败处理 | purge 触达 object store 时可能遇到“对象已不存在”或部分删除 | `medium` | 把缺失对象视为幂等成功，把真实失败记录为 retriable request failure |
| ops surface 权限边界 | CLI/API 是高权限入口，容易越过 team/auth 边界 | `medium` | 统一复用 control plane auth/team guard 与 audit log；force 操作默认 gated |
| P5/P6 观测面重复 | 若 P6 平行重做 debug surface，会造成 operator 视角分裂 | `medium` | 明确 P6 只扩展 P5 debug/log/search surface，优先复用已有 tracing 与 inspect 习惯 |

### 7.2 约束与前提

## A5. Substrate-fit / 技术路线（TR）过滤复核

本节使用五条固定技术路线过滤 legacy 参考：

- `TR-1`：运行时从 Cloudflare queue / Worker RPC / Durable Object 迁移到 Python monolith + `core.db` + `vec.db` + local API/CLI。
- `TR-2`：`restart_requests/purge_requests` 必须是显式 DB request 状态机，而不是直接的管理调用。
- `TR-3`：`task_claims` 是唯一 lease 权威记录，heartbeat / lease renew / lease_timeout 是正式恢复机制。
- `TR-4`：系统不依赖跨库强事务，任何 purge / mismatch / pending_purge 都必须走补偿与 detector。
- `TR-5`：operator surface 必须是可审计、可脚本化的 API/CLI，而不是 generic RPC router 或调度内部细节。

| 借鉴点 | 原机制 | 与本项目技术路线（TR）是否冲突 | 过滤后落地形态（降级/重映射/直采） |
|--------|--------|-------------------------------------|-------------------------------------|
| `KICKSTART / RECOVERY / FORCE_*` 恢复模式 | queue + D1 state rollback + debug_context | `TR-1: 部分冲突`, `TR-2: 冲突` | 直采 mode taxonomy 与 debug payload，重映射为 DB request + worker execution |
| diff-based replay decision | D1 relation/hash diff + purge_before_write | `TR-1: 部分冲突`, `TR-2: 兼容` | 直采 replay selection 思想，重映射到 workflow/step/downstream graph 与 chunk/artifact 关系 |
| purge request + audit step + lock conflict | RPC request -> DO purge -> process row | `TR-1: 部分冲突`, `TR-2: 兼容`, `TR-4: 兼容` | 直采 request contract、audit-first、lock conflict，执行体改成 `purge_requests` + SQLite worker |
| claim pending / release stranded task | `processing_status` + instance_id | `TR-3: 冲突` | 只借 claim/release 分离的意识；正式落地改为 `task_claims + heartbeat + lease_timeout` |
| detector 先 inspect 再恢复 | stuck pending detection + autoRecover | `TR-2: 兼容`, `TR-4: 兼容`, `TR-5: 兼容` | 直采 inspect-first 节奏，扩展为 pending_purge / mismatch / stale claim 多 detector 体系 |
| northbound auth/team guard 再进 handler | admin RPC router | `TR-1: 部分冲突`, `TR-5: 兼容` | 直采 guard 顺序，入口改成 FastAPI/CLI |
| alarm loop / background scheduler | DO alarm | `TR-1: 冲突`, `TR-4: 兼容` | 借“定时健康任务”概念，重映射到 worker scheduler / cron-like background jobs |
| RPC router 充当 admin/ops 入口 | generic service/method switch | `TR-5: 冲突` | 不采；P6 单独交付面向 operator 的 API/CLI surface |

- **substrate-fit 总结（对 HEAD）**：legacy 最值得借的是恢复模式 taxonomy、audit-first purge contract、lock conflict 显式化、inspect-first detector 节奏和 operator-facing debug payload；最不该借的是 queue/DO/RPC 作为新真相层、`processing_status` 充当 lease 模型、以及“没有 CLI 就拿管理 RPC 顶上”的做法。P6 必须把这些旧经验全部重映射到 `restart_requests/purge_requests + task_claims + workflow_core + storage_sqlite + management + apps/cli` 的显式本地运维链路上。
