## 0. 执行背景与目标

当前仓库的唯一旧代码事实真理是 `legacy-family/`。从旧代码现状看，系统仍然由多个独立 Cloudflare Worker 包构成：`smind-admin`、`smind-clean-dispatcher`、`smind-rag-dispatcher` 以及一组 clean / rag skill worker；每个包各自维护 `package.json`、`wrangler.toml`、局部运行脚本和重复基础件。重构文档则已经冻结了新的目标形态：以 Python 3.12+ 为统一技术基线，按 `apps/`、`packages/`、`tests/`、`tools/`、`data/` 组织为单仓模块化单体，并以 `core.db` / `vec.db` / 对象存储承接后续状态与数据平面。

P0 的任务不是开始迁业务，而是把这份冻结设计落成一个**可执行、可扩展、可交接**的基础骨架。没有 P0，后续 P1~P6 会立刻遇到三个问题：新仓库没有统一工作区与运行入口；旧代码里被多处复制的基础件会继续污染新仓库；apps 与 packages 的边界不先冻结，后面的控制面、workflow、storage、ingestion 会重新长成“按部署拆包”的旧形态。

- **服务业务簇**：`smind-family / platform-foundation`
- **计划对象**：`P0 基础骨架`
- **本次计划解决的问题**：
  - 新仓库尚未存在可承载后续重构的顶层目录、运行入口与工作区基线。
  - 旧代码中 `core/log.ts`、`core/errors.ts`、`core/schemas_common.ts`、`core/schemas_smcp.ts`、`core/db.ts` 在多个 worker 中重复出现，必须先收敛最小公共面。
  - 如果不先冻结 `apps -> packages` 的依赖方向，后续实现会回流到旧的“按部署拆包”方式。
- **本次计划的直接产出**：
  - 新仓库顶层骨架与 `legacy-family/` 只读迁移边界。
  - 统一 Python workspace / 包管理 / lint / test / run 工程基线。
  - `apps/api`、`apps/worker`、`apps/cli` 三类最小运行壳。
  - `packages/common`、`packages/contracts`、`packages/config` 最小公共基础面。
  - P0 smoke 验收闭环与交接文档。
- **本计划不重新讨论的设计结论**：
  - 新系统的目标目录树、模块化单体方向、技术栈主线已经冻结（来源：`docs/refactor/index.md`）。
  - `core.db` / `vec.db` 分层、workflow 作为统一状态内核已经冻结（来源：`docs/refactor/database.md`）。
  - P0 的完成标准是目录骨架、统一包管理、API/worker/CLI 基础壳、tests/tools/data 补齐（来源：`docs/refactor/todo-list.md`）。
  - `legacy-family/` 是旧代码事实依据，但不是继续增量开发的目标目录（来源：`docs/refactor/index.md`, `docs/refactor/todo-list.md`）。

P0 的旧代码原始依据如下：

- `legacy-family/smind-admin/src/index.ts`：现有控制面、ingestion、查询与运维入口仍聚集在单个 admin Worker 中，说明新仓库必须先拆出独立 `apps/api` 入口承接 HTTP 面。
- `legacy-family/smind-clean-dispatcher/src/index.ts`：clean 侧同时存在 Queue 消费与 `fetch` 触发路径，说明新仓库必须先有独立 `apps/worker` 运行壳承接异步执行面。
- `legacy-family/smind-rag-dispatcher/src/index.ts`：rag 侧也以 dispatcher 形式独立运行，进一步证明 worker 入口不能继续散落在多个包中。
- `legacy-family/*/package.json` 与 skill 目录结构：旧系统按部署单元拆成多包，新的 P0 必须把“部署单元”还原成“仓内入口 + 共享业务包”。
- `legacy-family/**/core/log.ts`、`core/errors.ts`、`core/schemas_common.ts`、`core/schemas_smcp.ts`、`core/db.ts` 的重复存在：P0 必须先抽出共享基础件，否则后续迁移会把重复复制带进新结构。

## 1. 执行综述

### 1.1 总体执行方式

这份 action-plan 共分四个 Phase，执行方式是**先骨架与边界、后工作区；先入口、后共享基础；最后用 smoke 收口**。P0 只解决“仓库该怎么长、后续代码该落在哪里、如何统一启动与测试”，不进入真实业务迁移，也不提前实现数据库与 workflow 细节。

### 1.2 Phase 总览

| Phase | 名称 | 规模 | 目标摘要 | 依赖前序 |
|------|------|------|----------|----------|
| Phase 1 | 仓库骨架与迁移边界 | `S` | 建立新仓库顶层骨架，冻结 `legacy-family/` 只读参照地位 | `-` |
| Phase 2 | Python workspace 与工程约定 | `M` | 建立统一 workspace、包管理、开发命令、依赖与 import 边界 | `Phase 1` |
| Phase 3 | API / Worker / CLI 运行壳 | `M` | 建立三类入口应用的最小可运行壳，明确“入口在 apps，能力在 packages” | `Phase 2` |
| Phase 4 | 公共基础包与 smoke 收口 | `M` | 提取 common / contracts / config 的最小公共面，并补齐 P0 的测试与文档闭环 | `Phase 3` |

### 1.3 Phase 说明

1. **Phase 1 — 仓库骨架与迁移边界**
   - **核心目标**：把 `apps/`、`packages/`、`tests/`、`tools/`、`data/` 真实落到仓库中，并明确 `legacy-family/` 仅为只读迁移依据。
   - **为什么先做**：如果顶层骨架和边界没先冻结，后续所有配置和入口都会失去落点。
2. **Phase 2 — Python workspace 与工程约定**
   - **核心目标**：建立整个新仓库的唯一工作区与根级工程命令，让后续模块共享同一依赖与测试基线。
   - **为什么放在这里**：只有目录先存在，工作区配置、脚本和依赖边界才有明确挂载位置。
3. **Phase 3 — API / Worker / CLI 运行壳**
   - **核心目标**：为 HTTP、异步执行、运维命令三类运行面提供最小入口应用。
   - **为什么放在这里**：没有统一工作区，入口应用无法形成一致运行方式；没有入口应用，共享基础包也缺少上层消费方。
4. **Phase 4 — 公共基础包与 smoke 收口**
   - **核心目标**：收敛最小共享基础面，并以 smoke 闭环保证 P0 的工程可用性。
   - **为什么放在这里**：只有入口壳先存在，才能准确判断哪些基础件是真正的跨入口公共面。

### 1.4 执行策略说明

- **执行顺序原则**：先冻结仓库边界，再建立工作区，再建立入口应用，最后抽取共享基础件与 smoke。
- **风险控制原则**：P0 只做最小工程骨架，不提前引入业务逻辑、workflow 状态机或存储实现。
- **测试推进原则**：以“能装、能导入、能启动、能 help”为 P0 主验收线，避免在骨架阶段过早追求业务正确性。
- **文档同步原则**：目录职责、启动命令、P0 完成状态必须在 README / 开发文档 / `todo-list` 中同步。
- **回滚 / 降级原则**：所有改动应集中在新目录骨架与根配置内；若某一工具链选型需要调整，应只影响工作区层，不影响 Phase 1 已冻结的目录边界。

  - `legacy-family/` 的只读定位被写清楚。
  - P1 之后的工作不再需要重新讨论仓库顶层结构。
- **本 Phase 风险提醒**：
  - 最大风险是边界文字写了，但团队仍按旧路径继续开发；因此目录与文档必须同步给出明确约束。

### 5.2 Phase 2 — Python workspace 与工程约定

- **Phase 目标**：建立整个新仓库的唯一工作区与工程基线，让所有后续包都能在同一套依赖管理、测试、格式化与运行命令下开发。
- **本 Phase 对应编号**：
  - `P2-01`
  - `P2-02`
  - `P2-03`
- **本 Phase 新增文件**：
  - `pyproject.toml`
  - 根 lockfile / workspace manager config
  - 根级 lint / test / format 配置
  - `tools/scripts/*`（或等价脚本目录）
- **本 Phase 修改文件**：
  - 根 README / 开发文档
  - 目录说明或开发约定文件
- **本 Phase 删除文件**（如无可删去）：
  - 无
- **具体功能预期**：
  1. 多应用多包通过单根工作区解析依赖，而不是各自持有一套包管理配置。
  2. apps 只能依赖 packages 暴露的能力；packages 之间遵循明确分层，不允许把业务代码回灌到入口层。
- **具体测试安排**：
  - **单测**：`N/A`
  - **集成测试**：从根目录一次性 bootstrap 依赖；执行基础 lint / format / test 命令。
  - **回归测试**：确认新增模块接入时不需要再创建独立包管理体系。
  - **手动验证**：审阅依赖与 import 边界说明，确认 apps / packages 职责清晰。
- **收口标准**：
  - 新仓库拥有唯一工作区配置与根开发命令。
  - apps / packages 的依赖方向有明确约束。
  - 后续新模块接入不再需要额外创建独立包管理体系。
- **本 Phase 风险提醒**：
  - 不要在 P0 把时间花在高级工具链微优化上；只保留后续阶段必需的工作区与根命令基线。

### 5.3 Phase 3 — API / Worker / CLI 运行壳

- **Phase 目标**：把 refactor 文档要求的三个运行入口全部建立起来，但只做到最小可运行壳，不进入真实业务。
- **本 Phase 对应编号**：
  - `P3-01`
  - `P3-02`
  - `P3-03`
- **本 Phase 新增文件**：
  - `apps/api/**`
  - `apps/worker/**`
  - `apps/cli/**`
- **本 Phase 修改文件**：
  - 根工作区配置（纳入三个应用）
  - 开发文档 / 启动说明
- **本 Phase 删除文件**（如无可删去）：
  - 无
- **具体功能预期**：
  1. `apps/api` 提供最小 FastAPI 生命周期与健康探针壳，后续可承接 admin / ingest / query / search 路由。
  2. `apps/worker` 提供最小主进程与空转 consumer / dispatch loop 壳，后续可承接 clean / rag / workflow。
  3. `apps/cli` 提供命令组、help 与 bootstrap 壳，后续可承接 repair / replay / maintenance。
- **具体测试安排**：
  - **单测**：入口模块导入测试。
  - **集成测试**：API 启动 smoke、worker 启动 smoke、CLI `--help` smoke。
  - **回归测试**：确认三类入口共同依赖 `packages/`，而不是把业务实现写回入口目录。
  - **手动验证**：检查启动命令、help 输出、健康检查路径是否与文档一致。
- **收口标准**：
  - 三类入口均存在且可独立启动。
  - 入口职责已与后续业务能力解耦。
  - P2 / P3 / P5 阶段不再需要先重建入口应用。
- **本 Phase 风险提醒**：
  - 最大风险是把业务逻辑提前塞进入口应用；入口层必须保持轻壳。

### 5.4 Phase 4 — 公共基础包与 smoke 收口

- **Phase 目标**：把所有后续阶段都会复用的最小基础件先抽出来，并通过 smoke / 文档闭环验证 P0 的工程可用性。
- **本 Phase 对应编号**：
  - `P4-01`
  - `P4-02`
  - `P4-03`
- **本 Phase 新增文件**：
  - `packages/common/**`
  - `packages/contracts/**`
  - `packages/config/**`
  - `tests/smoke/**`
  - 开发 / 启动 / 目录说明文档
- **本 Phase 修改文件**：
  - 根工作区配置
  - README / 开发文档
- **本 Phase 删除文件**（如无可删去）：
  - 无
- **具体功能预期**：
  1. `packages/common` 吸收所有入口都会复用的基础件：logging、errors、time、ids、result / typing helpers。
  2. `packages/contracts` 提供最小 command / event / workflow DTO 与协议对象命名空间，避免每个入口自定义一套载荷结构。
  3. `packages/config` 统一 settings、env、path、bootstrap config 加载，避免配置读取方式在各入口分叉。
- **具体测试安排**：
  - **单测**：common / contracts / config 的导入与基础配置解析测试。
  - **集成测试**：API / worker / CLI 与公共包的组合 smoke。
  - **回归测试**：从干净工作区执行 bootstrap -> test -> run 的最小闭环。
  - **手动验证**：检查 README、启动说明、P0 完成状态是否与实际目录和命令一致。
- **收口标准**：
  - 重复基础件的第一次收敛已经完成。
  - P0 形成明确交付件，而不是只有目录没有可运行性。
  - P1 可以直接在既定工作区和共享基础件上开始实现数据库与状态内核。
- **本 Phase 风险提醒**：
  - 不要把 common / contracts / config 扩成“万用包”；只收敛跨入口必需的最小交集。

## 7. 风险、依赖与完成后状态

### 7.1 风险与依赖

| 风险 / 依赖 | 描述 | 当前判断 | 应对方式 |
|-------------|------|----------|----------|
| 旧拓扑回流 | 团队按旧经验再次把新逻辑拆成多个独立部署包 | `medium` | 在 P0 文档、目录和依赖规则中明确“入口在 apps，能力在 packages” |
| 共享基础件抽取不足 | logging / errors / schemas / config 继续在多个入口各写一份 | `medium` | 以 legacy 重复文件为依据，只先收 common / contracts / config 的最小交集 |
| 工具链过度设计 | 在 P0 里把时间花在高级脚手架而不是基础可用性上 | `medium` | 只保留后续阶段必需的 workspace、lint、test、run 基线 |
| CLI 范围膨胀 | 过早实现真实运维命令，拖慢基础骨架收口 | `low` | P0 只做 help 与 bootstrap 壳 |
| 文档与落地漂移 | 最终目录、命令、边界与 refactor 文档不一致 | `medium` | Phase 4 必须同步 README / 开发文档 / `todo-list` 状态 |

### 7.2 约束与前提

- **技术前提**：以 `docs/refactor/index.md` 冻结的 Python 3.12+ 模块化单体为前提，不在 P0 重新选择另一条技术路线。
- **运行时前提**：P0 的运行闭环必须在没有真实业务数据与没有完整数据库内核的前提下成立。
- **组织协作前提**：`legacy-family/` 只读，所有新实现都落在新骨架下，且遵守 apps -> packages 的依赖方向。
- **上线 / 合并前提**：P0 必须保持独立可合并，不依赖 P1+ 的数据库、workflow、vector 或对象存储实现。

### 7.3 文档同步要求

- `docs/refactor/todo-list.md`：P0 落地后需要回填完成状态。
- 根 README / 开发启动文档：说明如何 bootstrap、如何运行 API / worker / CLI、如何理解目录边界。
- `tests/` / `tools/` 说明文档：说明 smoke 与工程命令的使用方式。

### 7.4 完成后状态

1. 新旧边界清晰：`legacy-family/` 只作为迁移依据，新开发全部进入新骨架。
2. 工程基线清晰：统一 workspace、统一依赖入口、统一 lint / test / run 命令已经存在。
3. 运行入口清晰：API / worker / CLI 三类入口都已具备最小可运行壳。
4. 共享基础清晰：common / contracts / config 已存在，后续阶段不再需要重复创建基础件。
5. 交接边界清晰：P1 可以直接开始数据库与状态内核实现，而无需回头重做骨架。
