## 0. 执行背景与目标

P0 已经把 monorepo 骨架、目录边界与阶段顺序冻结下来；P1 现在要把这些“可放代码的位置”变成真正的状态内核。依据 `docs/refactor/todo-list.md:152-216`，这一阶段必须把 `core.db` / `vec.db` 落成可运行基础设施，并把 workflow kernel 的 claim、lease、heartbeat、retry、reaper、event writer 打牢；否则后续 P2/P3/P4 的业务迁移会继续沿用“业务逻辑硬编码 + 调度不可靠”的旧路径。

本计划只消费已经冻结的重构结论，不再在 action-plan 内重开设计题。旧系统 `legacy-family/` 只作为行为事实锚点：我们要恢复哪些旧行为值得借、哪些只是旧底座（D1 / Durable Object / Queue / Vectorize）下的临时机制、哪些必须在 SQLite 单体里净新实现。

- **服务业务簇**：`smind-family / data-kernel / workflow-kernel`
- **计划对象**：`P1 数据库与状态内核`
- **本次计划解决的问题**：
  - `core.db` / `vec.db` 还只是 SSOT 文档，尚未变成可执行 migrations、repositories 与 runtime bootstrap。
  - workflow kernel 的最小闭环尚不存在，P2/P3/P4 暂时没有可依赖的状态机、claim 语义与 request backlog。
  - legacy 里“状态留痕”“purge/restart”“vector finalize”有原始依据，但旧底座的 D1 + DO + Queue + Vectorize 机制不能原样照抄。
- **本次计划的直接产出**：
  - `packages/storage_sqlite` / `packages/vector_sqlite_vec` / `packages/workflow_core` 的 P1 落地顺序与文件级执行拆解。
  - `core.db` / `vec.db` migrations、repositories、scheduler 最小实现的 phase 拆解与验收口径。
  - 一份追加在本文底部的 legacy reference-anchor，明确哪些旧行为可借、部分借、反例、净新。
- **本计划不重新讨论的设计结论**：
  - `core.db` 是 workflow kernel，不是普通业务库（来源：`docs/refactor/database.md:78-88`）。
  - `vec.db` 只做向量索引，不做工作流控制（来源：`docs/refactor/database.md:90-105`）。
  - `core.db` 与 `vec.db` 不依赖跨库强事务，一致性依赖显式状态字段与 request 状态机（来源：`docs/refactor/database.md:106-115`）。
  - step payload 与数据库字段只存引用，不存大正文或大对象（来源：`docs/refactor/database.md:116-142`）。

legacy 的原始依据本轮主要锚在以下代码：

## 1. 执行综述

### 1.1 总体执行方式

本计划采用**先底层后上层、先状态后业务、先闭环后扩面**的执行方式：先把 SQLite 引擎、migration runner 与 SSOT schema 落成硬基础，再把 repositories 与 workflow kernel 变成可调用能力，之后才接 vec 写路径、restart/purge request 与最小 mock 执行闭环。legacy 只借行为与状态机轮廓，不借 Cloudflare 专属机制；所有可执行状态推进都要回收到 `core.db` 事务与显式请求表。

### 1.2 Phase 总览

| Phase | 名称 | 规模 | 目标摘要 | 依赖前序 |
|------|------|------|----------|----------|
| Phase 1 | 存储引擎与迁移基线 | `M` | 建立 `core.db` / `vec.db` 的 bootstrap、PRAGMA、migration runner、测试 fixture 与目录约定 | `-` |
| Phase 2 | `core.db` schema 与 repository 基线 | `L` | 按 `core.sql` 落表、索引、视图，并先交付 P1 必需 repositories | `Phase 1` |
| Phase 3 | workflow kernel 与 lease 控制 | `L` | 交付 ready-step 查询、claim 事务、heartbeat、finish/fail/retry、reaper、event writer | `Phase 2` |
| Phase 4 | `vec.db` 与 chunk/vector 一致性 | `M` | 落 `vec.sql`、`VectorStore`、chunk `vec_status` 推进与写删路径 | `Phase 2` |
| Phase 5 | request 闭环与 P1 验收收口 | `M` | 落 restart/purge request backlog、mock executor 闭环、P1 最小验收与下游 handoff | `Phase 3, Phase 4` |

### 1.3 Phase 说明

1. **Phase 1 — 存储引擎与迁移基线**
   - **核心目标**：把 `packages/storage_sqlite` 与 `packages/vector_sqlite_vec` 需要的 engine、连接管理、migration runner、fixture 与数据目录约定先定下来。
   - **为什么先做**：P1 的其余所有工作都依赖“空库可启动、可重复 migration、可在测试里重建”的基础设施。
2. **Phase 2 — `core.db` schema 与 repository 基线**
   - **核心目标**：把 `core.sql` 变成真正的表 / 索引 / view，并交付 `WorkflowRepository`、`StepRepository`、`ArtifactRepository`、`ChunkRepository`、`RestartRequestRepository`、`PurgeRequestRepository`。
   - **为什么放在这里**：workflow kernel 只有在真实 schema 与 repository contract 稳定后才有可靠执行面。
3. **Phase 3 — workflow kernel 与 lease 控制**
   - **核心目标**：把 `task_claims` 语义、claim 事务、heartbeat、retry_wait、expired-claim reaper 与 `workflow_events` 写入做成最小 scheduler。
   - **为什么放在这里**：这一步定义了后续所有 worker lane 的统一运行规则，是 P1 的真正核心。
4. **Phase 4 — `vec.db` 与 chunk/vector 一致性**
   - **核心目标**：把 `vec.db` 与 `VectorStore` 变成可写删的向量基础设施，并与 `core.db.chunks.vec_status` 建立显式一致性桥接。
   - **为什么放在这里**：`vec.db` 依赖 `chunks` 和 request 状态，但不应反过来主导 workflow kernel，因此放在 state kernel 稳定之后。
5. **Phase 5 — request 闭环与 P1 验收收口**
   - **核心目标**：补齐 `restart_requests` / `purge_requests` backlog 语义、最小 mock executor 闭环，并把 P1 的验收标准转成可执行测试。
   - **为什么放在最后**：只有当前四个 Phase 都具备之后，P1 才能真正形成“claim -> execute mock -> success/fail/retry”的最小闭环。

### 1.4 执行策略说明

- **执行顺序原则**：先落 SSOT schema 与 repository，再落 scheduler / lease / reaper，最后接 vec 与 maintenance request；不允许先写业务 executor 再反推状态模型。
- **风险控制原则**：只借 legacy 的行为形状，不借 D1 / DO / Queue / Vectorize 的 substrate；所有 claim 与状态推进都以 `core.db` 为唯一控制面。
- **测试推进原则**：每个 Phase 必须产出一个更接近最终闭环的可验证资产；P1 的最终最小闭环固定为 `step claim -> execute mock -> success/fail/retry`（来源：`docs/refactor/todo-list.md:543-550`）。
- **文档同步原则**：执行若发现 schema 或路径需要调整，必须先回写 `docs/refactor/core.sql` / `vec.sql` / `database.md`，再调整代码与 action-plan。
- **回滚 / 降级原则**：P1 期间允许 engine / repository / scheduler 分阶段提交，但不允许让下游 Phase 直接依赖半成品接口；若某 Phase 未收口，保持在测试夹具或非默认 worker lane 中。

## 2. In-Scope / Out-of-Scope

### 2.1 In-Scope（本次 action-plan 明确要做）

- **[S1]** 落 `core.db` / `vec.db` 的 engine、migration runner、fixture、PRAGMA 与数据目录约定。
- **[S2]** 按 `docs/refactor/core.sql` / `docs/refactor/vec.sql` 落地表、索引、视图，并保证空库可初始化。
- **[S3]** 交付 P1 明确要求的 repositories：`WorkflowRepository`、`StepRepository`、`ArtifactRepository`、`ChunkRepository`、`RestartRequestRepository`、`PurgeRequestRepository`、`VectorStore`。
- **[S4]** 交付 workflow kernel 的 claim、lease renew、heartbeat、release / finish claim、retry_wait、expired-claim reaper、workflow event writer。
- **[S5]** 建立 `restart_requests` / `purge_requests` 的显式 backlog 与 `chunks.vec_status` 的过渡状态推进。
- **[S6]** 用 mock executor 与 integration tests 跑通 P1 验收标准：可创建 run/step、可 claim、可 heartbeat、可 success/fail/retry、claim 过期可重领、request 可持久化。

### 2.2 Out-of-Scope（本次 action-plan 明确不做）

- **[O1]** API ingestion / auth / workflow start 的完整上游入口与管理读接口（属于 P2）。
- **[O2]** clean / rag planner、finalizer、provider adapters、真实业务 executor（属于 P3 / P4）。
- **[O3]** 面向查询侧的 `vec.db` top-k search 与 `core.db` hydration API（属于 P5）。
- **[O4]** restart / purge / inspect / debug CLI 与完整运维可观测面（属于 P6）。

### 2.3 边界判定表

| 项目 | 判定 | 理由 | 重评条件 |
|------|------|------|----------|
| `core.sql` 全量表结构（含 config/provider 类表） | `in-scope` | SSOT 已冻结，migration 应能完整落地；但不要求 P1 同时交付这些表的业务 repository | 若 `docs/refactor/core.sql` 被拆分为更细 phase |
| config / provider 的业务读写接口 | `out-of-scope` | 不在 `todo-list` P1 验收标准内，会分散 kernel 收口注意力 | P2/P3 需要真实消费这些配置时 |
| `vec.db` schema 与 `VectorStore` 写删路径 | `in-scope` | `todo-list` P1 已明确要求 `vec.db` 四张产物与 `VectorStore` | 若 `vec.sql` 发生结构性改版 |
| `vec.db` top-k search / query hydration | `defer` | `database.md` 允许 `vec.db` 提供检索，但 `todo-list` 的阶段闭环把查询放在 P5 | P5 action-plan 冻结后 |
| synthetic `system-purge` workflow row | `out-of-scope` | 这是 legacy 的审计折中，不符合新设计里的 `purge_requests` 显式状态机 | 若设计文档显式要求把 maintenance 动作纳入 workflow_steps |
| mock executor lane | `in-scope` | P1 最小闭环必须证明 scheduler / claim / retry 能实际运转 | 若后续决定由真实 worker 桩替代 mock executor |

## 7. 风险、依赖与完成后状态

### 7.1 风险与依赖

| 风险 / 依赖 | 描述 | 当前判断 | 应对方式 |
|-------------|------|----------|----------|
| SSOT 漂移 | `core.sql` / `vec.sql`、`database.md`、代码 migration 很容易出现三份真相 | `high` | 规定 schema 变更必须先改 SSOT，再改 migration 与 tests |
| legacy 机制误抄 | 旧系统大量依赖 D1 / DO / Queue / Vectorize，若照抄机制会把新系统重新做成 split-brain | `high` | 用本文附录做 TR 过滤，只借状态机轮廓，不借 Cloudflare substrate |
| vec 范围膨胀 | 很容易把 query/search/hydration 一并塞进 P1，冲掉 kernel 核心任务 | `medium` | 把 `VectorStore` 范围固定为 schema + upsert/delete + namespace stats；检索留给 P5 |
| request 语义偷渡到 workflow_steps | 若为了快而继续用 synthetic step 表示 purge/restart，会污染状态机 | `medium` | 强制使用 `restart_requests` / `purge_requests`，并通过 backlog view 暴露 |
| sqlite-vec 运行条件 | `vec.db` 依赖固定 embedding 维度与 sqlite-vec 能力，测试环境需要相同假设 | `medium` | 先冻结单一 embedding 维度与测试前提，必要时在集成测试中分层跳过 |

### 7.2 约束与前提

- **技术前提**：`TEXT` 逻辑主键、UTC ISO-8601 时间、`task_claims` 唯一 lease、`chunk_id` 全局唯一，这些约束必须贯穿 repository 与 tests。
- **运行时前提**：本地与 CI 运行环境都要能写 `data/`，并能加载 `vec.db` 所需能力；不以跨库强事务为前提。
- **组织协作前提**：P2/P3/P4 起草时必须直接依赖本计划输出的 repository / scheduler / request contract，不得自行重定义 workflow state。
- **上线 / 合并前提**：在 P1 最小闭环与 migration smoke suite 未稳定前，不把后续业务 Phase 建在临时 SQL 或手写脚本上。

### 7.3 文档同步要求

- `docs/refactor/core.sql`、`docs/refactor/vec.sql`、`docs/refactor/database.md` 与本计划必须保持同步；执行时若 schema 有漂移，优先更新这些 SSOT。
- `docs/refactor/index.md` 与 `docs/refactor/todo-list.md` 中的 package 责任边界若调整，必须同步回写本计划的 Phase 文件路径与影响结构图。
- P2 / P3 / P4 action-plan 起草时，必须把本文件作为上游 closure，直接复用这里定义的 kernel 与 repository 边界。

### 7.4 完成后的系统状态

- `core.db` / `vec.db` 都有可重复执行的 migration、fixture 与 engine bootstrap。
- `core.db` 成为真实 workflow kernel，`workflow_runs` / `workflow_steps` / `task_claims` / `step_attempts` / `workflow_events` 可驱动调度。
- worker 可以 claim step、heartbeat、finish/fail/retry，并在 lease 过期后回收再调度。
- `vec.db` 可以围绕稳定 `chunk_id` 做 upsert/delete，并通过 `chunks.vec_status` 与 request 状态保持一致。
- P2 / P3 / P4 不再需要回到 legacy 追溯状态机，只需要消费 P1 提供的接口与闭环。

## A5. Substrate-fit / 技术路线（TR）过滤复核

本节使用三条固定技术路线过滤 legacy 参考：

- `TR-1`：运行时从 Cloudflare D1 / Queue / Durable Object / Vectorize 迁移到 Python monolith + local apps/packages + SQLite。
- `TR-2`：`core.db` 是唯一 workflow kernel，`vec.db` 只是向量索引伴生库。
- `TR-3`：一致性依赖显式状态、request backlog、lease/reaper，不依赖 synthetic process row 或扫历史猜模式。

| 借鉴点 | 原机制 | 与本项目技术路线（TR）是否冲突 | 过滤后落地形态（降级/重映射/直采） |
|--------|--------|-------------------------------------|-------------------------------------|
| DB 持久化 workflow / step / log | D1 表 + worker 直接 SQL | `TR-1: 兼容`（数据库留痕是共性），`TR-2: 需重映射`（表模型升级） | 直采“控制面必须持久化”，重映射到 `core.db` 的 `workflow_runs/steps/events/audit_logs` |
| pending before dispatch | dispatcher 先插 `smind_rag_process` 再发 Queue/DO | `TR-1: 部分冲突`（分发机制变化） | 直采“先落状态再执行”，改造成 `workflow_steps + task_claims + step_attempts` 事务 |
| claim / release / finalize | `smind_vec_process` 内嵌处理状态字段 | `TR-2: 冲突`（lease 真相必须集中），`TR-3: 兼容`（状态推进思路可借） | 重映射到 `task_claims` + `workflow_steps.status` + `step_attempts` |
| DO mutex + internal queue | Durable Object 内存锁 + SQLite 队列 | `TR-1: 冲突` | 降级为 worker lane + scheduler polling；不保留 DO 锁模型 |
| WAL -> vector db -> finalize | DO storage WAL，再写 Vectorize，再回 D1 | `TR-1: 部分冲突`，`TR-2: 兼容` | 借顺序，不借 substrate；必要时在 `VectorStore` 内保留本地 staging，但状态完成始终由 `core.db` 决定 |
| purge 作为审计动作 | purger 创建 synthetic row 后同步调 VectorizerDO | `TR-2: 部分冲突`, `TR-3: 兼容` | 直采“purge 必须显式留痕”，重映射为 `purge_requests` + chunk `vec_status` + `workflow_events` |
| history-driven restart | 扫旧历史行决定 KICKSTART/RECOVERY | `TR-2: 部分冲突` | 借“restart 需要 run/step 历史”的原则，改成基于 `workflow_runs/steps/requests` 的显式策略 |

- **substrate-fit 总结（对 HEAD）**：legacy 最值得借的是“状态推进顺序”“审计留痕”“向量写删前后的控制面协调”；最不该借的是 D1 / DO / Queue / Vectorize 的底座机制。P1 应把这些旧行为全部重映射到 `core.db` 事务、`task_claims`、request backlog 与 `vec.db` 索引伴生层。
