### 2.1 legacy-family（TypeScript / Cloudflare）

| 证据 | 可借鉴 | 必须删除 / 升级 |
|---|---|---|
| `smind-admin/core/r2.ts`：presign PUT、HEAD、DELETE、static bucket | 对象与关系分账；HEAD 校验存在性 | 删除公网 presign 上传产品面；删除双 bucket 平台语义；MKB 无外部 upload API |
| 各 skill `io_manager.ts`：typed slots（`raw_text` / `structured_json`…）+ `r2.putObject` | **typed port/slot** 思想：业务只关心 read text / write JSON | 删除 `r2_key` 进入 wire/callback；Dispatcher 指定绝对 key 的模式升级为 S13 handle |
| `smind-console` storage-quota/usage、artifacts API | 容量与反扫是运营关注点 | 删除 UI/platform quota/billing；MKB 不建对象浏览器 |
| Worker 全量缓冲 `putObject(buffer)` | — | 大对象必须 **bounded stream**；禁止无界内存缓冲作为唯一路径 |

**踩坑（反例）**：

1. **对象存在 ≠ 业务成功**（D1/R2 写成功 + DB/callback 失败留下 orphan 或幽灵成功）；
2. **`r2_key` 泄漏到 SMCP payload** → 耦合部署与 bucket 命名；
3. **无 content-address 复用**：同一内容多次写多份 key，缺 digest 级对账；
4. **无统一 reference ledger**：删除靠业务状态猜测，易删活引用或漏删 orphan。

### 2.3 legacy-specs ES-04（草案 · 非冻结真相）

`context/legacy-specs/execution-spec/04-persistence-and-artifact-storage.md` 已写过一套 **local CAS + reservation/promote + reference/GC** 草案。其价值是 **设计分母候选**，**不是**已接受 baseline 真相。可对照借鉴：

- team-scoped content-addressed path：`objects/<team>/sha256/aa/bb/<64hex>`；
- staging / quarantine / backups 分目录；
- opaque handle 语法候选：`mkbobj:v1:<team>:<stored_object_uuid>`（最终以 S13 Spec 冻结为准）；
- write：reservation → stream → digest 校验 → atomic promote → 再 canonical UoW 建 reference；
- orphan grace + reference release 与 delete proof 分账；
- v1 明确 **不**做 public object CRUD、不强制 S3。

S13 progressive QNA 的任务是：用 owner 裁决 **重新冻结** 哪些草案进入 truth，哪些简化/推迟，而不是静默继承 ES-04。

### 2.4 网络层一手资料（2026-08 检索 · 可借鉴原则）

| 来源 | 原则摘要 | 对 S13 的含义 |
|---|---|---|
| LLVM CAS / `ObjectStore` | CAS 默认 **immutable**；`ObjectRef` 轻量且不保证对象存在，load 可失败；同 store 内 equality = 内容相等 | 对齐 **handle ≠ existence proof**；read 必须 verified load |
| Bazel remote cache CAS | 按 **SHA-256 digest** 存 blob；AC 与 CAS 分账（元数据 map ≠ bytes store） | 对齐 **S12 关系元数据 / S13 bytes** 分账；禁止混成一表万能 blob |
| WarpStream object GC 文 | orphan 处理：metadata 删除 + **delayed delete queue** 同事务，避免活读被抢删 | 对齐 **reference release + grace + recheck fence** 再物理删 |
| Chainloop / pipeline CAS issues | upload 后 attestation 失败产生 orphan，需 GC/retention | 直接对应 MKB **bytes-first + TX 回滚 orphan** |
| 行业 artifact store 叙事 | content-addressed + immutability 使 integrity、dedup、safe cache 同一决策 | 支持 Q2 倾向 CAS；dedup 范围建议 **team-scoped** 防跨租户泄漏 |

**不直接照搬**：公有对象 CDN、signed URL 产品面、多区域对象服务、计费级 lifecycle policy 平台。

### 2.5 云 backend 对照与业主成本裁决（2026-08-11）

| 候选 | 技术结论（摘要） | 业主裁决 |
|---|---|---|
| **Cloudflare R2** | 成熟 S3 兼容、强一致、零 egress；适合作未来云 substrate；**不**继承 legacy `r2_key` wire | **v1 不启用**。原因：免费约 **10GB**，超出即按存储+操作计费；现阶段优先 **本地盘零边际云存储费** |
| **HF Xet / Storage Buckets** | 强在 chunk dedup 与 Hub ML 工作区；租户轴是 HF org，非 MKB `team_uuid`；不宜作内部 SSOT | **不作 S13 主路径**（export 旁路另议） |
| **Local filesystem** | 与 D01 本地 I/O、S12 同机主库、atomic rename/fsync 协议一致 | **v1 权威默认** |

实现纪律：即便未来加 R2，也必须经 `ObjectStorePort`；domain 永不感知 path/bucket。

### Q1 — 首版对象 backend 拓扑（关闭 `G-11`）

- **影响范围**：`S05–S07`、`S12`、`S13`、`17` topology、部署与验收
- **为什么必须确认**：`G-11` 仍 open（本地 filesystem / S3-compatible）。backend 选择决定原子写协议、fsync 假设、运维备份面和 v1 readiness 探针；不可 internally 默认。
- **驱动输入**：`T-O-111/112`、`OD-06` 单体 leaf-worker、`D01-T037`（首版本地 I/O adapter）、S12 单主库同进程

#### 选项清单

| 选项 | 方案 | 含义 |
|---|---|---|
| **A** | **Local filesystem only（硬固定）** | v1 唯一 backend = 与进程同机的 POSIX-like 本地盘；无 S3 代码路径；换 backend 必须 reopen |
| **B** | **S3-compatible only** | v1 唯一 backend = S3/R2/MinIO 等；本地盘仅作 cache 非 SSOT |
| **C** | **Port + v1 默认 Local（推荐）** | 定义 `ObjectStorePort`；**v1 必选实现 = local filesystem**；S3-compatible 允许作为 **可选 adapter 骨架**（可不进 v1 readiness），domain 永不感知 backend |
| **D** | **双写 Local+S3** | 每次 promote 写两处；任一侧失败语义复杂 |

#### 当前建议 / 倾向

**推荐 C（Port + v1 默认 Local）** — 已被业主采纳（见下）。

#### 推荐执行细节（选 C 时 · 已采纳）

1. **v1 运行时 backend**：本地目录树 `object_root`（配置项），与 Turso 主库 **同部署单元** 挂载；要求同 filesystem 上 **atomic rename / exclusive create / fsync file+dir / no-follow open**。
2. **Ports（domain 可见）**：`put_immutable` / `open_write_stream` / `promote` / `open_read_stream` / `stat` / `delete_if_unreferenced`（或等价最小集）；返回 `(logical_handle, size, digest)`。
3. **Adapter 边界**：filesystem 实现在 S13 adapter；**禁止** domain/S02–S06 引用 `pathlib`/boto3。
4. **R2 / S3 adapter**：**v1 不实现、不进 readiness**；Spec 可只保留 Port 形状以便未来扩展。需要时再加 R2，**不 reopen** 业务状态机。
5. **HF Xet/Buckets**：不作 SSOT；不进 v1。
6. **明确禁止**：public presigned upload、对象浏览器 API、v1 双写 local+云、跨进程共享无 fence 的 NFS 半语义（若用网络盘必须证明 POSIX 原子语义或 fail-loud）。
7. **验收**：crash suite 在 local backend；path 逃逸测试；domain 无 backend import 的 architecture test。

#### Supporting Reasoning

- **对齐已冻方向**：D01 已写“首版本地 I/O adapter”；S12 单进程主库；leaf-worker 非多租户对象平台。
- **关闭 G-11 的干净方式**：v1 生产路径钉死 local，同时用 Port 避免把 path 写进 domain（未来换 R2 不 reopen 业务状态机）。
- **业主成本**：R2 免费档约 10GB，超出即计费；v1 本地盘避免云存储固定成本。
- **反对 B 作为 v1 唯一**：费用 + 网络 RTT + 凭证面，当前无强制。
- **反对 D**：双写放大 orphan/对账面。
- **HF Xet**：Hub 租户轴与 dedup 场景不匹配 MKB 文档流水线 SSOT。

#### 问题（请业主裁决）

**Q1：S13 v1 对象 backend 选 A / B / C / D（或混合说明）？是否允许 S3 adapter 骨架进入 Spec 但不进入 v1 readiness？**

- **业主回答**：`C（实质）` — **v1 默认本地存储**；R2 因免费额度与计费不划算 **后续再支持**；不把 R2/HF 当 v1 必选。→ **冻结为 `T-O-117`**

### Q2 — 物理寻址与 layout 模型

- **影响范围**：路径安全、dedup、跨 team 隔离、backup/restore、orphan 扫描
- **为什么必须确认**：layout 决定 handle 解析、是否按 digest 复用、以及 GC 扫描成本；legacy 的“业务路径 key”与现代 CAS 不可并存为同一 identity。
- **驱动输入**：`T-O-112/113`、S05 SHA-256 digest、team 隔离

#### 选项清单

| 选项 | 方案 | 含义 |
|---|---|---|
| **A** | **Owner-keyed path** | 如 `team/task/execution/artifact_type/uuid`；易读，难 dedup，易泄漏业务结构到盘 |
| **B** | **Team-scoped content-addressed（推荐）** | 物理键 = `(team_uuid, sha256(bytes), size)`；路径如 `objects/<team>/sha256/<aa>/<bb>/<64hex>`；同 team 同 digest 复用 |
| **C** | **Global CAS（跨 team dedup）** | 全库按 digest 去重；省空间，**跨租户 existence/timing 侧信道风险** |
| **D** | **Hybrid mutable+CAS** | staging 用 UUID 路径，final 用 CAS；但 identity 混用两套 |

#### 当前建议 / 倾向

**推荐 B（Team-scoped CAS）**。Staging 可用 UUID 临时名，但 **final durable object 的物理 identity 以 content digest 为准**；logical handle 仍用 UUID 级 opaque id（不把 digest 当对外身份唯一键也可，但 stored object 行必须绑 digest）。

#### 推荐执行细节（选 B 时）

1. **Final layout（示意）**：
   ```text
   <object_root>/
     identity.json                 # deployment/format 绑定
     objects/<team_uuid>/sha256/<hex[0:2]>/<hex[2:4]/<64-hex>
     staging/<team_uuid>/<reservation_or_write_id>.tmp
     quarantine/<team_uuid>/...
   ```
2. **Dedup 范围**：仅 **同 team** 内相同 digest+size 复用 bytes；不同 team 即使 digest 相同也分目录/分行，避免跨 team 探测。
3. **Logical handle**：opaque（如 `mkbobj:v1:<team>:<stored_object_uuid>` 或等价）；**不含 path**；解析经 DB `stored_objects` + team guard。
4. **冲突规则**：final 已存在且 digest/size 一致 → 复用；不一致 → **integrity conflict**，禁止覆盖。
5. **用途/role**（raw/clean/structure…）只存在于 **S12 元数据 / reference purpose**，不进入 path 身份。
6. **禁止**：把 `r2_key`、业务 UUID 路径当唯一物理 identity；把绝对路径写入 wire。

#### Supporting Reasoning

- **与 S05/S06 digest 文化一致**：完整性与 identity 对齐 SHA-256，而不是路径字符串。
- **网络层共识**：LLVM CAS、Bazel CAS 均以 content hash 为 blob 键；immutable by construction。
- **安全**：team 前缀防止跨租户 path 遍历与 dedup 侧信道（C 的主要风险）。
- **反对 A**：legacy R2/key 模式导致 key 规划泄漏到 dispatcher，难 orphan GC，难字节级对账。
- **D 可作实现细节**：staging 本来就是 UUID tmp；但 final 必须 CAS，避免“双 identity”。

#### 问题（请业主裁决）

**Q2：物理寻址选 A / B / C / D？是否确认 team-scoped dedup（禁止跨 team 复用）？logical handle 是否采用 opaque UUID（推荐）而非直接暴露 digest？**

- **业主回答**：接受推荐 **B** 全部执行细节（team-scoped CAS；禁止跨 team dedup；opaque handle；staging 非 durable identity）。→ **冻结为 `T-O-118`**
- **裁决状态**：`accepted / frozen`

### Q3 — 写入 / promote 协议与 reference·GC 地基

- **影响范围**：S04 acceptance orphan、S05 staging、S06 generation accept、S12 TX 矩阵、S15 运维
- **为什么必须确认**：bytes-first 已冻，但 **写协议厚度**（是否要 reservation ledger、reference purpose、grace 数值谁定）仍决定表与验收；过薄会重演 legacy 半文件/幽灵引用，过厚会拖慢 v1。
- **驱动输入**：`T-O-114/115`、S04 orphan 规则、S05 open-gate 保护

#### 选项清单

| 选项 | 方案 | 含义 |
|---|---|---|
| **A** | **Minimal put_immutable** | temp 写 + digest + atomic rename；成功返回 handle；无 reservation 表；orphan 靠“无 meta 行扫描”；实现快但并发/崩溃较弱 |
| **B** | **Stage → Promote → Reference ledger（推荐）** | TX 外 stream；轻量 reservation；promote 后 canonical TX 登记 `stored_object` + live `object_reference`；release 与 delete proof 分账；orphan grace 后 GC |
| **C** | **Small-inline / large-object 双路径** | 小于阈值的 bytes 进 DB BLOB，大对象走文件；破坏“无界正文不进关系库” |
| **D** | **仅应用层约定、无 reference 表** | 业务表自带 handle 字符串；GC 反查全库；open gate 保护难证明 |

#### 当前建议 / 倾向

**推荐 B**。v1 可对 reservation 做 **轻量实现**（不必照搬 ES-04 全表），但 **live reference ledger + orphan/missing 二分 + grace GC + delete recheck** 不可删。

#### 推荐执行细节（选 B 时）

1. **写路径（事务外 I/O）**：
   ```text
   (optional) create write reservation / budget
     → exclusive staging file + bounded stream
     → running SHA-256 + size + media/budget checks
     → fsync(temp) → digest match guard
     → atomic promote to CAS final (or verify-reuse)
     → fsync(parent dir)
     → return (handle_candidate, size, digest)
   ```
2. **登记路径（S12 TX 内）**：
   ```text
   insert/reuse stored_objects(team, digest, size, media, handle)
     + append object_references(owner_kind, owner_uuid, purpose, expected_digest)
     + domain artifact/evidence rows
   ```
   仅当该 TX commit 后，caller 才得到 **usable** handle（与 S12 bytes-first 一致）。
3. **Reference purpose 最小闭集（v1 建议，Round 2 可细化）**：  
   `intake_artifact | clean_candidate | gate_evidence | generation_artifact | process_io | backup_hold | operator_hold`（最终表由 Spec 冻结）。
4. **Orphan vs Missing**：
   - **Orphan**：promoted bytes 无 live reference（或 reservation 失败残留）→ grace 后可删；
   - **Missing**：live reference 的 expected digest 无 bytes 或校验失败 → **incident**，不得当 orphan 清掉真相。
5. **GC 顺序**：release reference（append）→ 无 live ref + 过 grace + 无 hold/pointer 保护 → delete fence recheck → 删 bytes → delete proof；失败可重试。
6. **数值**：orphan grace **默认建议 24h**（ES-04 同量级）；是否 v1 钉死数值或留给 S15 配置 — 建议 **Spec 给安全默认，S15 可上调不可调 0**。
7. **明确禁止**：TX 内做无界 stream；成功返回未 promote 的 handle；覆盖不同 digest 的 final；Process/Task terminal 级联硬删对象。

#### Supporting Reasoning

- **上游硬约束**：S04 明确 “Artifact 已写、DB 回滚 → S13 orphan”；S05 open gate 引用保护；S12 TX-06 要求 digest 已存在才登记。
- **网络层**：WarpStream 式 “元数据删除与延迟物理删同事务/同账本” 比“扫盘猜孤儿”可靠；LLVM 明确 ref 不保证存在 → MKB 用 reference ledger 表达 liveness。
- **反对 A 作为最终合同**：可作 spike，但无 reference purpose 时无法证明 open-gate/serving 不被 GC。
- **反对 C**：与 S12/S04 “数据库不承载无界正文”直接冲突。
- **反对 D**：全库反查 handle 字符串无法 CAS 保护，也难 team 围栏索引。

#### 问题（请业主裁决）

**Q3：写/promote 与 GC 地基选 A / B / C / D？是否接受 v1 强制 `object_references`（或等价 live ref 账本）+ orphan grace 默认 24h（可配置上调、禁止 0）？**

- **业主回答**：接受推荐 **B** 全部执行细节（stage→promote→reference ledger；orphan/missing 二分；grace 默认 24h 可上调禁 0）。→ **冻结为 `T-O-119`**
- **裁决状态**：`accepted / frozen`

### Q4 — Object catalog 与 S12/S13 所有权边界（**驱动：`T-O-117` / `T-O-119` / S12-T008**）

- **影响范围**：S12 schema 模块、migration、TX-06/accept 路径、S13 Port 实现、readiness
- **为什么必须确认**：`stored_object` / `object_reference` 已强制存在，但 **谁拥有表语义、几张表、reservation 是否落库** 仍决定 v1 DDL 与验收；过厚复制 ES-04 全套会拖垮 v1，过薄无法证明 live-ref。
- **不在本题裁决**：purpose 枚举细表（Q5）；grace 以外 retention 年（S15）；R2 adapter。

#### 选项清单

| 选项 | 方案 | 含义 |
|---|---|---|
| **A** | **S13 逻辑拥有 + S12 物理承载（推荐）** | 表落在 **同一 Turso 主库**（S12 `ops` 或 `object` 逻辑模块）；**业务语义/Port 归 S13**；migration 仍走 S12 单一线性链；domain 只依赖 Port |
| **B** | 对象 catalog 另文件/另库 | 与主库跨库事务；orphan 对账更难 |
| **C** | 无 catalog 表，只靠 CAS 目录 + 业务行内 handle 字符串 | 违反 `T-O-119` live-ref 强制 |
| **D** | 完整 ES-04 全套（reservation/outcome/incident/delete_proof 全表一刀切必选） | 正确但 v1 过重；易未用先建 |

#### 当前建议 / 倾向

**推荐 A + 最小表集**（不是 D 的全量 ES-04）。

#### 推荐执行细节（选 A 时）

1. **物理位置**：Turso `mkb_primary` 内逻辑模块（建议名 `object` 或并入 S12 `ops`）；**单一 migration 链**（继承 S12 `T-O-108`）。
2. **v1 最小必选表**（名称可微调，语义固定）：
   | 表 | 角色 |
   |---|---|
   | `mkb_stored_objects` | immutable catalog：`stored_object_uuid`、`team_uuid`、`sha256`、`size`、`media`、`created_at`、`payload_extra`；unique `(team, sha256, size)` |
   | `mkb_object_references` | live-ref 账本：owner_kind/owner_uuid、purpose、expected_digest/size、created_at、**released_at NULL=live**（或分 release 表，二选一须在 Spec 钉死） |
   | `mkb_object_delete_proofs`（或等价） | 物理删除证据；可与 ops 合并但语义要有 |
3. **Write reservation（v1 轻量）**：
   - **推荐**：可选/内存+staging 文件名即可；**不强制**完整 `object_write_reservations` 表；
   - 若崩溃残留 `.tmp`，由 scanner 按 mtime/grace 清 staging；
   - 若后续需要预算审计，再 reopen 加 reservation 表。
4. **S12 TX 接合**：
   ```text
   S13.promote → (digest, size, path_internal)
     → same UnitOfWork:
          upsert stored_objects by (team, digest, size)
          insert object_reference(s)
          insert domain artifact/evidence rows
     → commit → usable handle
   ```
5. **Ports 可见形状**（domain）：create/open stream、promote/stat/open_read、register_ref 由 repository 与 Port 协作；**domain 不写 SQL**。
6. **禁止**：第二对象库；在业务表 JSON 里塞 path；无 `stored_objects` 只靠文件系统 enum 当 catalog。

#### Supporting Reasoning

- **S12 已冻**：单主库 + 模块化 + bytes-first；对象 catalog 是 **元数据**，属于关系库，字节仍在盘上（`T-O-103/114`）。
- **另库（B）** 破坏 accept 单 TX，重蹈 legacy 双写窗口。
- **无表（C）** 无法证明 open-gate/serving 保护与 missing incident。
- **全量 ES-04（D）** 可作为未来展开；v1 用 2–3 张核心表即可验收 `T-O-119`。
- **reservation 表 defer**：local backend 下 staging 文件 + grace 已能覆盖崩溃；减少 migration 表面。

#### 问题（请业主裁决）

**Q4：catalog 选 A / B / C / D？是否接受 v1 最小三语义（stored_objects + object_references + delete_proof）且 write reservation 表 defer？**

- **业主回答**：接受推荐 **A** 全部执行细节（同库 catalog；最小三语义；reservation 表 defer）。→ **冻结为 `T-O-120`**
- **裁决状态**：`accepted / frozen`

### Q5 — Reference purpose 闭集与 release / cleanup 权威（**驱动：`T-O-115` / `T-O-119` / S04-T048 / S05-T030**）

- **影响范围**：S04 cleanup intent、S05 open gate、S06 generation pointer、S12 GC scanner、S15 hold
- **为什么必须确认**：有 reference 表但无 **purpose 闭集与谁能 release**，GC 仍无法证明“不误删 open gate / serving / current generation”。
- **不在本题裁决**：物理 grace 数值（已 24h）；backup 全协议（S15）。

#### 选项清单

| 选项 | 方案 | 含义 |
|---|---|---|
| **A** | **Code-owned purpose 闭集 + owner 域 release（推荐）** | purpose 为内部 immutable 注册枚举；**创建 ref 的 domain owner** 在语义允许时 release；S13 只执行“无 live ref 才 GC”，不解释业务 |
| **B** | 自由字符串 purpose | 灵活；无法验收保护矩阵 |
| **C** | 单一万能 `artifact` purpose | 过粗；gate/serving/generation 无法分账 |
| **D** | S13 定时按 Task/Process 状态自动 release | 状态机泄漏进 S13；易误删 |

#### 当前建议 / 倾向

**推荐 A**。

#### 推荐执行细节（选 A 时）

1. **v1 purpose 闭集（建议最小集，Spec 可微调命名）**：

   | purpose | 典型 owner | 释放条件（语义） |
   |---|---|---|
   | `intake_snapshot_artifact` | S04 Snapshot-owned Artifact | cleanup intent 允许且无 serving 依赖 |
   | `intake_revision_artifact` | S04 Revision-owned Artifact | 同上；serving pointer 仍指则 **不可** release |
   | `clean_candidate` | S05 staging candidate | CandidateSet abandoned/accepted 后按 S04/S05 规则 |
   | `gate_evidence` | S05 open Gate | Gate **terminal** 前 **禁止** release |
   | `generation_artifact` | S06 GenerationArtifact | 非 current 且 retention 允许；**current pointer 保护** |
   | `process_io` | S03 Process I/O | Process terminal + compaction eligibility（S03-T） |
   | `operator_hold` / `backup_hold` | S15/ops | 显式解除 hold 前禁止 GC |

2. **Reference 行不变量**：
   - 同 `(owner_kind, owner_uuid, purpose, ordinal?)` 策略由 Spec 钉（通常一 owner 一 purpose 一条 live ref，或允许 multi-part）；
   - **release = CAS/append 设 `released_at`**，不物理删 ref 历史（或 append release ledger）；
   - **禁止** S13 因“磁盘紧”擅自 release。

3. **与 S04 CleanupIntent**：
   - S04 发 cleanup intent → 各 substrate 交 proof；
   - S13 在 intent 允许后 **release refs**（或确认已 release）→ grace → 删 bytes → **cleanup proof(object)**；
   - **物理删 bytes ≠ 删 Intake 行**。

4. **保护优先级（GC 前必须全满足）**：
   ```text
   no live reference
   AND no operator/backup hold
   AND no open gate_evidence ref
   AND not target of current/serving/latest-protected pointer (via domain or ref)
   AND orphan grace elapsed
   AND delete fence recheck
   ```

5. **禁止**：Process success 级联硬删；用 mtime 猜“可删”；UI 一键清空 bucket。

#### Supporting Reasoning

- S05-T030 / S04-T048 明确 **open gate 引用保护**——必须有可查询 purpose。
- S06 current pointer 与 S04 serving 是不同 SelectionPointer——purpose 分账才能避免“GC 掉仍在 serving 的 clean”。
- 自由字符串（B）无法做 HARD 验收；万能 purpose（C）无法区分 gate vs candidate。
- S13 自动按 runtime 状态 release（D）会把 S03 状态机泄漏进存储层，违反 `T-O-111`。

- **业主回答**：接受推荐 **A** 全部执行细节（purpose 闭集；owner 域 release；永不因容量自动 release）。→ **冻结为 `T-O-121`**
- **裁决状态**：`accepted / frozen`

### Q6 — Staging / Read 校验 / 容量与 incident 围栏（**驱动：`T-O-113` / `T-O-118` / `T-O-119`**）

- **影响范围**：S05 staging port、大文件/HTML、S15 告警、本地盘运维、readiness
- **为什么必须确认**：写协议已冻，但 **staging 生命周期、读路径是否强制边读边哈希、单对象/卷容量、损坏如何 quarantine** 仍决定实现与 HARD 测试；加解密/压缩是否 v1 做也需一次钉死以免 scope 膨胀。
- **不在本题裁决**：云 backend；跨机备份编排细节（可 defer S15，但须声明）。

#### 选项清单

| 选项 | 方案 | 含义 |
|---|---|---|
| **A** | **严格 verify-on-read + 有界 staging + 配置化预算 + quarantine incident（推荐）** | 每次完整 read 校验 digest/size；staging 有 TTL；超预算 fail-closed；坏对象进 quarantine；v1 **不做**应用层压缩/加密 |
| **B** | Trust-on-write only（读不重算哈希） | 快；bitrot/半截文件难发现 |
| **C** | 应用层默认压缩+加密 | 安全加分；复杂度/CPU/调试成本高；密钥生命周期归 S16 未冻 |
| **D** | 无容量预算，写满靠 OS ENOSPC | 简单；难给上游 typed error |

#### 当前建议 / 倾向

**推荐 A**。

#### 推荐执行细节（选 A 时）

1. **Staging**：
   - 路径：`staging/<team_uuid>/<write_id>.tmp`（exclusive create）；
   - **TTL / grace**：建议默认 **24h**（可与 orphan grace 对齐或略短）；scanner 删除过期/失败残留；
   - staging **永不** 出现在 live reference；不得被业务 handle 直接指向。

2. **Read 协议**：
   ```text
   auth team + resolve handle → load stored_object + require live ref (unless internal repair path)
     → open no-follow under object_root
     → stream bounded chunks + running SHA-256 + size count
     → EOF 后 digest/size 必须匹配 catalog
     → 否则 fail-closed + object_integrity_incident + optional quarantine
   ```
   - **禁止** 把 partial stream 标为业务成功输出。
   - 内部“只读前 N 字节预览”若存在，必须另 API 且 **不得** 当 verified completion。

3. **容量 / 预算（v1 配置项，Spec 给安全默认）**：
   | 项 | 建议默认（可调） | 超限 |
   |---|---|---|
   | 单对象 max size | 例如 **256 MiB**（可按部署调大） | fail-closed typed error |
   | 单次 stream buffer | 有界 chunk（如 1 MiB） | 禁止整文件 `read()` 无界 |
   | volume free space floor | 例如保留 **5–10%** 或固定 GiB | 拒绝新 promote；readiness/degraded 信号归 S15 |
   - **精确数字可部署覆盖**；**禁止**“无上限”作为默认。

4. **Incident / quarantine**：
   - missing / digest mismatch / 非 regular file / path escape → **incident**；
   - 可疑文件可移至 `quarantine/<team>/...`（保留证据），**不**自动改 catalog digest；
   - repair 走 typed intent（S04/S15），不 silent restore。

5. **压缩 / 加密**：
   - v1 **不做**应用层 compression/encryption；
   - 磁盘级加密归部署/OS（S16/S15 运维）；
   - 未来压缩/加密必须 **进 digest 合同**（明文 digest vs 密文 digest）再 reopen。

6. **Backup 边界声明**（本轮只钉接口，细节可 S15）：
   - v1 至少要求：**DB + object_root 一致性** 的 quiesced/copy 协议入口存在；
   - 不在 Q6 钉排程与保留份数。

#### Supporting Reasoning

- **bitrot / 半文件**：只信 write 时哈希不够；LLVM CAS 也强调 load 可失败——verify-on-read 与 `T-O-113` 一致。
- **Staging TTL**：防止磁盘被失败任务打满；与 orphan grace 同量级便于运维心智。
- **预算**：S05 已有 stream/page budget 思想；S13 必须有对象级上限，否则 browser/PDF 可拖垮节点。
- **压缩/加密进 v1（C）**：密钥、nonce、是否进 CAS key 全部未冻，会拖住 S13 formal Spec。
- **无预算（D）**：ENOSPC 难映射到 MKB typed error 与 readiness。

#### 问题（请业主裁决）

**Q6：选 A / B / C / D？是否接受 verify-on-read、staging TTL、配置化单对象/卷预算、v1 无应用层压缩加密？单对象默认上限是否接受 256 MiB 量级（可配置）？**

- **业主回答**：接受推荐 **A** 全部执行细节（verify-on-read；staging TTL；预算含默认 256 MiB 量级可配；v1 无应用层压缩/加密）。→ **冻结为 `T-O-122`**
- **裁决状态**：`accepted / frozen`

### Q7 — `ObjectStorePort` 精确表面、handle 语法与本地并发（**驱动：`T-O-112/117/118/120/122`**）

- **影响范围**：S03/S05/S06 调用方、S12 repository 协作、架构测试、实现模块边界
- **为什么必须确认**：Port 已存在为抽象，但 **方法闭集、handle 字面语法、多协程写同一 object_root 时锁/串行策略、fsync 是否强制** 仍可 internally 漂移；不钉则 formal Spec 无法验收。
- **不在本题裁决**：GC 周期秒数（Q8）；backup 排程（Q9）；R2 方法差异。

#### 选项清单

| 选项 | 方案 | 含义 |
|---|---|---|
| **A** | **窄 Port + 强制 fsync + 有界并发 + 钉死 handle 语法（推荐）** | 最小方法集；promote 路径 fsync file+dir；同 root 写并发有界；handle 语法稳定版本化 |
| **B** | 胖 Port（含 GC/backup/admin 全进 domain Port） | domain 易耦合运维 |
| **C** | 不钉 handle 语法，实现随意字符串 | 跨版本/日志不可解析；难测试 |
| **D** | 无并发控制，依赖 OS 碰运气 | rename 竞态与半文件风险 |

#### 当前建议 / 倾向

**推荐 A**。

#### 推荐执行细节（选 A 时）

1. **Handle 语法（v1 钉死）**：
   ```text
   mkbobj:v1:<team_uuid>:<stored_object_uuid>
   ```
   - 仅内部/契约使用；**解析必须**校验 team 与 catalog 行一致；
   - **不含** path、digest、backend；digest 在 catalog/调用参数中另传。

2. **Port 方法闭集（名称可微调，职责固定）**：

   | 方法 | 职责 |
   |---|---|
   | `open_write_stream(team, budget, media?)` | exclusive staging；返回 write handle/session |
   | `finalize_write(session) → (digest, size)` | 关流、算哈希、校验 budget |
   | `promote(team, digest, size) → PromoteResult` | atomic CAS path 或 verify-reuse；fsync |
   | `open_verified_read(team, handle, expected_digest?)` | live-ref 策略由 caller/repo 保证；流式 + 读后校验 |
   | `stat(team, handle)` | size/digest/media 元数据（来自 catalog，非扫盘猜） |
   | `exists_bytes(team, digest, size)` | CAS 复用探测（内部/repo） |
   | （repo 协作，可非 Port）`register_reference` / `release_reference` | 在 S12 UoW 内 |

   **不进 Port（运维/扫描器）**：`gc_scan_once`、`backup_quiesce`、path 调试——属 S13 内部 ops 或 S15。

3. **本地并发**：
   - 允许多协程 **读**；
   - **写/promote**：对同一 `object_root` 使用 **有界写闸**（单写者队列或 per-team 细锁 + digest 级互斥）；同 digest 并发 promote → 一方 verify-reuse 成功即可；
   - **禁止** 无协调多 OS 进程写同一 `object_root`（与 S12 单写主库同纪律）；若未来多进程，必须另开题。

4. **fsync 策略（v1 强制）**：
   - promote 成功前：`fsync(temp file)` + `fsync(parent dir)`（或平台等价 durability）；
   - 配置项 **不允许** 默认关闭 durability 换吞吐（debug profile 可另开且 **禁止生产 readiness**）。

5. **Architecture test**：domain/S02–S06 包 **不得** import `pathlib` 写 object_root、不得拼 `mkbobj` 以外的 path 身份。

#### Supporting Reasoning

- 窄 Port 对齐 S12 Persistence Ports 纪律，避免 S13 变成“小操作系统 API”。
- handle 语法不钉会导致日志/fixture/跨版本不可比（legacy `r2_key` 教训）。
- 无写闸（D）在 CAS rename 与同 digest 竞态下难证明 immutability。
- 强制 fsync 是 local backend 崩溃验收的前提；可选关闭会变成假绿色。

#### 问题（请业主裁决）

**Q7：选 A / B / C / D？是否接受 `mkbobj:v1:<team>:<uuid>`、上表 Port 闭集、有界写闸、生产强制 fsync？**

- **业主回答**：接受推荐 **A** 全部执行细节。→ **冻结为 `T-O-123`**
- **裁决状态**：`accepted / frozen`

### Q8 — GC 扫描环、delete fence 与 object_root readiness（**驱动：`T-O-119/120/121` + S12 readiness**）

- **影响范围**：S12/S15 扫描器、磁盘膨胀、启动门禁、missing incident
- **为什么必须确认**：release+grace 已冻，但 **谁周期性跑 GC、如何 fence、启动时 object_root 与 DB 如何互认** 未钉则实现会 silent 选“启动扫全盘”或“从不 GC”。
- **不在本题裁决**：backup 全流程（Q9）；metric 名（S15）。

#### 选项清单

| 选项 | 方案 | 含义 |
|---|---|---|
| **A** | **同发布单元周期 scanner + delete fence + object identity readiness（推荐）** | 进程内/同单元定时 GC；删前 CAS recheck；readiness 校验 root+identity.json |
| **B** | 仅手动 ops 命令 GC | v1 易胀盘 |
| **C** | 独立 GC 微服务 | 违背单体 leaf-worker |
| **D** | 启动时全量 walk 文件系统对账为唯一 GC | 启动慢；大库危险；仍缺周期回收 |

#### 当前建议 / 倾向

**推荐 A**。

#### 推荐执行细节（选 A 时）

1. **GC 扫描环（同 MKB 发布单元）**：
   ```text
   periodic (config interval, e.g. 5–15 min) OR after release burst
     → query candidates: stored_objects with zero live refs
        AND released long enough / orphan promoted older than grace
        AND no hold purposes
     → for each: delete fence (re-read live ref count == 0)
     → unlink CAS file (missing-at-delete 可记 proof 成功/已不存在)
     → append delete_proof
     → optional: soft-tombstone catalog row (保留 digest 元数据防幽灵复用审计) — Spec 选 “保留 tombstone” 或 “硬删 catalog 行”，推荐 **保留 catalog tombstone**
   ```
2. **Staging GC**：独立规则清过期 `.tmp`（TTL `T-O-122`），不产生 delete_proof（或轻量 ops log）。
3. **Delete fence**：与 S03 claim fence 同构思想——**观察版本 → 删 → 再确认**；并发新 ref 插入则 **中止删**。
4. **object_root readiness**（`readiness=false` 当任一）：
   - `object_root` 未配置/不可写/非目录；
   - `identity.json` 缺失且非 empty bootstrap；
   - `identity.json` 的 deployment/format 与 DB 记录的 object store binding **不一致**（防挂错盘）；
   - 强制 capability（fsync/atomic rename probe）失败。
5. **Bootstrap**：empty root 时创建 `identity.json` + 目录骨架，与 S12 empty-DB bootstrap **同启动路径**协调；已有 root 且 identity 冲突 → fail-loud。
6. **禁止**：GC 删业务表；GC 在仍有 live ref 时 unlink；把 “目录 mtime” 当 SSOT。

#### Supporting Reasoning

- 单体 + 本地盘 → 同进程 scanner 足够（对齐 S12 outbox loop 哲学）。
- 手动-only（B）在生产必胀；独立服务（C）违反 OD-06。
- readiness 绑定 identity 防止“DB 是 A 机、盘挂到 B 机”的灾难性错挂。
- delete fence 防止 release 与新 generation 引用竞态。

#### 问题（请业主裁决）

**Q8：选 A / B / C / D？是否接受周期 scanner、delete fence、identity.json readiness、catalog 删除后保留 tombstone 元数据（推荐）？**

- **业主回答**：接受推荐 **A** 全部执行细节（含 catalog tombstone）。→ **冻结为 `T-O-124`**
- **裁决状态**：`accepted / frozen`

   | `OBJECT_AUTH_*` | team 不匹配 / handle 伪造 | 拒绝 |
   | `OBJECT_UNAVAILABLE_*` | root 只读 / readiness false | 拒绝写入 |

3. **对外表面**：
   - **禁止** v1：public object CRUD、presigned upload/download、bucket list API、对象浏览器；
