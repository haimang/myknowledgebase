### Q1 — Inference Port 能力面与跨层边界应冻结成什么形状？

- **驱动真相**：`T-O-180` / `T-O-182` / `T-O-184` / `T-O-185` / D03 contracts  
- **单一裁决面**：v1 **最小 Inference Ports 方法闭集** + 与 S03/S06–S10 的边界（谁调 Port、返回什么、什么禁止泄漏）  
- **不在本题裁决**：具体 model ID 钉选（Q2）、DB 表（Q3）、S09 ANN 参数、完整 timeout 毫秒产品台  
- **影响范围**：`src/contracts/inference/`、`src/llm_adapters/`、S06/S07/S08/S10 调用方式、architecture tests  
- **事实驱动**：legacy `IAiProvider` 过窄（无 embed/rerank）；contexter 能力拆分正确但 CF 绑定；D03 要求原始 token 流进入业务前 parse  

#### 执行方案选项

| 选项 | 摘要 | 含义 |
|---|---|---|
| **A** | 单一 `invoke(model_id, raw_request)` | 实现快；业务重新耦合供应商；破坏 D03 校验纪律 |
| **B** | **分能力 Port 闭集（推荐）** | `embed` / `rerank` / `structured_generate` / `text_generate`（summary 可归 text 或独立）各有 typed request/response；统一 `InferenceUsage` + `model_ref` + `latency`；禁 path/secret 进返回 |
| **C** | 仅 embed+rerank，生成类仍直连 SDK | 违背 T-O-182；S06/S07 继续散落 |
| **D** | Port 含 Workflow 路由/claim | 越权 S03 |

#### 推荐执行方案（选项 B）

1. **Port 最小闭集（逻辑名，可微调拼写）**  
   - `embed(EmbedRequest) -> EmbedResult`  
   - `rerank(RerankRequest) -> RerankResult`  
   - `structured_generate(StructuredGenerateRequest) -> StructuredGenerateResult`  
   - `text_generate(TextGenerateRequest) -> TextGenerateResult`（承载 summary/rewrite 等非 JSON 强制任务）  
2. **统一附属字段**：`provider_id`、`model_id`（逻辑）、`adapter_kind`（`local_vllm`|`remote_gemini`|…）、`usage{input_tokens?,output_tokens?,total_tokens?}`、`latency_ms`、`request_digest`（对输入规范摘要，非正文）。  
3. **调用方**：仅 `src/services/*` / runtime 编排经 Port；**禁止** intake 适配器直接 embed 当业务 SSOT。  
4. **返回纪律**：structured 路径 **必须** 已 parse 为 contracts 类型；非法 → typed error，不 partial apply。  
5. **禁止**：返回绝对 path、API key、未校验 dict 当合同；Port 内推进 Process 状态。

#### Reasoning 与证据

- legacy 同时存在「窄 IAiProvider」与「contexter 四分能力」——生产需要 **能力分面**，但实现却绑 CF；B 保留分面、去掉平台。  
- D03 `T-O-154`：未 parse token 流不得跨层；B 把 parse 边界钉在 adapter→Port 出口。  
- OD-07 adapter-first：B 使 vLLM 与 Gemini 可替换而不改 S06/S07。  
- A/C 会重演硬编码 model 与双源 SDK。  

#### Owner 问题

Owner 是否接受 **选项 B**：v1 冻结 **分能力 Inference Port 闭集**（embed / rerank / structured_generate / text_generate）+ 统一 usage/model_ref；业务只经 Port；structured 出口必须 contracts 校验通过？

#### 业主回答

业主 **修正接受**（2026-08-12）：

1. **Inference 层与 Adapter 层必须分离**：  
   - **Adapter** = LLM **对接层**（provider SDK/HTTP、协议翻译）→ `src/llm_adapters/`；  
   - **Inference** = **runtime 的一部分**，对业务暴露 **分能力抽象**（非万能 invoke）；  
2. 同意 **按能力** 构建 inference 抽象（对齐推荐 B 的能力闭集）；  
3. 业务/services **只依赖 Inference 抽象**，不依赖具体 adapter 类型。

`🔒 frozen → T-O-189`（分层）+ `T-O-190`（分能力 inference 面）

#### 裁决状态

`accepted / frozen`（owner-amended B′：显式 Inference≠Adapter）

- **事实驱动**：业主双 adapter；Qwen3-VL-Embedding-2B；gemini-embedding-2；semantic-ranker-default-004；legacy 本地无、远端 Gemini 生成 + Workers embed/rerank  

#### 执行方案选项

| 选项 | 摘要 | 含义 |
|---|---|---|

#### 推荐执行方案（选项 B）— v1 默认路由矩阵

### 7.1 Vectorizer 机制事实

```text
SMCP → VectorizerDO.fetch
  ├─ Purge：内存 isLocked；忙 → HTTP 429 ATOMIC_LOCK_CONFLICT
  └─ 任务：internal_tasks 入队 → alarm
alarm（持锁）:
  flush WAL(buffered_vectors) → Vectorize → D1 completed
  claim smind_vec_process pending→in_progress
  prepare → embedder(AI.run, 429 指数退避×3) → bufferVectors
  有进度 cool-down 1s；无 pending → success callback + dequeue
```

| 主题 | 证据文件 | 行为 |

### Q7 — Transport 429 / 限流 / 瞬时故障：S11 必须冻结什么重试合同？

- **驱动真相**：`T-O-185` / `T-O-191` / `T-O-197`；空洞 **G-S11-V1**  
- **单一裁决面**：Inference **transport 错误分类** + **有界退避** + **与 S03 Process retry 的分账**（不含换模型）  
- **不在本题裁决**：背压闸（Q8）、embed/index 两阶段表（Q9）、具体毫秒产品调参台终值（可给安全默认）、S09 ANN  
- **影响范围**：`src/runtime/inference/policies`、`src/llm_adapters/local_vllm`、`mkb_inference_invocations` 的 error_code、S03 `retryability`、S08 vectorize handler  
- **事实驱动**：vectorizer 在 **调用内** 对 429 退避；DO 另有 **资源忙 429**；MKB 无 Workers AI 错误码但仍有 vLLM HTTP 限流  

#### 执行方案选项

| 选项 | 摘要 | 含义 |
|---|---|---|
| **A** | **零 S11 退避**：adapter 一次失败即上抛；只靠 S03 Process `max_retries` / `retry_wait` | 实现最简单；限流 burst 时每个 429 都消耗工序重试配额，噪声大、收敛慢 |
| **B** | **S11 有界 transport 退避 + 错误分类（推荐）** | 同模型/同 binding 上短退避；耗尽后 typed 上抛；S03 决定是否工序级重试；**禁** 因 429 换 model/adapter |
| **C** | **无限/超长退避直到成功** | 可“扛过”限流，但 Process lease/deadline 易假死；不可验收 |
| **D** | **429 → 自动换模型或换 adapter** | 直接破坏 embedding 空间隔离（T-O-192/197）；禁止 |
| **E** | **仅 log 后吞掉错误当成功** | 假成功；禁止 |

#### 推荐执行方案（选项 B）

**B1. 错误分类（逻辑闭集，contracts 可枚举）**

| 类 | 判定（逻辑） | S11 内行为 | 上抛后对 S03 的建议 retryability |
|---|---|---|---|
| **TransportRetryable** | HTTP **429**、**503**、网关超时、连接重置/失败、显式 `rate_limited` / `overloaded` / `capacity`；兼容 legacy 消息子串语义（`429`、`limit exceeded`、`timeout`、`overload`、`connection`、`fetch failed`；CF `9002`/`9003` 仅作历史映射注释） | **进入有界退避循环** | 耗尽后：`retryable` 或 `indeterminate`（Spec 钉默认 `retryable`） |
| **ValidationNonRetryable** | 4xx 请求非法、schema/contracts 失败、空输入策略拒绝、token/budget 超限（非瞬时） | **立即失败**，不退避 | `non_retryable`（修输入/配置） |
| **ConfigNonRetryable** | model 未注册、binding disabled、adapter 未启用、维度与 namespace 不一致 | 立即失败 | `non_retryable` |
| **SpaceViolation** | 试图换 model/adapter 跨空间、filter/Layer A 不匹配 | 立即失败 | `non_retryable` |
| **LogicBusy（背压）** | 并发闸满（见 Q8） | **不**占用 transport 退避配额；返回 `INFERENCE_BACKPRESSURE` | `retryable`（可延后 outbox / Process） |

**B2. Transport 退避参数（安全默认，可配置，非 Truth 硬秒数产品台）**

| 参数 | v1 安全默认 | 约束 |
|---|---|---|
| `max_transport_attempts` | **3**（与 legacy `MAX_RETRIES: 3` 同量级） | ≥1；配置上限须有界（如 ≤10） |
| `initial_delay_ms` | **1000** | >0 |
| `backoff_factor` | **2** | ≥1 |
| `max_delay_ms` | 建议 **30000** 封顶 | 防止单次调用占满 lease |
| jitter | 允许小幅随机 | 降惊群 |

公式（逻辑）：`delay = min(max_delay_ms, initial_delay_ms * backoff_factor^(attempt-1))`（±jitter）。

**B3. 与 S03 分账（强制）**

```text
单次 Inference.embed/rerank/... 调用
  └─ S11 transport loop（同 model_key/version/adapter_kind）
        success → 返回结果 + 写 inference_invocation(succeeded)
        transport 耗尽 → INFERENCE_TRANSPORT_EXHAUSTED
              → Process Outcome retryability=retryable（默认）
              → S03 账本 retry_count / max_retries / retry_wait
```

1. **S11 内 attempt 不写入** `mkb_processes.retry_count`（那是工序级）。  
2. **S11 应写入** `mkb_inference_invocations`：每次最终 outcome（及可选每次 attempt 的 diagnostic_logs）。  
3. Process **lease/heartbeat**：长退避不得无声吃光 lease；实现须保证 lease 覆盖或中途 heartbeat（细节归 S03 配置，S11 不得假设无限租约）。  
4. **禁止**：transport 失败后 **silent** 改 `model_key` / `adapter_kind` / `dimension` 再试（T-O-192/197）。  
5. **禁止**：把 Workers AI 错误码写进对外合同；仅保留 HTTP/语义类映射。

**B4. 能力差异（默认可写进 Spec）**

| capability | transport 退避 | 备注 |
|---|---|---|
| `embed` | **启用 B** | vectorize 主路径；对齐 embedder |
| `rerank` | **启用 B** | 与 embed 同 policy 类，除非 binding 覆盖 |
| `structured_generate` / `text_generate` | **启用 B** | 模型限流同样适用 |
| 全部 | Validation/Config/Space | **从不**走 transport 退避 |

#### Reasoning 与证据

- **生产证据**：`vectorizer/embedder.ts` 在 **adapter 调用环内** 识别 429/限流/超时并指数退避，而不是每次 429 都回到 dispatcher 重开整步；说明 S11 需要 **短 transport 环**。  
- **分账证据**：S03 已冻 max-retries/retry_wait；若无 S11 退避（A），限流会 **放大** Process 失败与重调度成本。  
- **隔离证据**：T-O-192/197 禁止跨模型混空间；D（换模型扛 429）在向量路径上是正确性灾难。  
- **C** 无限重试与 Process lease/deadline 冲突，legacy 也用 **有界** 3 次。  
- **E** 吞错 = 假向量化完成，违背 T-O-185。  
- 本地 vLLM 同样会返回 HTTP 429/503；合同应 **提供商无关**。

#### Owner 问题

Owner 是否接受 **选项 B**：冻结 **TransportRetryable vs 不可重试** 分类；S11 内 **有界指数退避**（默认约 3 次、1s×2^n、可配置封顶）；耗尽后 typed 上抛并由 S03 决定工序重试；**S11 attempt 不计入 Process retry_count**；**禁止** 因 429 换 model/adapter；失败须可审计（invocation/diagnostic）？

#### 业主回答

业主接受 **选项 B** 全部执行推荐（2026-08-12）。

### Q8 — 无 Durable Object 时：本地 vLLM 的并发、背压与“资源忙”语义如何冻结？

- **驱动真相**：`T-O-181`（禁 DO 必选）/ `T-O-191`（全本地）/ `T-O-196`（runtime/inference）/ G-S11-V2  
- **单一裁决面**：v1 **Inference 并发闸与背压错误** 的归属、粒度、与 S03 claim 的正交关系  
- **不在本题裁决**：transport 退避参数（Q7）、WAL 表（Q9）、多机分布式锁、精确 GPU 拓扑  
- **影响范围**：ai-dev 稳定性、多 Process 并行 embed/generate、outbox 延迟语义、architecture tests  
- **事实驱动**：VectorizerDO **单实例串行** alarm + **内存 mutex** + cool-down；Purge 冲突返回 **429 资源忙**；MKB 多 Process 可同时 claimed  

#### 执行方案选项

| 选项 | 摘要 | 含义 |
|---|---|---|
| **A** | **无闸**：凡 claimed Process 可无限并行打 vLLM | 实现快；易 OOM/排队雪崩；行为依赖进程运气 |
| **B** | **Runtime Inference 有界闸 + 背压错误（推荐）** | 进程内（及可选 per-capability）信号量；超额不执行模型调用 |
| **C** | **仿 DO：每 team 一常驻队列 Actor** | 接近 legacy 拓扑；运维重；与 leaf-worker 单体简单模型冲突 |
| **D** | **仅 OS/文件锁或全局 flock** | 脆弱、难测、跨线程语义不清 |
| **E** | **只靠拉长 outbox `available_at` 做全局串行** | 可减峰，但不能表达“GPU 正在忙”的同步调用路径；且与多 capability 细粒度冲突 |

#### 推荐执行方案（选项 B）

**B1. 闸的位置与粒度**

```text
services / vectorize handler
  → runtime.inference  (门面)
       → [ConcurrencyGate: global + optional per-capability]
            → llm_adapters.local_vllm
```

1. **默认**：`global_max_in_flight`（配置；ai-dev 安全默认建议偏保守，例如个位数～十余，**非 Truth 硬数**）。  
2. **可选**：`embed` / `generate` / `rerank` **分闸**（generate 往往更重）；未配置则继承 global。  
3. **不** 按 team 强制串行（避免假公平饥饿）；team 公平属未来 reopen。  

**B2. 超额语义（对齐 legacy“资源忙 429”，但不绑 HTTP）**

| 情况 | 行为 |
|---|---|
| 闸有空位 | acquire → 调 adapter → release（须 finally） |
| 闸满 | **不**进入 transport 退避环；立即返回 typed **`INFERENCE_BACKPRESSURE`**（或等价名） |
| retryability | **retryable**；调用方可：短暂等待后重试 **同 binding**，或让 outbox `available_at` 延后，或让 Process 走 S03 retry_wait |
| 与 Q7 关系 | Backpressure **≠** TransportRetryable；**不得**算作 model 429 去换模型 |

**B3. 与 S03 / outbox 正交**

1. **S03 claim 成功 ≠ 已获得 GPU 配额**。多个 Process 可同时 `claimed`，但仍受 Inference 闸约束。  
2. **fence/lease 仍有效**：背压等待不得无限持有过期 lease；实现应快速失败或受控短等（上限可配置），超时后上抛 retryable。  
3. **outbox**：允许 handler 在 backpressure 时 **延迟 re-pending**（更新 `available_at`），**不得** mark done。  
4. **禁止** 用“丢掉任务”缓解背压（legacy DO 删队列是反模式，见 Q9）。  

**B4. 可观测**

- 每次 backpressure：`mkb_ops_diagnostic_logs` 或 invocation 记 `status=failed` + `error_code=INFERENCE_BACKPRESSURE`（若未真正调用模型，可用 attempts=0 的失败 invocation 或仅 diagnostic——Spec 二选一须统一；**推荐**：记一条 failed invocation 便于对账）。  
- metrics 钩子归 S15（计数、等待时间），不在本题冻数值。  

**B5. v1 明确不做**

- 跨进程分布式信号量（多 OS 进程写同一 vLLM 时，v1 仍遵守 T-O-102 单写权威/单发布单元假设）。  
- DO / 每 file 一 Actor。  
- 全局强制单线程到“整个 leaf 只有一个 embed”（过死）；用有界闸代替。  

#### Reasoning 与证据

- **生产证据**：`vectorizer_do.ts` 用 **单 DO 串行 alarm + isLocked + cool-down** 防止与 Purge 并发打爆资源；忙时对外 **429**。说明限流之外还有 **容量闸**。

- **C** 过重且像微服务化 DO；**D** 难测；**E** 只覆盖异步 outbox，不覆盖同步 generate 路径。  
- 与 Q7 分工：Q7 = **远端/引擎限流**；Q8 = **本进程准入**；二者都 retryable，但错误码不同，避免混治。

#### Owner 问题

### Q9 — Embed 已算 vs Index/登记未完成：耐久、重放与“丢任务”禁令？

- **驱动真相**：`T-O-185` / `T-O-169` / D04 records 幂等 / G-S11-V3 / G-S11-V4  
- **单一裁决面**：vectorize（及同类两阶段副作用）在 **模型已成功、持久化未成功** 时的 **重放与中间态**；以及致命失败时 **是否允许丢意图**  
- **不在本题裁决**：ANN 算法、S09 serving、具体 cool-down 毫秒  
- **影响范围**：S08 vectorize handler、outbox、`mkb_vector_records` upsert、S03 失败收敛、是否 reopen D04 增 WAL 表  
- **事实驱动**：legacy **WAL 保向量** 以省重算；flush 失败不删 WAL；但 DO **致命错误删 internal_tasks** 以疏通队列——后者是正确性负债  

#### 执行方案选项

| 选项 | 摘要 | 含义 |
|---|---|---|
| **A** | **无中间态、整段重放、总是重 embed** | 失败则 outbox 重试整条路径；实现最简单；重复 embed 成本高但语义清晰 |
| **B** | **无 WAL 表 + 幂等 upsert + 允许重 embed（推荐 v1）** | 与 A 同“无新表”，但强制 **幂等键** 与 **禁丢意图**；成功路径原子性要求写清 |
| **C** | **新建 durable 向量 WAL 表**（仿 `buffered_vectors`） | embed 后先落库 blob/侧表再 index；省重算；增加表闭集与 GC 复杂度，像 DO |
| **D** | **embed 成功即业务成功**（index 异步尽力） | 假完成；违背 T-O-185 / 存在≠serving 纪律的相邻精神 |
| **E** | **致命失败时删除 outbox/意图以疏通队列**（仿 DO dequeue bad task） | 不可恢复；禁止 |

#### 推荐执行方案（选项 B）

**B1. 成功路径（逻辑时序）**

```text
outbox vectorize_* claimed
  → Inference.embed (Q7/Q8 约束)
  → UnitOfWork（或紧邻等价可证明顺序）:
       upsert mkb_vector_records  (幂等：team+namespace+gen+block+channel+model)
       写 mkb_inference_invocations (succeeded)
       可选 domain_event vector.upserted
  → mark outbox done
```

1. **不** 引入 `buffered_vectors` / DO SQLite 作为 v1 必选。  
2. **幂等**：重复执行同一 vectorize 意图不得产生双行业务真相（D04 unique / upsert）。  
3. **embed 成功但 TX/upsert 失败**：outbox **不得** done；保持 pending/in_flight→retry；**允许** 再次 embed（v1 接受算力换正确性）。  

**B2. 失败路径矩阵**

| 失败点 | durable 结果 | 重放行为 |
|---|---|---|
| embed transport 耗尽 | 无新 records 行（或无 partial 可服务行） | outbox/Process 按 Q7+S03 重试 |
| embed 成功，records upsert 失败 | 无 committed 可服务向量 或 旧版仍在 | 重放：再 embed + 再 upsert（幂等） |
| records 成功，outbox mark done 失败 | 可能已有向量 | 重放：upsert 幂等 + mark done |
| handler 进程崩溃 | outbox 仍 pending/in_flight | 投递环恢复（S12） |
| 逻辑/校验失败 | 不写假成功 | Process failed 或 non_retryable |

**B3. 与 legacy WAL 的关系（明确 defer）**

| Legacy | MKB v1 |
|---|---|
| `buffered_vectors` 存 Float32 blob | **不做** 必选表 |
| flush 失败保留 WAL | 用 **outbox 未完成** 表达“未完结意图” |
| 省重算 | v1 **接受重 embed**；若成本不可接受 → 未来 reopen 有界 staging 表 |

**B4. 致命失败与“丢任务”禁令（G-S11-V4）**

1. **禁止** 为疏通队列而删除未终态 outbox / 未收敛 Process 意图（legacy `removeCurrentTask` 在 MKB **反例**）。  
2. 不可恢复错误：Process → `failed`（或 S03 规定终态）+ invocation failed + diagnostic；意图 **可审计**。  
3. 可恢复错误：outbox retry / Process retry_wait；**不** silent drop。  
4. `releaseTasksToPending` 的 **升级形态**：S03 lease recovery / claim 释放，而不是 DO 私有队列删除。  

**B5. 数据库结构安排（本题冻结的边界）**

| 表/机制 | v1 角色 |
|---|---|
| `mkb_outbox` | vectorize 意图 SSOT（传输+重放） |
| `mkb_vector_records` | 最终向量 + 幂等坐标 |
| `mkb_inference_invocations` | 调用审计（非成功定义） |
| `mkb_processes` | 工序状态/fence/retry 账本 |
| **不建** `smind_vec_process` / DO `internal_tasks` / `buffered_vectors` | 禁止回潮 |

#### Reasoning 与证据

- **WAL 证据**：`engine.flushBufferedVectors` 失败时 **保留 WAL**——模式是“已算向量不因 index 失败而丢”；MKB 用 **幂等 records + 未完成 outbox** 达到“不丢意图”，v1 用重 embed 换不建 WAL 表。  
- **丢任务证据**：`vectorizer_do.ts` 在 catch 中 **dequeue 坏任务** 以防堵队——这是 **可用性优先于完整性** 的 legacy 债；MKB 有 S03/outbox 恢复，**禁止** 复制。  
- **D** 假成功：与 T-O-185、向量存在≠业务成功一致禁止。  
- **C** 可优化成本，但引入第二耐久面与 GC，应 **defer reopen**，不阻塞 v1。  
- **A vs B**：语义接近；B 额外钉死幂等键与禁丢意图，避免实现写成“随便重跑产生双行”或“失败就删 outbox”。  
- 与 D04：`UNIQUE(... generation, block, channel, model) WHERE deleted_at IS NULL` 已为 B 的幂等提供物理锚。

#### Owner 问题

Owner 是否接受 **选项 B**：v1 **不建** 向量 WAL/DO 队列表；vectorize 以 **outbox + 幂等 `mkb_vector_records` upsert** 为耐久核心；embed 成功但登记失败时 **可重复 embed**；**禁止** 静默删除未终态意图；embed 成功 **≠** 业务/Process 成功；未来若需省重算再显式 reopen staging 表？

#### 业主回答

业主接受 **选项 B** 全部执行推荐（2026-08-12）。

`🔒 frozen → T-O-201`

#### 裁决状态

`accepted / frozen`
