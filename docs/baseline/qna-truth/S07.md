### 2.3 业务流层（Constructor + 上下游）

#### 2.3.1 端到端（生产事实）

```text
Dispatcher
  → (meta-only 时按 step name 含 "constructor" 跳过 Structurizer)
  → Constructor:
       读 struct_source JSON
       → 校验 LayeredJson
       → [非 meta-only] Summarizer 整文一次 LLM 填 llm_summary
       → MetaFuser（始终）
       → 写 layered_json 到对象存储
       → Recorder 按块扇出 original/summary 行到 smind_vec_process
       → STEP_CALLBACK 成功（含 layered_json_r2_key）
  → Vectorizer: 按 file_uuid claim pending 行，embed content_full
  → Contexter: summary 命中后按 (file_uuid, block_id, granularity) 查 original
```

#### 推荐执行细节（选 C 时）

1. **Summary plan（kernel 可复验）**：

   - 每个 model call = 独立 GenerationInvocation（或 S11 账本等价物）；

   - 缺 prompt/model = fail-fast。
3. **Grounding 最小合同（v1）**：
   - 每个非空 summary 必须声明 `grounds_coordinate` = 本 unit 的 generation-scoped coordinate（与 original 相同）；
   - **不**强制句子级 citation 列表为 v1 kernel（可 extension/profile 升级）；
   - 禁止 summary 指向其他 unit coordinate 却不记账。
4. **`summary_disposition` 闭集骨架（Spec 可增，不得变自由字符串）** v1 最小：
   - `present_grounded` — dual-channel 该 unit 完成；
   - `omitted_by_profile` — profile 允许跳过摘要生成；
   - `empty_model_output` — 模型返回空/null 槽；
   - `failed_extension` — schema/grounding 失败且 repair 未救回；
   - `not_applicable` — 无 original 可摘要（罕见，须 report）。
5. **默认 profile 与整单 full-valid**：

6. **Repair**：仅 summary 文本/扩展字段；不改 plan 目标集合；不改 original；全量复验。
7. **禁止**：silent 回填 context/summary；无 Invocation 的“内部重试到成功”；无 plan digest。

#### Supporting Reasoning

- **Grounding 从轻**：满足 `T-O-133`“能回溯 original unit”；不在本轮发明未授权的重型 citation 体系。

### Q7 — 整包 artifact 成败语义（单文档 Execution）（**驱动：`T-O-132/133/134/135/136` · Owner 产品模型**）

- **影响范围**：S07 validator、Process 成败、S03 retry、S08 能否消费 current、Workflow 后续步骤
- **为什么必须确认**：Owner 澄清管线心智——**一次 Execution 对应一份 intake 文档**；双通道（original + summary）的多粒度结构 **封装在同一 JSON schema artifact 内**；处理对象是 **整包 artifact**，不是“每个结构单独 LLM 请求”。成败与恢复必须按此心智冻结，避免错误的 unit 级中间态设计。
- **驱动输入**：Owner 2026-08-11 产品模型；生产 Constructor 整文填 summary（`summarizer`）+ 多块封装于一份 layered JSON；`T-O-130/134`；对 `T-O-133/136` 成功面的收窄需要

#### 产品模型（Owner 给定 · 规范性前提）

```text
Task / Execution
  └── 一份 intake 文档（单文档管线）
        └── lsrag.construct（一次 Process）
              └── 处理「整包」Construction schema artifact
                    ├── 内含多粒度 / 多结构 dual-channel 记录
                    │     （original 层 + summary 层，共享坐标）
                    ├── 一次（整包）摘要生产：填充全部应有 summary
                    │     （不是每个粒度单独发起一次 LLM 成功单元）
                    └── 结果：整包成功 或 整包失败
```

#### 选项清单

| 选项 | 方案 | 含义 |
|---|---|---|
| **A** | **软成功 / 半包可用** | 部分结构缺 summary 或仅 original 仍可 CAS current；对齐生产“空 summary 仍成功” |
| **B** | **整包二元成败 + S03 重试 + 显性失败后续（推荐 / Owner）** | 只处理整包 artifact：校验与接受以 **整包** 为单位；**要么** dual-channel 构造 full-valid 并 CAS current，**要么** 失败且不 CAS；恢复只走 S03 max-retries；耗尽后显性 failed 记录并抛错，Workflow **继续后续任务**（按 loss policy） |
| **C** | **结构级中间成功** | 按单个粒度/结构 admit 成功或 original-only；分级策略 |
| **D** | **仅 shape 通过即成功** | 不管 dual-channel 是否完备 |

#### 当前建议 / 倾向

**推荐 B（整包二元成败）** — Owner 产品模型直接采纳。

#### 推荐执行细节（选 B · 已按 Owner 模型书写）

1. **处理单元 = 整包 artifact**  
   - 一次 `lsrag.construct` Process 消费/产出 **一套** Construction 成员（`construction_document` + `dual_channel_projection` + proof 面，见 `T-O-135`），对应 **本 Execution 的这一份文档**。  
   - 包内可有 **多条** dual-channel 结构记录（多粒度），但它们是 **同一 schema 契约下的整体**，不是 N 次独立 construct。  
   - 摘要：按整包生成（生产对齐：一次填充全部应有 summary）；`T-O-136` 的 `document_single` 为默认生产对齐模式；`per_unit` 仅实现/profile 手段，**不得**变成“按结构单独计成败”。

2. **成功（唯一）**  
   - 整包通过校验：binding/schema/original 保真/双通道完备（凡应有 summary 的结构位均有 grounded summary；original 不由模型伪造）；  
   - **同 UoW CAS** 全部 S07 current 成员；  
   - 可发 outbox intent（`T-O-137`）；  
   - **禁止** 部分结构缺 summary 仍成功、original-only 成功、0 有效通道仍成功。

3. **失败**  
   - **不 CAS** 任何 S07 current（半包不得变 usable）；  
   - 可落 invalid/失败 report 供审计（取证，不是第二种成功）；  
   - Process Outcome = failed + typed error；  
   - **不**在 S07 内再开一轮“内部修补摘要”（无 process-local 再生成）；直接交给 S03。

4. **恢复与显性失败后续**  
   ```text
   Process failed
     → S03 同 command_input_digest 重试（未超 max-retries）
     → 仍失败直至 max-retries
     → Process 终态 failed：显性记录 + 抛出/返回错误
     → 不 CAS current；S08 不得当 usable construct 消费
     → Workflow 按 S02/S03 既有 loss policy 继续后续任务/步骤
        （失败不抹账、不卡死引擎；也不把半包当成功往下传）
   ```

5. **对 `T-O-133` / `T-O-136` 的 v1 收窄（写入本 Truth，不改写旧行）**  
   - **取消** v1 full-valid 成功态中的 `original-only admitted` / `allow_original_only`；  
   - disposition 闭集若保留，**仅**出现在失败/invalid report，**不**驱动 CAS；  
   - “extension repair≤1” **v1 不启用** 为成功路径上的内部修补；摘要不合格 = 本 Process 失败 → 只靠 S03 重试。

6. **与“多结构”的正确关系**  
   - 多结构 = artifact **内部数据**；  
   - 成败 = artifact **外部结果**（一次成功/一次失败）；  
   - 禁止把内部结构条数误解为 N 次 LLM 成功单元或 N 次 Process。

#### Supporting Reasoning

- **对齐 Owner 管线**：单文档 Execution、双通道、整包 schema artifact、一次处理所有粒度 summary——与 production 心智一致，纠正“每结构单独 LLM 成败”的错误 reframing。  
- **对齐成本立场**：无结构级中间成功、无分级 admit，实现与验收最简。  
- **对齐 `T-O-130/134`**：重试在 S03；无 current 则不可用。

- **反对 C**：正是 Owner 否决的复杂度源。  
- **反对 D**：放弃 dual-channel 产品承诺。  
- **“继续后续任务”**：失败显性化后由 Workflow 继续调度，不是静默当成功，也不是删除历史。

#### 问题（请业主裁决）

**Q7：整包成败选 A / B / C / D？若选 B，是否确认：单文档 Execution、整包 artifact 二元成败、无结构级中间成功、仅 S03 重试、max-retries 后显性 failed 并继续后续任务、收窄 T-O-133/136 的 original-only 成功面？**
