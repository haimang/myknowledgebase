## 1. S03 重新校准后的 Scope

### 1.1 S03 的唯一定位

S03 是 **MKB 单体内部唯一 durable、declarative、future-agent-ready 的 LS-RAG Workflow Engine**。第一次重构不开放 Workflow authoring；它同时拥有两类职责：

1. **Internal Workflow registry/compiler**：只接收 MKB 内部创建并注册的 Workflow，以分解后的关系型 schema 严格管理各控制平面，并生成声明式 compiled JSON；
2. **Workflow runtime**：把已发布 revision 与一次 Execution context 编译为可恢复的运行计划和独立 Process command，推进 Execution tree，并把 Process outcome/proof 自下而上归约。

S03 不是：

- 外部 Task API 或第二套 Task 状态机；
- 对外 Workflow create/update/delete API；
- 第一次重构中的 agent Workflow authoring/publish 系统；
- 只会按 rank 找下一节点的 queue wrapper；
- 只有 node/edge 的拓扑文件；
- 允许任意 Python/SQL/表达式执行的通用自动化 SaaS；
- legacy Clean/RAG Dispatcher、SMCP callback 或 Cloudflare Worker 拓扑的本地复刻；
- Source/Document relation、Artifact、Vector、Event/Log 的替代真相表。

### 1.2 S03 必须完成的设计责任

| 责任平面 | S03 必须冻结的内容 |
|---|---|
| Workflow program | 声明式多平面 Source schema、capability/process registry、拓扑与 guard 语义、typed ports、模板/引用语言 |
| Internal registry governance | 内部 registration、严格 validation、immutable revision、active/disable/deprecate、审计与未来 agent adapter 接口 |
| Compiler | Source normalization、静态检查、capability/port binding、资源上下文与 I/O 渲染、compiled plan/command digest |
| Local process protocol | ProcessCommand/ProcessOutcome 的 identity、authority、resource、I/O、control、error、proof、observation 契约 |
| Runtime binding | Task intent/Execution context 到已发布 workflow revision 的选择、授权、immutable binding 与可复现性 |
| Execution control | root/child role、control status、RAG phase、current process、generation/tree summary |
| Process runtime | process key/instance、state、dependency、I/O/outcome guard、error classification |
| Scheduling/recovery | durable scheduling intent、claim/lease/fencing、retry/backoff/timeout，以及 Workflow 语义不变量与 deterministic recovery transition |
| Control propagation | Task cancel/retry intent 向 root/child/Process 传播，fan-out/fan-in 收敛 |
| Durability/cleanup | terminal summary、publication proof attachment、Process projection cleanup eligibility；物理 archive/delete 由 S12 实现 |

### 1.4 本轮不得重新提出的问题

1. 是否拆分 Task、Execution、Process；
2. 是否需要一个 Task 对多个 Execution；
3. scatter 是否首版支持，或是否需要 root + child Executions；
4. Task status 是否应加入 clean/structurize/vectorize；
5. 是否重新引入 Attempt 或为 automatic Process retry 创建新 Execution；
6. queue send/callback/log 是否可作为成功或状态 SSOT；
7. Task 成功是否需要 publication proof；
8. child 在 parent failed/cancelled 时是否保留已验证发布；
9. cancel 是否应隐式删除已发布知识；
10. 是否复制 D1/R2/SMCP/Worker/Dispatcher 的物理部署方式。

### 3.3 对 v0.1 扫描盲点的结论

1. **原 Q1 错在先问 DAG**：Workflow 的首要问题不是 linear 还是 DAG，而是它是否仍是包含资源、I/O、控制、结果和观测的声明式程序。拓扑只能在该宪法冻结后再问。
2. **原 Q2 错在对 agent 能力判断过度**：Legacy 只证明 AI tool 能修改 editor draft，没有形成完整 authoring/publish 治理。Owner 已裁决第一次重构不实现 agent 直接定义 Workflow，只把内部 registry/schema/interface 做到 future-agent-ready。
3. **原 Q3 错在跳到表格物化**：Process row 何时创建是 runtime 细节；更基础的边界是 Workflow 如何编译成一个 Process 可独立消费、可验证、可恢复的 command/outcome contract。
4. **不得复制的债务**：mutable workflow row、`steps:any[]`、多项目复制 SMCP、物理 R2/queue binding、control 信息后补进 `extra`、callback 直接驱动真相。

### Q1 — MKB Workflow Contract 是否应被定义为“多平面声明式程序”

- **影响范围**：`S03-S09/S12-S15`；Owner-Gate `G-03`。

- **本题只裁决**：端到端 Workflow Program 的规范性语义平面，以及 authored declaration 与 compiler-injected runtime fact 的分界；即什么必须进入可编程、可校验的 Workflow Contract。
- **本题不裁决**：linear/DAG/loop 的 exact topology、agent 是否能 publish、runtime 如何选择 revision、Process row 何时创建、状态与 retry 算法。
- **Codex 当前建议**：确认 `Workflow Program Contract = 可编写但受治理的 Workflow Source + compiler 注入的 runtime envelope`。整体是 **RAG-specific、多平面、声明式、无任意代码的业务程序**，至少强制包含以下六类 schema，而不是用自由 `payload/extra` 兜底。Source 只声明需求、规则与引用；Execution/Process/resource identity、实际 authority 和 correlation 等运行事实必须由 Engine 注入，定义方不得伪造：

  1. **Resource/context plane**：Source 声明步骤需要哪类 Source/Document/Version/Artifact/manifest/parent-child context 及允许读取的属性；Engine 注入 S04/S05 的实际逻辑身份或 immutable snapshot，不复制资源真相；
  2. **Authority/admission plane**：Source 声明 owner/scope/domain/purpose、所需 capability/权限与允许的调用上下文；Engine 注入并校验实际 author/publisher/invoker authority，所有 decision 可审计；
  3. **Process capability plane**：每个工序绑定 S03 注册的 RAG `process_key + contract_version`，声明 action/branch 或等价的受控 capability，不绑定 Worker、queue、DO、路径等部署细节；

  6. **Outcome/evidence/observation plane**：Source 声明 terminal guard、typed output/error/proof 要求；Engine 注入 workflow/process/revision/correlation identity 并保留 transition evidence；log/queue ACK 不得代替 outcome。

### Q2 — Agent authoring 与 Workflow revision 的治理边界

  2. 人与 agent 都通过同一组 schema-aware authoring tools 创建、replace/merge、解释和校验 draft；工具只能修改 draft，不能直接改 published revision 或 running Execution；
  3. 每次 validate 必须执行 schema、process capability、port/dataflow、reference、control-policy、reachability/terminal、authority/security 与 proof-path 检查，返回 machine-readable diagnostics；
  4. publish 必须是显式、具权限、带 expected revision/digest 的 control-plane command；可由 owner 发出，也可由拥有明确 delegated publish authority 的 agent 发出，但不能由普通聊天 tool loop 隐式完成；
  5. publish 只创建新 immutable revision；切换 active/default alias 或 rollback 只改变未来 binding，不能覆盖历史 revision，也不能改变已绑定 Execution；
  6. author/publisher/agent identity、输入 revision、变更 diff、validation report、publish reason 与时间必须进入 durable audit。

- **Reasoning**：agent programmability 是产品能力，不能因为 Task API 禁止 caller-defined graph 就被删除；真正需要禁止的是未经验证地修改运行态。Legacy 的 draft-tool + Save 分离证明了正确方向，MKB 应把这个 UI 级习惯提升为持久化的 admission/publish 状态机。
- **问题**：Owner 是否确认采用上述“agent 可编写和校验 draft；published revision 不可变；publish 必须显式授权；running Execution 永不被热改”的治理模型？特别请裁决：agent 是否允许在获得 delegated publish authority 后直接发起 publish command。
- **业主回答**：第一次重构不要求 agent 直接定义 Workflow；legacy-family 也没有深度实现该能力。S03 只需把内部 schema/interface 边界设计好，使未来可以接入 agent；agent authoring、validation tool loop、delegated publish 与 agent publish API 均为本轮 `out-of-scope`。
- **裁决状态**：`modified / v1 out-of-scope / frozen as T-O-13`

### Q3 — 是否建立本地版 SMCP 的 compiler + ProcessCommand/ProcessOutcome 强契约

- **影响范围**：`S03/S05-S09/S12-S15`；Owner-Gate `G-13`。
- **上游冻结输入**：`U-S03-02`、`U-S03-05`–`U-S03-09`、`U-S03-13`–`U-S03-14`。
- **Legacy 事实来源**：`LF-S03-01`–`LF-S03-07`、`LF-S03-11`–`LF-S03-12`。Legacy 的 mapper + SMCP + IoManager + callback 才真正完成 Process 解耦。
- **本题只裁决**：Published Workflow 如何编译成 Process 可独立消费的本地运行契约，以及 Process 与 Engine 的职责分界。
- **本题不裁决**：exact command intent enum、Process status、lease/fencing、retry counter、topology、全部 plan 是否预建、queue/outbox DDL。
- **Codex 当前建议**：建立 **集中版本化的 Workflow Compiler 与本地 `ProcessCommand / ProcessOutcome` 宪法**；不复制 SMCP 名称和跨 Worker transport，但继承其多平面 handshake：

  1. Compiler 输入固定为 `published workflow revision + process registry snapshot + immutable Execution/resource/config context`，输出可核验的 compiled plan、per-node contract 和 digest；Source 不得被 Process 直接解释执行；
  2. `ProcessCommand` 至少携带 Task/Execution/Process/correlation identity、workflow revision/node、process capability/contract version、authority/resource snapshot refs、typed I/O handles、business parameters、separate control instructions、deadline/priority 与 command schema version/digest；
  3. `ProcessOutcome` 必须回传相同 correlation 与 contract version，并包含受限 terminal outcome、typed output refs/hash、structured error、proof/evidence refs、control acknowledgement 与 timing；
  4. Process runner 只校验/消费自己的 command、访问自己的 typed ports、返回 outcome；它不能读取完整 Workflow 来找下一步，不能创建下游 Process，不能直接推进 Execution/Task，也不能自行选择物理存储路径；
  5. Workflow Engine 对 outcome 做 schema、fencing、output/proof guard 后，才在 durable transaction 中推进 Process/Execution 并产生下一 scheduling intent；queue/in-process call/function return 都只是 transport；
  6. 在首次 dispatch 前，至少 durable 保存或可确定性重建本次 compiled contract，并记录 revision/digest 与 resolved input snapshot；Process 被清理后，Execution terminal summary 仍能证明“执行了哪份程序、收到什么结果”；
  7. 本地 I/O 使用 S13 logical Artifact handle/adapter，替代 R2 binding/key；协议 schema 只有一份权威定义，禁止像 legacy 一样复制到每个 Process 实现。

- **Reasoning**：如果只把 Worker 改成本地函数并直接传 dict，Workflow 会重新耦合到函数签名、路径和下游调用，失去 legacy 最重要的竞争优势。集中 compiler + command/outcome contract 可以在单体内保留声明式可编程性、严格边界、恢复与审计，同时删除网络 callback 和 Cloudflare 平台负担。
- **问题**：Owner 是否确认 S03 需要上述本地 compiler + `ProcessCommand/ProcessOutcome` 强契约，并确认 Process 必须是“只消费本工序 command、只返回 outcome”的叶节点，所有编排/状态/下一步决策都归 Workflow Engine？
- **业主回答**：第一次重构采用内部注册制。Workflow 只由 MKB 内部创建和注册，不提供对外 create/update/delete；外部工具只能 list 已注册 Workflow，并获取由系统 compile 后的声明式 JSON 详情。Workflow 各控制平面的旋钮、状态、流程、路由等必须分解到关系型数据库表格，由固定 schema 严格校验和管理，不再以 legacy 的自由 JSON 作为 truth。Compiled JSON 是对外只读详情和后续执行载体的候选表示，但关系型 schema 才是 durable SSOT。原建议中的 exact `ProcessCommand/ProcessOutcome` runtime envelope 尚未被本回答直接裁决，必须由 Round 2 继续冻结。
- **裁决状态**：`modified / registry + relational truth frozen as T-O-14..16 / runtime envelope deferred to Q6`

## 7. Round 2 — Execution Schema & Runtime（Q4–Q6）

### Q4 — Workflow 关系型 SSOT 应拆成哪些职责表，JSON 的允许边界在哪里

- **影响范围**：`S03/S12/S14`；Owner-Gate `G-14`。
- **Truth-Gate 驱动**：`T-O-12`、`T-O-14`、`T-O-15`。
- **本题只裁决**：Workflow definition truth 的 normalized table responsibilities，以及任何 JSON/extension value 的允许边界。
- **本题不裁决**：route 是否允许 loop、compiled artifact 何时生成、Execution/Process status、claim/retry 与 exact Turso DDL type。
- **Codex 当前建议**：v1 采用以下 **七张 Workflow definition/control truth tables**；它们不属于 D01 的三张 runtime state tables，也不新增执行身份：

  1. `workflow_registry`：稳定 `workflow_key/uuid`、domain/purpose、read exposure、registry status、active revision pointer；
  2. `workflow_revisions`：immutable revision、schema version、digest、code/migration provenance、registration/activation evidence；
  3. `workflow_steps`：稳定 step key、RAG `process_key`、process contract version、required/optional 与展示顺序；
  4. `workflow_routes`：from/to step、outcome selector、route priority、join/fan-in mode 与 guard ref；
  5. `workflow_bindings`：resource/context/input/output/parameter 的 typed binding、source selector、target port、requiredness；
  6. `workflow_controls`：workflow/step/route scope 下的 timeout、max-retries、backoff、cancel、purge、case、fan-out/fan-in 等固定控制列；
  7. `workflow_guards`：typed predicate、allowed operand/ref、route/terminal/proof guard 与 failure code。

  核心 identity、status、route、binding、control、guard 不允许 opaque JSON。Process-specific 扩展值若首版确有需要，应通过 `contract_version + value_type + typed scalar/ref columns` 严格保存和校验；JSON 只允许出现在可重建的 compiled representation、只读 API envelope 或非权威 diagnostic 中。

- **Reasoning**：这组拆分使六平面都有明确 FK、unique/check 与版本边界，同时避免为每个 RAG Process 复制一套 Workflow 表。将所有 knob 塞回一个 `config_json` 会直接违反 `T-O-15`；完全禁止任何派生 JSON 又会失去声明式 read/runtime representation。
- **问题**：Owner 是否确认以上七表职责和“core truth 无 opaque JSON、compiled JSON 仅派生”的边界？若表格需要合并或继续拆分，请明确指出哪一类约束仍必须由数据库 schema 而不是 application-only validation 承担。
- **业主回答**：支持 Codex 的七表路径，并要求将其冻结为以下更明确的责任模型。字段名可在 S12 exact DDL 中按驱动限制微调，但表职责、所有权、可变性和约束语义不得改变。

  | 表 | 身份与核心列族 | 可变性与主要约束 | 明确禁止承载 |
  |---|---|---|---|
  | `workflow_registry` | `workflow_uuid`（UUIDv7 PK）、稳定唯一 `workflow_key`、domain/purpose/role、read exposure、`registry_status`、`active_revision_uuid` | 只允许内部 registration/activation path 修改；`workflow_key` 不复用；active revision 必须属于同一 Workflow 且已通过完整校验 | step/route/control JSON、运行状态、Task/Execution/Process payload |
  | `workflow_revisions` | `workflow_revision_uuid`（UUIDv7 PK）、`workflow_uuid` FK、单调 `revision_number`、`schema_version`、registration/code provenance、canonical/compiled digest、registered time | `(workflow_uuid, revision_number)` 唯一；一经激活内容 immutable；新变化只能新建 revision；被 Execution 引用的 revision 不得物理删除 | mutable active flag 的第二真相、完整 compiled JSON SSOT、运行进度 |
  | `workflow_steps` | `workflow_step_uuid`、revision FK、revision 内唯一 `step_key`、`step_kind`、RAG `process_key`、`process_contract_version`、phase、requiredness、display/order hint | `process_key` 只对 process step 必填；control/terminal 使用固定 step kind；不得跨 revision 复用 row | Process instance status、claim/lease/retry counter、业务算法实现 |
  | `workflow_routes` | `workflow_route_uuid`、revision FK、`from_step_uuid/to_step_uuid`、outcome selector、priority、join/fan-in mode、guard group ref | 两端 step 必须属于同一 revision；route identity/priority 在 revision 内唯一；可达性、无环和 terminal coverage 由 registration compiler 强制验证 | retry loop、cancel state、scatter child identity、自由表达式 |
  | `workflow_bindings` | `workflow_binding_uuid`、revision/step FK、binding kind（context/input/output/parameter）、slot name、value/data type、source kind、source step/port/ref、requiredness、typed literal/ref value | `(step, binding_kind, slot_name)` 唯一；source step 必须同 revision；value type 与 process contract port 必须匹配；typed value 只能命中一个允许列 | 物理文件路径、secret、未校验 JSON、Artifact 正文 |
  | `workflow_controls` | `workflow_control_uuid`、revision FK、可选 step/route FK、scope type，以及 timeout、max-retries、backoff、cancel、purge、case、concurrency/fan-out limit 等固定控制列 | scope 必须且只能指向 revision/step/route 中一个合法层级；step/route 必须同 revision；数值范围和 enum 用 DB check + registration validation 双围栏 | 当前 retry_count、lease、deadline runtime state、任意 control JSON |
  | `workflow_guards` | `workflow_guard_uuid`、revision FK、route/terminal/proof scope、group/order、predicate type、operand kind/ref、operator、typed expected value、failure code | 仅允许注册的 predicate/operator/operand；同一 guard group 只支持固定 all/any 组合，不支持任意嵌套代码；引用必须可静态解析 | Python/SQL/自由表达式、业务算法、运行时 outcome 大对象 |

  七表共同遵守以下围栏：

  1. 所有 definition child row 都显式归属一个 immutable revision；跨表 FK/unique/check 必须阻止跨 revision wiring；
  2. `workflow_registry.active_revision_uuid` 是激活指针 SSOT，revision 表不再保存相互冲突的 `is_active`；
  3. active revision 不做原地 UPDATE；registration/activation 使用新 revision + guarded pointer switch；
  4. core identity/status/route/binding/control/guard 不使用 opaque JSON；process-specific 扩展值只能按 `process_key + contract_version + value_type` 落入 typed scalar/ref；
  5. compiled JSON/cache、registration diagnostic 与 read API envelope 不计入第八张 Workflow truth table，均可由七表重建；
  6. `tasks/executions/processes` 仍是 D01 runtime truth；七张 Workflow 表不得保存一次运行的 UUID、claim、retry 或 outcome；
  7. exact Turso column type、migration ordering、deferred FK 技巧和 transaction implementation 交由 S12，但不得改变上述责任模型。

- **裁决状态**：`accepted with detailed table contract / frozen as T-O-17..18`

### Q5 — Workflow route/control 应采用什么可执行图语义

- **影响范围**：`S03/S05-S09/S12`；Owner-Gate `G-15`。
- **Truth-Gate 驱动**：`T-O-12`、`T-O-15`；继承 `U-S03-04`–`U-S03-08`、`U-S03-10`–`U-S03-12`。
- **本题只裁决**：关系型 `workflow_steps/routes/controls/guards` 首版允许表达的控制流、路由与 guard 边界。
- **本题不裁决**：表名/列型、registration transaction、Process command envelope、lease/retry backoff 算法或 scatter manifest 的资源 DDL。
- **Codex 当前建议**：v1 使用 **严格、可静态校验的 RAG 有向无环 route graph**：

  1. 每个 revision 只有一个显式 start，并有一个或多个 typed terminal；所有 required step 必须从 start 可达并能到达 terminal；
  2. route 只由固定 outcome selector 与 allowlisted guard type 触发，例如 success/failure/skipped、resource capability、manifest/diff decision、case mode、validated Process output；禁止任意脚本、SQL 或自由表达式；
  3. 允许受控 branch、同一 Execution 内的 Process fan-out/fan-in、required/optional predecessor 与 deterministic route priority；join 的 expected set 必须在调度前 durable 确定；
  4. API scatter 仍按 D01/S02 建模为 root controller + child Executions。Workflow 可以声明 `scatter manifest → spawn children → fan-in` 控制节点/阶段，但 child Execution 不能降级成普通 step row；
  5. automatic retry、lease recovery 与 cancel convergence 是 Engine control transition，不通过 graph self-loop/任意回边表达；purge/compensation 可以是 typed control instruction 或显式 step，但仍不得制造任意回边；v1 business routes 禁止 loop/recursion；
  6. standard path 仍清楚表达 clean/resolve → structurize → construct → vectorize/index → publication validate，同时允许经过严格 guard 的 skip、metadata-only、purge、fallback/failure terminal。

- **Reasoning**：legacy runtime 实际按 rank 线性推进，visual editor 虽能画图却把 graph 再线性化；MKB 需要让 route 成为真实可执行 truth。DAG 足以覆盖 LS-RAG 的已知 branch/fan-in，而 retry/cancel 的循环由状态机管理，避免 graph 与 Process retry 双重真相。
- **问题**：Owner 是否确认 v1 采用上述“typed、guarded、acyclic RAG route graph”，并把 retry、lease recovery、cancel convergence 等循环行为留给 Engine control state machine？如果 owner 认为 v1 必须支持业务 loop，请明确 loop 的真实 LS-RAG 用例和终止证明要求。
- **业主回答**：支持 Codex 的 typed、guarded、acyclic RAG route graph；v1 不支持业务 loop/recursion。Owner 同时要求将职责 cutoff 固定如下，保证 Q5 不借 route/control 扩张 S03 scope。

  | 能力/真相 | S03 在本题内拥有 | S03 明确不拥有 / 权威下游 |
  |---|---|---|
  | Graph structure | start/terminal、step/route identity、acyclic/reachability/terminal coverage、deterministic priority | 具体 RAG 内容 schema 与算法（S06-S09） |
  | Guard language | predicate/operator/operand allowlist、静态类型检查、guard evaluation 与 route decision evidence | `manifest/diff/resource capability` 的业务值和计算（S04-S05）；S03 只读取 immutable decision/ref |
  | Process fan-out/fan-in | 同一 Execution 内 eligible Process 的 dependency、required/optional predecessor、expected set、join readiness 与 route progression | API scatter 的 canonical child set、Document relation、manifest revision（S04-S05） |
  | Scatter orchestration | 根据已提交 manifest ref 创建 child Executions、传播 control、读取 child terminal summary、collect-all fan-in | child Document identity/content/hash/diff truth（S04-S05）；Task aggregate/public items（S02） |
  | Retry/recovery/cancel | 解释 Workflow control policy并推进 Execution/Process control state；不以 graph loop 表达 | 外部 cancel/retry command admission/CAS（S02）；exact transaction/queue driver（S12） |
  | Purge/compensation | 表达 typed control instruction/step、安排依赖与验证其 outcome contract | 实际知识/向量删除规则与 proof 算法（S04/S08-S09） |
  | I/O route | 校验 logical port compatibility、binding reference 与 outcome-to-input wiring | Artifact backend/path/atomic write（S13）；具体 Process output schema（S05-S09） |
  | Model/prompt/config refs | route/step 只绑定 immutable logical ref/version/digest | 内容、fallback、registry policy（S11/S14） |
  | Route observation | 必须产生 decision/transition evidence 与 correlation requirement | event/log/metric envelope、retention、告警（S15） |
  | Persistence | 声明必须成立的 FK/unique/check、atomicity 与 durable-before-wakeup 语义 | exact Turso DDL/driver/migration/transaction adapter（S12） |

  因此，S03 只负责“用已冻结的外部业务事实选择哪条 route、何时可推进、如何归约 Execution/Process”；它不负责生成这些业务事实，也不成为 Source/Document/Artifact/Vector/Model/Event 的第二真相层。

- **裁决状态**：`accepted with S03 cutoff / frozen as T-O-19`

### Q6 — Compiled JSON 如何绑定 Execution，并继续保持 Process 解耦

- **影响范围**：`S03/S05-S09/S12-S15`；Owner-Gate `G-16`。
- **Truth-Gate 驱动**：`T-O-12`–`T-O-16`；继承 `U-S03-02`、`U-S03-05`–`U-S03-09`、`U-S03-13`。
- **本题只裁决**：内部 registration → validation/compile → Execution immutable binding → per-Process dispatch/outcome 的端到端边界。
- **本题不裁决**：exact Process status enum、claim/lease token、retry/backoff 数值、queue implementation、compiled JSON 的 HTTP 字段命名。
- **Codex 当前建议**：采用以下 deterministic pipeline：

  1. Workflow 只通过 MKB code/migration/bootstrap 的内部 `register` path 写入；registration 在单一事务或 S12 证明等价的边界内写 normalized revision、执行跨表静态校验并产生 canonical compiled JSON/digest，校验失败不得激活；
  2. revision 一经激活不可修改；新变化创建新 revision。active/disabled/superseded 只影响未来选择，已创建 Execution 不热切换；
  3. compiled JSON 至少包含 schema version、workflow key/revision/digest、steps、routes、bindings、controls、guards 与 process contract refs，不包含 Task/Execution/Process UUID、实际 authority、物理文件路径或 secret；
  4. MKB resolver 在创建 Execution 时选择一个 active revision，并把 `workflow_revision + compiled_digest` durable 绑定到 Execution；retry/recovery 继续读取同一 binding；
  5. Workflow Engine 解释 compiled plan，只在 step eligible 时创建 Process，并在 wake-up 前 durable 保存 Process row、resolved input snapshot/ref、control snapshot 与 command digest；compiled JSON 不整包交给 Process 自行找路；
  6. Process 只消费集中 schema 定义的本地 `ProcessCommand`，只返回 `ProcessOutcome`。Command/Outcome 保留 SMCP 的 identity、authority/resource、typed I/O、separate control、structured error/proof、correlation 语义；Process 不创建下一步、不推进 Execution/Task、不选择物理存储；
  7. Engine 对 Outcome 做 contract/digest、fencing、typed output、proof guard 后，在 durable transition 中推进 Process/Execution 并产生下一 scheduling intent；in-process call/local queue 只是 transport；
  8. 对外 list/get 只读取 registry 与 canonical compiled view；compiled cache 丢失时从关系型 SSOT 重建，digest 不一致时 fail loud。

- **Reasoning**：`T-O-15/T-O-16` 只解决“Workflow 真相在哪里”，还没有解决“Process 如何不重新耦合到完整 Workflow”。该 pipeline 将 JSON 限定为 immutable compiled plan，把运行事实放入 Execution/Process，并通过 command/outcome 恢复 legacy SMCP 的解耦优势而不复制网络协议拓扑。
- **问题**：Owner 是否确认以上 registration/compile/binding/runtime pipeline，尤其确认 compiled JSON 由 Engine 解释、Process 只接收本工序 `ProcessCommand` 并返回 `ProcessOutcome`？
- **业主回答**：支持 Codex 推荐的完整 pipeline。内部 registration 必须跨七表校验后才能激活 revision；canonical compiled JSON/digest 是可重建派生物；Execution 创建时 durable 绑定 exact revision/digest，之后不得热切换；Engine 解释 route 并按 eligibility 创建 Process；Process 只接收本工序 `ProcessCommand`、只返回 `ProcessOutcome`。所有 command/input/control snapshot 或可验证 digest 必须在 wake-up 前 durable，Outcome 经 contract、fencing、typed output 与 proof guard 后才允许推进状态。外部仍只有 list/get compiled detail，不能借 compiled JSON 形成反向写面。
- **裁决状态**：`accepted / frozen as T-O-20..21`

### Q7 — Process exact state、claim/lease/fencing 与 automatic retry 如何统一

- **影响范围**：`S03/S12/S15`；Owner-Gate `G-17`。
- **Truth-Gate 驱动**：`T-O-17`–`T-O-21`；继承 `U-S03-05`–`U-S03-09`、`U-S03-13`–`U-S03-15` 与 `D01-T018/T024/T027/T036`。

#### Q7 Internal Reference-Anchor

#### Q7 推荐执行（legacy 原理 → MKB 全局升级）

```text
ready
  → claimed
  → running
     ├── succeeded
     ├── retry_wait → ready
     ├── failed
     └── cancelling → cancelled

claimed/running -- lease expired + fenced recovery --> ready | failed
ready/claimed/running/retry_wait -- cancel intent --> cancelling → cancelled
```

1. Process 只在 Workflow step 已 eligible 时创建；`ready` 表示 scheduling intent 已 durable，不表示 dependency waiting。未命中 route 不创建 Process，只保存 route decision evidence。
2. `ready → claimed` 是 DB atomic CAS，生成 claim token、递增 fencing generation，并写 lease owner/expiry；只有 current fence 可进入 running、heartbeat 或提交 Outcome。
3. heartbeat 只能延长 current lease。旧 token/generation、late Outcome 一律 stale reject；同一已接受 Outcome 重放为 idempotent no-op。
4. queue redelivery 只增加 delivery diagnostics；lease expiry/fenced recovery 增加 `recovery_count`；二者都不消耗业务 `retry_count`。
5. 只有 current-fenced 业务运行返回 retryable failure，才 `running → retry_wait`、`retry_count + 1` 并写 `next_retry_at`；达到 `max_retries` 或 non-retryable error 直接 failed。
6. `retry_wait → ready` 保持同一 `process_uuid`；下一次 claim 获得新 fencing generation；不得引入 Attempt 表。
7. cancel intent 阻止新 claim/materialization；running work 的 late commit 被 fence，待停止或受控补偿完成后才 cancelled。
8. `succeeded` 必须同时满足 current fence、ProcessOutcome contract、typed output/hash 与 type-specific proof guard；函数返回或 transport ACK 不构成成功。

- **辨证结论**：legacy 已证明“durable process row + outcome-driven next step + same-process retry/max-retries”有效；它没有证明 `pending` 足够，也没有 claim/lease/fencing。Q7 的推荐是用统一 Process 状态机消除两个 dispatcher 各自 hotfix 后仍存在的重复、晚到提交和状态漂移窗口。
- **问题**：Owner 是否确认以上 Process 状态机及 claim/lease/fencing/recovery/retry 分账？特别请裁决：未命中的 route step 是否按建议“不创建 Process，只保存 route decision evidence”。
- **业主回答**：同意 Q7 经双 Dispatcher reference-anchor 校准后的完整推荐执行方案，并冻结以下综合口径：

  1. Process exact states 使用 `ready/claimed/running/retry_wait/succeeded/failed/cancelling/cancelled`；dependency waiting 不进入 Process enum；
  2. Process 仅在 route step 已 eligible 时创建。未命中 route 不创建 Process，route/skip decision 必须进入 durable evidence/Execution summary；
  3. `ready→claimed` 必须 atomic CAS；claim token、lease owner/expiry、fencing generation 共同决定唯一合法 runner；heartbeat、running transition 与 Outcome 均只接受 current fence；
  4. stale/late Outcome 必须拒绝，同一已接受 Outcome 重放必须 no-op；queue ACK、函数返回或 delivery 不等于业务成功；
  5. delivery diagnostics、`recovery_count` 与 `retry_count` 分离。只有 retryable business failure 才消耗 retry budget；automatic retry 保持原 `process_uuid`，不得创建 Attempt；
  6. `max_retries`、non-retryable error、type-specific guard failure 决定 failed；cancel intent 阻止新 claim/materialization 并 fence late commit；
  7. MKB 继承 legacy 的 durable Process、Outcome-driven progression 与 same-process retry 原理，但 claim/lease/fencing、统一状态机和可重建 scheduling intent 是本轮 MKB 全局升级，不伪装成 legacy 既有能力。

- **裁决状态**：`accepted / frozen as T-O-22..24`

- **Truth-Gate 驱动**：`T-O-19`–`T-O-21`；继承 `U-S03-03`–`U-S03-05`、`U-S03-10`–`U-S03-13` 以及 S02 collect-all/early-publication/no-rollback truth。

#### Q8 推荐执行（legacy 双 Dispatcher → MKB 单一 Execution Engine）

```text
created → ready → running ↔ waiting
                      │        │
                      ├────────┴──→ succeeded
                      ├───────────→ failed
                      └→ cancelling → cancelled
```

1. `created`：Execution identity 已 durable，但 revision/resource binding 尚未完整；Q6 binding、initial route decision 与首个 scheduling intent 完整后进入 ready。
2. `ready`：至少一个初始 Process 已 durable 可调度；首个 Process claimed/running 后进入 running。
3. `waiting`：没有立即可运行 Process，但有明确 durable wait reason，例如 retry due time、同一 Execution join、scatter children 或受控 durable prerequisite；不能用 waiting 掩盖无触发源的卡死。
4. `running ↔ waiting` 可多次发生；不增加 generic `retrying` Execution status，原因由 waiting reason + Process/child summary 表达。
5. RAG phase 独立采用 `resolving_source / cleaning / scattering / structurizing / constructing / vectorizing_indexing / validating_publication / fan_in` 等受注册值，并由 route/active Process 集合归约；不能扩入 Task status。
6. single Execution 只有在全部 required route terminals、Process guards 与 publication proof 满足后 succeeded；required path 出现 non-retryable failure 或 automatic retry budget 耗尽则 failed。
7. scatter root 先绑定已提交 manifest expected set，再幂等创建/wake children，并进入 waiting/fan_in；healthy child 不因 sibling failure 停止。全部 required child terminal 后 collect-all：存在 required failure 则 root failed，否则按 proof/cancel policy 终结。
8. cancel 自上而下阻止新 route/materialization，传播到 Processes/children 并 fence late commit；descendants 全部 terminal/安全停止后 Execution 才 cancelled；proof-valid child 不隐式 rollback。
9. Execution 终态写 durable route/process/child counts、phase history、retry/recovery totals、final error、artifact/vector/proof 与 workflow revision/digest summary，再由 Task 自下而上归约。
10. 并行时 active Process set 以 `processes` 查询/summary 为真。D01 要求的 `current_process_uuid` 只能是 nullable focus/last pointer，不能冒充并发集合 SSOT。

- **辨证结论**：Q8 不是把 generic Execution 状态套在 RAG 上；它把 legacy 中分散于 Clean file status、RAG file/relation status、job UUID 和 callback 的控制事实，升级为一个 durable Execution control plane，同时保留独立、可观测的 RAG phase。
- **问题**：Owner 是否确认上述 Execution control status、独立 RAG phase 与 single/scatter/cancel 收敛规则？特别请裁决并行场景下 `current_process_uuid` 仅作为非权威 focus pointer。
- **业主回答**：同意 Q8 经 Clean/RAG 生命周期与 scatter 流转对照后的完整推荐执行方案，并冻结以下综合口径：

  1. Execution exact control states 使用 `created/ready/running/waiting/succeeded/failed/cancelling/cancelled`；`waiting` 必须有 durable wait reason/trigger，不能遮蔽 stranded run；
  2. RAG phase 与 control status 分列，至少能表达 source resolution、cleaning/scattering、structurizing、constructing、vectorizing/indexing、publication validation 与 fan-in；phase 不进入 Task enum；
  3. single 的同一 document Execution 贯穿 clean→LS-RAG→publication，不再在 Clean/RAG 边界重生 job/execution identity；
  4. scatter root 绑定 committed manifest revision/expected set，幂等创建 child Executions；root 使用 collect-all，healthy child 不因 sibling failure 被 fail-fast 停止；
  5. child proof-valid 后可早发布；parent failed/cancelled 不隐式回滚。cancel 只 forward-stop 未完成工作，并在 descendants terminal/fenced 后收敛；
  6. Execution succeeded/failed/cancelled 必须由 required Process/child terminal、guard/proof 与 automatic retry budget 归约，不得由某个 worker/Process 直写；
  7. terminal Execution 必须保存可长期查询的完整 summary；`current_process_uuid` 仅为 nullable focus/last pointer，active set 以 `processes`/summary 为真。

- **裁决状态**：`accepted / frozen as T-O-25..27`

#### Q9 事实裁决：原问题有哪些无依据扩充

1. **Legacy 没有完整通用 reconciler 的证据。** 两个 restarter 都实现了 stuck-pending detector/compensating failure，但 dispatcher 入口没有调用或周期调度它们。能证明的是“生产代码已认识到 pending 会卡死”，不能证明“legacy 已有闭环自动 reconciliation”。
2. **Legacy 没有 Process compaction 的证据。** 没有发现 `smind_clean_process/smind_rag_process` 的 summary-before-delete/归档实现。RAG `purge` 清理的是 vector/knowledge business data，不是 Process history。
3. **原 Q9 把 operator command 与 Workflow revision retention 挂在同一题，违反高内聚。** 两者已从 Q9 删除：revision lifecycle 回到 Q4 的 registry governance；v1 operator 写面不由 S03 QNA 自动扩充。
4. **“compaction”一词容易误导成数据压缩。** 本文改称 **Process projection cleanup**：先把必要摘要上卷 Execution，再判断 Process row 是否可 archive/delete；S03 不做压缩算法。

| `T-R-S03-Q9-02` | callback 是 `mark current terminal → create/send next`，不是一个跨 DB/transport 原子事务。 | crash 可留下前序 succeeded、Execution nonterminal、却没有后继 Process 的 stranded run。 |

#### Q9 必要性证明

S03 已被 Q1–Q6 冻结为唯一解释 compiled Workflow、route guard、ProcessOutcome、Execution tree 与 fan-in 的 Engine。因此对任意 nonterminal Execution，系统必须持续满足以下至少一个条件：

```text
存在可 claim/due 的 durable Process
  OR 存在带明确触发条件的 durable waiting reason
  OR 存在 current-fenced active lease
  OR 正在 cancelling 且仍有明确 descendants 待收敛
```

若四者皆不成立，该 Execution 已经违反 Workflow 进展不变量。Queue 只能看见消息，S12 只能看见行和事务，S15 只能看见事件；只有 S03 掌握“按绑定 revision 本应出现哪个 Process、哪个 join 已满足、root 是否可归约”的业务语义。因此：

- **S03 必须定义** invariant、异常分类与 deterministic/idempotent repair transition；
- **S12 必须实现** transaction/outbox、启动/周期扫描、wake-up 与物理 cleanup；
- **S15 必须记录** repair decision/event/metric/alert；
- 不强制存在一个名为 `Reconciler` 的独立服务、表或进程。它可以是 Workflow Engine 的 startup/periodic recovery pass；
- transactional outbox 只能关闭“DB commit 后漏投递”，不能独自解决 lease expiry、terminal→next 断点、partial fan-out、fan-in/cancel convergence，因此不能替代 semantic recovery。

#### Q9 推荐执行与 cutoff

1. S03 冻结最小 repair matrix：ready 漏 wake、due `retry_wait`、expired lease、terminal Process 未推进 route、manifest 下缺失 child、waiting join/fan-in 可归约、cancelling descendants 未收敛、terminal Execution summary/pointer 未收口。
2. repair 只能复用 Q7/Q8 的合法 transition，并使用 revision/fencing/uniqueness CAS；重复扫描必须 no-op，不能重复创建 Process/child Execution 或重复业务提交。
3. workflow revision/digest 缺失、proof 与 terminal 冲突、无法验证的业务 output 不自动“修好”，而是 fail loud/quarantine 并产生 evidence；recovery 不能猜 route 或伪造成功。
4. Process cleanup eligibility 只在 `Execution terminal + summary complete + retry/recovery/cancel/compensation/outbox/lease 全关闭 + no dangling pointer` 时成立；这条 predicate 属 S03，因为它依赖 Workflow terminal semantics。
5. archive/delete SQL、批次、retention 时长与 scheduler 属 S12；Event/Log retention 属 S15。S03 v1 不新增 operator 写 API，人工 full/atomic restart 仍走 S02 的因果链。

- **辨证 Verdict**：**Q9 有必要，但原 Q9 的命名和范围不成立。** 必要的是 S03 定义“如何识别并修复 Workflow 语义断点”以及“何时允许清理 Process projection”；不必要的是声称 legacy 已有通用 reconciler、在 S03 内建设独立 daemon、把 cleanup 称为压缩，或顺带扩张 operator/revision 治理。
- **反方条件**：若删除 Q9，必须改为证明所有 Process state、queue wake、leaf side effect、route advance、scatter fan-out/fan-in 能在一个原子提交中完成。现有 local queue + 外部 I/O/向量写入不具备该原子边界，且 legacy 两个 dispatcher 已给出相反证据；因此首版不能安全删除 semantic recovery invariant。
- **问题**：Owner 是否接受缩限后的 Q9：S03 只冻结 semantic recovery invariant/repair transition 与 Process cleanup eligibility；具体 scanner/outbox/delete 归 S12，观测归 S15，且 v1 不新增 S03 operator 写面？
- **业主回答**：同意缩限后的 Q9 及推荐执行方案，并冻结以下综合口径：

  1. legacy 只有 stuck-pending detector/compensating failure 的未接通代码能力，没有完整通用 reconciler；legacy 也没有 Process compaction 实现。两者不得被倒写为生产事实；
  2. S03 必须定义 nonterminal Execution progress invariant、异常分类与 deterministic/idempotent repair transition；这属于 Workflow 语义所有权，而不要求独立 `Reconciler` 服务、表或公开 API；
  3. 最小 repair matrix 必须覆盖 ready 漏 wake、due retry、expired lease、terminal Process 未推进 route、manifest 下缺 child、join/fan-in 可归约、cancel descendants 未收敛以及 terminal summary/pointer 未收口；
  4. 所有 repair 复用 Q7/Q8 合法 transition、revision/fencing/uniqueness CAS；重复扫描 no-op。无法校验的 revision、route、output 或 proof 必须 fail loud/quarantine，不能猜测或伪造成功；
  5. S03 定义 repair semantics 与 Process cleanup eligibility；S12 实现 scanner、transaction/outbox、wake-up、archive/delete；S15 负责 evidence、metric、alert 与 Event/Log retention；
  6. Process projection 只有在 Execution terminal、summary 完整、retry/recovery/cancel/compensation/outbox/lease 全关闭且无 dangling pointer 后才可清理；cleanup 不是“压缩”；
  7. v1 不新增 S03 operator 写面。外部 full/atomic restart 继续只走 S02 durable causal/admission boundary；Workflow revision lifecycle 留在 Q4 registry governance。

- **裁决状态**：`accepted / scope-corrected / frozen as T-O-28..29`

### 10.1 裁决汇总

| 问题 | Owner 裁决 | 冻结落点 | 结果 |
|---|---|---|---|

### 10.2 三轮形成的完整真相骨架

```text
七张 normalized Workflow definition/control tables（SSOT）
  → internal registration + static validation
  → immutable revision activation
  → canonical compiled JSON/digest（derived）
  → Execution binds exact revision/digest
  → Engine evaluates typed guarded acyclic routes
  → eligible step materializes Process(ready)
  → durable command/input/control + scheduling intent
  → atomic claim + lease/fencing
  → leaf consumes ProcessCommand / returns ProcessOutcome
  → contract + fence + output + proof validation
  → Process transition / automatic retry / terminal
  → route advance / same-Execution fan-in / scatter child convergence
  → Execution terminal durable summary
  → Task aggregate projection
  → semantic recovery maintains invariants
  → eligible Process projections may be cleaned after all fences close
```

这个结构同时锁定：

1. Workflow 保持声明式、可编程、future-agent-ready，但 v1 不开放 authoring/CUD；
2. 关系型七表是定义真相，compiled JSON 是派生；D01 三表是运行真相，两类表不重叠；
3. Process 保持 leaf 边界，不知道 route/Task/物理存储；Engine 是唯一编排者；
4. single/scatter 使用同一 Execution/Process engine；差异只在 root role、manifest 和 child tree；
5. queue、in-process call、callback、日志都不是成功或状态 SSOT；
6. recovery 是 Workflow 语义不变量，不是复制 legacy 的独立 Dispatcher/Reconciler 拓扑；
7. Process 可清理，但 Execution summary、Task aggregate、Audit/restart lineage 和 Event/Log retention 不因此失真。

### 10.3 诚实反方制衡

- 七张定义表增加 registration/compiler 复杂度，但这是消除 mutable JSON 与控制平面漂移的必要成本；不得为了少表退回单列 JSON。
- claim/lease/fencing 增加 runtime 列与 CAS 路径，但没有它们就无法在本地 queue redelivery、worker crash 与 late Outcome 下保证唯一提交。
- `waiting` 若没有 strict reason/trigger 会变成新的 generic pending；实现必须通过 invariant query 将 stranded Execution 识别为故障。
- semantic recovery 若直接写任意 status 会成为第二套 Engine；它只能调用同一 transition service。
- cleanup 若在 summary/proof/outbox/lease 尚未闭合时执行会破坏追溯；S12 必须把资格 predicate 当 hard precondition，而非运营建议。

### 10.4 Final Verdict

S03 Q1–Q9 已全部完成 owner-gate，`T-O-12..29` 构成完整且连续的 S03 QNA 真相层。不存在需要第四轮继续提问的开放架构分母；后续 exact DDL、业务 schema、Artifact/Vector proof、event envelope 与 retention 数值按已冻结 cutoff 交给 S05-S09/S12-S15，不得反向改变本 Campaign。
