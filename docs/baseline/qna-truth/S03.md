## 1. S03 重新校准后的 Scope

### 1.1 S03 的唯一定位

S03 是 **MKB 单体内部唯一 durable LS-RAG Workflow Engine**。它从已提交的 Task scheduling intent 开始，选择并绑定 MKB-owned Workflow Definition，创建/推进 Execution tree 与 RAG-specific Processes，最后将 outcome、error、counts 和 completion proof 自下而上归约。

S03 不是：

- 外部 Task API 或第二套 Task 状态机；
- 任意业务都可上传脚本和 DAG 的通用 workflow SaaS；
- queue consumer 的薄封装；
- legacy Clean/RAG Dispatcher、SMCP callback 或 Cloudflare Worker 拓扑的本地复刻；
- Source/Document relation、Artifact、Vector、Event/Log 的替代真相表。

### 1.2 S03 必须完成的设计责任

| 责任平面 | S03 必须冻结的内容 |
|---|---|
| Workflow definition | RAG-specific definition schema、node/edge/guard/I/O contract、版本与校验 |
| Binding | request intent/target 到 workflow revision 的 resolver、immutable snapshot/ref/digest |
| Execution control | root/child role、control status、RAG phase、current process、generation/tree summary |
| Process runtime | process key/instance、state、dependency、I/O/outcome guard、error classification |
| Scheduling | durable scheduling intent、eligible materialization、priority/deadline mapping、execution lane |
| Concurrency | claim、lease、heartbeat、fencing、late/stale completion rejection |
| Recovery | queue redelivery、lease recovery、automatic retry/backoff/max-retries、timeout、replay、reconciliation |
| Control propagation | Task cancel/retry intent 向 root/child/Process 传播，fan-out/fan-in 收敛 |
| Durability/cleanup | terminal summary、publication proof attachment、Process compaction fence |

### 1.3 S03 明确不拥有的真相

| 不属于 S03 | 权威归属 | S03 只能引用什么 |
|---|---|---|
| Task HTTP、六态、revision CAS、full/atomic restart public semantics | `S02` | Task command 与 current generation；向上发布 aggregate outcome |
| Source/Document/Version/manifest 的长期资源身份和 diff 业务真相 | `S04-S05` | target/ref、manifest revision、required set 与 resource command |
| Structurizer/Constructor schema、embedding/index 算法与 proof 内容 | `S06-S09` | process contract、type-specific validator 与 proof ref |
| Model/prompt 的具体内容、fallback 与 registry policy | `S11/S14` | immutable version/digest/capability refs |
| Turso exact DDL、transaction driver 和 local queue 选型 | `S12` | 需要被实现的原子性、唯一性和 wake-up 语义 |
| Artifact backend/path layout | `S13` | logical Artifact ref、schema/hash |
| Event/Log/Trace envelope 与 retention 数值 | `S15` | transition 必须产生的 evidence/correlation 语义 |

### 1.4 本轮不得重新提出的问题

1. 是否拆分 Task、Execution、Process；
2. 是否需要一个 Task 对多个 Execution；
3. scatter 是否首版支持，或是否需要 root + child Executions；
4. Task status 是否应加入 clean/structurize/vectorize；
5. 是否重新引入 Attempt 或为 automatic Process retry 创建新 Execution；
6. queue send/callback/log 是否可作为成功或状态 SSOT；
7. Task 成功是否需要 publication proof；
8. child 在 parent failed/cancelled 时是否保留已验证发布；
9. cancel 是否应隐式删除已发布知识；
10. 是否复制 D1/R2/SMCP/Worker/Dispatcher 拓扑。

## 5. Round 1 — Workflow Foundation（Q1–Q3）

> 本轮只裁决 Workflow 的定义形态、绑定权和实例化边界。Execution/Process exact status、claim/lease/fencing、retry/backoff、并发 lane 与 reconciler 算法留待 owner 回答后的 Round 2/3。

### Q1 — Workflow Definition 的表达能力边界

- **影响范围**：`S03/S05-S09/S12/S14`；Owner-Gate `G-03`。
- **上游冻结输入**：`U-S03-04`、`U-S03-06`、`U-S03-07`、`U-S03-14`。
- **Legacy 事实来源**：`LF-S03-01`、`LF-S03-02`、`LF-S03-03`。Legacy 的生产主链是 rank-sorted linear pipeline；它证明 typed step/dataflow 的价值，但没有证明 MKB 需要任意动态 DAG。
- **本题只裁决**：MKB Workflow Definition 首版允许表达到什么 topology 边界。
- **本题不裁决**：谁选择 workflow、版本如何绑定、Process 何时创建、state enum、lease/retry、具体 Structurizer/Constructor schema。
- **Codex 当前建议**：采用 **MKB-owned、版本化、RAG-specific 的受限有向无环 blueprint**：

  1. node 只能引用 S03 注册的 RAG-specific `process_key` 与严格 input/output/outcome schema；
  2. edge 明确 dependency 和 dataflow；允许 fan-out/fan-in，以及来自 allowlist 的 declarative condition；
  3. condition 只能读取已校验 outcome、target/source capability、manifest/diff decision 或受控 config，不允许任意代码表达式；
  4. 禁止 loop、递归 sub-workflow、运行时注入未知 node、caller 上传 graph/code，以及把 queue/Worker binding 当业务 node；
  5. single document、scatter root controller 与 scatter document child 可以使用不同 blueprint key，但共享一套 definition schema、Process registry 和 engine；scatter child 本身仍是 Execution，不是一个 DAG node；
  6. 标准 LS-RAG 主链保持清楚：clean/resolve → structurize → construct → vectorize/index → publication validate；skip/no-op/metadata-only/purge 等真实分支通过受控 edge 表达。

- **Reasoning**：纯固定线性 pipeline 无法优雅表达 clean skip、API diff/no-op、metadata-only、scatter fan-in 与资源撤销；任意动态 DAG 又会把 leaf-worker 变成通用编排平台，并让 completion proof、retry 和治理失去边界。受限 RAG DAG 只增加已知业务需要的分支与汇合，同时让定义可静态校验。
- **问题**：Owner 是否确认 S03 首版采用上述“版本化、RAG-specific、受限 DAG blueprint”，允许静态可校验的 dependency/condition/fan-out/fan-in，但禁止 loop、任意代码、caller-defined graph 和运行时未知 node 注入？

### Q2 — Workflow 选择权与 immutable binding 的归属

- **影响范围**：`S03/S04-S05/S11/S14`；Owner-Gate `G-12`。
- **上游冻结输入**：`U-S03-01`、`U-S03-02`、`U-S03-03`、`U-S03-06`。
- **Legacy 事实来源**：`LF-S03-03`、`LF-S03-04`、`LF-S03-06`。Legacy 同时存在 file/workflow UUID、跨 domain config 引用、Admin 原地热改和 runtime config merge，导致“本次到底执行了哪份定义”难以长期证明。
- **本题只裁决**：谁选择 workflow，以及一次 Execution 在何时、以什么证据绑定一份不可变定义。
- **本题不裁决**：full retry 是否沿用旧 revision 还是重新 resolve、Registry 的 exact DDL/API、model fallback、Process materialization。
- **Codex 当前建议**：采用 **MKB-owned resolver + per-Execution immutable binding**：

  1. caller 只提交 S01/S02 冻结的 `request_intent` 与资源输入，不能提交 workflow UUID、graph、node、process key 或配置覆盖；
  2. MKB resolver 根据 `request_intent + target/resource kind + source capability + manifest/diff decision + accepted system policy` 选择一个 workflow key 与 immutable revision；
  3. Execution 在进入 runnable 前必须保存/引用完整 normalized definition revision，并记录 schema version、workflow key/version/digest，以及 config/prompt/model/capability 的 immutable refs/digests；
  4. binding 成功后，Registry 的发布、撤回或新版本不得改变这次 Execution；缺失、无效或 capability 不满足时在产生可执行 Process 前 fail loud；
  5. resolver decision 本身必须可审计，能够回答候选集合、选择规则、最终 revision 与拒绝原因；
  6. 是否允许未来 caller 传入一个 allowlisted profile 不是 v1 能力，若需要必须 reopen S01/S03，而不是借 `payload_extra` 绕过。

- **Reasoning**：S01 已把 caller 权限限制在 request intent；把 workflow 选择权再交回 caller 会重新泄漏内部编排。只保存 mutable registry UUID 也不够，因为 legacy 已证明 definition/config 会热改和合并。Execution 必须绑定不可变 revision/digest，才能支持 crash recovery、Process compaction、审计和结果复现。
- **问题**：Owner 是否确认 Workflow 由 MKB resolver 选择，caller 首版不能指定 workflow/profile；每个 Execution 在 runnable 前绑定并持久记录 immutable definition/config/prompt/model refs 与 digest，后续 Registry 变化不得影响该 Execution？

### Q3 — Immutable Execution Plan 与 Process row 的 materialization 边界

- **影响范围**：`S03/S12/S15`；Owner-Gate `G-13`。
- **上游冻结输入**：`U-S03-02`、`U-S03-04`、`U-S03-05`、`U-S03-09`、`U-S03-10`、`U-S03-13`。
- **Legacy 事实来源**：`LF-S03-02`、`LF-S03-05`。Legacy 只在当前 step 完成后创建下一 step row，避免预建无效分支；但没有一个完整 immutable plan，crash 后常依赖重新读取 mutable workflow 和专用 restarter 猜恢复位置。
- **本题只裁决**：Execution 创建时要冻结多少 runtime plan，以及 Process row 是全量预建还是按 eligibility 逐步 materialize。
- **本题不裁决**：Process exact status、claim/lease、retry counter/backoff、transition SQL、reconciler 扫描周期或 outbox 表形状。
- **Codex 当前建议**：采用 **immutable normalized plan + eligibility-driven Process materialization** 的混合模型：

  1. Execution 被接受为 current root/child 时，先冻结该 Execution 的完整 normalized plan：node keys、dependencies、conditions、typed I/O/outcome contracts、terminal guards、workflow revision/digest；可以是 immutable definition revision 引用加可验证 snapshot，不要求全部塞入 Execution JSON；
  2. 不为所有潜在 branch 预建 Process rows；只有 node 的 dependencies/condition 已 durable 满足、确定需要实际执行时，才创建唯一 Process instance；
  3. 初始 eligible Process 与 scheduling intent 必须在同一原子或可证明等价的提交边界产生，commit 后才能 wake queue；
  4. 一个 Process outcome 提交时，同时持久化 branch decision、Execution summary/current pointer，并创建下一批 newly eligible Processes/scheduling intents；
  5. 永不进入的 branch 不伪造一个“成功 Process”；其未选择事实由 immutable plan + durable branch decision/Execution summary 解释；
  6. materialization 必须有稳定幂等键，使 crash/reconciler 可以发现“plan 中已 eligible 但 Process/intent 缺失”的 node并补齐，而不会重复创建；
  7. scatter manifest children 仍按 D01/S02 创建独立 child Executions；root plan 只包含 scatter/register/fan-out/fan-in controller nodes，不把 N children 压成 N 个 Process nodes。

- **Reasoning**：全量预建会制造大量永不执行的 branch Process，并让 Process status 混合“计划节点”和“真实工序实例”；完全边走边读 mutable definition 又无法证明执行计划、难以 crash recovery。冻结完整 plan、只实例化 eligible Process，同时保留了可复现性、真实 Process 语义和可靠补偿能力。
- **问题**：Owner 是否确认采用“完整 immutable normalized Execution Plan + 按 eligibility 创建 Process row”的混合边界，并确认未选择 branch 不创建虚假 Process、scatter child 继续是独立 Execution？
