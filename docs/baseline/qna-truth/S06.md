## 1. S01-S05 回流后，S06 的唯一工作面

### 1.1 重新定位

S06 是 MKB 的 **LS-RAG 内容结构建模与 grounded block projection 域**。它回答：一个已经被 S04 接受、已经通过 S05 admission 的 exact `IntakeRevision + clean IntakeArtifact`，如何在不改写来源语义的前提下形成可验证的内容层级、阅读顺序、typed node、source anchor 和稳定 block coordinate，供 S07 构造 original/summary 双通道。

S06 不是通用“文本切块器”，也不是再次清洗内容的模型步骤。它不得：

- fetch/decode/OCR/clean 外部内容；
- 创建或修改 IntakeSource/Snapshot/Item/Revision；
- 生成 summary、融合检索 filter metadata；
- 生成 embedding、写 vector index 或切 serving pointer；
- 创建自己的 job/status/retry 状态机；
- 读取完整 Workflow 后自行选择下一步。

这些边界把过去 legacy `structured_json` 中混在一起的“来源正文、结构、摘要预留槽、知识树 UUID、模型输出和物理 R2 key”重新拆开。

### 1.2 Canonical contract chain

```text
Task / Execution / Workflow binding                         [S01-S03]
  → accepted IntakeItem + exact IntakeRevision              [S04]
  → exact clean IntakeArtifact + PreflightOutcome           [S05]
  → ProcessCommand: lsrag.structurize                       [S03→S06]
       exact revision/artifact/profile/model/prompt binding
  → immutable structure candidate                          [S06]
       ordered typed nodes + parent/child relations
       source anchors + reading order + coverage evidence
  → deterministic retrieval-block projection               [S06]
       stable coordinates + original-content refs
  → accepted ProcessOutcome + structure proof               [S06→S03]
  → original/summary construction                           [S07]
  → embedding / vector / publication proof                  [S08-S09]
```

S06 成功只表示本 Process 提交了 schema-valid、proof-valid 的 structure output。它不等于 Execution、Task 或 serving 成功。

### 1.3 六个工作平面

| 平面 | S06 v1 负责 | 状态/证据表达 | 明确不负责 |
|---|---|---|---|
| Binding 平面 | 锁定 exact IntakeRevision、clean Artifact、structure definition、capability、model/prompt refs | Execution binding + ProcessCommand digest | active version 热切、Workflow route |
| Structural semantic 平面 | root、section、paragraph、list、table、code、quote、media reference 等 typed nodes 与 ordered tree | immutable node/edge envelope | summary/topic tree、Knowledge identity |
| Coordinate/projection 平面 | node-local identity、parent、sibling ordinal、depth、reading order、retrieval block projection | generation-scoped coordinate + projection digest | vector UUID、retrieval ranking |
| Grounding/fidelity 平面 | clean input到node/block的exact或诚实近似 anchor、覆盖/重复/遗漏/顺序证明 | anchor ledger + validation report + proof digest | 重新清洗、用模型补写缺失原文 |
| I/O/artifact 平面 | logical input/output handles、immutable derived artifact descriptors | S13 logical refs + digest/size/media | local path、R2 key、physical GC |
| Runtime/control 平面 | 作为 S03 `lsrag.structurize` leaf Process消费Command并返回Outcome | S03八态 Process、claim/fence/retry | S06专属job表、callback SSOT、内部无限retry |

### 1.4 Single 与 scatter 的位置

- single intake：一个内容型 Execution 对 exact IntakeRevision 运行 S06；
- scatter intake：root Execution 仍负责 collection control，S06 默认在每个 required child Execution 内独立运行；
- root 只有在它自身拥有可结构化的 accepted Revision/clean Artifact 时才运行 S06；集合清单本身不能伪装成全文结构；
- child 的 structure failure 按 S02/S03 collect-all 和 proof 规则汇总，不创建 child Task，不把多个 child 拼成一棵跨 Item 文档树；
- 跨 Item 的 Knowledge tree、collection summarization 或 graph 属未来 Knowledge/S07/S10 语义，不进入 S06 v1。

### 1.5 v1 scope fence

S06 必须冻结：

- exact input/output/proof contract；
- derived structure build 与 IntakeRevision 的关系；
- MKB-native typed structure schema；
- ordered hierarchy、stable coordinate 与 source anchor；
- full-document/root 与子结构的表达；
- structure-aware block projection；
- deterministic/model-assisted binding；
- semantic validation、允许的 repair 和 fail-loud 边界；
- large input budget、idempotency、retry/error 和 recovery 的 S06 业务要求；
- S07-S09 所需的 lineage 与 acceptance proof。

S06 不冻结：

- S07 summary/meta fusion、双通道 construction schema；
- S08 tokenizer/embedding batch、model dimension；
- S09 index/storage/publication；
- S11 provider/fallback runtime 实现；
- S12 exact DDL/table count/transaction driver；
- S13 filesystem/object layout；
- S14 prompt/model registry 的物理 schema；
- S15 metric/alert/retention 数值；
- S16 model endpoint、secret 和 authorization 实现；
- **完整 human-in-the-loop 管线**（clean curation 工作台、inspection 编辑闭环、RAG 内人工 patch、用户 generation 精修 UI、mass-scatter 逐项精修）。v1 只继承上游已冻结的最小人工/运维入口能力，不把 HITL 扩展成 S06 生产路径。

| `WEB-S06-05` | [RAPTOR（ICLR 2024）](https://arxiv.org/abs/2401.18059)构建不同抽象层次的递归summary tree用于多层检索。 | 证明层级抽象具有检索价值，同时强化cutoff：summary/abstraction是S07产物，不应混入S06 original structure truth。 |
| `WEB-S06-06` | [JSON Schema 2020-12 fundamentals](https://json-schema.org/blog/posts/applicability-json-schema-fundamentals-part-1)说明`properties`本身不代表required，未知字段默认可能通过，严格验证需要type、required、additionalProperties等完整约束。 | 支持strict output schema；JSON Schema只证明形状，tree/coverage/anchor等跨字段语义仍需S06 validator。 |
| `WEB-S06-07` | [Docling Core GitHub](https://github.com/docling-project/docling-core)将document model、serialization与chunking定义为分离但可组合的API。 | 支持MKB把structure representation和projection contract分离；不引入运行依赖。 |

### 4.1 外部证据 verdict

1. 结构化不应从“一组最终chunks”开始，而应先有可回溯的元素、层级和reading order；
2. retrieval blocks是面向下游budget/模型的projection，可以由同一结构生成不同版本；
3. parent-child、多粒度和ancestor context是有效设计分母，但具体retrieval策略归S10；
4. strict JSON只关闭形状错误，无法单独证明无遗漏、无乱序、无虚构和坐标稳定；
5. 递归summary tree不是S06 v1结构真相，继续由S07负责。

每个GenerationArtifactRecord语义上绑定一个immutable logical file；pointer指向artifact identity，不直接指向本地路径。S13可以在物理层优化存储，但不能改变“一条generation记录对应一个exact logical artifact/digest”的业务语义。

### 5.4 推荐 v1 只读历史接口与写边界

语义接口建议为：

```text

GenerationArtifactQueryPort.list_by_execution(...)

GenerationArtifactQueryPort.get_current(...)
GenerationArtifactPointerPort.compare_and_set(...)         internal only
```

如向上游HTTP开放，必须是Task-scoped只读投影：

```text
GET /v1/tasks/{task_uuid}/generation-artifacts
    ?execution_uuid=&artifact_type=&validation_disposition=&cursor=

GET /v1/tasks/{task_uuid}/generation-artifacts/{generation_artifact_uuid}

GET /v1/tasks/{task_uuid}/generation-artifact-pointers
    ?execution_uuid=&artifact_type=
```

服务端必须验证`team + Task + Execution + artifact`归属链；不得借该接口开放Execution/Process写面。Create只由current fenced Process执行；Update禁止原位覆盖；Delete不作为普通v1 API，未来只能通过retention/cleanup且必须保留审计骨架。该CRUD边界已由Q1冻结为`T-O-79`。

### 5.5 推荐独立版本化 Structure Schema Registry

```text
StructureSchemaDefinition                          [immutable version]
  schema_key / schema_version / schema_digest
  schema_dialect
  deterministic_kernel_schema
  governed_extension_schema
  semantic_invariant_manifest
  artifact_type + media contract
  compatibility declaration
  registration origin / created_at / payload_extra

StructureSchemaRegistry
  internal register
  list/get exact version
  resolve exact key+version+digest
  active pointer only for new Execution binding
```

推荐规则：

1. Schema由S06拥有业务语义并在MKB内部注册；S12承接物理持久化，S03 `ProcessCapabilityManifest`引用其exact input/output schema。
2. 每个Execution/GenerationArtifact锁定`schema_key + version + digest`。生产者和下游都必须按artifact envelope主动加载该exact版本，禁止解析`latest`。
3. S07-S10 capability manifest必须声明支持的schema versions/digests；Workflow compile/readiness在执行前拒绝不兼容producer/consumer组合。
4. schema version immutable：同version同digest幂等，同version异digest fail readiness；新version不重解释历史artifact。
5. Registry提供内部register和只读list/get/resolve，不向外部工具开放任意create/update/delete。缓存或compiled schema是可重建projection，不是truth。
6. JSON Schema负责shape；`semantic_invariant_manifest`负责single root、acyclic、parent/order、anchor、coverage、coordinate等跨字段验证。二者共同构成可消费contract。

该registry、runtime load与consumer handshake已由Q2冻结为`T-O-80..82`；exact tree/node/block字段继续由Q4裁决。

### 5.6 推荐 deterministic kernel 与 governed extension

#### Deterministic kernel

不得由agent修补的最小kernel包括：

- schema/generation/artifact identity与exact binding；
- IntakeRevision、clean Artifact、Execution/Process/fence refs；
- root、parent、sibling ordinal、reading order和stable coordinate；
- source anchor、original content ref/digest、coverage/order proof；
- artifact type、logical handle/digest、validation/proof refs；
- 下游用于original/summary traceback的坐标关系。

Kernel只能通过注册新schema version演进，不能原位修改既有schema或artifact。实例kernel不合规时禁止agent patch，直接记录失败并进入S03 retry。

#### Governed extension

可以允许agent修补的范围必须由exact schema version显式声明，例如：

- optional heading normalization；
- non-authoritative labels/classification；
- typed explanatory annotations；
- namespaced、versioned extension values。

flexible不等于`payload_extra`。任何被下游读取、路由、过滤、授权或影响proof的extension，必须拥有正式`extension_key/version/schema/digest`；`payload_extra`继续禁止承载业务truth。

#### Validation / repair / retry

```text
generate immutable artifact + invocation/token record
  → validate deterministic kernel
       invalid
         → append validation report
         → pointer unchanged
         → S03 retry_wait / retry
  → validate governed extension
       valid
         → full validation
       invalid + registered repair allowed
         → agent repair creates NEW immutable artifact
         → append repair invocation/token/causation
         → rerun kernel + extension + semantic validation from zero
  → fully valid
       → CAS unique current pointer
       → accepted ProcessOutcome
  → repair/full validation failed
       → pointer unchanged
       → S03 retry_wait / retry
  → max_retries exhausted
       → Process failed
       → Execution follows Workflow failure convergence
```

repair永不原位覆盖artifact；每次生成或修补都必须留下独立artifact/invocation/token历史。bounded repair次数写入exact profile；不得在一次Process attempt内形成不可见、无限循环。该kernel/extension cutoff与最终失败边界已由Q3冻结为`T-O-83..85`。

### 5.7 推荐 canonical structure shape（Round 2 Q5 裁决）

```text
GenerationArtifact(structure_document)
  └── root StructureNode (document scope)
      ├── ordered child node
      │   ├── ordered child node
      │   └── ...
      └── ordered child node

StructureNode
  node_id / generation_artifact_uuid
  parent_node_id? / sibling_ordinal / depth / reading_ordinal
  node_kind / content_role
  source_anchor_refs[]
  content_digest / subtree_digest
  governed_extension_values?
  payload_extra

RetrievalBlockProjection
  structure_generation_artifact_uuid + projection_generation_artifact_uuid
  projection_profile ref/digest
  block_coordinate
  source_node_refs + ordered source spans
  original_content_ref/digest
  ancestor heading/context refs
  token/char estimates
```

exact node_kind 闭集、anchor 形态与 coordinate 字段由 **Round 2 Q5** 冻结；本节是推荐形状，不是 Truth。D02 只规定它们不得成为 StateFamily。

### 5.8 v1 明确不建设

- 通用document editor、generation artifact任意Update/Delete或外部Execution写面；
- **完整 human-in-the-loop 生产管线**：clean curation 命令面、inspection 编辑台、RAG 内人工 patch、candidate promote、用户 generation 精修闭环、mass-scatter 逐 member 精修；
- agent动态定义/发布structure schema；
- cross-document Knowledge graph/tree；
- RAPTOR式递归summary tree；
- runtime plugin、shadow/canary、自动profile优化；
- 结构节点的独立mutable lifecycle；
- 为每种node kind建立专用表；
- 从legacy layered JSON导入、翻译或双读；
- 将整份正文复制到每个父节点以换取“方便”；
- agent修补deterministic kernel；
- 为未知结构、缺anchor或超budget静默fallback成一个generic block；
- S06私有max-retries或不可观测的无限repair loop；
- 跨generation node mapping / semantic merge / “同名heading即同一node”。

## 8. Round 1 — Foundational Q1-Q3

### Q1 — GenerationArtifact 是否采用“完整历史账 + 每Execution每类型唯一current pointer + 受限CRUD”

- **Owner reframe输入**：Structurizer消费token；所有generation历史必须durable并可按`execution_uuid`审计。任何Execution在任一时刻，对每个具体generation artifact type只能有一个pointer，指向一个唯一文件。
- **单一裁决面**：generation artifact历史、current pointer和v1 CRUD/read API的权威边界。
- **不在本题裁决**：artifact内部tree schema、kernel/extension repair规则、物理表数、filesystem layout和retention时长。

### Q2 — S06结构Schema是否成为独立、immutable、版本化注册并由上下游按exact version共享加载的Contract

- **Owner reframe输入**：Schema必须与各业务执行解耦，拥有自己的版本并在系统内注册；生产者和下游主动拉取对应版本，统一上下文，避免各部门猜测。

#### 推荐执行方案

1. 建立S06 domain-owned、内部注册、immutable versioned的`StructureSchemaDefinition`。最小identity为`schema_key + schema_version + schema_digest`；同version同digest幂等，同version异digest立即fail readiness。

2. 一个definition至少包含：

   - schema dialect与严格shape schema；
   - deterministic kernel schema；
   - governed extension schema；
   - semantic invariant manifest及validator refs；
   - 适用artifact types/media contract；
   - compatibility declaration；
   - registration origin、created_at和`payload_extra`。

3. Schema与业务handler、model和prompt解耦，但不与语义责任解耦：S06拥有结构contract及invariants；S03 capability manifest引用输入/输出schema；S12只承接物理registry；S07-S10只消费，不各自复制或重定义。

5. 下游根据artifact声明主动加载exact schema。加载顺序为：

```text
read artifact envelope
  → resolve schema_key/version/digest from local registry
  → verify registry digest == artifact binding digest
  → verify consumer capability supports this exact version/range
  → validate artifact
  → consume typed context
```

缺schema、digest drift或consumer不兼容时fail-loud，不猜字段、不fallback到latest。

6. S07-S10 `ProcessCapabilityManifest`必须声明supported schema keys/versions/digests。S03 compiler/readiness在Workflow注册或Execution materialization前检查producer output与consumer input可兼容；不能等到下游运行时才发现。

8. 允许进程内缓存exact compiled schema，但缓存不是truth；cache miss必须回到registry，digest不符隔离readiness。为保证本地单体运行，不把schema加载实现成外部网络依赖。

### Q3 — Structure Schema是否冻结“deterministic kernel不可修补 + governed extension可agent修复 + 全量复验/max-retries失败”

- **Owner reframe输入**：Schema必须同时包含不可改变的确定性部分与灵活部分。确定性部分不合规必须retry；灵活部分允许agent修补，但传递下游前必须再次强制校验，修复失败继续retry，达到max-retries必须宣告生产失败。
- **单一裁决面**：kernel/extension cutoff、agent repair transaction和retry/max-retries成功失败边界。
- **不在本题裁决**：exact字段清单、具体retry次数、agent/model/provider选择、window大小、物理表数和alert/retention数值。
- **影响范围**：S03 ProcessOutcome/retry；S06 schema/validation/artifact pointer；S11/S14 repair model/prompt binding；S15 token/quality审计；S07输入可信边界。
- **事实驱动**：`LF-S06-04..12`；`WEB-S06-03/WEB-S06-06`。Legacy采用schema失败重试是有效原理，但自动清UUID、补summary、coerce ID也证明“所有字段都可修补”会掩盖contract drift。

#### 推荐执行方案

1. 每个StructureSchemaDefinition显式划分`deterministic_kernel_schema`与`governed_extension_schema`。不能由handler、prompt或agent自行判断某个失败字段属于哪边；分类本身是versioned schema truth。

2. v1 kernel至少涵盖identity/binding、IntakeRevision/Artifact refs、Execution/Process/fence、tree topology、reading order、stable coordinate、source anchor、original content digest、coverage/proof、artifact handle/digest和schema refs。任何kernel字段缺失、冲突、越界、被改写或无法证明时：

   - 保存原始generation artifact、validation report和token invocation；
   - 不调用agent patch kernel；
   - 不更新current pointer；
   - 返回typed retryable/non-retryable evidence，由S03进入`retry_wait`或`failed`。

3. extension只允许承载schema正式声明的optional、non-authoritative或namespaced typed annotations。凡是影响identity、route、filter、authorization、coordinate、source fidelity或proof的字段必须晋升kernel，不能继续作为flexible extension或`payload_extra`。

4. extension validation失败且schema/profile登记`repair_allowed=true`时，才可调用agent repair。Repair command必须锁定source generation artifact、exact schema、允许修改的JSON pointers/field set、model/prompt/profile、最大repair passes和expected input digest；agent没有写入其他字段的权限。

5. repair不修改原artifact。每次repair产生新的immutable GenerationArtifact，记录`repaired_from_artifact_uuid`、repair invocation/token、changed-field manifest、before/after digest和causation。若输出触碰kernel或未授权extension字段，直接判invalid。

6. repair输出必须从零执行完整校验，顺序为：

```text
strict envelope/schema
  → deterministic kernel
  → semantic invariants
  → governed extensions
  → source fidelity / coverage / coordinate proof
```

不能只复验被修字段，也不能因为agent返回JSON成功就更新pointer。

7. 只有full validation通过后，才能在同一S12事务/CAS边界内：登记validation proof、把该artifact设为`(execution,type)` current pointer、接受ProcessOutcome并写后续wake/outbox。任一步失败pointer保持原值。

8. repair失败、full validation失败或agent runtime失败均回到S03统一retry模型。建议每个Process attempt只允许profile声明的bounded repair pass；每次generation/repair模型调用都进入Q1 Invocation账，禁止嵌套不可见无限重试。

9. `max_retries`来自S03 Process spec/manifest并在Execution binding时冻结。达到上限时Process必须`failed`，保存最后错误分类、全部generation/repair artifact refs、validation reports和token summary；不得fallback成generic block、自动放宽schema或切latest schema。

10. 新schema version可以演进kernel或extension定义，但既有schema version、既有artifact和既有validation verdict都不可修改。升级只影响新Execution/new generation因果链。

11. S06继续禁止summary。Agent repair只能修复S06 schema允许的结构extension；任何abstractive summary仍由S07生成并通过共享coordinate回溯original。

#### Reasoning 与制衡
