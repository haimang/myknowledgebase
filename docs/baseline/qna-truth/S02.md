## 1. S02 校准后的 Scope

### 1.1 S02 的唯一职责

S02 只定义**外部可见的 Task API 与 Task aggregate lifecycle**。Task 是上游请求账本，不是 LS-RAG 工作单元，也不是 Workflow/Process 的别名。

S02 必须负责：

1. Task create/get/list/patch/soft-delete 的 API 语义；
2. `request_intent` 驱动的 strict Task envelope 在 API 层的接收与返回；
3. Task aggregate status、合法转移和终态语义；
4. polling response 中的 aggregate progress、result/error summary 与 not-ready 表达；
5. scatter Task 的原子子项列表/结果投影，以及指向稳定 Document 资源的链接语义；
6. cancel/retry/rebuild command 的 Task 级 admission、并发、幂等与响应语义；
7. priority、deadline、revision、list/filter/pagination；
8. Task soft-delete、可见性、retention 与 immutable Audit/durable Execution summary 的保护；
9. 稳定的 HTTP/API error namespace。

### 1.2 S02 明确不负责

| 不属于 S02 的事项 | 权威归属 | S02 只能做什么 |
|---|---|---|
| Execution tree、root/child 创建与 retry lineage | `D01 / S03` | 消费其 aggregate，不定义内部创建算法 |
| Process type/key、状态机、claim/lease/fencing、自动 retry | `D01 / S03` | 不暴露外部写面，不复制工序状态到 Task enum |
| clean/structurize/construct/vectorize/validate/purge 工序 | `S03/S05-S09` | 只读取最终 aggregate/proof |
| Source/Document/Version 与 parent-child manifest | `S04-S05` | 不把 Execution tree 当资源关系；S02 只定义 Task-scoped 投影、链接与命令入口 |
| Artifact I/O、local filesystem locator | `S13` | 只返回受控 result/artifact references |
| vector/filter metadata publication proof 算法 | `S08-S09/S12` | 只把 durable proof 作为 Task success guard |
| Process compaction 与 Event/Log retention | `S03/S15` | Task soft-delete 不触发越权级联删除 |
| queue/outbox 选型和 crash recovery | `S03/S12` | 只要求 Task 投影最终可对账 |

### 1.3 S02 不得重新引入的旧模型

- 不得重新引入 `attempt_uuid`、`task_attempts` 或“一个 Task 一个 Attempt”的模型；
- 不得使用 `task_type`；canonical 外部字段是 `request_intent`；
- 不得把 `document.ingest/rebuild/...` 解释成内部 Process 分类；
- 不得让外部 caller 创建、PATCH 或直接 command `execution_uuid/process_uuid`；
- 不得假设一个 Task 永远只有一个 flat Execution；
- 不得给 Task 增加 singular `current_process_uuid` 来表示 scatter；
- 不得重新询问 Task 成功是否需要向量和 filter metadata proof；
- 不得复制 legacy Worker callback、D1、R2 或 Durable Object 拓扑。

#### 2.2.2 SMCP 与 Clean Dispatcher 的四个协议分面

| 分面 | Legacy 约定 | MKB 吸收方式 |
|---|---|---|
| 身份/信息平面 | SMCP 同时携带 `trace_uuid/file_uuid/job_uuid/workflow_uuid/process_step_uuid/team_uuid`；散射用 `parent_file_uuid + atomic_id + 双 hash` 表达原子线索。 | 不复制多套 job/file 身份；映射为 Task、root/child Execution、Process、Document/manifest 与 Trace 的独立 UUID/稳定键。 |
| I/O 平面 | `io_payload` 以 input/output slots 声明 I/O；散射输出使用 prefix；完整 child metadata 由 callback output 回传。 | 保留逻辑 slot、schema/hash 和完整 manifest；R2 binding/key 改为 S13 的本地 Artifact reference/relative locator。 |
| 编排/控制平面 | `WORKFLOW_START → STEP_START/STEP_RESTART → STEP_CALLBACK`；`control_payload` 携带 atomic hint 与 case mode；Clean Dispatcher 在回调后执行 diff/register/fan-out。 | 由 S03 的 durable Process transition、workflow definition、local queue/outbox 与 reconciler 实现；控制状态不能只活在消息中。 |

#### 2.2.3 必须显式修复的 legacy 债务

1. **身份分配与 UPSERT 漂移**：provider 每次扫描先生成随机 child UUID（`processor.ts:175-177`）；Differ 虽计算并声称复用历史 `child_file_uuid`（`differ.ts:103-106`），但 relation UPSERT 实际写入的是 `child.uuid`（`core/db.ts:279-305`）。同时基线 DDL 只有 `child_file_uuid` 主键，没有代码 `ON CONFLICT(team_uuid, atomic_id)` 所假设的唯一约束（`smind-console/db/05-files.sql:197-257`）。MKB 必须在持久化事务内按稳定 source key 分配/复用 Document UUID，并用真实唯一约束锁死。
2. **“并行调用完成”不等于“可靠入队”**：queue helper 使用 `ctx.waitUntil(queue.send(...))` 后立即返回（`smind-clean-dispatcher/core/queues.ts:46-68`）；外层 `Promise.all` 因而不是 fan-out durability barrier。MKB 必须以已提交 scheduling intent/outbox 为真相，由 reconciler 补发。
3. **没有父级 fan-in**：child finalizer 明确更新 child 后 `Parent status untouched`。因此 legacy 生产经验能证明 child 独立状态必要，却不能提供 Q2 所需的 root/Task 完成算法；MKB 必须新增 expected-set 驱动的 collect-all aggregator。
4. **重启不是原子事务**：legacy Restarter 的恢复路径是先发送队列、再更新 process row；队列已发而 DB 更新失败时只能记录/补偿，不能形成单事务。MKB 必须遵守 D01 的 durable state-before-wakeup 与幂等恢复围栏。
5. **CRUD 能力散落**：legacy 已证实 list、artifact、timeline、restart 等原子能力，但没有一个一致的 atomic resource contract；父/子查询、stage restart 与 debug API 分散在多条 route。MKB 应从第一天建立稳定 Document identity + Task-scoped projection，而不是复制路由拼补历史。

## 4. Round 1 — Task Aggregate Lifecycle（Q1–Q3）

> 本轮只裁决 Task aggregate 的三个基础问题。每题只有一个主要 decision，不把 API response、Process 实现、retention 或 retry admission 混入同一问题。

### Q1 — 对外 Task aggregate status 的最小词汇与基础状态图

- **驱动真相**：`U-01`、`U-05`、`U-06`、`U-10`。
- **本题只裁决**：Task polling API 的 status enum，以及不涉及 retry/cancel race 细节的基础有向边。
- **本题不裁决**：Execution/Process status、RAG phase、scatter fail-fast/collect-all、cancel 与 success 的赢家、retry command 允许从哪些终态发起、soft-delete 可见性。
- **Codex 当前建议**：Task v1 只使用六个 aggregate status：

  ```text
  queued
    ├──→ running
    └──→ cancelling

  running
    ├──→ succeeded
    ├──→ failed
    └──→ cancelling

  cancelling
    └──→ cancelled
  ```

  语义边界：

  | Status | 只表示什么 | 明确不表示什么 |
  |---|---|---|
  | `queued` | Task/Audit 已提交，工作尚未进入 active running aggregate | 不区分 root 尚未创建、待 claim 或 backpressure |
  | `running` | current root 或至少一个 required child 仍在执行/等待内部恢复/fan-in | 不泄漏 clean、structurize、construct、vectorize、retrying 等内部 phase |
  | `cancelling` | cancel intent 已被 durable 接受，但内部工作尚未完全收敛 | 不等于已经停止 |
  | `succeeded` | current root 的 required set 与 type-specific durable proof 已通过 | 不等于 queue 为空或 callback 成功 |
  | `failed` | current root 已按 S02 aggregation policy 收敛为失败，且没有仍在进行的内部自动恢复 | 不表示 Process 的某一次临时失败 |
  | `cancelled` | cancel 已传播并确认没有仍可提交业务结果的 active work | 不等于收到 cancel HTTP 请求 |

  不增加：

  - `accepted`：Task/Audit 原子提交后的首个可见状态直接是 `queued`；
  - `retrying`：属于 Execution/Process；
  - `partially_succeeded`：D01 首版是 all-required success；
  - `deleted`：soft-delete 是资源可见性，不是执行 status；
  - clean/RAG 阶段词汇：属于内部 Execution phase/Process type。

- **Reasoning**：Task 已被 owner 定义为稳定的外部请求账本，因此 status 必须能支持 polling 与命令竞态，但不能重新吸收 RAG workflow。六个值覆盖等待、活动、取消收敛和三个外部终局，同时把内部恢复、阶段和 scatter 并发留给 Execution/Process。
- **问题**：Owner 是否确认上述六个 Task aggregate status 及基础状态图？如不确认，请只给出需要增加、删除或改名的 status，以及对应基础有向边；retry reopening 和 cancel race 暂不在本题回答。
- **业主回答**：同意 Codex 本题建议。上述六态 status、语义边界与基础有向边全部接受并冻结；登记为 `T-O-1`。

### Q2 — Scatter 中 required child 最终失败后的 Task 收敛时机

- **驱动真相**：`U-04`、`U-05`、`U-07`。
- **本题只裁决**：一个 required child 已耗尽内部恢复并终态失败，而其他 required children 仍 active 时，Task/root 是立即失败还是等待全部 required children 终结后失败。
- **本题不裁决**：Process retry budget、child 创建算法、manifest schema、成功 child 的知识可见性、失败 child 的人工 retry、Task result response 字段。
- **Codex 当前建议**：首版采用 **collect-all terminal convergence**：

  1. 一个 required child 终态失败后，不自动取消仍健康运行的 siblings；
  2. 只要还有 required child active，Task aggregate 保持 `running`；polling progress 可以显示 `failed_count > 0`；
  3. 当 manifest 中全部 required children 都进入终态后，只要任一 required child 为 failed，root 与 Task 收敛为 `failed`；
  4. Task 永远不能因此进入 `succeeded` 或 `partially_succeeded`；
  5. 运维紧急停止仍通过显式 cancel command，不把 child failure 偷换成 cancel。

- **Reasoning**：D01 已冻结 all-required success，但尚未决定“已注定失败时是否中止健康 siblings”。Collect-all 能最大化完成互不依赖的 child 工作、获得完整失败清单，并避免一个坏文档使整批健康文档被反复重做。代价是 Task 已经出现 failed child 时仍会保持 `running`，因此 polling 必须能展示失败计数，避免“看似仍有成功希望”的误解。
- **问题**：Owner 是否确认 scatter 采用 collect-all terminal convergence？如果选择 fail-fast，请明确 required child 终态失败后，剩余 active children 是继续运行、禁止新 claim，还是进入 cancel/stop；本题只需要确定这一收敛策略。
- **业主回答**：同意 Codex 本题建议。Scatter 采用 collect-all terminal convergence；不得因一个 required child 最终失败而自动取消健康 siblings，全部 required children 终态后再做失败归约；登记为 `T-O-2`。

### Q3 — Cancel 与成功提交并发时的唯一线性化规则

- **驱动真相**：`U-05`、`U-06`、`U-10`、`U-11`。
- **本题只裁决**：cancel command 与 current root 成功归约并发时，以哪个 durable commit 判定最终赢家。
- **本题不裁决**：cancel endpoint URI、Process cooperative-cancel 实现、lease fencing 算法、Artifact/Vector 补偿细节、retry eligibility、HTTP response envelope。
- **Codex 当前建议**：采用 **Task lifecycle CAS 先提交者获胜**：

  1. success aggregator 只有在 Task 仍为 `running/queued` 且没有 durable cancel intent 时，才能在同一受控 terminalization path 中提交 `Task → succeeded`；
  2. cancel command 只有在 Task 非终态时，才能以 `expected_revision` 提交 `Task → cancelling`；该提交一旦成功，禁止新的 Process claim 和新的 success terminalization；
  3. 若 `Task → succeeded` 先提交，后到 cancel 幂等返回既有 `succeeded`，不得把成功回滚为 cancelled；
  4. 若 `Task → cancelling` 先提交，后到 success terminalization 必须被 CAS/guard 拒绝；内部传播停止/补偿，待 current root 与 children 全部收敛后才 `cancelling → cancelled`；
  5. 对 `failed/cancelled` 重复 cancel 不改写历史；queued Task 也先进入 `cancelling`，确认没有 claim 后再进入 `cancelled`；
  6. 赢家只由数据库 durable commit 决定，不由 HTTP 到达时间、日志时间、worker callback 时间或进程内 flag 决定。

- **Reasoning**：Task 是外部轮询 SSOT，cancel receipt 与实际停止又是两个事实。使用 Task revision/CAS 作为单一线性化点，能够让 success 和 cancel 在 crash/retry/并发请求下给出唯一结果；`cancelling` 则为内部停止和补偿保留真实时间窗口。
- **问题**：Owner 是否确认上述“Task lifecycle CAS 先提交者获胜”的 cancel/success 竞态规则？如不确认，请指定唯一 durable linearization point，以及 cancel 先赢和 success 先赢时各自允许的最终 Task 状态。
- **业主回答**：同意 Codex 本题建议。Cancel/success 竞态以 Task lifecycle CAS 的 durable first-commit-wins 为唯一裁决点；登记为 `T-O-3`。

## 6. Round 2 — Atomic Child Public Surface（Q4–Q5）

> 本轮按 owner 指令只提出 Q4–Q5。每题只裁决一个 S02 public-surface decision；Document schema、manifest DDL、Execution/Process transition 与队列算法仍分别归 S04/S03/S12。

### Q4 — Scatter Task 与原子 child 的公共读取边界

- **驱动真相**：`T-O-2`、`T-O-4`。
- **Legacy 事实来源**：`LF-08`；legacy 把 single file 与 atomic relation UNION 成混合列表，并让 child UUID 独立读取 artifacts/timeline。这证明了原子寻址的必要性，也暴露了 file/relation/debug routes 散射的问题。
- **本题只裁决**：Get Task 的聚合响应与原子 child 明细读取之间如何分层。
- **本题不裁决**：Document 字段全集、manifest schema、Artifact 下载、内部 Execution/Process 诊断 API、restart 命令。
- **Codex 当前建议**：采用 **Task aggregate + Task-scoped paginated items projection + canonical Document link** 三段式读面：

  1. `Get Task` 只返回稳定 aggregate：Task status、revision、current root summary、manifest revision、`total/required/active/succeeded/failed/cancelled/skipped` counts、result/error summary，以及原子 items collection link；不内嵌无界 child 数组；
  2. 提供 Task-scoped 的 paginated items 查询（精确 URI 交给 OpenAPI 定稿），支持按 child aggregate status/result readiness 过滤；每项至少返回稳定 `document_uuid`、source/atomic key 的安全投影、canonical Source/Document relation links、该 Task generation 中的 aggregate status、result/error summary 与 canonical Document link；
  3. 原子 child 的长期资源详情由 S04 的 canonical Document endpoint 提供；Task-scoped item 是“该 Document 在本 Task/current root generation 中的执行结果投影”，不是第二个 Document SSOT；
  4. 不创建 child `task_uuid`，不要求 caller 使用 `execution_uuid/process_uuid`，也不把 legacy `file_status` 原样暴露为 Task status；
  5. Task-scoped items 必须来自 committed manifest + Execution aggregate，可在 Process 清理后继续查询。

- **Reasoning**：`T-O-2` 使 Task 在出现 failed child 时仍可能保持 `running`，仅有总 status 无法诚实解释进度；但把所有 children 内嵌到 Get Task 会导致响应无界、分页失效，并混淆请求账本与长期 Document 资源。三段式读面同时保住 Task 聚合、原子可检索性和 S04 的 Document SSOT。
- **问题**：Owner 是否确认上述“Task aggregate + paginated items projection + canonical Document link”的公共读取边界？如不确认，请只裁决原子 child 应内嵌在 Get Task、作为 Task 子资源分页读取，还是只允许从独立 Document API 检索。
- **业主回答**：基本同意并接受 Codex 推荐方法。冻结“Task aggregate + Task-scoped paginated items + canonical Document link”三段式公共读面；不得创建 child Task，也不得向 caller 暴露 Execution/Process UUID。登记为 `T-O-5`。

#### Q4 冻结执行方案

1. `Get Task` 只返回有界 aggregate、current generation/root summary、manifest revision、child counts、result/error summary 和 items link，禁止内嵌无界 child 数组；
2. Task-scoped items collection 的成员资格由 `(team_uuid, task_uuid, root generation, manifest revision)` 固定，使用 opaque cursor 分页；item status/result 从 durable Execution aggregate 读取，不依赖可清理的 Process row；
3. 每个 item 返回稳定 `document_uuid` 与 canonical Source/Document links；Document 长期内容与版本真相只由 S04 持有；
4. Task item 只是“某 Document 在本 Task generation 中的结果投影”，不得另建第二份 Document 状态；
5. Get Task counts、items membership 与 manifest 必须可由 durable truth 对账；发现 projection 漂移时由 reconciler 重建，不允许人工 PATCH aggregate。

### Q5 — 原子 child 的外部重启应产生新的 Task，还是复活原 scatter Task

- **驱动真相**：`T-O-1`、`T-O-3`、`T-O-4`。
- **Legacy 事实来源**：`LF-09`；legacy 允许用 child `resource_uuid` 选择 clean/rag stage，恢复旧 process step 或 kickstart。它验证了原子重启的需求，但把外部资源命令、workflow stage 和内部 step recovery 混在一起。
- **本题只裁决**：caller 对一个稳定原子 Document 发起重启时，公共 Task identity 与 lifecycle 如何表达。
- **本题不裁决**：内部从哪个 Process 恢复、自动 retry budget、workflow branch、锁/lease/fencing、同 Document 并发 publication 的 admission 算法。
- **Codex 当前建议**：原子 child 的**外部人工重启创建一个新的 Task**，而不是复活或改写原 scatter Task：

  1. caller 以稳定 `document_uuid` 提交新的 Task Create，使用既有 canonical `request_intent=document.rebuild`（或 S01 已冻结集合中的语义等价 intent），获得新的 `task_uuid`；
  2. 新 Task 记录 `caused_by_task_uuid` / `source_task_uuid` 等只读因果引用，指回发现该 child 的 scatter Task；精确字段名由 S02 Domain Truth/OpenAPI 定稿；
  3. 原 scatter Task、root/child Executions 及其终态保持 immutable，不因原子重启从 `failed/succeeded/cancelled` 回到 `running`；
  4. 新 Task 创建自己的 root Execution 和全新 Processes；是否复用既有 Artifact/DocumentVersion 由 S03-S05 根据 rebuild workflow 决定；
  5. Process 自动 retry 或运维级 step recovery 仍是内部 S03 能力，不通过公共 S02 API 暴露 `stage/process_uuid/force-step`；
  6. 如果 caller 要求“整批原请求重跑”，仍使用 S01 已冻结的 full Task retry command，在原 Task 下创建新的 root Execution tree；它与“单原子 Document rebuild”是两个不同命令语义。

- **Reasoning**：一次原子人工重启是新的外部工作请求，应该拥有独立 ACK、幂等键、Audit、状态与结果。若在已终态的 scatter Task 内只复活一个 child，会改写原请求的 historical aggregate、引入 partial retry generation，并使 `T-O-1/T-O-3` 的终态与 CAS 失去稳定含义。新 Task 同时保留了因果链，又不泄漏内部 execution/process identity。
- **问题**：Owner 是否确认“原子 child 外部重启 = 针对该 Document 创建新 Task，旧 scatter Task 永不复活”的边界？如不确认，请明确选择“在原 Task 下创建新 root/child retry generation”，并说明旧 Task 终态是否允许重新进入 `queued/running`。
- **业主回答**：基本同意并接受“原子 child 重启创建新的 `document.rebuild` Task，旧 scatter Task 不复活”。补充强制要求：每次原子重启必须形成完整因果链，并由独立 restart 表作为 durable truth，保证 Audit 完整、全局任务追溯和状态拉取。登记为 `T-O-6/T-O-7`。

#### Q5 冻结执行方案

**A. 公共命令与生命周期**

1. caller 使用稳定 `document_uuid` 创建新的 `request_intent=document.rebuild` Task，并提供新的 `(team_uuid, task_uuid)`、root trace、Task Audit 与 creation fingerprint；
2. 原 scatter Task、source root、source child Execution 与其终态不可变；新的 rebuild Task 拥有自己的 ACK、Audit、root Execution、Processes、status 与 result；
3. rebuild Task 必须保留 immutable causation，可从新 Task 反查来源 Document/source Task，也可从来源 Task/Document 枚举全部后续 restart Tasks；
4. Process 自动 retry 与内部 step recovery 不创建外部 restart Task；它们仍属于 S03 的同 Process/Execution 恢复，不得混入本表的外部人工重启语义。

**B. 独立 durable `task_restarts` 真相表**

`task_restarts` 是正式的第五张最小业务真相表。它不替代 Task/Audit/Execution/Process，而是专门保存跨 Task 的重启因果与 admission 事实。

| 列族 | 冻结的最小语义 |
|---|---|
| Identity | `restart_uuid`（MKB 生成 UUIDv7）、`team_uuid` |
| Target | `document_uuid`，以及可选的 source/version reference |
| Cause | `source_task_uuid`、可选 `source_root_execution_uuid/source_child_execution_uuid`、`causation_trace_uuid` |
| New request | caller-supplied `restart_task_uuid`、该 Task 的 root trace/Audit FK、`request_intent=document.rebuild` |
| Admission evidence | request fingerprint/idempotency identity、reason、requested_at、admission outcome = accepted/rejected、稳定 rejection/error code |
| Runtime attachment | 可单次附着的 initial restart root Execution reference；后续 Execution generations 仍通过 Task lineage 查询 |
| Governance | created/decided timestamps；因果列、fingerprint 与 admission outcome 一经提交不可改写 |

最低约束与索引：

```text
PK (restart_uuid)
UNIQUE (team_uuid, restart_task_uuid) WHERE restart_task_uuid IS NOT NULL
INDEX (team_uuid, source_task_uuid, requested_at)
INDEX (team_uuid, document_uuid, requested_at)
INDEX (team_uuid, admission_outcome, requested_at)
INDEX (causation_trace_uuid)
```

**C. 原子提交、幂等与状态唯一真相**

1. 对已认证且 schema-valid 的原子重启请求，系统生成 `restart_uuid`；admission accepted 时，`task_restarts` row、新 Task、immutable Task Audit 与 durable scheduling intent 必须同事务提交，任一失败则全部不成立；
2. admission rejected 时，可以只有 immutable restart rejection row，不创建 Task/Execution；未通过认证或连 strict schema 都未通过的流量不创建业务真相，只进入安全/拒绝事件面；
3. 网络重放以 `(team_uuid, restart_task_uuid, creation fingerprint)` 收敛到同一 restart row + Task；同 UUID 不同 fingerprint 返回冲突；
4. `task_restarts` 只权威保存因果与 admission，不独立复制/推进 `queued/running/succeeded/...`；目标 rebuild Task 是运行状态唯一 SSOT；
5. 全局 restart status 查询通过 `task_restarts LEFT JOIN tasks` 返回 admission outcome 与当前 Task status/result summary；可缓存的 status 只能是可重建 projection，不得成为写入真相；
6. Task soft-delete、Process compaction 或日志 retention 都不得删除 restart causal row、Task Audit、Execution terminal summary 或断开 FK/逻辑引用。

## 7. ★ 中场评估 II（Round 2 → Round 3）

### 7.1 对 Round 2 的判定

Q4 与 Q5 均已形成可执行、无二义的 owner verdict：

- Q4 冻结了 bounded Task aggregate、Task-scoped paginated items 与 canonical Document SSOT 的分层；
- Q5 冻结了 atomic restart 创建新 Task、旧 scatter Task 不复活，并增加独立 durable restart causal truth。

Owner 的“更优雅、长期治理型状态机”要求不是新增一个大而全的状态 enum，而是将不同真相分别归位：Task 持有外部运行状态，Execution/Process 持有内部运行，Document/manifest 持有资源，`task_restarts` 持有跨 Task 因果。各表可关联，但禁止复制彼此可独立写入的 current state。

### 7.2 本轮已锁定真相

- `T-O-5`：三段式 scatter 公共读面；
- `T-O-6`：atomic restart = 新 `document.rebuild` Task，旧 Task/tree immutable；
- `T-O-7`：独立 `task_restarts` causal/admission truth，与 Task/Audit 原子提交，Task status 仍是唯一运行真相。

`T-O-7` 对 D01/S01 的最小表数形成显式增量：四张核心 Task/运行表不变，但启用外部 restart 后，durable 业务真相最小集合为五张。此项必须在 S02 accepted 后回填 D01/S01/S12，不得以“避免多表”为由把 restart JSON 塞回 tasks。

### 7.3 诚实反方制衡

1. 独立 restart 表提高了审计与全局追溯能力，也增加跨表事务、FK retention 和 reconciliation 成本；这属于 owner 明确接受的治理成本。
2. 如果 restart 表再维护一份可独立推进的 Task status，会立刻产生双 SSOT；因此它只保存 immutable admission/causation，运行状态通过 Task join 获取。
3. 新 rebuild Task 避免污染旧 scatter Task，但同一 Document 的并发 rebuild/publication 仍需 S03/S04 的单写者/fencing admission；本轮不偷定具体锁算法。
4. Q4 让成功 child 可被精确定位，但“root 尚未终态时是否已允许读取/检索成功 child”仍未冻结。
5. Full Task retry 仍按 S01 保持原 task UUID、创建新 root；它与 atomic restart 新 Task 的状态边必须在同一治理模型中明确区分。

### 7.4 Round 3 的问题注入依据

- **Q9** 由 `T-O-5/T-O-7` 驱动：需要冻结全局 restart lineage/status 的外部查询面与 retention 边界。

是否增加 Round 4 不在本节预判。Owner 已明确将在 Q6–Q9 结束后通知；当前不生成 Round 4 题面。

## 8. Round 3 — Durable Lifecycle Governance（Q6–Q9）

### Q6 — Full Task retry 的 admission、generation 与 Task 状态回边

- **驱动真相**：`T-O-1`、`T-O-3`、`T-O-6`、`T-O-7`；上游 `U-08`。
- **本题只裁决**：对原 Task 发起整批/full retry 时，允许的来源状态、新 generation 以及 Task aggregate 如何重新进入运行态。
- **本题不裁决**：Process 自动 retry、atomic Document rebuild、root/child 创建 SQL、lease/fencing 算法。
- **Codex 当前建议**：

  1. full Task retry 只允许从 `failed` 或 `cancelled` 发起；`queued/running/cancelling` 返回 active conflict；`succeeded` 不使用 retry，而应创建新的 `document.rebuild/index.rebuild` Task；
  2. command 必须携带 `expected_revision`，以同一 Task lifecycle CAS 接受；
  3. 接受后创建新的 root Execution generation 与新 Processes，旧 root/tree 终态和 proof summary 永久不可变；
  4. Task 增加 `current_generation`，原子切换 current root，并通过**仅命令可走**的 `failed|cancelled → queued` 回边重新进入运行态；Q1 的终态含义因此是“当前 generation 已终结”，不是“Task 永不可接受显式 full retry”；
  5. `task_restarts` 同时承接 full Task retry 因果，使用 `restart_scope=full_task|atomic_document` 区分；full retry 的 `source_task_uuid` 与 `restart_task_uuid` 相同，但 source/retry root Execution 不同；
  6. Task history/result 必须按 generation 查询，默认 Get Task 返回 current generation，并链接历史 generations，禁止覆盖旧结果。

- **Reasoning**：S01 已冻结 full retry 保持 Task identity，而 Q5 又冻结 atomic restart 创建新 Task。用 scope + generation 明确区分二者，才能既保住上游 Task ACK，又保持每棵 Execution tree terminal immutable。显式 retry-only 回边也比偷偷把 `failed` 改回 `running` 更可审计。
- **问题**：Owner 是否确认上述 full Task retry 规则，特别是只允许 `failed/cancelled → queued`、`succeeded` 改走新 rebuild Task，并让 `task_restarts` 统一记录 full/atomic 两类人工重启因果？
- **业主回答**：同意 Codex 的完整推荐。Full Task retry 只允许从 `failed/cancelled` 以 command + CAS 回到 `queued`，创建新 root generation；`succeeded` 改走新 rebuild Task；`task_restarts` 统一记录 `full_task/atomic_document` 两类人工重启因果。登记为 `T-O-8`。

### Q7 — Collect-all 期间已成功 atomic child 的发布与读取时机

- **驱动真相**：`T-O-2`、`T-O-5`、`T-O-6`。
- **本题只裁决**：一个 required child 已取得完整 publication proof，但 scatter root 仍 `running` 或最终因其他 child 而 `failed` 时，该 child 是否已可独立读取和检索。
- **本题不裁决**：向量写入算法、DocumentVersion schema、失败 child restart admission、Task 总状态。
- **Codex 当前建议**：采用 **child proof-gated early publication**：

  1. child Execution 一旦通过向量 + filter metadata publication proof，即把该 Task item/DocumentVersion 标为 ready，并允许按 `document_uuid` 读取和检索；
  2. 不等待 root Task terminal，也不因 sibling 失败而撤销已经 proof-valid 的 child；
  3. Get Task 仍按 `T-O-2` 保持 `running` 或最终 `failed`，同时通过 counts/items 明确呈现哪些 child 已 ready、哪些 failed/active；
  4. failed child 后续按 Q5 创建独立 rebuild Task；successful siblings 不重复构建；
  5. 只有明确的 `document.deactivate/delete` 或版本替换策略可以撤销其检索可见性，parent Task 失败本身不是撤销命令。

- **Reasoning**：Collect-all 的价值之一就是保留健康 child 的有效工作。如果所有 child 都必须等待 root 成功才可见，那么任一坏 child 会把已经验证成功的知识无限期扣住，也会迫使重试整批。原子 proof 是更准确的发布围栏。
- **问题**：Owner 是否确认成功 child 在 root 尚未终态或最终失败时仍可 proof-gated 独立发布、读取和检索，并且 parent Task 失败不回滚这些成功 child？
- **业主回答**：同意 Codex 的完整推荐。成功 child 取得 publication proof 后即可独立发布、读取和检索，不等待 root 终态；parent Task 最终失败不回滚成功 child，撤销必须通过显式资源命令。登记为 `T-O-9`。

### Q8 — Cancel scatter Task 时已完成/已发布 child 的处理

- **驱动真相**：`T-O-2`、`T-O-3`、`T-O-5`。
- **本题只裁决**：cancel command 赢得 CAS 后，对已经 publication-proof succeeded 的 child 是否补偿删除，以及 root 何时进入 `cancelled`。
- **本题不裁决**：具体 cooperative cancellation、lease fencing、向量 purge 实现或 delete/deactivate workflow。
- **Codex 当前建议**：采用 **forward-stop, no implicit rollback**：

  1. cancel 赢后禁止新 claim/fan-out，并向 active child/Process 传播 stop；尚未开始的 required child 归约为 cancelled/skipped-by-cancel；
  2. 已经 publication-proof succeeded 的 child 保持 ready，不因 parent cancel 被隐式删除或 purge；
  3. root 只有在全部 active descendants 被 fencing 后终态、已无可能提交晚到业务结果时，才从 `cancelling → cancelled`；
  4. Task result 保留已完成/已取消/失败 counts 与 child links，但总状态是 `cancelled`，不产生 partial-success 状态；
  5. caller 若要撤销已发布知识，必须另发 `document.deactivate/delete` Task，形成独立 Audit/因果链。

- **Reasoning**：Cancel 表达“停止继续执行”，不是资源删除命令。把两者混合会让一次运行控制操作偷偷删除已验证知识，并破坏 Q5 的因果审计。显式 deactivate/delete 才能提供可追溯的资源补偿。
- **问题**：Owner 是否确认 scatter cancel 只停止未完成工作、不隐式回滚已发布 child，并以所有 active descendants 已 fenced/terminal 作为 `cancelled` guard？
- **业主回答**：同意 Codex 的完整推荐。Scatter cancel 采用 forward-stop、no implicit rollback；已发布 child 保持 ready，全部 active descendants 已 fenced/terminal 后 Task 才进入 `cancelled`，资源撤销另建 deactivate/delete Task。登记为 `T-O-10`。

### Q9 — 全局 restart lineage 与状态拉取的公共查询边界

- **驱动真相**：`T-O-5`、`T-O-7`。
- **本题只裁决**：如何从全局枚举所有 restart、按因果链追溯并拉取当前状态，同时保持 Task/Document/Execution 权限边界。
- **本题不裁决**：复杂 RBAC、日志搜索引擎、Process debug payload、具体 retention 时长。
- **Codex 当前建议**：建立两类 team-scoped durable read model：

  1. **Global restart list**：按 team 分页，支持 `restart_uuid/source_task_uuid/restart_task_uuid/document_uuid/restart_scope/admission_outcome/current_task_status/time range` 过滤；status 来自 join Task，不从 restart 表复制；
  2. **Causal lineage query**：以任一 `restart_uuid/task_uuid/document_uuid` 为入口，返回有向因果链 `source Task/Document → restart record → restart Task → generation summaries`；默认只返回外部稳定 Task/Document identity、status/result/error summary；
  3. Execution/Process UUID 和 step error detail 只进入内部诊断扩展，不成为普通 caller 操作参数；
  4. 查询必须基于 durable tables/terminal summaries，不能依赖短期 Process rows 或日志；
  5. Task soft-delete、Process compaction 不得让 lineage 断链；默认业务列表可以隐藏 soft-deleted Task，但 lineage 查询必须返回 tombstone identity 与最后 durable summary；
  6. cursor、filter 与排序必须稳定，所有查询强制 `(team_uuid, ...)` 隔离。

- **Reasoning**：Owner 要求的是全局可治理的 restart 业务账本，不是把日志搜索包装成 API。以 restart causal truth 关联 Task 状态，可以完整追溯又不产生 status 双真相；普通 read model 继续隐藏内部 Execution/Process 控制面。
- **问题**：Owner 是否确认上述 global restart list + causal lineage query，并确认 soft-delete/Process cleanup 不得破坏 lineage、普通查询不暴露 Execution/Process UUID？
- **业主回答**：同意 Codex 的完整推荐。冻结 team-scoped global restart list 与 causal lineage query；状态从 Task join，soft-delete/Process cleanup 不得断链，普通 caller 不操作 Execution/Process UUID。登记为 `T-O-11`。

### 9.3 最终反方制衡与下游移交
