## 1. S05 重新校准后的唯一工作面

### 1.1 定位

S05 是 MKB 的 **摄入获取、解码、确定性规范化、内容清洗与观察候选构建域**。它回答：一个已获授权的 `IntakeSource` 如何被读取，输入的 bytes/representation 如何被识别和验证，single/scatter 观察如何证明完整性，各 member 如何获得 source-scoped `ExternalKey` 与 canonical semantic values，以及 clean 产物如何携带足够 provenance 交给 S06。

S05 不是“把任何东西变成一段字符串”的通用 converter，也不是第二套 Task/Execution/Process/Intake 状态机。它通过 S03 `ProcessCapabilityManifest` 暴露 RAG-specific leaf capabilities，通过 S04 `CandidateSetStagingPort` 产出 `IntakeCandidateSet`，但不能自行创建 accepted `IntakeSnapshot`、决定 `IntakeRevision`、推进 serving pointer 或选择下游 Workflow route。

### 1.2 Canonical contract chain

```text
Task request / exact Intake target                         [S01/S02]
  → WorkflowRevision + typed ProcessCommand               [S03]
  → resolve source + acquire representation               [S05]
  → media/encoding/envelope validation                    [S05]
  → deterministic source mapping/canonicalization         [S05]
  → optional clean extraction                             [S05]
  → CandidateSetPage(s) + evidence + CandidateSetSeal     [S05→S04 port]
  → canonical acceptance transaction                      [S04]
       Snapshot + Membership + Item/Revision decision
       ChangeSet + scheduling outbox
  → typed route and downstream clean/structurize build    [S03/S05/S06]
```

这里有两个必须长期保持的线性化边界：

1. S05 handler 返回、HTTP 2xx、对象写入、queue ACK、日志成功都不等于 accepted Intake truth；
2. `CandidateSetSeal` 只证明候选集合具备 acceptance 资格，只有 S04 canonical transaction 才创建 Snapshot/Revision/Membership 真相。

### 1.3 五个工作平面及状态投影

| 平面 | S05 负责 | 状态/证据如何表达 | 明确不负责 |
|---|---|---|---|
| Source/capability 平面 | source kind、descriptor/config schema、adapter/capability binding、部署可用性 | immutable versioned definition + S03 capability/readiness evidence | Workflow graph、Task intent enum |
| Acquisition/I/O 平面 | inline/object/HTTP/registered API 读取、redirect/pagination、限额、logical handle | Process phase/outcome + representation evidence | 物理 backend、绝对路径、secret 明文 |
| Decode/canonicalize 平面 | MIME/encoding 判定、typed envelope validation、ExternalKey normalizer、canonical bytes/value | versioned profile refs + digest + validation report | 接受 IntakeRevision、修改旧 Revision |
| Observation integrity 平面 | single/scatter scope、page chain、member validation、complete/partial 声明 | CandidateSet head/pages/seal + rejection/completeness evidence | absence transition；S04 才能计算并提交 |
| Clean/provenance 平面 | deterministic parser 或显式 browser/PDF/OCR/Vision clean，loss/quality/lineage | staged clean candidate + typed ProcessOutcome/proof | S06 structure、S07 summary、S08 embedding、serving publication |

S05 的业务步骤可以投影为：

```text
resolve → acquire → decode → map/extract → validate → stage → seal
```

这些词是 Process 的 RAG phase/evidence，不新建 `intake_clean_jobs` 或另一套 mutable status table。S03 仍是 `ready/claimed/running/retry_wait/succeeded/failed/cancelling/cancelled` 的唯一 Process 状态机；S04 仍是 `open → sealed → accepted | abandoned` 的唯一 CandidateSet staging 状态，其中 S05 只能请求 append/seal/abandon，不能写 `accepted`。

### 1.4 S05 的输入与输出边界

| 方向 | Contract | S05 可以做 | S05 不可以做 |
|---|---|---|---|
| 输入 | typed `ProcessCommand`、exact Workflow/Capability version、team-scoped Intake target、logical input handles、secret refs | 校验 fence/schema/digest，按 capability 获取输入 | 读取完整 Workflow JSON后自行选 route；解释 opaque payload |
| 中间 | raw/decoded/canonical/clean staged representations | 计算 digest、记录 provenance/loss/quality、通过 S13 logical adapter 持久化 bytes | 把本地路径/R2 key当业务身份；吞掉 write failure 后继续宣称完整 |
| 输出 | typed `ProcessOutcome`、CandidateSet page/seal refs、staged artifact descriptors、validation/completeness evidence | 提交已验证 candidate；对失败 fail-loud 或显式 partial | 直接写 Snapshot/Item/Revision；根据当前 DB rows猜 expected set |

### 1.5 明确 out of scope

- Task HTTP/六态、retry/restart ledger、TaskItem projection：`S02`；
- Workflow definition、route、claim/lease/fencing、Process retry：`S03`；
- accepted Snapshot、Item/Revision identity、ChangeSet、serving、retention：`S04`；
- layered LS-RAG schema、block/coordinate/structure repair：`S06`；
- summary/meta fusion、embedding/vector/index/publication：`S07-S09`；
- model/prompt registry、fallback 和推理 endpoint：`S11/S14`；
- Turso exact DDL、queue/outbox driver：`S12`；
- bytes backend、atomic write、locator、physical GC：`S13`；
- event/log/metric/trace 的物理 schema 与 retention 数值：`S15`；
- URL/connector 授权、network egress policy、secret lifecycle 的权威规则：`S16`。
- 通用validator插件平台、动态脚本/agent生成规则、shadow/canary rollout与全局readiness控制面：v1明确不建设；未来若需要必须reopen S05/S14-S16；
- review SLA、自动超时处置、retention数值、物理GC、metric/alert/runbook：分别归S13/S15，S05只提供稳定引用、typed event与不得误放行的不变量。

S05 必须定义对上述域的需求和端口，不得把需求实现偷回自身。

### 1.6 Owner v1 scope correction（2026-07-16）

Preflight在S05中只承担一个有限职责：**对clean链路已经提交的frozen acquisition/collection/artifact evidence进行确定性准入校验，并决定是否具备自动进入RAG的资格**。它不是第二套fetch/clean执行器，也不是通用policy、plugin、deployment或reliability平台。

v1必须实现：

- 每条allowlist binding指向exact、code-owned、versioned validator；
- validator只读frozen evidence，返回`passed | blocked`；运行异常复用S03 Process retry/failed；
- `passed + allowlisted`直接继续RAG并保留Outcome，不创建虚构的released gate；
- 只有需要人工动作时创建Execution-owned durable gate，并以CAS/audit/outbox恢复同一Execution；
- stable manifest/version/check-key/typed outcome/gate ports为未来扩展留边界。

v1不提前实现空表、空状态、动态规则语言、runtime fixture治理、shadow/canary、全局adapter readiness、自动timeout、retention/GC或完整observability平台。未来能力通过新manifest version、正式schema migration和对应Spec reopen增加，不借`payload_extra`暗中生长。

## 4. Websearch 外部一手事实支持

> 外部标准提供设计约束与术语分辨，不替代 MKB owner verdict，也不直接规定 MKB 表结构。

| Ref ID | 一手事实 | 对 S05 的支持边界 |
|---|---|---|
| `WEB-S05-01` | [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) 区分 HTTP message content、representation data/metadata、Content-Type/Content-Encoding 与 validator fields；ETag/Last-Modified 服务 conditional semantics。 | HTTP header/validator 是 acquisition evidence，不自动成为 Intake identity、Revision fingerprint 或完整性证明。 |
| `WEB-S05-02` | [RFC 9530](https://www.rfc-editor.org/rfc/rfc9530.html) 分离 `Content-Digest` 与 `Repr-Digest`，并要求 digest 携带算法语义。 | 支持 exact transfer bytes、selected representation 与 canonical semantic digest 分账；digest 不能省略 scope/algorithm/version。 |
| `WEB-S05-03` | [IANA Media Types Registry](https://www.iana.org/assignments/media-types/media-types.xhtml) 是标准 media type 注册表。 | MIME allowlist 应使用规范 media type，并保留原始声明与 MKB verified type；扩展名不能成为唯一判断。 |
| `WEB-S05-04` | [WHATWG Encoding Standard](https://encoding.spec.whatwg.org/) 定义编码 label、BOM 优先及 decoder error 行为。 | encoding 决策必须可复验；BOM/label/sniff/fallback 与 replacement/error count 应进入证据，而不是静默“猜成 UTF-8”。 |
| `WEB-S05-05` | [Unicode UAX #15](https://unicode.org/reports/tr15/) 定义 NFC/NFD/NFKC/NFKD；兼容分解会改变部分语义区分。 | 推荐 canonical text 使用 versioned NFC；不得默认用 NFKC 抹平源语义。 |
| `WEB-S05-06` | [RFC 8785 JCS](https://www.rfc-editor.org/rfc/rfc8785.html) 给出 I-JSON 的确定性 canonical serialization，但不会替应用决定字段语义。 | provider JSON/member/root digest 可采用 JCS；字段选择、Unicode策略和 source semantics 仍必须由 versioned adapter 定义。 |
| `WEB-S05-07` | [RFC 8288](https://www.rfc-editor.org/rfc/rfc8288.html) 定义 typed link relations，包括 `next`，但 link relation 本身不证明源集合完整。 | pagination continuation 必须被保留；`no next` 仅在 adapter contract 明确时才构成 exhaustion evidence。 |
| `WEB-S05-08` | [W3C PROV-DM](https://www.w3.org/TR/prov-dm/) 区分 entity、activity、derivation、revision 与 collection membership。 | raw representation、clean activity、clean entity、CandidateSet collection 与 producer lineage 应显式分开；日志文本不是 provenance SSOT。 |
| `WEB-S05-09` | [Airbyte Python CDK `AbstractSource`](https://github.com/airbytehq/airbyte-python-cdk/blob/main/airbyte_cdk/sources/abstract_source.py) 将source-specific `check_connection`与`discover/read`分离，并由具体connector代码实现。 | 支持每个allowlist绑定code-owned validator；但validator不应复制acquisition/read职责。 |
| `WEB-S05-10` | [Great Expectations ValidationDefinition](https://docs.greatexpectations.io/docs/core/run_validations/create_a_validation_definition/)与[Checkpoint](https://docs.greatexpectations.io/docs/reference/api/checkpoint_class/)分离固定数据/规则引用、validation run/result与后续action。 | 支持binding、outcome与Workflow action分账；不证明MKB必须建设九张表。 |
| `WEB-S05-11` | [Kubernetes Validating Admission Policy](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/)分离policy、binding、Deny/Warn/Audit；其[admission good practices](https://kubernetes.io/docs/concepts/cluster-administration/admission-webhooks-good-practices/)强调低副作用、测试和谨慎扩展。 | 支持“匹配不等于绕过验证”和只读validator；复杂rollout/readiness属于平台治理，不是MKB v1准入链路的必需前提。 |
| `WEB-S05-12` | [LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)使用durable checkpoint与stable thread pointer暂停/恢复；[Argo Workflows suspend](https://argoproj.github.io/argo-workflows/walk-through/suspending/)支持显式suspend/resume与可选duration。 | 支持Execution-owned durable gate与same-execution resume；不支持把统一自动timeout→failed当作行业强制规范。 |
| `WEB-S05-13` | [Temporal Python SDK](https://github.com/temporalio/sdk-python)提供history replay并检测non-determinism。 | 支持运行中binding不可被新代码静默重解释；MKB只需锁定exact version/digest，不复制Temporal deployment/versioning平台。 |

### 4.1 综合辨证

1. **Content-Type 不等于可信类型**：它是 representation metadata；S05 必须保留“declared、detected、verified”三个层次及冲突结果。
2. **ETag 不等于内容身份**：同一资源可能因 content negotiation 获得不同 representation，弱 validator 也不保证 byte equality；它只能用于条件请求与辅助一致性判断。
3. **Digest 不等于 UUID**：digest 证明某个明确输入的完整性或相等性；Intake UUID 与 ExternalKey 仍由 S04 身份规则决定。
4. **Canonicalization 不等于 cleaning**：JCS/NFC 可以确定性规范表示；browser render、boilerplate removal、OCR、Vision/LLM extraction 属可能有损的派生活动。
5. **Pagination 不等于 completeness**：看到一页、一个 `next` 或没有 `next` 都不足以跨 provider 通用证明 authoritative scope；该证明必须在 provider adapter contract 内定义。
6. **Preflight不是一项单独的RAG行业标准**：MKB只组合connector check、data validation、admission binding与durable HITL的有效原理；外部项目不能反向规定MKB的表数量或治理平台范围。

## 6. Round 1 — Foundational Intake & Cleaning Constitution（Q1-Q4）

### Q1 — IntakeSource kind、Process capability 与 v1 可执行范围如何正交

- **单一裁决面**：S05 接受什么来源，以及来源身份、获取方式、清洗方式如何被注册和静态组合。
- **不在本题裁决**：exact CandidateSet member 字段、限额数值、retry/error taxonomy、quality threshold。
- **证据驱动**：`U-S05-01..05/U-S05-10..12`；`LF-S05-01..08/LF-S05-12..13`；`WEB-S05-01/03/04`。

#### 推荐方案

1. v1 将 `IntakeSource.source_kind` 冻结为四个语义清晰的入口族：

   | source kind（推荐 key） | 身份/descriptor 语义 | 典型输入 | cardinality |
   |---|---|---|---|
   | `inline_payload` | 请求已携带 representation，不需要外部 fetch | UTF-8 text、HTML、JSON/API payload | single；受控 adapter 可声明 collection |
   | `local_object` | 指向 S13 管理的本地 logical object，名称/路径不是业务身份 | upload、text/HTML/JSON/PDF/image object | 通常 single |
   | `http_resource` | 指向一个受 S16 egress policy 约束的 HTTP(S) resource | static HTML/text/JSON/PDF | single；不得因页面内链接隐式 scatter |
   | `registered_api` | 指向内部注册的 provider operation 与 typed query scope | single API、paged/scatter API | single 或 scatter，由 definition 声明 |

   不提供 `file`、`document`、`other` 或任意字符串 fallback。未来新增 source kind 必须注册新 versioned definition，不能塞进 `payload_extra`。

2. Source kind 只描述 **来源身份与 descriptor schema**；下列执行维度必须正交：

   - acquisition：`inline_read / object_read / static_http / browser_render / registered_api_fetch`；
   - decode/parse：`text_decode / html_parse / json_map / pdf_text_extract / image_decode`；
   - clean：`deterministic_clean / ocr / vision_extract / model_assisted_clean`；
   - cardinality：`single / collection`；
   - completeness contract：provider-specific scope/exhaustion definition。

   `browser`、`PDF`、`Vision` 都不是 IntakeSource kind；`scatter` 也不是 source kind。

3. S05 提供一个内部注册、immutable、versioned 的 source-kind definition manifest（候选名 `IntakeSourceKindDefinition`），至少绑定 descriptor/config schema、ExternalKey normalizer、允许的 cardinality、允许的 acquisition capabilities 与 completeness contract refs。它不开放外部 CRUD，并进入既有 GreenfieldBootstrap `RegistryManifest` digest/readiness 校验；exact storage/code-owned 形式留给 Round 2，但同 key/version 异 digest 必须 fail-loud。

4. 执行能力继续使用 S03 已冻结的 `ProcessCapabilityManifest`，不另建平行 action registry。Workflow step 绑定 exact `process_key + contract_version`，manifest 同时声明 typed ports、参数、side-effect class、outcome schema和proof。Source-kind definition 只能引用这些 capability，不复制 handler 或 route。

5. Owner 已确认 legacy-family 对网页、PDF、API single/scatter、多 API 通道和多种网页 fetch 方式均有生产 ReferenceAnchor；OCR 虽缺少同等 legacy 实现，也可基于本机能力直接完成。因此冻结后的 v1 launch matrix 为：

   | 能力 | v1 contract | v1 实现要求 |
   |---|---|---|
   | inline/local 的 `text/plain`、`text/html`、`application/json` | 必须 | 一等能力，必须交付 |
   | static HTTP、browser render 与网页 PDF 获取 | 必须 | 多 fetch 通道分别注册、必须交付 |
   | local/HTTP PDF deterministic text-layer extraction | 必须 | 一等能力，必须交付 |
   | internally registered API 的多 provider/channel、single/scatter、pagination | 必须 | 一等能力，必须交付并有 golden adapters |
   | 本机 OCR | 必须 | 一等本地能力，必须交付 |
   | Vision/model-assisted clean | 必须 | 显式 Workflow capability，必须交付 |
   | arbitrary remote code、caller-defined provider、页面递归 crawl | 不纳入 | admission reject |

6. “v1 必须交付”不意味着所有请求都可任意调用所有策略。每条 web/API/PDF/OCR/Vision capability 仍必须有独立 manifest、typed schema、适用 media/source constraints 与 readiness evidence。active Workflow 引用的 handler/model/secret/policy 缺失时，在 Task admission 或 Process materialization 前 fail-closed，不能运行到一半才换算法。

7. source kind、capability、media allowlist、normalizer、clean profile 都绑定 exact version/digest。Workflow retry 继承原 Execution binding；新的独立 rebuild 才能按当时 active resolver选择新 generation，遵守 S03/S04 冻结语义。

#### Reasoning 与制衡

- legacy action registry 证明显式注册有效，但 `htmlCrawl-geminiClean` 证明把 acquisition 和 clean 拼进 branch name 会快速产生组合债务。正交维度可让 Workflow 静态选择并校验，而不是由 cleaner 内部猜 fallback。
- source kind 必须稳定，因为它参与 IntakeSource descriptor 与 ExternalKey namespace；browser/model 是可替换执行能力，不能反向改变来源身份。
- Owner 对生产覆盖的确认关闭了“是否纳入 v1”的问题：网页多 fetch、PDF、API 多通道/single/scatter 与本机 OCR 都是交付范围，而不是 future/optional placeholder。
- PDF text-layer 与 OCR/Vision 都是一等能力，但必须由 Workflow/typed policy 显式选择。若把 Vision 设为不留证据的隐式 fallback，同一输入会因运行环境不同得到不可复验结果。
- 新增 source-kind definition 会增加一个治理对象，但它补的是 S04 已明确留给 S05 的 source kind/descriptor/normalizer truth，且不会与 S03 capability manifest 重叠。

#### Owner 问题（已回答）

Owner 是否接受上述正交宪法与 v1 范围：四类 `IntakeSource` kind；source kind、acquisition、parse/clean、cardinality 分离；source-kind definition 内部版本化注册并引用 S03 `ProcessCapabilityManifest`；网页多 fetch、PDF、registered API 多通道/single/scatter、OCR/Vision/model clean 均进入 v1，且禁止无证据自动 fallback 与 caller-defined adapter？

#### 业主回答

业主接受 Q1 的正交注册与执行推荐，并进一步确认：legacy-family 的 Clean Worker 已对网页、PDF、API 等能力提供可核查的生产 ReferenceAnchor；API 本身存在多条通道，网页也存在多种 fetch 方式。OCR 即使缺少同等 legacy 实现，也可以基于本机能力直接实现。因此上述能力全部进入 MKB S05 v1 的正式实现范围，不再以 future 或 optional placeholder 处理。MKB 只借鉴 legacy 原理与踩坑，所有能力均在本地重新实现，并继续遵守 source kind、acquisition、parse/clean、cardinality正交，versioned manifest、typed port/readiness、显式 Workflow 选择和禁止 caller-defined adapter 的边界。

#### 裁决状态

`frozen → T-O-49 / T-O-50 / T-O-51`

### Q2 — Allowlist 是否必须通过强制 Preflight 才具备自动放行资格

- **单一裁决面**：任何白名单web/API/local通道是否都必须先获得完整preflight proof，只有proof通过才能自动进入RAG。
- **不在本题裁决**：review state归属、批准target、CRUD URI、具体阈值数值和Task terminal映射。
- **证据驱动**：Owner明确要求白名单也预检、API不可用或混入不可解析member时整体阻塞；`LF-S05-07..10/LF-S05-14..21`；S03 typed ProcessOutcome/route与S04 complete/partial边界。

#### 推荐方案

1. 将allowlist定义为 **conditional auto-admission eligibility**：它只说明某个exact source/fetch/clean profile在preflight全部通过后可以自动放行，绝不授予validation bypass。Cloudflare Docs式确定性网页fetch、registered API、PDF/OCR等均可进入allowlist，但必须绑定各自的versioned preflight profile。

2. 建立内部注册、immutable、versioned 的preflight definition；v0.6统一由`PreflightValidator`读取S05 Processes已经冻结的typed evidence并聚合exact outcome，不重新执行fetch/clean。至少覆盖三个证据段：

   | 检查段 | 必须证明 | 典型阻塞 |
   |---|---|---|
   | source/acquisition | endpoint可达、鉴权/状态、response envelope、declared/detected media、redirect/pagination/scope | API不可达、403/5xx、响应类型漂移、分页链断裂 |
   | collection/member | required member全量可见、ExternalKey/schema/digest有效、duplicate/conflict/completeness受控 | 混入不可解析member、required字段缺失、同key冲突、silent skip |
   | clean/artifact | exact input/output refs、artifact可读、digest/size、非空/结构/质量最低门、clean profile匹配 | 空clean输出、截断、parser/模型异常、artifact缺失或digest不符 |

3. Preflight可以由多个leaf Process产生证据，但最终必须由一个versioned aggregator对exact evidence set作出`passed | blocked`结论。`blocked`必须带结构化`block_class/reason/affected refs/profile version/evidence digest`；日志warning、异常数组或`payload_extra`不能替代。

4. 自动放行矩阵冻结为推荐路径：

   | Allowlist match | Preflight | Admission结果 |
   |---|---|---|
   | 是 | `passed` | 保存Outcome并自动继续RAG；不创建gate/decision |
   | 是 | `blocked` | 有可审核Artifact则进入Execution gate；否则retry/remediation/failed |
   | 否 | `passed` | `human_review_required` |
   | 否 | `blocked` | 全部阻塞，并携带preflight异常证据 |

5. 对single，`blocked`阻止该exact target；对scatter/API collection，只要一个required page/member/check失败，默认阻塞当前root Execution代表的整个collection scope。proof-valid members不得提前进入RAG；preflight不能通过删除坏项把collection伪装为成功。

6. transient acquisition错误先遵守S03 retry/backoff/max-retries。预算耗尽后，若没有可审核artifact，记录`source_unavailable`类阻塞；人工只能执行remediate后retry或abandon，不能“批准不存在的内容”。若artifact存在但schema/quality异常，则可进入内容review；是否允许override由注册policy明确，人工不能伪造缺失digest/completeness proof。

7. Preflight outcome必须绑定team、execution/process fence、source/adapter/capability/profile versions、observation/member/root digests、artifact refs/digests、check-set digest与时间。相同evidence重复计算必须幂等；evidence或profile变化必须产生新outcome/fence。

8. policy与preflight profile在Execution binding时锁定exact version/digest。运行中更新allowlist/profile不得热切正在等待的Execution，也不得自动释放旧blocked gate；重评必须显式触发并留下因果审计。

9. `preflight passed`、allowlist自动路由和clean Process succeeded都不是Task success。Task/Execution仍须完成S03 Workflow的后续RAG Processes与terminal proof。

#### Reasoning 与制衡

- 确定性API或网页通道只代表历史上稳定，不代表未来响应永远不漂移。白名单若跳过preflight，会把最常自动运行的通道变成最大静默污染源。
- 将source、collection和clean evidence聚合为一个admission preflight，可以在不混淆各Process职责的前提下给Workflow一个明确route fact。
- collection fail-closed会牺牲部分可用数据，但符合Owner“混入无法解析内容则全部自动阻塞”的要求，并保护S04 completeness与absence语义不被silent skip破坏。
- 区分`source_unavailable`与“已有artifact但内容异常”很重要：前者需要修复/retry，后者才存在可被人类实际审阅的内容。

#### Owner 问题

Owner 是否接受上述mandatory preflight方案：allowlist只在exact preflight profile全部通过后授予自动放行；source、collection/member和clean/artifact均需typed evidence；任一required异常默认阻塞当前single/collection Execution scope；无artifact的source failure只能remediate+retry/abandon，有artifact的异常才进入可审阅路径？

#### 业主回答

业主同意mandatory preflight推荐。Allowlist不是API或确定性fetch通道的无条件信任，而是exact source/fetch/clean profile在全部preflight checks通过后的自动放行资格；确定性API、Cloudflare Docs式网页fetch、PDF/OCR等白名单通道都必须执行相同的预检原则。若API突然不可请求、response/schema发生漂移、collection混入无法解析的required member，或clean/artifact proof不满足要求，当前single/collection Execution scope必须整体自动阻塞，不能silent skip后继续。无可审核artifact的source failure只允许remediate后retry或abandon；存在artifact的内容异常才进入受policy约束的人审/override路径。业主接受versioned profile/evidence、collection fail-closed、运行中不热切policy以及preflight不等于Task success的完整方案。

#### 裁决状态

`frozen → T-O-52 / T-O-53`

### Q3 — Human review 是否只作为 Execution-owned durable gate

- **单一裁决面**：human review的durable state、等待与恢复权威是否完全归属Execution，而不进入Intake lifecycle或由Process lease承载。
- **不在本题裁决**：复合ReviewTarget字段、root/child粒度、decision schema、API和terminal聚合。
- **证据驱动**：Owner明确指出Intake与Execution已解耦，review发生在`execution_uuid`之后、clean之后、RAG之前；S03 Execution `waiting`与Process claim/lease边界；D01三层运行身份。

#### 推荐方案

1. 撤回“review truth由S04 acceptance拥有/调度”的旧推荐。Intake可以独立收录Snapshot/Item/Revision/Artifact事实，但不得出现`pending_review/approved/rejected` lifecycle或pointer；这些状态不改变Intake latest/serving/deactivate/delete语义。

2. Human content review的唯一业务位置为：同一`execution_uuid`内，clean Process及可审阅artifact已经完成，且任何required preflight异常已被记录，S06-S09 RAG Processes尚未materialize/运行。

3. 复用S03已冻结的Execution control state：

```text
Execution running
  → clean Process terminal
  → preflight outcome
       passed + allowlisted
         → continue running → RAG
       passed + non-allowlisted
         → waiting(reason=human_review_required)
       blocked with reviewable artifact
         → waiting(reason=preflight_content_blocked)
       blocked without artifact
         → S03 retry/failed or explicit remediation/abandon（no human gate）

waiting + fenced decision/command
  → released → ready/running（same execution_uuid）
  → rejected/abandoned → terminal convergence（exact Task映射后定）
```

4. 需要human input时引入Execution-owned supporting truth（候选名`ExecutionGate`），保存gate UUID/generation、execution UUID/fence、gate kind/reason、opened evidence ref/digest、resume condition、current projection与时间。无Artifact的source/runtime failure不创建此gate。它不是新运行身份，也不是Intake asset；exact logical table由Round 2/S03-S12交叉冻结。

5. Clean/preflight Process在提交typed Outcome后进入正常terminal，不持有claim/lease等待人类。Execution进入`waiting`时不得存在“正在运行但等人”的假Process；Task aggregate保持非terminal，polling必须显示typed wait reason而不是伪装为stuck pending。

6. Policy或人工decision必须在同一事务中CAS current Execution/gate fence、append audit并写resume/terminal outbox；commit后才wake queue。HTTP响应、UI点击、queue send或日志不构成release。

7. 批准或remediation后恢复 **同一个 execution_uuid**。只有full Task retry、明确的新Task或Execution generation语义才创建新Execution；普通human resume不能借机热切WorkflowRevision、capability/profile或输入artifact。

8. 新artifact/preflight outcome若改变gate target digest，旧decision/fence自动失效并开启新gate generation。IntakeRevision可以作为evidence ref参与校验，但不拥有gate状态，也不因release/reject发生mutation。

9. Execution/Process projection后续清理不能删除长期review causation/decision audit；retention物理归属由S12/S15后定，但必须持续支持按task/execution/intake/artifact追溯。

#### Reasoning 与制衡

- Intake回答“收录了什么”，Execution回答“这次运行是否继续处理”。把review写入Intake会让同一Revision因不同Workflow/Execution产生互相覆盖的处理状态。
- Execution `waiting`已经是声明式Workflow暂停与恢复的正确控制面；新增Intake state或clean-review job只会制造第二套状态机。
- Process不等待人类，可保留claim/lease/fencing语义，避免人工等待数小时或数天期间出现stale lease、假running和错误retry。
- same-execution resume保留完整program binding和因果链；gate fence确保恢复时仍处理人工看到的exact evidence。

#### Owner 问题

Owner 是否接受将human review完全冻结为Execution-owned durable gate：Intake不保存review state；clean/preflight Process先terminal，Execution以typed reason进入`waiting`；decision经CAS+audit+outbox释放同一execution_uuid，且任何artifact/evidence变化都使旧gate decision失效？

#### 业主回答

业主同意将human review完全冻结为Execution-owned durable gate。Intake与Execution保持解耦：Intake可以收录Snapshot/Item/Revision/Artifact，但不保存review lifecycle、批准状态或恢复控制。Human review发生在`execution_uuid`已经创建、clean完成之后、RAG Processes之前；clean/preflight Process先terminal，Execution使用既有`waiting` control state与typed reason持久等待，不占用Process claim/lease。Policy或human decision经Execution/gate fence CAS、append-only audit与outbox恢复同一个`execution_uuid`；artifact/evidence变化使旧gate generation失效。Review因果审计不得随Process projection cleanup消失。

### Q4 — ReviewTarget 是否必须绑定 Execution + Intake + Artifact + Preflight Evidence

- **单一裁决面**：policy/human decision究竟批准哪个不可替换的复合目标，以及single/scatter如何使用root/child Execution gate防止跨运行或跨artifact复用。
- **不在本题裁决**：UI、exact URI、S16角色名、超时天数、Task最终状态与人工评论格式。
- **证据驱动**：Owner要求至少绑定`execution_uuid`，并确认批准对象应组合Intake、Execution与Artifact；Q2 collection整体阻塞原则；D01/S02 execution/restart因果与S04 native scatter身份。

#### 推荐方案

1. 定义execution-scoped复合审核对象（候选名`ExecutionReviewTarget`），最小绑定：

```text
team_uuid
+ task_uuid / execution_uuid / execution_generation / execution_fence
+ workflow_revision_uuid / compiled_digest
+ gate_uuid / gate_generation / gate_kind
+ IntakeSource/Snapshot/Membership/Item/Revision exact refs（按scope）
+ clean artifact or DerivedGeneration ref + media/size/content digest
+ clean capability/profile version + producer Process fence
+ preflight profile/outcome/check-set digest
```

   `task_uuid`用于因果查询，真正的运行批准权落在exact `execution_uuid + fence`；Intake和Artifact是被批准处理的证据，不承载review state。

2. Decision只能作用于上述target digest。禁止批准裸IntakeItem、`latest_revision_uuid`、裸Execution、路径、provider key或“当前clean输出”。相同IntakeRevision在不同Execution/Workflow/profile下必须独立评估；一个Execution的decision不得成为另一个Execution的通行证。

3. Single入口使用一个Execution gate，target绑定exact Item/Revision与clean artifact/preflight outcome。Artifact重写、clean retry产生新digest或Execution fence变化时，旧target成为stale并开启新gate generation。

4. Scatter采用两级围栏：

   | Gate scope | 绑定对象 | 职责 |
   |---|---|---|
   | root collection gate | root `execution_uuid` + IntakeSnapshot/CandidateSet/root digest + expected required set + collection preflight outcome | 任一required page/member/check失败时阻塞整个collection；root未release前不允许RAG children推进 |
   | child content gate | child `execution_uuid` + Membership/Item/Revision + exact clean artifact + item preflight evidence | collection gate通过后，对非白名单或需人工判断的proof-valid child逐项批准/拒绝 |

5. Root gate不能用人工布尔值伪造缺失artifact、digest、required member或complete-authoritative proof。`source_unavailable`只能remediate后retry/abandon；已有artifact的非关键内容异常，只有preflight policy显式声明`human_override_allowed`时才能override，并必须保留原blocked evidence。

6. Snapshot/batch操作只是command便利层：它必须绑定root gate fence，并确定性展开为exact child target decisions或root remediation decision。禁止一个无member明细的`approved=true`覆盖整个scatter集合。

7. Decision truth归Execution control/audit域，推荐append-only（候选名`ExecutionGateDecision`），至少保存target digest、decision/action、source=`policy|human`、actor、policy/preflight versions、reason、expected fence、causation、occurred_at与decision digest。所有MKB-owned表继承`payload_extra`，但核心字段不得下沉其中。

8. Release transaction必须原子执行：validate team/auth/execution/gate/target/evidence fence → append decision → CAS gate/Execution projection → 写RAG resume outbox。重复同target同decision幂等；同fence异decision冲突；stale target拒绝。

9. Child approved可在root gate已release后独立推进；rejected/pending child不进入RAG。root collect-all按committed required set与durable gate decisions聚合。parent Task如何表达部分拒绝、source remediation失败或超时留给Round 2与S02交叉裁决。

#### Reasoning 与制衡

- 只绑定IntakeRevision会让批准跨Execution/Workflow错误复用；只绑定execution_uuid又无法证明人工看到的是哪份artifact。复合target同时解决program binding与content TOCTOU。
- root gate实现Owner要求的“混入一个不可解析内容则全部自动阻塞”，child gate则保留问题修复后逐项准入与native scatter独立处理能力。
- exact artifact/preflight digests让任何clean retry、parser变化或collection变化都使旧decision自动stale，避免审核A、投产B。
- append-only decision与CAS/outbox增加表和事务，但换来全局可按Task/Execution/Intake/Artifact追溯的因果链，且不污染Intake生命周期。

#### Owner 问题

Owner 是否接受上述复合ReviewTarget与两级scatter围栏：任何decision绑定exact Execution/fence、Intake refs、clean Artifact/digest和preflight evidence；root collection gate负责required异常整体阻塞，child gate负责通过root后逐项准入；decision不可跨Execution复用，release必须CAS并原子写audit/outbox？

#### 业主回答

业主同意复合ReviewTarget与两级scatter围栏推荐。任何policy/human decision至少必须绑定exact`execution_uuid`，并同时绑定对应Intake refs、clean Artifact/DerivedGeneration digest、Workflow/capability binding及preflight evidence；仅凭IntakeRevision或Execution均不足以授权继续处理。Single使用exact Execution target gate；scatter使用root collection gate先对Snapshot/CandidateSet required set与root preflight执行整体围栏，root未release前children不得进入RAG，再由child content gate对proof-valid非白名单/异常项逐项决策。Decision不可跨Execution复用，artifact/evidence/fence变化使其stale；release必须在同一事务完成校验、append audit、CAS projection与resume outbox，且人工不得通过布尔批准伪造缺失artifact、member、digest或completeness proof。

#### 裁决状态

`frozen → T-O-56 / T-O-57 / T-O-58`

| `PreflightAdapter.manifest/validate/selfTest`运行时治理接口 | 收缩为`PreflightValidator.manifest/validate`；fixtures归CI/golden acceptance | v1不建设fixture registry/readiness平台 |

## 8. Round 1 总结与中期评价

### 8.1 冻结后的统一业务链

```text
registered IntakeSource kind + exact capability/profile binding
  → Execution created with immutable Workflow/capability binding
  → acquire/decode/map/clean Processes
  → mandatory preflight
       source/acquisition checks
       collection/member checks
       clean/artifact checks
  → admission control
       allowlisted + passed
         → PreflightOutcome → continue RAG（无gate/decision）
       non-allowlisted + passed
         → Execution waiting(human_review_required)
       blocked + reviewable artifact
         → Execution waiting(preflight_content_blocked)
       runtime/source failure + no artifact
         → S03 retry/failed或显式remediation；无内容approve gate
  → fenced decision against composite ReviewTarget
       Execution + Intake + Artifact + preflight evidence
  → same Execution resumes or terminally converges
  → S06-S09 RAG Processes + publication proof
```

### 8.2 Round 1 Verdict

| 平面 | 已冻结结论 | 评价 |
|---|---|---|
| Capability | 网页多fetch、PDF、API多通道/single/scatter、本机OCR、Vision/model clean全部进入v1；source kind与执行策略正交。 | 继承legacy生产覆盖，但删除branch拼装与平台绑定。 |
| Admission safety | Allowlist仅在mandatory preflight通过后自动放行；required异常对当前root scope fail-closed。 | 解决“白名单变质量豁免”和silent skip。 |
| Runtime control | Human review只属于Execution durable `waiting` gate；Intake与Process都不持有review state。 | 与D01/S03状态机一致，无第二套job lifecycle。 |
| Approval identity | Decision绑定Execution/fence、Intake refs、clean Artifact/digest与preflight evidence。 | 阻断跨Execution复用和审核A投产B。 |
| Scatter | root collection gate整体阻塞；release后child content gate逐项准入。 | 与S04 native Snapshot/Membership和S02 collect-all一致。 |
| Audit/atomicity | Decision append-only；release经CAS并原子写audit/outbox。 | UI、HTTP、queue和日志都没有成功权。 |

Round 1与D01/S01-S04不存在身份或状态冲突：Task仍是外部aggregate，Execution仍是durable run，Process仍是短期工序实例；Intake仍只保存来源与资产事实。S05新增的是typed capability/preflight/output contract，以及Execution control所需的业务证据，不创建新的顶层运行身份。

1. 四类source kind的descriptor/config/secret/media/normalizer如何形成strict v1 input contract；
2. S05如何确定性产出source semantics、clean Artifact与paged CandidateSet，并计算可复验digest；
3. Preflight、ExecutionGate、ReviewTarget与Decision需要哪些最小持久职责、状态、CAS/outbox和terminal聚合；不预设表数量。

这三项分别形成Q5、Q6、Q7，不相互代答。

## 9. Round 2 — Execution & Schema（Q5-Q7）

### Q5 — 四类 IntakeSource 的 exact Source/Input Contract 如何落成

- **单一裁决面**：`inline_payload/local_object/http_resource/registered_api`各自允许哪些descriptor/config/secret/media字段，以及如何确定性解析source identity、ExternalKey和acquisition capability。
- **不在本题裁决**：CandidateSet输出字段、clean artifact schema、preflight/gate状态表和模型质量阈值。
- **Truth驱动**：`T-O-49..53`；S04 `IntakeSource`/source-scoped ExternalKey；S03 ProcessCapabilityManifest/typed ports；S13 logical locator；S16 secret/egress边界。

#### 推荐执行方案

1. 将Q1候选词`IntakeSourceKindDefinition`正式化为内部注册、immutable、versioned definition，并纳入GreenfieldBootstrap RegistryManifest。最小字段族：

   | 字段族 | 必需语义 |
   |---|---|
   | Identity | `source_kind_key, definition_version, definition_digest` |
   | Schemas | descriptor/config schema refs+digests，`extra=forbid` |
   | Cardinality | `single | collection`及允许的scope/completeness profile refs |
   | Capabilities | allowed acquisition/decode/clean process keys+versions和typed port compatibility |
   | Media/I/O | declared/detected/verified media policy、encoding profile、stream/size/redirect/page budgets |
   | Identity resolution | ExternalKey normalizer ref/version、singleton key rule、duplicate/conflict policy |
   | Security | secret slot specs、egress/auth policy refs；不含secret value |
   | Admission | required preflight profile ref/version、allowlist eligibility class |

   同key/version同digest重注册no-op，同version异digestfail-loud；无外部CRUD。

2. 四类descriptor推荐如下：

   | Source kind | 必需descriptor | 严格限制 |
   |---|---|---|
   | `inline_payload` | staged logical representation ref、declared media/encoding、client correlation ref、byte digest/size | bounded inline bytes可以从Task入口接收，但Execution前必须变为S13 logical handle；正文不进入IntakeSource row/payload_extra |
   | `local_object` | logical object ref、declared media、optional filename hint、expected digest/size | 路径/filename不构成identity；禁止绝对路径进入domain contract |
   | `http_resource` | canonical target URI、method/profile ref、expected media、redirect/cache/validator policy refs | 禁止userinfo、fragment、任意headers/cookies/fetch_options；auth只经registered secret slot |
   | `registered_api` | provider key/version、operation key/version、typed query scope ref+digest、pagination/completeness profile、secret refs | 禁止caller URL/code/cookie/raw params；operation schema必须同时验证request、envelope与member |

3. Descriptor中身份字段与运行配置必须分账：source identity-bearing fields创建后immutable；connector/secret binding采用versioned config ref。Definition必须声明哪些config变化不改变source identity（如secret rotation），哪些变化需要新IntakeSource（如provider/operation或authoritative namespace改变）。不得由运行代码临时判断。

4. HTTP canonicalization只做标准上安全且语义不变的处理：scheme/host规范化、default port处理、fragment剥离、userinfo拒绝；query参数排序、大小写、trailing slash等由exact source definition决定，禁止通用重写把不同资源合并。Redirect每跳重新执行S16 egress/host policy，最终URI进入acquisition evidence而不偷换IntakeSource identity。

5. ExternalKey normalizer必须source-definition-specific、pure、versioned并返回`normalized_external_key + normalizer_version + key_digest + validation evidence`：

   - singleton source默认使用definition注册的固定key（推荐`primary`），由IntakeSource namespace保证唯一；
   - registered API使用provider稳定业务字段，先strict type/schema再规范化；
   - text默认Unicode NFC；是否trim/case-fold/零填充必须逐definition声明，禁止全局lowercase或从随机UUID/内容hash补key；
   - 空key、冲突key或同key不同canonical member均fail-closed。

6. Media判定保留`declared_media_type/detected_media_type/verified_media_type`与冲突结果。扩展名或HTTP header只是evidence；verified type必须进入capability/allowlist。Encoding保留label/BOM/detector/decoder/error count，输出统一UTF-8，但原始bytes digest不变。

7. Size/time/page/redirect limits属于versioned acquisition profile正式字段。所有reader必须stream计数并在解压前后分别设budget，不能先完整`arrayBuffer`后检查；超限形成typed Process failure/preflight evidence，不能截断后自动成功。

8. Secret只通过`secret_ref + registered slot`在adapter边界按需解析；descriptor、compiled Workflow、ProcessCommand持久快照、Outcome、日志与artifact中均不得出现token/cookie明文。缺secret/readiness在admission/materialization前fail-closed。

9. ProcessCommand只传exact definition/config/profile refs与logical handles；handler不得接受opaque source payload。相同descriptor/config/profile/digests应产生相同command spec digest和可复验acquisition行为。

#### Reasoning 与制衡

- 四类Source共用一个宽JSON会重演legacy `fetch_options`和provider payload漂移；每类strict schema能在Execution前拒绝未知行为。
- 身份字段与secret/config rotation分开，可避免换token制造新IntakeSource，也避免换provider namespace却错误复用旧Item。
- singleton固定ExternalKey在source namespace内稳定，优于随机UUID、URL全文或content hash；内容变化应产生Revision，不应改变Item身份。
- declared/detected/verified三分可同时保留来源声明和安全判断，不会把扩展名/MIME hint误当事实。
- 流式双budget和redirect逐跳授权增加实现成本，但直接关闭legacy整包读入、压缩炸弹、无限response与SSRF redirect窗口。

#### Owner 问题

Owner 是否接受上述Source/Input Contract：内部versioned`IntakeSourceKindDefinition`统一约束四类strict descriptors、identity/config分账、source-specific ExternalKey normalizer、declared/detected/verified media、encoding与stream budgets、logical handle/secret refs，并禁止opaque fetch/provider payload、绝对路径和随机key fallback？

#### 业主回答

业主同意Q5的完整推荐。S05以内部注册、immutable、versioned的`IntakeSourceKindDefinition`承接四类strict Source/Input Contract；descriptor、config与secret binding分账，identity-bearing fields不可被运行配置偷换。ExternalKey必须由source-definition-specific normalizer确定性产生，singleton使用source namespace内固定key，registered API使用provider稳定业务字段，禁止随机UUID/content hash fallback。Declared/detected/verified media、encoding evidence、stream/decompression/page/redirect budgets、logical handles与secret refs全部进入正式typed contract；opaque fetch/provider payload、绝对路径、secret明文和任意header/cookie被禁止。

#### 裁决状态

`frozen → T-O-59 / T-O-60 / T-O-61`

### Q6 — S05 的 Candidate/Artifact/Canonical Output Contract 如何确定性落地

- **单一裁决面**：S05从raw representation到source semantic candidate、clean output和paged IntakeCandidateSet应输出哪些typed对象，以及如何确定性计算digest并保持lineage。
- **不在本题裁决**：source descriptor、review gate状态表、S06 layered schema、模型/prompt选择与retention天数。
- **Truth驱动**：`T-O-52..58`；S04 CandidateSetPage/Seal/CanonicalAcceptancePoint、四类SemanticDefinition与IntakeArtifact XOR ownership；S03 typed ProcessOutcome；S13 logical storage。

#### 推荐执行方案

1. S05输出分为四个严格对象，不再返回一个`clean_text + child_files`宽payload：

   | Typed object（候选名） | 唯一职责 |
   |---|---|
   | `AcquisitionEvidence` | exact source/config/capability、request/response/validator、media/encoding、raw logical handle/digest/size、scope/page链 |
   | `IntakeCandidateMember` | member ordinal、raw/normalized ExternalKey证据、required flag、source-grounded semantic values、member artifacts、validation decision |
   | `CleanArtifactCandidate` | clean logical handle、format/media/digest/size、producer/profile/model refs、source anchors、loss/quality evidence |
   | `IntakeCandidateSet` head/pages/seal | observation identity、scope/completeness、definition set、counts/budgets、ordered member/page/root digests与preflight refs |

   这些是ProcessOutcome引用的durable staged outputs；它们不是Task/Execution/Process identity，也不在S04 acceptance前成为Snapshot/Revision truth。

2. Raw、source semantic与clean derived必须分账：

   | 层 | Revision语义 | Artifact处置 |
   |---|---|---|
   | raw source representation | 保存`source_repr_digest`与acquisition provenance；是否参与fingerprint由SemanticDefinition声明 | acceptance后可成为Snapshot/Revision role的IntakeArtifact |
   | deterministic source semantics | strict provider fields或确定性text/HTML/PDF mapper产生的canonical content/context/filter values | 进入CandidateMember，S04 acceptance后形成RevisionSemantic/适当IntakeArtifact |
   | browser/OCR/Vision/model clean output | 供review/S06消费，不因profile/model重跑自动制造IntakeRevision | 作为Execution-produced clean DerivedGeneration/artifact绑定exact accepted Revision与producer lineage |

3. 每个source definition声明`revision_basis_kind`：`typed_source_semantics | deterministic_canonical_text | opaque_representation`。运行时不得因某个cleaner可用/不可用切换basis；AI/OCR输出不能单独决定Revision。Source canonicalizer definition升级是显式re-observation/recanonicalization，不是普通rebuild。

4. Canonicalization/digest v1推荐：

   - digest算法统一`sha-256`并在字段中显式保存algorithm；未来升级追加algorithm/version，不原位重解释历史；
   - exact raw bytes直接digest，不先decode；
   - JSON先strict schema/type，再按RFC 8785 JCS canonical bytes；
   - text统一UTF-8、LF、Unicode NFC；禁止默认NFKC；
   - HTML使用结构parser，canonical mapper/profile版本进入semantic definition；禁止regex strip成为canonicalizer；
   - digest input envelope必须包含schema/canonicalizer/normalizer/semantic definition versions与value，digest不替代UUID。

5. `CleanArtifactCandidate` v1至少包含：target candidate/member ref、input representation digest、output logical handle、`content_format`、media type、digest/size、clean capability/profile、parser/model/prompt refs、producer Execution/Process fence、language/page/segment stats、source anchor map、removed/unsupported/truncated/OCR flags、quality signals/verdict、created_at。推荐允许`text/plain;charset=utf-8`与`text/markdown;charset=utf-8`，但每个capability必须声明exact output；S06不得接收未声明格式。

6. Candidate member最小字段：`member_ordinal, raw_external_key_evidence_ref, normalized_external_key, normalizer_version, required, source_member_digest, semantic_definition/value tuples, raw/canonical artifact descriptors, clean_artifact_candidate_ref, validation_outcome_ref, payload_extra`。核心identity/semantic/proof不得放入`payload_extra`。

7. CandidateSet head最小字段：team/source、producer Execution/fence、source/capability/definition-set digests、observation identity/fingerprint、scope/authoritative scope、completeness、validator、expected/observed/accepted/rejected/duplicate counts、expected pages/members/bytes、root digest、preflight outcome ref、expiry和`payload_extra`。

8. Page与seal采用确定性算法：member先按source definition规定的stable order排序；page digest=`sha-256(JCS(page envelope + ordered member digests))`；root digest=`sha-256(JCS(head immutable fields + ordered page digests))`。同candidate/page ordinal同digest幂等，异digest冲突并abandon；缺页、count/bytes不符、duplicate conflict或artifact不可读不能seal。

9. Rejected/gap evidence不能从CandidateSet消失。Tolerant policy可把valid members封为partial，但必须引用immutable rejection manifest；complete要求rejected required count为0与provider-specific source-exhausted proof。Owner已冻结的root preflight仍可因任一required异常阻止RAG，即使S04允许保存partial observation。

10. S04 acceptance负责把staged descriptors绑定canonical Snapshot/Revision/Artifact owners；失败staged bytes/pages进入orphan cleanup。S05不得因physical object存在创建virtual Artifact或从storage listing/log恢复缺失candidate truth。

#### Reasoning 与制衡

- 分开AcquisitionEvidence、CandidateMember、CleanArtifactCandidate与CandidateSet，能让raw事实、Revision语义、可重建clean输出和collection seal分别校验，而不再依靠`child_files`数组猜业务含义。
- source-grounded semantics与AI/OCR clean分账，落实S04“model/prompt/rebuild不创建Revision”，同时仍让review精确看到本次Execution产物。
- JCS/NFC/LF只解决确定性表示；把definition/profile versions纳入digest input，才能说明“按什么规则得到相同”。
- 双层page/root digest与稳定排序增加一次canonical pass，但为large scatter retry、seal、stale review检测和全局审计提供共同基准。
- partial observation可以保存可信事实，但mandatory root preflight仍可阻断RAG，避免资产收录与生产准入再次混义。

#### Owner 问题

Owner 是否接受上述Output Contract：以AcquisitionEvidence、IntakeCandidateMember、CleanArtifactCandidate和paged IntakeCandidateSet四类typed输出分账raw/source semantic/clean derived；采用versioned revision basis与SHA-256+JCS/NFC canonicalization；严格member/page/head/seal字段、稳定排序、rejection evidence和S04 acceptance ownership边界？

#### 业主回答

业主同意Q6的完整推荐。S05输出冻结为`AcquisitionEvidence`、`IntakeCandidateMember`、`CleanArtifactCandidate`与paged`IntakeCandidateSet`四类typed对象，raw representation、source-grounded canonical semantics与clean derived output严格分账。每类source definition绑定versioned revision basis；AI/OCR/model clean不能单独制造IntakeRevision。Digest/canonicalization采用显式algorithm/profile/schema/definition版本，v1以SHA-256、JCS、UTF-8/LF/NFC和结构化HTML parser为基线。Member/page/head/seal字段、stable ordering、page/root digest、rejection evidence、partial/complete边界及S04 acceptance ownership全部按推荐冻结；storage object/log不能反向合成candidate truth或virtual Artifact。

#### 裁决状态

`frozen → T-O-62 / T-O-63 / T-O-64`

### Q7 — PreflightValidator 与 ExecutionGate 的 v1 最小闭环是什么

- **单一裁决面**：在不建设通用治理平台的前提下，mandatory preflight、allowlist、typed outcome与Execution-owned human gate如何跑通最小生产链路。
- **不在本题裁决**：九张固定表、动态规则/插件、runtime fixture registry、shadow/canary、全局readiness、timeout/retention/observability平台。
- **Truth驱动**：`T-O-52..58/T-O-65..69`的有效核心；§1.6 Owner scope correction；S03 Process retry/Execution waiting/fence/outbox；S04 exact Intake/Artifact refs。

#### 推荐执行方案

1. v1将业务实现称为`PreflightValidator`，避免与source/fetch/clean adapter混义。每条allowlist entry必须绑定一个exact `validator_key + validator_version + check_set_version`；不同entry可以复用同一validator版本，但不存在无validator的自动放行路径。

2. 最小代码接口只有两个职责：

```text
manifest() → key/version + applicable binding + input/check/output schema refs + implementation digest
validate(frozen_context) → passed | blocked + typed check evidence
```

   Golden fixtures属于代码仓库CI/acceptance，不建设runtime `selfTest` registry。Validator不得选route、写Task/Execution/Intake、写decision/outbox或直接wake queue。

3. `frozen_context`只引用当前Execution已经锁定并由上游Process提交的`AcquisitionEvidence`、Candidate/collection evidence、clean Artifact及其digests。Validator v1不重新请求API、不重新抓网页、不重新解析或清洗，也不拥有network/secret/path访问能力。

4. Preflight复用S03 Process状态机，不增加`preflight_job` lifecycle：

   - validator正常执行且全部required checks通过，返回typed `passed`；
   - validator正常执行并发现业务内容/完整性异常，返回typed `blocked`；
   - handler crash、timeout、schema-invalid result或evidence不可读，作为Process error进入S03 retry/max-retries/failed，不伪装成`blocked`。

5. v1 route matrix冻结为推荐：

   | Allowlist | Preflight结果 | v1动作 |
   |---|---|---|
   | match | `passed` | 保存immutable Outcome并继续RAG；不创建gate/decision |
   | no match | `passed` | 创建`human_review_required` gate，Execution进入`waiting` |
   | 任意 | `blocked`且Artifact可审核 | 创建`preflight_content_blocked` gate，Execution进入`waiting` |
   | 任意 | Process error或无Artifact source failure | S03 retry/failed或显式remediation；禁止内容approve |

6. 只有人工等待才创建ExecutionGate。v1 gate projection只需：

```text
open → released
     → rejected
     → superseded
```

   `request_reclean`、artifact/evidence/fence变化使旧gate `superseded`并创建新generation；普通approve/reject作用于exact ReviewTarget并恢复或终结同一个`execution_uuid`。

7. 不在S05冻结表数量，只冻结四组持久职责：

   | 逻辑职责 | v1最小真相 |
   |---|---|
   | registration/binding | allowlist selector、exact validator/check-set/source-fetch-clean binding、version/digest |
   | validation | Execution/fence/target、`passed|blocked` Outcome、required check evidence与reason |
   | human gate | gate generation/state、exact composite ReviewTarget/digest、row revision |
   | decision | append-only actor/action/idempotency/target/fence/causation；resume复用S03 outbox |

   S12可在保持FK/CHECK/CAS和查询能力的前提下决定物理合并或拆表。所有最终落地的MKB-owned表继续包含`payload_extra`，核心binding/outcome/state/target/decision不得下沉其中。

8. Gate opening与human release继续遵守已冻结原子边界：验证current Execution/gate/target fence → 写Outcome或append decision → CAS projection → 写统一outbox。自动`passed`路径没有human decision；它的审计权威是exact PreflightOutcome和Execution transition。

9. Scatter继续使用S02/S03/S04既有root/child与required set：root required evidence未通过时不推进children；root通过后，只有确实需要人工判断的child创建自己的gate。S05不新建review-specific parent/child模型。

#### Reasoning 与制衡

- Airbyte式connector check证明source-specific代码验收合理，但check不应复制read；因此MKB validator只读上游frozen evidence。
- ValidationOutcome回答“机器验收结果”，ExecutionGate回答“是否正在等人”。自动通过也建released gate会把两个概念重新耦合。
- 先冻结四组职责而非九张表，可保留严格关系约束，同时避免在S12设计前为未实现治理功能建立空表。
- 稳定manifest、binding、typed check key、Outcome和gate ports已经为未来validator治理留出升级面，不需要v1提前建设平台。

#### Owner 问题

Owner 是否接受新的Q7最小闭环：每条allowlist绑定exact code-owned `PreflightValidator`；validator只读frozen evidence并返回`passed|blocked`，运行错误复用S03 retry；自动通过只保存Outcome并继续RAG，只有人工等待创建gate；S05只冻结四组持久职责而不规定九张物理表？

#### 业主回答

### Q8 — Execution 如何最小锁定 S05 实现版本并预留升级边界

- **单一裁决面**：v1在Execution创建时必须固化哪些S05 binding，使retry/recovery/human resume继续使用同一实现语义。
- **不在本题裁决**：ExternalKey/Revision演进（S04）、WorkflowRevision治理（S03）、Task restart schema（S02）、model/index migration、旧worker并行部署和canary。

#### 推荐执行方案

1. Execution的S05 binding只需保存本次实际使用的exact refs及一个聚合digest：

```text
source_kind_definition key/version/digest
acquisition capability key/version
clean capability/implementation key/version
preflight binding + validator/check-set key/version
input/output schema digests
s05_binding_digest
```

   如果clean调用S11/S14模型或prompt，只保存该capability已解析的exact logical refs；S05不再建立第二套model registry。

2. automatic Process retry、crash recovery和human resume必须沿用相同`s05_binding_digest`。运行中active registry变化不影响current Execution，也不得通过“重新resolve latest”偷换实现。

3. bootstrap只验证同一`key+version`对应同一manifest/implementation digest；同版本异digest fail-loud。它不负责旧版本流量路由、部署编排或自动迁移。

4. 新建Execution使用当时active binding。若Owner要让已有Task使用新validator/clean implementation，必须走S02明确的restart/new Execution generation因果；S05只验证新旧binding不可混用，不在本题设计restart表。

5. PreflightValidator对相同frozen evidence和相同binding必须产生相同check/outcome digest。Browser/OCR/Vision/model clean可以产生新的derived Artifact，但v1不建立`pure/evidence/model-assisted`治理分类，也不把模型输出宣称为Preflight确定性逻辑。

6. v1升级接口只预留versioned manifest、implementation digest、binding resolver和typed incompatibility error。未来需要migration、rollback、canary或旧版本drain时，必须reopen对应Spec，不创建placeholder state/table。

7. 最小验收：

   - registry更新后，已创建Execution的binding digest不变；
   - retry/resume不会重新resolve active validator；
   - 同key/version异digest启动或注册失败；
   - stale gate decision不能跨binding digest使用；
   - new Execution可以绑定新version，old Execution仍可解释。

#### Reasoning 与制衡

- MKB需要的是“历史不被最新代码静默重解释”，不是复制Temporal式版本部署平台。

### Q9 — PreflightValidator 如何以最小注册方式获得 allowlist 资格

- **单一裁决面**：一个本地code-owned validator在v1需要哪些最小manifest、代码测试与bootstrap校验，才能被allowlist exact引用。
- **不在本题裁决**：runtime plugin、动态规则、shadow/canary、全局readiness、S16角色设计、S15指标告警。
- **Truth驱动**：Owner要求每个allowlist有确定性验收代码；`T-O-65/T-O-66`修订核心；S03 ProcessCapabilityManifest与S04 RegistryManifest的内部注册纪律。

#### 推荐执行方案

1. Validator随MKB代码发布并进入内部registry；无外部CRUD，不接受数据库Python/JS/SQL、agent生成规则、第三方插件目录或`payload_extra` handler。

2. v1 `PreflightValidatorManifest`只保留：

   | 字段 | 用途 |
   |---|---|
   | `validator_key / validator_version` | immutable identity |
   | `handler_key / implementation_digest` | 代码解析与drift校验 |
   | `applicable_source/fetch/clean selectors` | 防止错误binding |
   | `input_context_schema_ref/digest` | 校验frozen evidence输入 |
   | `check_set_version + ordered required check keys` | typed验收目录 |
   | `output_schema_ref/digest` | 约束`passed|blocked`与evidence |
   | `manifest_digest` | bootstrap/no-op/conflict |

   不加入v1未使用的side-effect class、egress/secret slots、resource scheduler或deployment metadata。

3. 代码仓库必须为每个validator提供positive、negative、malformed和其实际支持的single/scatter golden tests。测试在CI/acceptance运行；数据库不保存fixture正文，应用启动不逐次重跑完整fixture suite。

4. Bootstrap只做静态校验：handler存在、manifest/schema digest一致、check keys可解析、allowlist exact binding完整。同版本同digest no-op，同版本异digest或缺handler fail-loud。

5. allowlist后台注册/激活必须引用已经存在的exact validator/check-set；不存在“先active，稍后补代码”。一个validator版本可以服务多个兼容entry，以binding约束而不是复制class。

6. Validator不可访问Task/Execution/Intake repository、任意路径、network或secret；它只通过typed context读取logical evidence handles。状态推进、gate创建、decision与outbox全部由application/Workflow service完成。

7. 某binding缺失或drift时，只拒绝使用该binding的新Execution或使对应Process失败；v1不因此建立全局degraded/readiness状态机，也不fallback到generic validator或无验证自动成功。

8. 未来扩展仅依赖稳定registry port和manifest version。若以后需要plugin签名、canary、在线readiness或第三方发布，再单独设计治理Schema与权限，不在v1保存placeholder行。

#### Reasoning 与制衡

- 代码、manifest、golden tests和exact binding足以证明v1自动路径拥有实际验收逻辑。
- 把fixtures留在代码测试层、bootstrap只校验manifest，可以避免每次启动演化成部署验证平台。
- 禁止live I/O让validator维持确定性leaf边界；API可达性等事实由acquisition Process生成并冻结为证据。

### Q10 — V1 waiting、resume 与 crash recovery 如何最小收敛

- **单一裁决面**：Preflight触发人工等待后，v1如何用最少状态和事务保证approve/reject、same-execution resume、stale防护与关键crash window可恢复。
- **不在本题裁决**：SLA/deadline、自动timeout terminal、retention天数、物理GC、完整metrics/alerts/runbook和通用reconciler。
- **Truth驱动**：`T-O-54..58/T-O-68..69`有效核心；S03 Execution waiting/fence/outbox；S04 exact target/Artifact refs；Owner先跑通核心链路的要求。

#### 推荐执行方案

1. Gate只在需要人工输入时创建。Execution进入既有`waiting`状态并保存`wait_reason + gate_ref`；Process已经terminal，不持有lease等待人类。

2. v1 gate state保持四态：

```text
open → released
     → rejected
     → superseded
```

   `released`恢复同一Execution；`rejected`进入S02/S03既有terminal聚合；target/artifact/evidence/fence变化只能supersede旧gate并创建新generation。

3. v1 human action只要求：

   - `human_review_required`：`approve | reject`；
   - `preflight_content_blocked`：`approve_override | reject | request_reclean`，且override必须由binding显式允许；
   - 无Artifact的source/runtime failure不创建内容gate，不提供approve。

4. Human decision transaction：

```text
validate team/authority + expected gate revision
+ validate Execution/generation/fence
+ validate exact ReviewTarget/artifact/preflight digests
→ append decision
→ CAS gate + Execution
→ write S03 unified outbox
```

   相同idempotency/target/action返回原结果；stale target或同fence冲突action拒绝。

5. v1只强制处理四个crash/inconsistency窗口：

   | Durable观察 | 唯一动作 |
   |---|---|
   | PreflightOutcome已提交、route/gate尚未提交 | 按same Execution fence幂等重试下一transition |
   | gate已open、Execution未投影waiting | 按gate/fence修复Execution projection |
   | decision+CAS已提交、outbox未投递 | 重放统一outbox |
   | late/stale decision或Outcome | fencing拒绝，不重写current truth |

   不建设独立通用Reconciler；复用S03/S12已有semantic recovery/repair入口。

6. v1默认允许durable indefinite waiting。系统永不自动approve；是否提醒、过期、timeout→failed或人工延长属于未来policy/S15，不在S05建立deadline状态和调度器。

7. S05只声明引用保护：`open` gate所引用的Artifact/evidence/decision causation在gate终结前不得被GC；具体RetentionFence、天数、cleanup proof和物理删除由S04/S13/S15实现。

8. 最小端到端验收：

   - allowlisted+passed无gate继续RAG；
   - non-allowlisted+passed进入waiting并approve后恢复same Execution；
   - blocked+reviewable Artifact进入waiting，reject终结且不进入RAG；
   - validator crash进入S03 retry而非human gate；
   - stale/double/concurrent decision被fence和idempotency阻止；
   - decision commit后进程崩溃可由outbox replay继续；
   - scatter root未通过时children不推进，required child rejection参与既有collect-all；
   - 全链路不从日志、UI、storage listing或`payload_extra`合成批准。

9. v1明确defer：自动timeout、escalation、retention数值、orphan/GC实现、完整metric/alert、canary rollback、production readiness阈值和大规模故障矩阵。对应接口只输出typed refs/events，不创建空实现。

#### Reasoning 与制衡

- Durable waiting、same identity resume和idempotent decision是核心正确性；deadline与运营平台不是核心链路的先决条件。
- 四个crash窗口覆盖Outcome→Gate→Decision→Outbox的真实提交边界，并复用S03/S12，避免S05再造recovery engine。
- 明确defer比提前创建placeholder状态更可治理：未来需求出现时可用真实查询和失败模式驱动Schema。

#### Owner 问题

Owner 是否接受Q10最小收敛：只有人工等待创建四态gate；decision以exact target/fence执行append+CAS+outbox并恢复同一Execution；v1只覆盖四个关键crash窗口、默认无限durable waiting且永不自动approve；retention/GC/metrics/alerts/timeout治理移交后续Spec？

#### 业主回答

Owner同意Q10最小收敛。只有确实等待人工输入时才创建`open→released|rejected|superseded`四态ExecutionGate；Process先terminal，Execution使用既有`waiting`。Decision必须校验authority、Execution/gate revision与exact ReviewTarget/Artifact/preflight digests，并以append-only decision、CAS gate/Execution及统一outbox原子提交，恢复同一Execution且拒绝stale/conflict。v1只强制恢复Outcome→transition、gate→Execution projection、decision→outbox及late/stale四个关键窗口，复用S03/S12 repair，不建设通用Reconciler。Waiting默认durable indefinite且永不自动approve；timeout、retention/GC、metrics/alerts/runbook留S13/S15。Owner同时接受本题列出的八项最小端到端验收。

#### 裁决状态

`frozen → T-O-75 / T-O-76`
