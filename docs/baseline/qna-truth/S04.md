## 1. S04 重新校准后的唯一工作面

### 1.1 定位

S04 是 MKB 的 **摄入资产（Intake asset）长期真相层**。它在数据进入 MKB 后，负责回答：外部来源是谁、本次可信观察是什么、观察中有哪些稳定业务项、某个业务项产生了哪些不可变修订、哪些物理表示能够证明这些事实，以及当前哪一修订具有下游服务资格。

S04 不把“进入系统的数据”提前宣称为 Knowledge。未来如果系统需要融合多个来源、人工策展、语义归并或知识晋升，可以引入独立的 `KnowledgeItem`；该对象必须拥有自己的身份和 provenance，而不是把 `IntakeItem` 原位换名。

S04 也不是第二套 Task/Execution/Process 状态机。运行是否成功由 S02/S03 的 proof contract 判断；S04 只持有运行完成后仍须长期存在的摄入资产事实。

### 1.2 五个核心名词

| 名词 | 一句话语义 | 必须承担 | 明确不承担 |
|---|---|---|---|
| `IntakeSource` | 一个可持续识别的外部输入绑定与身份命名空间 | team 归属、source kind、外部定位/连接配置引用、external key namespace、single/scatter 能力 | 抓取尝试状态、正文 bytes、secret 明文、Process 状态 |
| `IntakeSnapshot` | MKB 已接受的一次不可变来源观察结果 | source revision、观察时间、complete/partial、authoritative scope、validator、manifest 摘要、raw snapshot artifact 引用 | 网络失败尝试、可变“当前列表”、child 执行状态 |
| `IntakeItem` | 在一个 IntakeSource 内可独立修订、发布、失活、重建和审计的稳定业务项 | stable UUID、source-scoped external key、生命周期、latest/serving revision 指针 | 某次 API 请求、文件路径、某个 Process、某次内容版本 |
| `IntakeRevision` | IntakeItem 的一次不可变业务语义状态 | canonical digests、revision ordinal、predecessor、creation reason、source snapshot provenance | Workflow/model/embed 的构建代次、可变 metadata 覆盖 |
| `IntakeArtifact` | 承载 IntakeSnapshot 或 IntakeRevision 的不可变物理/逻辑表示 | role、media type、digest、size、locator、owner ref、producer lineage | Task log、LSRagBlock、VectorRecord、任意下游对象的万能容器 |

支撑关系 `IntakeSnapshotMembership` 用来记录某个 `IntakeSnapshot` 看见了哪个 `IntakeItem`、解析到哪个 `IntakeRevision` 或何种 no-op/absence decision。它是集合事实，不是第六种上层业务资产。

### 1.3 Canonical identity graph

```text
Team
  └─ IntakeSource
       ├─ IntakeSnapshot (0..N, immutable accepted observations)
       │    ├─ IntakeArtifact (snapshot/raw representation, 0..N)
       │    └─ IntakeSnapshotMembership (0..N)
       │          ├─ IntakeItem
       │          └─ observed IntakeRevision / no-change / absence decision
       └─ IntakeItem (0..N, stable source-scoped subjects)
            ├─ IntakeRevision (1..N, immutable semantic states)
            │    └─ IntakeArtifact (revision/canonical representation, 0..N)
            ├─ latest_revision_uuid
            └─ serving_revision_uuid (nullable, proof-gated)

IntakeRevision
  ├─ LSRagBlock / construction outputs       [S06-S07]
  └─ VectorRecord / index generation         [S08-S09]

IntakeItem / IntakeRevision
  └─ future promotion or fusion → KnowledgeItem [out of S04 v1 scope]
```

该图刻意保留两条不同轴线：`Snapshot → Membership` 表示“某次来源观察看见了什么”；`Item → Revision` 表示“稳定业务项如何随时间改变”。不能用一张 mutable child row 同时表达这两种事实。

### 1.4 single 与 scatter 的统一解释

| 入口 | Intake 真相 | 内部执行 |
|---|---|---|
| single upload/object/URL/API | 一个 `IntakeSource` 接受一次 `IntakeSnapshot`；通常产生一个 membership，解析到一个稳定 `IntakeItem` 及其 revision/no-op | 一个 Task 从一个 root Execution 开始；是否需要 child Execution 由 Workflow 决定，不改变 Intake 身份模型 |
| scatter API | 一个 `IntakeSource` 接受一次带完整性声明的 `IntakeSnapshot`；snapshot 的 0..N memberships 分别解析到稳定 `IntakeItem` | root controller 必须先提交 snapshot/manifest truth，再为需处理的 memberships 并行创建 child scheduling intent/Executions |

因此，scatter parent 是 `IntakeSource + IntakeSnapshot` 的集合上下文，不需要伪造一个“父文件”或“父 IntakeItem”。每个 child 的 durable 业务身份是 `IntakeItem`，其 durable 运行查询身份仍是 `execution_uuid`。

### 1.5 职责 cutoff

| 不属于 S04 | 权威归属 | S04 只冻结什么 |
|---|---|---|
| Task HTTP、六态、cancel/retry/restart admission | `S02` | command 最终针对哪个 Intake identity，以及长期结果引用 |
| Workflow schema、Execution/Process 状态、claim/retry/recovery | `S03` | runtime target refs、resource outcome 与 publication proof 的资产边界 |
| fetch/upload/parse/clean、provider adapter、canonicalization 算法 | `S05` | 输入/输出必须落在哪个 IntakeSnapshot/IntakeItem/IntakeRevision/IntakeArtifact 上 |
| layered block、construction unit、embedding/vector exact schema | `S06-S09` | 全部派生对象必须引用 exact IntakeRevision，并能随 serving fence 失效 |
| retrieval/rerank 算法 | `S10` | 只读取 team-scoped、lifecycle-eligible、serving revision 对应的数据 |
| Turso exact DDL、transaction/outbox、GC SQL | `S12` | 必须成立的 FK/unique/CAS/atomic visibility 语义 |
| IntakeArtifact backend、路径、bytes I/O 与物理 GC | `S13` | IntakeArtifact 的身份、owner、digest、lineage 和 retention fence |
| event/log/metric/alert 的物理模型 | `S15` | Snapshot acceptance、revision、serving、withdrawal 与 purge evidence |
| secret 与跨 team 授权 | `S16` | team fence 与 secret reference；IntakeSource 不保存 secret 明文 |
| 未来 Knowledge 融合、策展、晋升 | 后续独立 scope | 只预留可追溯的 Intake identity，不提前建表或偷换语义 |

### 1.6 Round 1 暂不裁决

- exact table 数量、列名、Turso index/trigger；
- exact lifecycle enum 和所有 transition；
- URL canonicalization、MIME/encoding/size、connector 类型；
- S05 canonicalization 细节及 digest 具体算法；
- LS-RAG Block/VectorRecord exact schema；
- retention 天数、GC 批次、queue/outbox 实现；
- 对外 Intake CRUD URI、分页和错误 envelope；
- `KnowledgeItem` 是否最终需要，以及它的 exact schema。

## 2. ★ Upstream Truth-Gate（继承，不改写）

> 下表引用 D01/S01-S03 当前已经冻结的原词，目的是保持证据可追溯，并不在本轮修改这些文档。S04 定稿前，`Document → IntakeItem` 等只是一份受控迁移映射，不反向宣称上游文本已经更新。

| Gate ID | 已冻结运行真相 | S04 兼容解释 | 对 S04 的限制 |
|---|---|---|---|
| `U-S04-01` | Task、Execution、Process 是运行身份；长期资源不得由运行 UUID 替代。 | 长期资源现在由 `Intake*` 表达。 | 禁止把 intake 状态塞进 Task，或把 Execution 当 IntakeItem。 |
| `U-S04-02` | Task item 只是 generation/manifest 下的结果投影。 | canonical item 指向 `IntakeItem`。 | Task item 不能成为 membership 或 Intake SSOT。 |
| `U-S04-03` | single 是 root Execution；scatter 是 root controller + 0..N child Executions。 | root target 为 IntakeSource/IntakeSnapshot，child target 为 IntakeItem/IntakeRevision。 | 禁止 child Task；禁止用 parent file 表达 scatter。 |
| `U-S04-04` | scatter 先提交 manifest revision/expected set，再创建 child scheduling intent。 | manifest truth 由 accepted IntakeSnapshot + memberships 承接。 | 不能从 Execution count 或当前 rows 猜 expected set。 |
| `U-S04-05` | proof-valid child 可独立发布，不等待 root terminal；parent failure/cancel 不回滚。 | 单个 IntakeItem 的 serving revision 独立推进。 | serving 资格不能只取 root Task status。 |
| `U-S04-06` | Task cancel 是 forward-stop，不等于长期资源 deactivate/delete。 | Intake withdrawal 必须是独立资源 command。 | cancel 不得清空 serving revision 或删除 IntakeArtifact。 |
| `U-S04-07` | atomic child rebuild 对稳定资源创建新 Task，不复活旧 tree。 | rebuild target 为稳定 IntakeItem/Revision。 | rebuild 不得生成新的 IntakeItem 或 IntakeRevision，除非输入语义确实变化。 |
| `U-S04-08` | 所有查询和 lineage 强制 team-scoped。 | 所有 Intake keys、relations、snapshots、artifacts 继承 team fence。 | 裸 external key 不得全局解析。 |
| `U-S04-09` | Execution 成功要求 type-specific publication proof。 | proof-valid transition 才可推进 serving revision。 | transport ACK、queue empty、日志都不能上线新 revision。 |
| `U-S04-10` | Process I/O 只使用 logical refs/digests；Process cleanup 不删长期资产。 | Process 可引用 Intake UUID/digest，但不拥有它们。 | IntakeArtifact/Revision retention 独立于 Process retention。 |
| `U-S04-11` | Workflow retry/recovery 不热切 revision，也不得猜输出/proof。 | 修复依据 immutable Intake truth。 | 禁止从日志反推 IntakeSnapshot/IntakeRevision/IntakeArtifact 成功。 |
| `U-S04-12` | fan-out/fan-in 与 recovery 依赖 durable membership。 | durable membership 是 IntakeSnapshotMembership。 | parent-child relation 不再作为 scatter hotfix。 |

## 4. 外部一手事实支持

| Ref ID | 一手事实 | 对 S04 的支持边界 |
|---|---|---|
| `WEB-S04-01` | [W3C PROV-DM](https://www.w3.org/TR/prov-dm/) 区分 entity/activity/agent、derivation、revision 与 collection membership。 | 支持 Revision 不覆盖前身、Snapshot membership 与派生 lineage 显式化；不规定 MKB 表结构。 |

| `WEB-S04-03` | [RFC 9530](https://www.rfc-editor.org/rfc/rfc9530.html) 区分 message content digest 与 selected representation digest。 | 支持 raw representation、canonical content 与 metadata digest 分账；digest 不自动等于身份。 |
| `WEB-S04-04` | [Apache Iceberg Specification](https://iceberg.apache.org/spec/) 使用 immutable files、snapshot/manifest 与 atomic current pointer。 | 支持不可变 candidate 完成后再原子切 serving pointer；MKB 不复制 Iceberg 格式。 |
| `WEB-S04-05` | [RFC 9110 DELETE](https://www.rfc-editor.org/rfc/rfc9110.html#name-delete) 首先解除资源与当前功能的关联，存储是否立即销毁由实现决定。 | 支持立即 serving fence 与异步物理 cleanup 分层。 |
| `WEB-S04-06` | [Amazon S3 Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/versioning-workflows.html) 以 delete marker 分离 current visibility 与旧版本保留。 | 提供 tombstone/visibility 与 permanent deletion 分层的工程证据；MKB 不采用 S3 作为初期 SSOT。 |

综合结论：稳定业务项与不可变修订必须分开；一次来源观察集合与业务项历史必须分开；external key 必须 source-scoped；上线/失活是原子业务可见性决策，物理清理是可恢复副作用。

## 5. Round 1 — Foundational Intake Constitution（Q1-Q3）

### Q1 — 五类 Intake 身份的 ownership 与 cardinality

- **单一裁决面**：五个核心名词分别是谁，以及它们之间唯一允许的长期关系。
- **不再重问**：是否采用 `Intake*` 命名；这是 owner 已给出的词汇方向。
- **证据驱动**：`U-S04-01..04/U-S04-10/U-S04-12`；`LF-S04-01..09/LF-S04-12`；`WEB-S04-01/02/04`。

#### 推荐方案

1. `IntakeSource` 是外部来源绑定和 external key namespace；一次性 upload 也创建 IntakeSource，以统一 provenance 和 single/scatter 模型。
2. 只有**成功完成协议校验并被 MKB 接受**的观察结果才能创建 immutable `IntakeSnapshot`。网络失败、鉴权失败、schema 无效等仅保留在 Execution/Process/Event，不制造“失败 Snapshot”。
3. Snapshot 必须显式声明 `complete | partial`、authoritative scope 和 validator。只有 `complete + authoritative` 的集合才能用缺席推导既有 member 的失活候选。
4. `IntakeItem` 是 source-scoped 稳定业务项；默认 resolver key 为 `(team_uuid, intake_source_uuid, external_key)`。相同 external key 在不同 IntakeSource 中默认不是同一 IntakeItem。
5. `IntakeRevision` 是 Item 的不可变语义状态；Item 可有多个 Revision，但只有受控指针表示 latest/serving。
6. `IntakeSnapshotMembership` 保存本次 seen set 及每项 decision；它不能被当前 Item 行或 child Execution 数量替代。
7. `IntakeArtifact` 有两种合法 owner：IntakeSnapshot 级 raw/collection 表示，或 IntakeRevision 级 canonical/clean 表示。每个 IntakeArtifact 必须只有一个直接 owner role，跨层派生通过 lineage 表达。
8. `LSRagBlock`、construction output 和 `VectorRecord` 不是 IntakeArtifact；它们是由 IntakeRevision 派生、分别受 S06-S09 管理的对象。
9. scatter parent 是 IntakeSource + IntakeSnapshot 集合上下文，不建立伪 parent IntakeItem；single 与 scatter child 均归一为 IntakeItem。
10. `KnowledgeItem` 仅作为未来不同语义层的保留名。若未来启用，它应支持对一个或多个 IntakeItem/Revision 的 promotion/fusion provenance，而不得与 IntakeItem 1:1 alias。

#### Reasoning 与制衡

- 该切分把“来源”“本次看见的集合”“稳定业务对象”“对象的不可变状态”“物理表示”放在正交平面，直接修复 legacy file/relation row 的职责叠加。
- 一次性 upload 多一条 IntakeSource 记录，但换来统一 team fence、provenance 与 external namespace，避免以后再次为 URL/API/scatter 打补丁。
- Snapshot 只记录 accepted observation，会使失败尝试必须去 runtime/event 查询；这是有意的职责分离，避免 Snapshot 既表示事实又表示失败。
- 不把所有派生物都叫 `Artifact`，会增加类型数量，但能防止宽泛的 `Artifact` 再次演变成任意 payload/R2 key 的垃圾桶。

- **问题**：Owner 是否接受上述五类 Intake ownership/cardinality：IntakeSource 负责来源命名空间，IntakeSnapshot 负责 accepted observation/collection，IntakeItem 负责稳定业务身份，IntakeRevision 负责不可变语义状态，IntakeArtifact 只负责 IntakeSnapshot/IntakeRevision 的具体表示；scatter 不建立伪 parent IntakeItem，未来 KnowledgeItem 必须是独立 promotion/fusion 身份？
- **业主回答**：业主同意五类 Intake 身份以及上述判断。冻结 `IntakeSource → IntakeSnapshot/IntakeItem → IntakeRevision` 两条正交轴线、`IntakeSnapshotMembership` 集合事实、Snapshot/Revision 两类 IntakeArtifact owner、single/scatter 统一解释、scatter 无伪 parent Item，以及未来 KnowledgeItem 必须拥有独立 promotion/fusion 身份的完整推荐。
- **裁决状态**：`frozen → T-O-30 / T-O-31`

### Q2 — 什么变化必须创建新的 IntakeRevision

- **单一裁决面**：稳定 IntakeItem 下，哪些变化属于新业务修订，哪些只是重新执行或重建派生物。
- **证据驱动**：`U-S04-07/U-S04-09..11`；`LF-S04-02/04..06/09`；`WEB-S04-01/03/04`。

#### 推荐方案

1. 每个 `intake_revision_uuid` 为 MKB UUIDv7；同一 Item 具有单调 ordinal、nullable predecessor 和 immutable creation reason。
2. 至少分离 `source_repr_digest`、`canonical_content_digest`、`context_meta_digest`、`filter_meta_digest`；`revision_fingerprint` 包含被纳入业务语义的 canonical tuple 与 schema/canonicalization version。
3. 首次 accepted membership 创建 IntakeItem + Revision 1。
4. canonical content、context metadata 或 filter metadata 任一业务语义变化，都追加新 Revision；禁止原位覆盖旧 Revision。
5. 所有 revision digests 相同则不新建 Revision；SnapshotMembership 记录 seen/no-change 和所解析到的既有 Revision。
6. force rebuild、Workflow/prompt/model/embed revision 变化、reindex、派生物修复，在 Intake 语义不变时只创建新 Task/Execution/build generation，继续引用同一 IntakeRevision。
7. ETag、Last-Modified 或 provider hash 只是 validator/hint；MKB 保存算法/schema version并计算 canonical digests。
8. 并发相同 fingerprint 必须唯一收敛；并发不同 fingerprint 必须通过 Item revision/CAS 明确排序，禁止 last-write-wins 覆盖。
9. 相同内容来自不同 IntakeSource/external key 时默认保留不同 IntakeItem/provenance；物理 bytes/vector 可在下游去重，不自动合并业务身份。

| 输入事实 | IntakeItem | IntakeRevision | 下游动作 |
|---|---|---|---|
| 新 source-scoped external key | 新建 | v1 | full build |
| 同 key，content/context/filter 变化 | 保持 | 追加 | 按 digest route 构建 |
| 同 key，全部 revision digests 相同 | 保持 | 不新增 | membership no-op |
| 同 revision，人工 rebuild | 保持 | 不新增 | 新运行/派生 generation |
| 同 revision，model upgrade/reindex | 保持 | 不新增 | 新模型空间或 index generation |
| 相同内容、不同 IntakeSource/key | 默认不同 | 各自维护 | 保留 provenance，可物理去重 |

#### Reasoning 与制衡

- Legacy 已验证 content 与 metadata 分账能选择不同工序；MKB 的升级是让 diff 决定“是否追加 Revision + 走哪条 Workflow route”，而不是覆盖 mutable row。
- metadata-only 也创建 Revision 会增加数量，但否则历史 filter/proof 无法解释。存储成本应由 retention 管理，不应用丢失历史换取表面简洁。
- rebuild/model upgrade 描述“如何派生”，不描述“来源业务事实改变”；把它们计为 IntakeRevision 会让业务历史被基础设施升级污染。

- **问题**：Owner 是否接受上述 Revision rule：Item 按 source-scoped external key 稳定；content/context/filter 的业务语义变化追加 immutable IntakeRevision；no-change、rebuild、Workflow/prompt/model/embed 变化只产生新运行或派生 generation，不制造新的 IntakeRevision？
- **业主回答**：业主同意上述专业判断。`IntakeRevision` 采用 source-scoped stable Item、immutable append、canonical semantic change 建新 Revision、no-change/rebuild/model/index generation 不建新 Revision的原则。同时要求执行层保留语义灵活度：当前四类 digest 是最小内建语义维度，不得硬编码成永远封闭的全部语义；未来新增维度必须通过内部注册、不可变 definition version、显式 fingerprint participation 与 typed route signal 扩展。既有 Revision 永久绑定创建时的定义版本，不因后续新增语义维度被静默重解释。
- **裁决状态**：`frozen → T-O-32 / T-O-33`

### Q3 — IntakeRevision 的 serving、deactivate 与 delete 如何分层

- **单一裁决面**：哪个 Revision 具有下游读取/检索资格，以及失活何时对业务生效。
- **证据驱动**：`U-S04-05/06/09..12`；`LF-S04-07..11`；`WEB-S04-04..06`。

#### 推荐方案

1. IntakeItem 至少维护两个 CAS 保护的逻辑指针：`latest_revision_uuid` 表示最新 accepted candidate，`serving_revision_uuid nullable` 表示当前允许下游构建/读取/检索的 proof-valid Revision。
2. 新 Revision 构建期间，旧 serving Revision 继续服务；候选失败不清空旧指针。
3. 只有 S03 汇总的 type-specific proof 满足后，S04 才能 CAS 切换 serving pointer，并记录 predecessor、proof digest、policy revision 与时间。逐条 vector 成功不能提前上线。
4. 切换后的旧 IntakeRevision 变为 noncurrent lineage；IntakeArtifact/Vector 是否保留由 retention、rollback 和 GC fence 决定。
5. deactivate 是可逆的 Item 业务失活：立即关闭 read/retrieval eligibility，保留身份、Revision 和审计；重新出现时复用 Item，再按 digest 决定复用 Revision或追加。
6. delete 是带 tombstone 的消亡意图：先提交 durable serving fence/causation，再异步清理 Vector/IntakeArtifact；物理 proof 未完成前不能声称 purge complete。
7. Task/Execution cancel 只 forward-stop，绝不撤销已经 serving 的 Revision；withdrawal 必须创建独立资源 command/Task。
8. 只有 `complete + authoritative` Snapshot 在明确 absence policy 下，才可对缺失 memberships 发起 deactivate；partial、timeout、provider error、parser skip 或空但非权威结果均不得推导全量下架。
9. 查询实行双围栏：关系 truth 要求 team + Item lifecycle + exact serving revision；index/filter 也携带 team/item/revision/generation。任一侧 tombstone 或 pointer mismatch 都拒绝返回。
10. S04 持有 semantic intent/pointer/tombstone；S09/S12 收敛 vector invalidation，S13 收敛 IntakeArtifact GC，S15保存 evidence。物理失败可重试，不得反向恢复可见性。

```text
new immutable IntakeRevision candidate
  → build and validate derived assets
  → publication proof complete
  → CAS IntakeItem.serving_revision_uuid
  → new revision retrieval-eligible
  → old revision retained until retention/GC fence

deactivate/delete intent
  → commit lifecycle fence/tombstone first
  → retrieval immediately excludes the IntakeItem
  → emit durable invalidation/cleanup intents
  → Vector/IntakeArtifact projections converge
  → physical purge proof / retention completion
```

#### Reasoning 与制衡

- 两指针防止“最新看见的候选”和“当前可安全服务的修订”混义，使失败更新不会污染健康版本。
- `serving` 是 Intake 层的技术/业务资格，不等同于未来 Knowledge 层的策展或认定；未来 KnowledgeItem 可以拥有自己的 promotion/publication 决策。
- logical withdrawal 后物理 vector 可能短暂残留，因此 retrieval 不能只相信 ANN 是否还有记录。
- tombstone 和 proof 增加事务/存储成本，但它们是完整审计、恢复与不误暴露的最低成本。

- **问题**：Owner 是否接受上述 serving/withdrawal 宪法：latest candidate 与 serving IntakeRevision 分离；proof-valid CAS 才切换服务资格；deactivate/delete 先提交 durable fence/tombstone，再异步收敛 Vector/IntakeArtifact；只有 complete authoritative IntakeSnapshot 才能依据 absence 自动失活旧 IntakeItem？
- **业主回答**：业主同意上述专业判断。冻结 latest/serving 分离、proof-valid CAS、deactivate/delete logical-first、physical-convergence、cancel 不撤销、complete authoritative absence fence 与查询双围栏。同时要求执行层不要用持续膨胀的状态枚举锁死未来语义：核心 lifecycle/serving effect 与安全不变量保持封闭，具体 action、reason、semantic branch 和 route condition 采用内部注册且不可变版本化；Workflow 消费类型化 facts/effects 选择路线，扩展分支不得绕过 team fence、proof、CAS、tombstone 或改写历史 transition。
- **裁决状态**：`frozen → T-O-34 / T-O-35`

## 7. ★ 中场评估 I（Round 1 → Round 2）

### 7.1 对 Round 1 的判定

`PASS / FOUNDATIONAL CLOSED`。Q1-Q3 均获得明确 owner 裁决，没有遗留的身份、Revision 或 serving 宪法问题。最关键的新约束不是“允许任意灵活”，而是同时锁定两件事：核心安全不变量必须稳定，业务语义分支必须可注册、可版本化、可路由。

### 7.2 本轮已锁定真相

- `T-O-30/T-O-31`：五类身份、membership、single/scatter 和 future Knowledge cutoff；
- `T-O-32/T-O-33`：Revision 创建边界与语义维度扩展机制；
- `T-O-34/T-O-35`：serving/withdrawal 宪法与 action/reason/route 扩展机制。

### 7.3 语义灵活度的执行解释

```text
closed invariant kernel
  identity ownership + team fence + immutable history
  proof + CAS + tombstone + authoritative absence

open, governed semantic layer
  versioned SemanticDefinition
  versioned ActionDefinition
  typed ChangeFacts / CoreEffects
  WorkflowRevision routes on registered facts
```

“可扩展”不意味着：任意 JSON 进入 core truth、任意字符串直接选择 Process、运行时热改已有 Workflow、后来的维度重算历史 Revision，或新增 action 可以直接写 lifecycle state。所有扩展都必须先注册定义，再由已绑定的 WorkflowRevision 消费类型化事实。

### 7.4 诚实反方制衡

- normalized semantic dimensions 比四个固定 digest 列增加 join 和 registry 治理成本；但它避免未来增加语言、policy、temporal 或 provider-specific 语义时修改 Revision 主表和硬编码路由。
- 过度开放会使不同 Workflow 对同一 semantic key 作出不一致解释；因此 definition 必须不可变版本化，Execution 必须绑定 definition set/WorkflowRevision，不能“按当前配置”重放历史。
- 小核心状态机限制了自定义 action 的自由度；这是必要限制。新 action 可以扩展原因与路由，但最终必须映射到受验证的 core effect，不能发明绕过 proof/CAS 的写路径。

### 7.5 为什么提出 Q4-Q6

- `Q4` 由 `T-O-30..35` 驱动，冻结能够承载五类身份、不可变语义定义和完整审计的关系 schema；

## 8. Round 2 — Execution & Relational Truth（Q4-Q6）

### Q4 — S04 需要哪些关系型 truth tables（驱动真相：`T-O-30..35`）

- **单一裁决面**：S04 的 normalized relational SSOT 应由哪些职责表承接，语义扩展放在哪里。
- **影响范围**：`S04/S05/S09/S12-S15`。
- **为什么必须确认**：五类身份已经冻结，但如果所有 digest、semantic branch、pointer 和 audit 再次塞入一个 mutable Item JSON，仍会重演 `smind_files`；反之，为每个未来分支增加表或列又会把路由锁死。

#### 推荐方案：十张 S04 logical truth tables

| 组 | 表 | 唯一职责 |
|---|---|---|
| Core identity | `intake_sources` | IntakeSource identity、team ownership、kind/config/secret refs、lifecycle |
| Core identity | `intake_snapshots` | accepted immutable observation、scope/completeness/validator、producer refs |
| Core identity | `intake_items` | source-scoped stable identity、lifecycle、latest/serving pointers 与 CAS revision |
| Core identity | `intake_revisions` | immutable ordinal/predecessor/fingerprint/creation provenance |
| Core identity | `intake_artifacts` | immutable Snapshot/Revision representation；XOR direct-owner constraint |
| Collection | `intake_snapshot_memberships` | Snapshot set、external key resolution、Item/Revision/no-op/absence decision |
| Semantic registry | `intake_semantic_definitions` | 内部注册的 immutable `(semantic_key, definition_version)`、value/schema kind、fingerprint policy、typed route signal |
| Revision semantics | `intake_revision_semantics` | Revision 对其 definition version 的 canonical value digest/value-ref；四个内建维度为 required rows |
| Action registry | `intake_action_definitions` | 内部注册的 immutable action/reason version、允许的 core effect、precondition class、route fact |
| Resource audit | `intake_item_transitions` | Item lifecycle/latest/serving before→after、action definition、causation、proof、CAS fence 的 append-only ledger |

#### 约束

1. 十张表是 S04 logical responsibility，不预判 S12 的 exact DDL、index、trigger 或 repository 分包。
2. Core truth 不允许 opaque JSON：definition 可引用受版本控制的 schema；复杂值保存为 typed scalar/normalized columns或 IntakeArtifact ref，JSON 只能是已验证表示。
3. `intake_semantic_definitions` 与 `intake_action_definitions` 采用内部注册制，无外部 CRUD；已有 definition version 不可修改或删除，只能追加新版本。
4. Revision 必须显式绑定参与其 fingerprint 的 definition versions；Action transition 必须显式绑定 action definition version。读取历史不得 join “当前最新版定义”后重解释。
5. `intake_revision_semantics` 采用 normalized rows，让新增 semantic dimension 不需修改 Revision 主表；四个内建维度仍通过 registry/schema validation 强制存在。
6. `intake_item_transitions` 是长期业务 audit，不等于 S03 Process event；更新 Item current pointers/state 与追加 transition ledger 必须同事务。
7. IntakeArtifact direct owner 只能是 IntakeSnapshot 或 IntakeRevision 之一；Block/Vector 不进入该表。

#### Reasoning 与制衡

- 五张 identity 表直接对应 owner 选定的五类 Intake 身份；membership 把集合事实独立出来；两张 definition 表承接可治理扩展；revision semantics 与 item transitions 保留不可变业务历史。
- normalized semantics 会增加读放大，可由 S12 建 projection/index 优化；不能为了少一次 join 把未来语义重新塞回 JSON。
- internal registry 增加发布纪律，但这与 S03 Workflow registry 的治理方式一致：灵活来自追加已验证定义，而不是生产数据自由造 key。

- **问题**：Owner 是否接受上述十张 S04 logical truth tables，以及“封闭 identity/invariant columns + 内部注册且不可变版本化的 semantic/action definitions + normalized values/audit ledger”的 schema 路径？
- **业主回答**：业主同意上述十张 S04 logical truth tables、normalized semantic/action registries、immutable values/audit ledger 与 JSON cutoff。业主补充并重申 `S01-T040/T041` 已冻结的跨数据库规则：**所有 MKB-owned 持久业务表都必须包含 `payload_extra` 灵活字段**，用于开发阶段承接尚未稳定、尚不值得立即调整正式 schema 的扩展信息；schema migration bookkeeping、Turso/SQLite 引擎内部表、虚拟向量表、FTS shadow 表和第三方组件私有表不受此规则约束。该字段逻辑上为非空 JSON object，默认 `{}`；exact Turso type/check/size limit 由 S12 落地。`payload_extra` 不得承载 identity、FK/relation、required state、CAS/fencing、proof、权限、幂等键、核心 route condition 或必须索引过滤的真相；一旦某个扩展键进入这些语义，必须晋升为正式列或已注册且版本化的 SemanticDefinition/ActionDefinition。immutable truth row 的 `payload_extra` 随该行不可变；mutable current row 只能随受审计 CAS mutation 更新。禁止 secret、无界正文和大对象 bytes 进入该字段。
- **裁决状态**：`frozen → T-O-36 / T-O-37`

### Q5 — Snapshot acceptance 与 Revision decision 的原子事务（驱动真相：`T-O-31..33`）

- **单一裁决面**：一次 single/scatter 观察如何原子地成为 Snapshot、memberships、Items、Revisions 和后续执行意图。
- **影响范围**：`S03-S05/S12/S15`。
- **为什么必须确认**：S02/S03 已冻结“先 durable manifest，后 child scheduling”；S04 又要求 semantic dimensions 可扩展。如果 Snapshot、identity resolution、Revision diff 和 child route 分多次无围栏写入，崩溃会产生半个 manifest、重复 Revision 或漏投 child。

#### 推荐事务

1. S05 Process 先在事务外产出并验证 `IntakeCandidateSet`：IntakeSource ref、observation identity、scope/completeness、validator、raw IntakeArtifact refs，以及每个 external key 的 canonical semantic values。失败候选不进入 S04。
2. 进入单个 Turso transaction，校验 team/IntakeSource、candidate digest、绑定的 semantic definition set 与调用 Execution fence。
3. 以 IntakeSource + observation id/fingerprint 幂等插入 `IntakeSnapshot`；重复提交必须返回同一 IntakeSnapshot 或检测 semantic conflict，不能创建平行 accepted observations。
4. 对每个 candidate 按 `(team_uuid, intake_source_uuid, normalized_external_key)` resolve/create IntakeItem。
5. 使用**该次绑定的 definition versions**规范化各 semantic values，比较 ordered fingerprint tuple：相同则引用既有 Revision并记录 no-change；不同则 append IntakeRevision + semantic rows，并 CAS 推进 Item.latest pointer。
6. 对所有 seen members 插入 SnapshotMembership；仅当 Snapshot 是 complete + authoritative 时，在同一 scope 内计算 absent set并登记 typed absence decisions。partial Snapshot 不运行 absence set-diff。
7. 从 durable comparison 生成 `IntakeChangeSet`：只包含 typed facts，如 `item_created`、`revision_created`、`semantic_keys_changed[]`、`no_change`、`absence_candidate`，不包含 Process 名称。
8. 同一事务写入 S03 可消费的 child scheduling intents/outbox，并绑定 WorkflowRevision、Snapshot/Item/Revision refs、ChangeSet digest 和 causation；commit 后本地 queue 只负责 wake-up。
9. 任一步失败则整个 acceptance 回滚；IntakeArtifact bytes 若已在事务外落地，由 S13 orphan reconciliation处理，不能留下部分 S04 truth。

#### 路由 cutoff

```text
S04 comparison
  → immutable typed IntakeChangeSet
  → S03 WorkflowRevision evaluates registered route guards
  → materialize eligible child Execution/Process
```

S04 决定“哪些已注册语义发生了变化”，S03 决定“该事实走哪条 Workflow route”，S05-S09 决定“工序如何实现”。因此未来新增 semantic branch 时，只需追加 definition + WorkflowRevision/route guard，不改历史 Revision，也不把 `full_update/context_update` 永久硬编码在 Intake 表中。

#### Reasoning 与制衡

- 大 scatter transaction 可能过长。Round 3 可冻结 staging/page/commit protocol，但对外可见的 Snapshot revision 必须存在一个原子 acceptance point；不能通过牺牲 manifest consistency 降低事务长度。
- IntakeArtifact I/O 不应持有 DB transaction，因此允许 bytes 先写、truth 后提交；代价是需要 orphan scan，这优于 DB 已提交但 IntakeArtifact 不存在。
- ChangeSet 不携带 Process 名会多一次 Workflow evaluation，但保持 S04/S03 cutoff，并允许后续新增 route branch。

- **问题**：Owner 是否接受上述 acceptance transaction：validated CandidateSet → 原子 Snapshot/Item/Revision/Membership/ChangeSet + child intent → commit 后 queue wake；S04 只输出 typed semantic facts，实际 Process 路由完全由绑定的 WorkflowRevision 决定？
- **业主回答**：业主同意上述 acceptance transaction 与路由 cutoff：validated CandidateSet 原子形成 Snapshot/Item/Revision/Membership/ChangeSet 和 child intent，commit 后 queue 仅 wake-up；S04 只输出 typed semantic facts，由绑定的 WorkflowRevision 决定 Process 路由。`payload_extra` 可在 CandidateSet、Snapshot、Membership、Revision、ChangeSet/outbox 等相应数据库行保留非关键调试、provider 或开发期扩展上下文，但默认不参与 observation idempotency、Revision fingerprint、semantic diff、absence decision 或 route guard；需要参与时必须先完成 schema/definition 晋升。写入 immutable accepted truth 后不得原位修订其中的 `payload_extra`。
- **裁决状态**：`frozen → T-O-38 / T-O-39`

### Q6 — 小核心 lifecycle/serving state 如何承接可扩展 action 路由（驱动真相：`T-O-33..35`）

- **单一裁决面**：哪些状态/effect 必须封闭，哪些 action/reason/route 允许后续追加。
- **影响范围**：`S02-S04/S09-S10/S12-S16`。
- **为什么必须确认**：如果把每个业务原因做成 Item state，enum 会随需求膨胀；如果允许自定义 action 直接写 pointer/state，又会绕过 proof、CAS 和 tombstone。

#### 推荐方案

1. `IntakeItem.lifecycle_state` 只保留三个 core states：
   - `active`：Item 可持有 serving pointer；是否实际可检索还须满足 pointer/proof/index/query fence；
   - `deactivated`：可逆业务失活，serving pointer 必须为 null；
   - `deleted`：durable tombstone，普通 intake/rebuild command 不得恢复或复用 external key，serving pointer 必须为 null。
2. `IntakeSnapshot` 和 `IntakeRevision` 不复制运行状态。Snapshot 一旦 accepted 即 immutable；Revision 的 build/validation failure 属 Execution/derived generation，是否 current 只由 latest/serving pointer 与 lineage表达。
3. 封闭 core effects：`ACCEPT_LATEST`、`SET_SERVING`、`CLEAR_SERVING`、`SET_ACTIVE`、`SET_DEACTIVATED`、`SET_DELETED`、`NO_CHANGE`。一个 action definition 可组合有限 effect，但不能发明任意字段写入。
4. 内建 action definitions 至少包括 `accept_revision`、`publish_revision`、`deactivate`、`reactivate`、`delete`、`absence_deactivate`；manual/provider/policy/compliance 等原因不是新 core state，而是 versioned reason/semantic facts。
5. 新 action 必须内部注册 immutable `action_key + definition_version`，声明 allowed from-state、required proof/policy、core effects、route fact 和 idempotency key scope；外部 API 只能调用已暴露的 command contract，不能自造 action key。
6. 所有 transition 在一个 transaction 内：validate team/expected state/expected pointer/proof/action definition → CAS Item → append `intake_item_transitions` → 写 invalidation/publication outbox。queue ACK 不参与线性化。
7. Workflow route 只使用 action/semantic typed facts及绑定 definition version。新增 action 或原因需要新 definition + WorkflowRevision；运行中的 Execution 不热切路由。
8. `deleted` 的 hard purge、tombstone retention 或 owner-governed reopen 是否允许，留给 Round 3；在此之前 delete 作为普通业务路径的终止 fence。

#### Core transition matrix

| Action class | From | Core result | 必要围栏 |
|---|---|---|---|
| accept new Revision | active/deactivated | latest → candidate；lifecycle 不自动改变 | expected latest + Revision fingerprint |
| publish/replace | active | serving → proof target | expected serving + proof + policy revision |
| deactivate | active | lifecycle → deactivated；serving → null | expected lifecycle/pointer + causation |
| reactivate | deactivated | lifecycle → active；serving 仍为 null，后续 proof-gated publish | expected lifecycle + policy |
| delete | active/deactivated | lifecycle → deleted；serving → null；tombstone | expected lifecycle + causation |
| no-change | active/deactivated | current pointers不变；只记录 membership/decision | idempotency + Snapshot refs |

#### Reasoning 与制衡

- 三态核心容易验证，也能给 S10 提供明确 eligibility fence；业务差异放在 versioned action/reason facts 中，避免 `inactive_due_to_xxx` 状态爆炸。
- `reactivate` 不自动恢复旧 serving pointer，是为了重新验证 policy、proof 和派生 projection；代价是恢复多一步，但不会误暴露陈旧数据。
- delete 暂时终止普通路径可能限制误删恢复；Round 3 必须专门裁决 break-glass restore 与 tombstone retention，不能在 Q6 暗中放宽。

- **问题**：Owner 是否接受“三态 lifecycle + 封闭 core effects + versioned action definitions”的执行模型：新增语义原因和路由分支无需修改核心状态机，但任何新 action 都必须映射到受验证 effect，并通过 CAS/audit/outbox 与 WorkflowRevision 路由？
- **业主回答**：业主同意三态 lifecycle、封闭 CoreEffect、versioned ActionDefinition、CAS/audit/outbox 和 WorkflowRevision 路由的完整执行方案。`payload_extra` 在 Item current row 与 transition ledger 中只保存非权威扩展上下文，不能改变 allowed from-state、required proof/policy、CoreEffect、idempotency scope 或 route fact；transition ledger 中的该字段 append-only，Item row 中的更新必须与 CAS 和 transition audit 同一事务。新增语义原因仍须注册 ActionDefinition，不能只写入 `payload_extra` 后由代码分支偷偷解释。
- **裁决状态**：`frozen → T-O-40 / T-O-41`

## 9. ★ 中场评估 II（Round 2 → Round 3）

### 9.1 对 Round 2 的判定

`PASS / EXECUTION MODEL CLOSED`。Q4-Q6 全部获得 owner 接受，S04 的 relational truth topology、acceptance transaction、typed routing 和 lifecycle transition 已具备可实现边界。Owner 对 `payload_extra` 的补充不是对 normalized schema 的否定，而是一条跨表开发弹性契约：每张表都有安全扩展口，但关键语义必须晋升。

### 9.2 本轮已锁定真相

- `T-O-36/T-O-37`：十张 S04 logical truth tables，以及所有 MKB-owned 持久业务表强制 `payload_extra` 的用途、禁区与引擎私表例外；
- `T-O-38/T-O-39`：Snapshot acceptance 原子事务、typed IntakeChangeSet 与 Workflow route cutoff；
- `T-O-40/T-O-41`：三态 lifecycle、有限 CoreEffect、versioned ActionDefinition 与 CAS/audit/outbox transition。

### 9.3 `payload_extra` 的治理判据

```text
unknown / diagnostic / experimental value
  → payload_extra is allowed

value becomes required for
  identity | relation | state | CAS | proof | auth
  idempotency | routing | indexed filter | public contract
  → promote to a first-class column or versioned definition
  → migrate/validate explicitly
  → stop reading the payload_extra key as business truth
```

字段普遍存在不代表所有业务代码可以自由解释它。否则系统会形成无法索引、无法约束、无法迁移的“影子 schema”。Round 3 的恢复、purge 和 migration 也必须遵守同一晋升规则。

### 9.4 诚实反方制衡

- 所有表增加 JSON object 会带来少量 storage 与序列化成本；默认 `{}`、size bound 和不建默认 index 可控制成本。
- 开发者可能长期不晋升字段，因此 S12/S15 必须能够统计 key/size/读取依赖，并对被 route/filter 使用但未注册的 key fail-loud。
- immutable rows 的 extra 不能修补会降低临时修正便利；正确做法是追加 correction/transition/revision，而不是改写历史。

### 9.5 为什么提出 Q7-Q9

- `Q9` 由 `T-O-30..42` 驱动，撤回错误的 legacy migration/cutover 前提，改为冻结 empty-database bootstrap、MKB 自身 schema evolution、registry seed 与 S04 acceptance gate。

## 10. Round 3 — Reliability & Governance（Q7-Q9）

### Q7 — Large-scatter acceptance 与崩溃恢复如何保持一个集合真相（驱动真相：`T-O-31/T-O-38..41`）

- **单一裁决面**：当 CandidateSet 很大或进程在 acceptance/outbox/queue/IntakeArtifact 边界崩溃时，如何恢复到唯一 accepted Snapshot，而不制造 partial truth 或重复 child。
- **影响范围**：`S03-S05/S12-S15`。
- **为什么必须确认**：Q5 冻结了原子 acceptance，但真实 scatter 可能包含大量 members，IntakeArtifact I/O 又在事务外。仅写“事务处理”不足以定义 staging、size fence、重放与对账。

#### 推荐方案

1. S05 先把 `IntakeCandidateSet` 分页写入 non-canonical staging/projection：固定 `candidate_set_uuid`、IntakeSource、Execution fence、semantic definition set、page ordinal/count、每页 digest、expected member count 与 root digest。staging 数据库表同样必须有 `payload_extra`，但其内容不参与 seal digest，除非某键已晋升为正式字段或 definition。
2. CandidateSet 只有在所有 pages 到齐、page/root digest 校验、external key 去重、IntakeArtifact refs 可读取、scope/completeness 合法后才进入 `sealed` staging 状态；sealed 后页面不可变。
3. 设置明确的 `max_members_per_snapshot`、`max_candidate_bytes` 和 transaction budget。超限必须在创建 accepted Snapshot 前 fail-loud；v1 不把一次 authoritative observation 静默拆成多个互相独立的 partial Snapshots。
4. seal 后使用 bulk SQL 在一个 Turso acceptance transaction 中完成 canonical resolve/diff/membership/ChangeSet/outbox。网络、解析、IntakeArtifact write 和页面校验均不得占用该事务。
5. `(team_uuid, intake_source_uuid, observation_id/fingerprint)` 与 candidate root digest 形成幂等 fence：相同输入返回同一 Snapshot；相同 observation identity 但不同 digest 返回 conflict并保留审计。
6. Recovery/reconciliation 只允许以下确定性动作：

| 发现的状态 | 合法恢复动作 |
|---|---|
| staged pages 不全或 seal 超时 | 标记 staging abandoned；保留事件，按 retention 清理；不得创建 Snapshot |
| sealed CandidateSet、无 Snapshot | 重新执行同一 fenced acceptance transaction |
| Snapshot/ChangeSet/outbox 已提交、queue 未 wake | 从 outbox 重新 enqueue；不重建 Snapshot/Revision |
| queue 重复投递或 child 重放 | 由 child intent/process idempotency 与 fencing 收敛 |
| IntakeArtifact 已写、DB acceptance 回滚 | S13 依据 owner ref/digest grace period 标记 orphan并清理 |
| DB truth 引用缺失 IntakeArtifact | fail-closed、阻止 publish，创建 repair intent；不得伪造 virtual IntakeArtifact |
| Item latest/serving 与 transition ledger 不一致 | 依据最后一条 valid fenced transition repair projection或隔离告警；不得从日志猜 |

7. Reconciler 只修复 projection/wakeup/缺失 intent，不得合成一个从未原子提交的 Snapshot、Revision 或 proof。所有 repair 写入 causation、fence 和 append-only audit。
8. MKB-owned staging、outbox、repair 等持久业务表仍遵守 universal `payload_extra`；引擎/第三方私表继承 `S01-T041` 例外。recovery decision 只能读取正式列和 registered definitions。

#### Reasoning 与制衡

- 给 v1 设置 transaction/集合上限比伪装成无限扩展更可靠；超出上限时可以在未来 reopen generation-pointer protocol，而不是今天引入无法验证的 chunk visibility。
- sealed staging 增加暂存表和清理任务，但将耗时 I/O/校验移出 canonical transaction，使真正的线性化窗口只包含本地关系写入。
- Reconciler 权限刻意受限，防止“修复器”成为第二个业务状态机。

- **问题**：Owner 是否接受上述 large-scatter/recovery 协议：paged immutable CandidateSet staging + explicit size fence + one canonical acceptance point + deterministic reconciliation matrix；任何恢复都不能凭日志、queue 或 `payload_extra` 合成未提交的 Intake truth？
- **业主回答**：业主同意上述完整推荐方案。Large-scatter 必须使用 paged immutable IntakeCandidateSet staging、seal digest、显式 `max_members_per_snapshot` / `max_candidate_bytes` / transaction budget 和唯一 canonical acceptance point；超限在 accepted IntakeSnapshot 形成前 fail-loud，v1 不把同一次 authoritative observation 静默拆成多份 partial IntakeSnapshots。崩溃恢复严格按上述矩阵执行：只依据 durable IntakeCandidateSet、IntakeSnapshot、IntakeChangeSet、outbox、IntakeArtifact owner/digest、IntakeItemTransition ledger 与 fencing truth 做幂等重放、补 wake、补 child intent、orphan cleanup、projection repair或隔离告警。Reconciler 不是第二套业务状态机，不得从日志、queue、`payload_extra` 或孤立 IntakeArtifact 合成从未提交的 IntakeSnapshot、IntakeRevision 或 proof；所有 repair 必须保存 causation、fence 和 append-only audit。
- **裁决状态**：`frozen → T-O-43 / T-O-44`

### Q8 — MKB 内生 Retention、reindex 与 physical purge 如何分账并收敛（驱动真相：`T-O-34..35/T-O-40..42`）

- **单一裁决面**：在完全独立的 MKB 内，业务可见性改变后，各层数据何时保留、何时重建、何时允许物理删除，以及何时可声称完成。
- **影响范围**：`S04/S08-S10/S12-S15`。
- **范围校正**：`legacy-family` Purger 只证明“vector delete、task reset、rebuild 混义”的生产风险，不构成兼容或迁移要求。Q8 的所有 identity、generation、retention、backup 和 rollback 都只属于 MKB 自身。
- **为什么必须确认**：Q3/Q6 已冻结 logical-first；如果 MKB 自己仍让 retention、reindex 和 purge 共用一个 command，仍会产生误删、检索空窗或虚假完成。

#### 推荐方案

1. 明确四类互不替代的 MKB intent：
   - `deactivate`：立即 clear serving + lifecycle deactivated，可逆；异步 invalidation；
   - `delete`：立即 tombstone + clear serving，普通路径终止；异步 purge；
   - `rebuild/reindex`：不改变 IntakeRevision；创建新的 MKB derived/index generation，旧 generation 继续服务到 proof-valid switch；
   - `physical_purge`：只删除已无业务资格且通过 retention fence 的 MKB bytes/vector/projection，绝不 reset Task 或改变 Item lifecycle。
2. Retention reference fence 至少保护：latest/serving Revision、MKB 自身 serving/index rollback grace window、未完成 Task/Execution/restart lineage、legal/owner hold、未完成 cleanup intent，以及仍被 Block/Vector generation 或未来 Knowledge projection 引用的对象。
3. IntakeSource、IntakeItem tombstone 和 `intake_item_transitions` 属 MKB 长期审计骨架；即使正文、IntakeArtifact 或旧 IntakeSnapshot 被清理，也保留最小 identity、causation、digest 与 purge proof stub，防止 external key 被静默复用。
4. Snapshot/Membership、noncurrent Revision、IntakeArtifact、Block 与 Vector 可采用不同 retention class。具体天数由 S12-S15 配置，但删除资格必须由 first-class policy/reference 决定，不能从 `payload_extra.retention` 临时读取。
5. reindex 采用 MKB generation isolation：build new → validate count/digest/model space/filter coverage → CAS switch serving index generation → grace period → purge old generation。失败时旧 generation 继续服务。
6. delete/purge 为每个 MKB substrate 产生独立 cleanup intent 与 proof：relationship truth、vector index、IntakeArtifact backend、derived projections。只有所有 required proofs 完成才标记 `physical_purge_complete`；部分失败持续 retry，不能反向恢复 serving。
7. hard purge 只允许：Item 已 deleted、serving null、retention/hold 清空、restart/lineage refs 已处理、全部 cleanup proofs可重放。建议 v1 不允许 ordinary restore、break-glass resurrection 或彻底删除 tombstone；未来改变必须 owner-governed reopen。
8. `payload_extra` 随宿主行执行同一 retention；不得单独保留 secret/正文，也不得在 hard purge 后留下可反推已删除内容的无治理副本。
9. 任何 retention、reindex、restore、backup 或 purge 实现都不得查询 legacy-family 数据库、ID、status、R2 locator 或 callback；legacy code 只可出现在设计 reference anchor 中。

#### Reasoning 与制衡

- `T-O-42` 移除了迁移/cutover 复杂度，但没有消除 MKB 自己的 lifecycle 与物理清理问题；Q8 的核心判断因此不变，只需去除错误的 legacy 关联。
- 长期保留 identity/audit stub 会占用少量空间，但能维持 external key 防重、因果链和全局追溯；大体积 bytes/vector 才是主要 GC 收益。
- generation switch 需要双份短期容量，却避免 MKB reindex 期间检索空窗或混合模型空间。
- v1 禁止恢复 deleted Item 较保守；误删应优先使用 deactivate 或 MKB 自身备份恢复，而不是让普通 API 绕过 tombstone。

- **问题**：Owner 是否接受校准后的 MKB-only lifecycle/retention 宪法：deactivate、delete、rebuild/reindex、physical purge 四类 intent 分离；MKB index generation proof-switch；按本地 substrate 独立 cleanup proof；v1 hard purge 后保留最小 tombstone/audit stub且不允许普通 restore，并且全流程不依赖 legacy-family？
- **业主回答**：业主同意校准后的全部 MKB-only 推荐方案。`deactivate`、`delete`、`rebuild/reindex`、`physical_purge` 必须保持四种独立 intent：deactivate/delete 先提交 lifecycle/serving fence；rebuild/reindex 只创建新的 derived/index generation，不创建 IntakeRevision；physical purge 只在 retention/reference fence 全部解除后清理各 substrate，不重置 Task 或改变 IntakeItem lifecycle。reindex 采用 build → validate → CAS switch → grace → purge old generation；失败继续服务旧 generation。每个关系、向量、IntakeArtifact 与派生 projection 分别持有 cleanup intent/proof，只有全部 required proofs 完成才声明 `physical_purge_complete`。v1 不开放 ordinary restore、break-glass resurrection 或 tombstone 删除；正文和大体积派生物可按 policy 清理，但最小 IntakeSource/IntakeItem tombstone、因果、digest 与 purge proof audit 骨架长期保留。全流程只属于 MKB，不依赖 legacy-family 的任何运行数据或契约。
- **裁决状态**：`frozen → T-O-45 / T-O-46`

### Q9 — Greenfield bootstrap、MKB schema evolution 与 S04 acceptance gate（驱动真相：`T-O-30..42`）

> **题面修订记录**：旧 Q9 的 legacy migration/cutover 前提在 owner 回答前被 `T-O-42` 判定为不成立，因此整体撤回且不产生 Truth ID。Q9 编号保留，改问 MKB greenfield governance；不存在 legacy compatibility 的隐藏子题。

- **单一裁决面**：一套全新、空数据库的 MKB 如何确定性建立 S04 truth，并以哪些证据证明能够独立启动、演进和验收。
- **影响范围**：`S04/S12-S18`；本题只冻结 S04 对 bootstrap、schema evolution 和 acceptance 的要求。
- **为什么必须确认**：没有 legacy migration 不等于不需要数据库 bootstrap、registry seed、MKB 自身 forward schema migration 和验收门。若这些内容不冻结，同一版本可能在不同安装中得到不同 definitions、routes 或表约束。

#### 推荐方案

1. MKB 的唯一初始数据面是全新空数据库。bootstrap 不读取 legacy-family 文件、数据库、R2、ID、status、callback、env 或配置，也不提供 legacy importer、dual-read、compatibility adapter 和 cutover switch。
2. MKB 自身 schema bootstrap 必须版本化且可重复执行：创建十张 S04 truth tables以及已冻结的 MKB-owned staging/outbox/audit/repair 表，验证 PK/FK/unique/CHECK/CAS columns、team fence、XOR IntakeArtifact owner，并为每张适用业务表创建非空默认 `{}` 的 `payload_extra`。
3. Registry seed 使用不可变、版本化 `RegistryManifest` 确定性注册：
   - 四个 required SemanticDefinitions：source representation、canonical content、context metadata、filter metadata；
   - 内建 ActionDefinitions：accept revision、publish、deactivate、reactivate、delete、absence deactivate；
   - 每个 definition 的 key/version/schema/effect/route fact/digest；
   - 与已存在 S03 WorkflowRevision/route guard 的引用完整性。
4. 相同 app/schema/registry version + 相同 manifest digest 重跑必须 no-op；相同 version + 不同 digest 必须 fail-loud。bootstrap 不允许原位修改已注册 definition version。
5. 外部内容只能在 bootstrap 完成后通过正常 MKB Task/Intake Contract 进入；seed script、管理员 SQL 或 fixture 不得直接伪造 serving IntakeItem/Revision。
6. MKB 自身未来 schema evolution 采用 forward-only、版本化、可审计 migration；这是 MKB 内部版本演进，不是 legacy migration。schema migration bookkeeping 继承 `S01-T041` 的 `payload_extra` 例外；业务数据 backfill 必须显式校验且不能重解释历史 definition version。
7. 每次启动执行只读 bootstrap verification：schema version、registry manifest digest、required definitions/actions、Workflow refs、team isolation/index constraints 与未完成 migration。发现漂移时拒绝 readiness，不在启动时自动猜测修复业务 truth。
8. S04 最小 acceptance matrix：

| 验收面 | 必须证明 |
|---|---|
| Fresh install | 空 DB 一次 bootstrap 成功，第二次幂等；无 legacy dependency |
| Identity | 五类 UUID、source-scoped external key、team cross-reference 全部受约束 |
| Single/scatter | accepted Snapshot、membership、complete/partial/authoritative absence、child intent 顺序正确 |
| Revision semantics | immutable append、no-change、semantic dimension extension、历史 definition binding 正确 |
| Serving/lifecycle | proof-valid CAS、失败候选不污染、三态 transition、cancel 不撤销、tombstone fence |
| `payload_extra` | 全部适用业务表存在且 round-trip；核心状态/route/proof 不读取未晋升 key |
| Failure/recovery | 纳入 Q7 最终冻结的 crash/replay/reconcile scenarios |
| Retention/purge | 纳入 Q8 最终冻结的 generation switch、cleanup proof 与 hard-purge fences |
| Restart/readiness | 进程重启后仅由 DB truth + registered manifests 恢复；schema/registry drift fail-loud |

9. 独立性验收必须扫描 runtime dependency graph、config/env、DDL、API、queue/event envelope 和 startup path：不得出现对 legacy-family package、database/table、Worker callback、Cloudflare R2/D1/DO 或 legacy UUID/status 的运行依赖。
10. Legacy reference anchors 只允许存在于 design evidence、注释中的 rationale 或测试场景来源说明；测试期望必须表达 MKB Contract，不得要求重现 legacy wire/schema/status。

#### Reasoning 与制衡

- `T-O-42` 让 Q9 从复杂迁移计划收敛为更符合产品事实的 greenfield readiness gate。
- 确定性 registry seed 比“代码里默认存在”多一个 manifest/digest 机制，但它能证明不同安装获得完全相同的 semantic/action universe。
- forward schema migration 仍然必要：它解决 MKB v1→v2 的自身演进，和 legacy-family 兼容没有关系。
- 完全禁止 direct SQL seed serving data 会增加测试 fixture 工具成本；可以建设 test-only factory，但其输出仍必须走相同 domain invariants，不能成为生产后门。

- **问题**：Owner 是否接受重建后的 Q9：MKB 只从空数据库 greenfield bootstrap；schema/registry seed 确定性且幂等；未来只做 MKB 自身 forward schema evolution；以 fresh install、identity、single/scatter、Revision、serving、payload_extra、failure/retention 和“零 legacy runtime dependency”组成 S04 acceptance gate？
- **业主回答**：业主同意重建后的 Q9 全部推荐方案。MKB 的唯一初始数据面是全新空数据库；bootstrap 必须版本化、确定性、可重复执行，并创建 S04 canonical/staging/outbox/audit/repair schema、全部约束和适用的 `payload_extra`。SemanticDefinition、ActionDefinition 与 S03 Workflow references 由 immutable versioned RegistryManifest 注册：同 app/schema/registry version 且同 digest 重跑 no-op，同版本不同 digest fail-loud。任何真实内容只能在 readiness 后经正常 Task/Intake Contract 进入，生产 bootstrap/SQL/fixture 不得伪造 serving truth。MKB 后续只执行自身 forward-only、版本化、可审计 schema evolution；启动执行只读 schema/registry/reference verification，漂移或未完成 migration 时拒绝 readiness。S04 acceptance gate 必须覆盖题中完整矩阵，并通过 dependency/config/DDL/API/event/startup 扫描证明零 legacy runtime dependency；legacy-family 仅可作为设计与测试场景的 reference-anchor。
- **裁决状态**：`frozen → T-O-47 / T-O-48`
