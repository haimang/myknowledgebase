## 1. S04 重新校准后的工作面

### 1.1 S04 的唯一定位

S04 是 MKB 的 **长期知识资产身份、版本、血缘与可见性真相层**。它回答的不是“某个 Process 现在跑到哪一步”，而是：

1. 一份外部来源、一个逻辑文档及其每次内容/语义快照分别是谁；
2. single 与 scatter 中，哪些 Document 属于哪次可信 Source 观察集合；
3. 哪个不可变 DocumentVersion 当前获准对读取/检索可见；
4. Artifact、LS-RAG Block、VectorRecord 如何证明自己派生自某个 Version；
5. update、rebuild、deactivate、delete、purge 分别改变哪一层真相；
6. 物理清理尚未完成时，系统如何先阻止失活知识继续被检索。

S04 不是第二套 Task/Execution 状态机，也不是把 legacy `smind_files` 换名后搬入 Turso。

### 1.2 S04 应拥有的语义

| 责任面 | S04 应冻结的内容 |
|---|---|
| Canonical identity | `Source / Document / DocumentVersion` 的稳定身份、归属、基数和唯一性 scope |
| Source observation | single/scatter 的 Source snapshot/manifest、membership、completeness 与 parent-child provenance |
| Version lineage | immutable version、predecessor/revision、content/context/filter digests 与 generation reason |
| Publication | latest observed candidate 与 retrieval-visible published version 的分离、proof-gated pointer |
| Lifecycle intent | active/deactivate/delete/restore 的资源语义，以及与 Task cancel/retry/rebuild 的区别 |
| Derived lineage | Artifact、LSRagBlock、VectorRecord 对 DocumentVersion/producer config/proof 的稳定引用规则 |
| Isolation | `team_uuid` 在所有 canonical key、relation、manifest、publication 与查询中的强制参与 |
| Invalidation contract | S05-S09/S12-S13 对 version replacement、deactivate、delete、reindex 必须执行的语义 |

### 1.3 S04 不拥有的实现

| 不属于 S04 | 权威归属 | S04 只冻结什么 |
|---|---|---|
| Task HTTP、Task 六态、cancel/full retry/atomic rebuild admission | `S02` | 资源 command 产生的长期语义与目标 identity |
| Workflow、Execution/Process exact state、claim/retry/recovery | `S03` | Execution target 的 Source/Document/Version refs 与资源 Outcome |
| fetch/upload/parse/clean、hash 输入字段的业务选择 | `S05` | canonical digest contract 与 version decision 输入边界 |
| layered block、construction unit、embedding/vector exact schema | `S06-S09` | 必须 version-scoped、可失效、可追溯的 lineage contract |
| retrieval/reranking 算法 | `S10` | 只能读取 retrieval-eligible published version |
| Turso exact DDL、transaction/outbox、GC SQL | `S12` | 必须成立的 FK/unique/CAS/atomic visibility/invalidation 语义 |
| Artifact bytes、locator、filesystem layout、physical GC | `S13` | immutable logical Artifact identity、digest、lineage 与 retention fence |
| Event/Log/metric/alert 的物理模型 | `S15` | 必须产生的 source observation、publication、withdrawal 与 purge evidence |
| token、secret、跨 team 授权 | `S16` | team ownership 与 access-policy reference；Source 不保存 secret 明文 |

### 1.4 对 spec-index 原叙事的校准

`spec-index` 曾把 Source、Document、DocumentVersion、Artifact、LSRagBlock、VectorRecord 全部列入 S04 范围。首轮审查后的更精确 cutoff 是：

- `Source / Document / DocumentVersion / Source observation manifest / publication pointer` 是 S04 canonical truth；
- `Artifact` 的逻辑 lineage 与 version attachment 受 S04 约束，物理记录和存储由 S13 实现；
- `LSRagBlock / VectorRecord` 是版本派生资产，其 exact schema 和存储分别由 S06-S09 冻结；S04 不复制其内容表，只定义有效性必须从 DocumentVersion 继承；
- 删除/reindex 的业务意图和可见性围栏属于 S04；物理 vector mutation 属 S09/S12，Artifact GC 属 S13。

### 1.5 Round 1 不提前裁决

本轮不冻结：

- exact table 数量、物理列名、Turso trigger/index；
- exact resource status enum 与所有 transition；
- Source connector 种类、URL canonicalization、MIME/encoding/size；
- S05 对每类 provider 选择哪些字段计算 canonical content；
- LS-RAG Block/VectorRecord schema、embedding model upgrade；
- retention 天数、GC 批次、outbox/queue 实现；
- 外部 Document CRUD URI 和错误 envelope。

### 3.3 Legacy verdict

应继承：

- team-scoped identity 和查询；
- API scatter 的稳定业务 `atomic_id`；
- content hash 与 metadata hash 分账；
- unchanged skip、content full rebuild、metadata-specific route；
- parent/source 到 child 的可追溯关系；
- logical deletion 与物理 cleanup 不必同一瞬间完成。

必须重写：

- `file_uuid` 同时代表 Source、Document、当前 Version 和运行目标；
- random child UUID 先生成、随后靠 mutable relation row“锁回”；
- `(team_uuid, atomic_id)` 跨 source 冲突；
- 当前 hash/payload/R2 key 原位覆盖，不保留 version lineage；
- relations rows 兼任 Document、membership 与 runtime status；
- 从 Process 日志猜 Artifact；
- Vector process row 兼任长期 VectorRecord；
- purge、deactivate、delete、pre-rebuild reset 混为一个动作。

## 4. Web research：外部一手事实支持

> 外部资料只支持可迁移的设计原则，不替代 owner 裁决，也不要求 MKB 复制对应产品。

| Ref ID | 一手事实 | 对 S04 的支持边界 |
|---|---|---|
| `WEB-S04-01` | [W3C PROV-DM](https://www.w3.org/TR/prov-dm/) 把 provenance 建模为 entity/activity/agent、entity derivation、revision 与 collection membership；revision 是从前一 entity 派生出的新 entity。 | 支持 DocumentVersion 不应覆盖前身，以及 Artifact/Block/Vector 应有显式 derivation；它不规定 MKB 表结构。 |
| `WEB-S04-02` | [CloudEvents v1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md) 要求 `source + id` 对不同事件唯一，重复重发可复用相同 id。 | 类比支持外部业务键必须在 Source namespace 内解释，不能把裸 `atomic_id` 当 team 全局身份；CloudEvents 本身不是 MKB 资源协议。 |
| `WEB-S04-03` | [RFC 9530](https://www.rfc-editor.org/rfc/rfc9530.html) 区分 message content digest 与 selected representation digest，并明确 digest 是 integrity mechanism，不自动覆盖认证、授权或全部 metadata。 | 支持 MKB 分离 raw/source representation、canonical content 与 metadata/policy digest；不能用一个 hash 同时冒充身份、权限和完整版本语义。 |
| `WEB-S04-04` | [Apache Iceberg Specification](https://iceberg.apache.org/spec/) 使用 immutable files、snapshot/manifest 与 atomic current pointer；读者只看到已提交 snapshot，旧 snapshot 保留 lineage。 | 支持“先构建不可变 Version/派生集合，再原子切 published pointer”，而不是逐项覆盖当前可见数据。MKB 不复制 Iceberg 文件格式。 |
| `WEB-S04-05` | [RFC 9110 DELETE](https://www.rfc-editor.org/rfc/rfc9110.html#name-delete) 定义 DELETE 首先移除目标资源与当前功能的关联，既有表示和存储是否立即销毁由实现决定；异步执行可返回 202。 | 支持资源立即失去读取/检索资格与物理 Artifact/Vector GC 分离。 |
| `WEB-S04-06` | [Amazon S3 Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/versioning-workflows.html) 在普通删除时保留旧 versions并插入 current delete marker；指定 version ID 才永久删除特定版本。 | 作为实践证据支持 tombstone/current visibility 与 physical version deletion 分层；MKB 不采用 S3 作为初期 SSOT。 |

### 4.1 Web research 的综合结论

外部事实与 legacy 缺口共同支持三条 foundational 分母：

1. “逻辑资源”与“某一不可变版本”必须分开，否则无法表达 revision、回溯和派生关系；
2. 外部 ID 只有放在明确 Source namespace 内才可用于幂等收敛；digest 用于内容/表示/metadata 判断，不能替代身份；
3. publication/deactivation 是原子可见性决策，physical cleanup 是可恢复副作用；两者不能用一个 mutable `file_status` 或一次 vector delete 表达。

## 5. Round 1 — Foundational Knowledge Constitution（Q1-Q3）

### Q1 — S04 的 canonical identity graph 应如何切分

- **单一裁决面**：谁是长期知识身份，谁只是一次观察、版本或派生资产。
- **影响范围**：`S04-S10/S12-S13/S15`，并约束 S03 Execution target 与 S02 Document link。
- **证据驱动**：`U-S04-01..04/U-S04-10/U-S04-12`；`LF-S04-01..04/LF-S04-07..09/LF-S04-12`；`WEB-S04-01/02/04`。
- **为什么必须先确认**：如果 Source、Document、Version、relation、Artifact 和 Process target 仍共用一个“file”概念，后续任何 status、DDL、delete 或 reindex 问题都会产生多重真相。尤其 scatter parent 在 legacy 中既像 API 请求、又像父文件、又像 child collection，必须先决定其领域身份。

#### 推荐方案

采用以下 canonical graph：

```text
Team
  └── Source
        ├── single: 1 logical Document（通常）
        └── scatter: Source Observation / Manifest revision
              └── 0..N membership → Document

Document
  └── 1..N immutable DocumentVersion
        ├── 0..N Artifact refs
        ├── 0..N LSRagBlock refs
        └── 0..N VectorRecord refs
```

1. **Source**：稳定描述“内容从哪里来以及外部 identity namespace 是什么”。至少持有 `team_uuid`、source kind、provider/connector logical ref、external namespace、provenance 与 sync policy ref；不得保存 secret 明文。一次 upload、一个 URL、一个 API collection 都可以有 Source，基数不同但模型统一。
2. **Source Observation / Manifest revision**：一次可信 fetch/scan 得到的集合快照，保存 complete/partial/failure 语义、expected membership、source cursor/validator ref 与 digest。它不是 Task/Execution，也不是 DocumentVersion。
3. **Document**：一个随时间保持稳定的逻辑知识项。single 通常由 Source 产生一个 Document；scatter 每个业务 item 都是独立 Document。
4. **DocumentVersion**：Document 在某一时刻的不可变内容/检索语义快照；所有可复验的 clean、LS-RAG、Artifact 和 Vector lineage 都指向 version，而不是仅指向 Document。
5. **Artifact**：不可变内容载体/派生产物的 logical identity，由 S13 保存 bytes/locator；S04 只冻结其 version lineage 和 validity fence。
6. **LSRagBlock / VectorRecord**：S06-S09 拥有的 version-scoped derived assets，不是新的 canonical Document，也不能成为 Version SSOT。
7. scatter root Execution target 是 Source/manifest；child Execution target 是 Document + candidate Version。只有当 API 返回的 collection 本身也是有业务意义、需要独立检索的内容时，才额外创建一个 parent Document；不能为满足父指针而制造假 Document。
8. 所有 canonical entity、manifest 和 relation 都带 `team_uuid`；任何业务唯一键都必须在 team + source scope 下解释。

#### Reasoning

- Legacy `smind_files_relations` 已证明 child 是可以独立 ready、失败、更新和检索的长期资产，因此 child 必须提升为普通 Document，而不是依附父行的弱 relation record。
- D01/S02/S03 已冻结 scatter root 是 source controller、child 是 document Execution；Source/manifest 与 Document 的分离是对上游运行模型的资源侧补全。
- W3C PROV 的 entity/revision/collection 模型说明“同一逻辑事物的版本”和“集合成员”是不同关系；把 membership 塞入 Version 或把 Version 塞入 relation row 会破坏 provenance。
- Source 是 external key namespace。没有它，`listing-123` 在两个 provider、两个 endpoint 或两个 source config 下会错误碰撞。
- Artifact/Block/Vector 虽然重要，但都是可从 Version + config/proof 解释的派生层。让它们与 Document 平级成为 canonical identity 会造成删除、版本和 ACL 多头治理。

#### 诚实反方制衡

- 一次性 upload 也创建 Source 会增加一行和一次 join；收益是所有 provenance、external namespace 和 scatter/single 入口统一，避免以后再为 URL/API 补 Source 表。
- Source Observation/Manifest 增加集合元数据；但没有它就无法区分“完整空集合”“部分抓取”“抓取失败”，也无法为 S02/S03 提供可信 fan-in 分母。
- derived rows 全部 version-scoped 会增加 FK 与 storage；代价换来可重建、可失效和不会跨版本混检。

- **问题**：Owner 是否接受上述 identity ownership：`Source + Source Observation/Manifest + Document + immutable DocumentVersion` 构成 S04 canonical truth，Artifact/LSRagBlock/VectorRecord 是 version-scoped derived assets；scatter parent 默认是 Source/manifest 而不是伪造的 parent Document？

### Q2 — 什么变化必须生成新的 DocumentVersion

- **单一裁决面**：稳定 Document identity 下，哪些观察算同一版本、哪些必须追加新 Version。
- **影响范围**：`S04-S09/S12-S15`，并决定 S03 workflow route、S02 atomic rebuild 与 S09 reindex 是否改变知识版本。
- **证据驱动**：`U-S04-07/U-S04-09..11`；`LF-S04-02/04..06/09`；`WEB-S04-01..04`。
- **为什么必须确认**：Legacy 的 `content_hash/meta_hash` 能正确选择部分工作，但最终仍原位覆盖 relation row。若 MKB 不先冻结 version creation rule，metadata update、force rebuild、model upgrade 和 source replay 会各自发明“新版本”语义。

#### 推荐方案

1. **稳定 Document resolver key**：scatter 默认使用 `(team_uuid, source_uuid, external_key)`；single upload/URL 由 Source 建立稳定 subject key。`external_key` 保存原值与 normalized key，不能只使用 provider 返回的裸 ID。
2. **Version append-only**：每个 `document_version_uuid` 使用 MKB UUIDv7；同 Document 具有单调 version ordinal、`predecessor_version_uuid` 和 immutable creation reason。已创建 Version 不原位改正文、context/filter metadata 或 source representation。
3. **分离 digest scope**：至少区分：
   - `source_repr_digest`：抓取/上传的原始表示；
   - `canonical_content_digest`：S05 规范化后的知识正文；
   - `context_meta_digest`：提供给 LLM/结果展示的语义上下文；
   - `filter_meta_digest`：影响检索过滤/路由的 metadata；
   - `version_fingerprint`：上述被纳入版本语义的 canonical tuple + schema version。
4. **首次观察**：创建 Document + Version 1。
5. **canonical content 变化**：创建新 Version，走 full clean/LS-RAG/vector publication。
6. **context/filter metadata 变化**：也创建新 Version，因为返回语义或检索集合已改变；Workflow 可依据独立 digests 跳过不受影响的 Structurizer，但不能覆盖旧 Version。
7. **完全不变**：不创建新 DocumentVersion；只在 Source Observation/Manifest 中记录本次 seen/membership、validator 和 no-change decision。
8. **force rebuild、Workflow revision变化、prompt/model/embedding升级、丢失派生物修复**：如果 source/content/context/filter fingerprint 不变，不创建 DocumentVersion；它们创建新的 Execution/build lineage和派生产物 generation，仍引用同一 Version。
9. **上游 ETag/Last-Modified/provider hash**：只作 fetch validator/hint，不直接成为 MKB version truth；MKB 必须保存算法/normalization/schema version并计算自己的 canonical digests。
10. **竞态收敛**：同一 Document + version fingerprint 的并发写入唯一收敛；不同 fingerprint 通过 Document revision/CAS 有序追加，禁止 last-write-wins 覆盖 published pointer。
11. **安全/可见性 policy**：`team_uuid` 永久不变；ACL/visibility 的即时控制属于 Document policy/lifecycle revision，不伪装成内容 Version，但 publication proof 必须快照其 policy revision，防止旧 filter metadata 继续暴露。

#### Case matrix

| 输入事实 | Document identity | DocumentVersion | 下游工作建议 |
|---|---|---|---|
| 新 external key | 新建 | 新建 v1 | full build |
| 同 key，content digest 变化 | 保持 | 追加 | full build |
| 同 key，只有 context/filter digest 变化 | 保持 | 追加 | metadata-sensitive partial/full route |
| 同 key，全部 version digests 相同 | 保持 | 不新增 | manifest seen/no-op |
| 同 version，人工 rebuild | 保持 | 不新增 | 新 Task/Execution，重建 derived assets |
| 同 version，embedding model升级/reindex | 保持 | 不新增 | 新 vector generation/space |
| 同内容来自不同 Source/external key | 默认不同 | 各自 version | 可存 digest 相同但不自动合并 provenance |

#### Reasoning

- Legacy 已证明 content 和 metadata 变化会触发不同路径；MKB 的升级不是删除这套 diff，而是让 diff 决定“追加哪个 immutable Version + 运行哪条 Workflow route”。
- Metadata-only 变化若原位覆盖旧 Version，会使过去的 Vector/filter proof 无法解释，也可能让历史查询得到今天的 metadata。
- rebuild/model upgrade 是“如何重新派生”，不是“Source 告诉了我们一份新知识”。把它们算成 DocumentVersion 会让业务版本随基础设施变动膨胀。
- RFC 9530 明确区分 content 与 representation digest；它支持 digest scopes 分离，但 MKB 仍需自己定义 canonicalization、metadata 和 version fingerprint。
- Iceberg 的 immutable snapshot + atomic pointer 提供了外部实践支持：新候选先完整建立，再切当前引用，比原位覆盖更容易并发控制和恢复。

#### 诚实反方制衡

- metadata-only 也生成 Version 会增加版本数；可以通过 retention/compaction 管理 storage，但不能通过覆写历史消除成本。
- 同内容来自不同 Source 默认不合并，会保留重复 bytes/vector 的可能；后续可由 S13/S08做内容级物理去重，但 logical identity/provenance 不应自动合并。
- canonicalization 版本变化可能使 digest 改变；因此算法/schema version 必须入 fingerprint，迁移必须显式 rebuild，而不能静默重算旧行。

- **问题**：Owner 是否接受上述 version rule：Document 按 source-scoped external key 稳定；任何 canonical content、context 或 filter 语义变化都追加 immutable DocumentVersion；无变化、force rebuild、Workflow/model/embedding 变化只产生新的运行/派生 generation，不制造新的知识版本？
- **业主回答**：
- **裁决状态**：`awaiting owner`

### Q3 — Published Version、deactivate 与 delete 应如何分层

- **单一裁决面**：哪个 Version 对读取/检索可见，以及知识消亡何时生效。
- **影响范围**：`S02-S04/S09-S10/S12-S13/S15-S16`。
- **证据驱动**：`U-S04-05/06/09..12`；`LF-S04-07..11`；`WEB-S04-04..06`。
- **为什么必须确认**：Legacy 用 `file_status=ready/deleted`、relation `is_active`、vector purge 和 process reset 分散表达可见性。结果是新构建失败可能污染“当前”、删除向量不等于资源已删除、R2 删除失败又可能与 DB 状态漂移。S04 必须先给出一个统一的业务线性化点。

#### 推荐方案

1. **分开 latest 与 published**：Document 至少维护两个受 CAS 保护的逻辑引用：
   - `latest_version_uuid`：最新被接受的 immutable source/metadata candidate；
   - `published_version_uuid nullable`：当前允许业务读取/检索的 proof-valid Version。
2. **构建不影响当前可见版本**：新 Version 在 building/validation 期间，旧 published Version 继续服务；新构建失败只终结候选的 build，不把旧 published 指针清空。
3. **publication 是唯一上线线性化点**：只有 S03 汇总的 Artifact/Block/Vector/filter proof 全部满足，S04 transition 才能 CAS 切换 published pointer，并同时记录 predecessor、proof digest、policy revision 和 publication time。逐条 vector 写成功不能提前切换。
4. **旧 Version 不等于立即删除**：pointer 切换后旧 Version 成为 noncurrent/superseded lineage；是否保留 Artifact/Vector 由 retention、rollback 与 GC fence 决定。
5. **deactivate 是可逆的业务失活**：立即关闭 Document 的 retrieval/read eligibility，不删除 identity/version/history；物理 vector cleanup 可异步执行。重新出现时保持原 `document_uuid`，依据 digest 决定复用既有 Version并重建派生物，或追加新 Version。
6. **delete 是带 tombstone 的资源消亡意图**：先提交 durable delete/deactivate truth、causation与 visibility fence，再异步清理 Vector、Artifact 和其他 projections。直到每层返回 deletion proof 前，不得声称 physical purge complete；hard purge/retention 由后续轮次冻结。
7. **cancel 不改变知识生命周期**：Task/Execution cancel 只停止未完成工作，已 published Version 保持；必须由独立 `document.deactivate/delete` Task 才能撤销。
8. **scatter absence 需要完整性围栏**：只有 Source Observation/Manifest 明确 `complete + authoritative + absence-policy=deactivate` 时，本次 expected set 中缺失的旧 member 才可进入 deactivate；empty、partial、timeout、provider error 或 parser skip 一律不能推导“全部下架”。
9. **查询双围栏**：S10 关系查询必须要求 team + Document lifecycle eligible + exact published Version；Vector filter/index 也必须携带 team/document/version/publication generation。任一侧发现 tombstone或 pointer mismatch都拒绝返回，不能等待物理 delete 才停止暴露。
10. **删除与 GC 分权**：S04 持有 semantic intent/pointer/tombstone；S09/S12执行 vector invalidation，S13执行 Artifact GC，S15记录 evidence/alert。任何物理清理失败都可重试，不能反向恢复可见性。

#### Publication / withdrawal flow

```text
new immutable Version candidate
  → build/validate derived assets
  → publication proof complete
  → CAS Document.published_version_uuid
  → new Version retrieval-visible
  → old Version retained as noncurrent until GC fence

deactivate/delete intent
  → commit lifecycle fence/tombstone first
  → retrieval immediately excludes Document
  → durable invalidation/cleanup intents
  → Vector/Artifact projections converge
  → physical purge proof / retention completion
```

#### Reasoning

- S02/S03 已冻结 proof-valid child 可早发布、parent cancel/failure 不回滚，因此 published Version 必须独立于 Task/root terminal。
- 两指针避免“最新抓到的候选”和“当前可安全检索的版本”混为一谈。它使失败更新不会让已发布知识暂时消失，也避免 partial vectors 可见。
- RFC 9110 明确 DELETE 的首要语义是移除资源与当前功能的关联，物理信息是否销毁可以另行完成；S3 delete marker 进一步提供了版本化系统中 logical visibility 与 permanent deletion 分层的工程实例。
- Legacy Purger 已证明 vector delete 是多批次、可部分失败的外部副作用。若先删物理向量再写业务状态，崩溃会产生不可解释的半删除；应先提交 durable visibility fence，再可恢复地收敛副作用。
- 空 API 响应在 legacy 中被警告但仍可能进入 child diff 路径。没有 complete/authoritative manifest，自动把 absent child 视为 deactivated 会形成大规模误删风险。

#### 诚实反方制衡

- 两个 version pointer 和 publication proof 会增加 transaction/CAS 复杂度；但它们正是避免失败更新覆盖健康版本的最小机制。
- logical deactivate 后物理 vector 可能短暂残留；因此检索必须同时受关系 truth 和 version metadata 约束，不能只依赖 ANN 中是否还有记录。
- tombstone retention 会占用空间；但直接硬删 identity 会破坏 Task restart lineage、审计和 external key 防重。retention 时长应在 Round 3 与 S12/S15 冻结。

- **问题**：Owner 是否接受上述 publication/withdrawal 宪法：latest candidate 与 published Version 分离；proof-valid CAS 才切换可见版本；deactivate/delete 先提交 durable visibility fence/tombstone，再异步收敛 Vector/Artifact cleanup；仅 complete authoritative manifest 才能依据 absence 自动失活旧 child？
- **业主回答**：
- **裁决状态**：`awaiting owner`
