## 2. Round 1 — Foundational Constitution（Q1-Q3）

> **本轮边界**：只裁决“D02有权决定什么”“哪些对象才拥有状态机”“运行时谁有权选择下一步”。本轮不裁决Execution物理target字段、Membership/gate/artifact exact enum、S06 schema kinds、S08/S09 process拆分、clean curation、表数或DDL。

### Q1 — D02在v1是否只冻结“跨域宪法”，而不成为所有domain的总Spec

#### 单一裁决面

D02的规范权威边界和完成判据。此题不讨论任何一个具体状态或kind应该叫什么。

#### 已知事实

1. D01/S01-S05已经分别拥有自己的accepted Truth；D02不能重写这些domain；
2. D02-v0.2同时收录`FROZEN / DERIVED / PROPOSED / OPEN / CONFLICT`，信息完整但owner难以一次审阅；
3. 如果D02继续承担每个downstream enum、schema、route profile和DDL，它会变成第二份全系统Spec，并扩大v1；
4. 如果D02只做索引而没有任何规范权威，跨域状态抢权和S06反复reframe的问题又无法解决。

#### 推荐执行方案

将D02 v1的正式权威严格限缩为四类输出：

| D02允许冻结 | 精确含义 |
|---|---|
| 跨域所有权 | 哪个domain拥有哪一类状态、结果、指针和路由决定 |
| 跨域不变量 | 例如状态不得跨owner合并、下层proof向上归约、控制命令向下传播 |
| 跨域cutoff | 只裁决两个domain交界处谁交付什么、谁不能越权 |
| 裁决/defer登记 | 真正阻塞v1的冲突在D02关闭；domain内部细节明确交还对应Spec |

D02 v1明确不拥有：

- 新公共API或统一`ProductionStateProjection`产品；
- S06-S09 exact业务schema、kind全集或process key；
- S12物理表数、DDL、index、trigger与事务driver；
- S13-S15 retention数值、运营平台、metrics/alert/runbook；
- 为“以后可能需要”而增加的状态、plugin、动态registry或治理面。

一个开放点只有同时满足以下条件，才允许在本轮D02 campaign内关闭：

1. 它跨越两个及以上owner domain；
2. 不裁决就无法继续当前v1核心链路或恢复S06 QNA；
3. 裁决可以停留在logical contract/cutoff，不要求提前设计下游完整实现。

#### Reasoning

- 这使D02成为宪法而不是百科全书：它负责阻止domain越权，但不替domain完成设计；
- “是否阻塞当前v1”成为统一准入标准，可以直接淘汰大量看似合理但暂时无用的问题；
- 已accepted的exact状态仍由S02-S05引用，不需要D02复制全部解释；
- 后续owner只需审阅少量跨域裁决和defer清单，而不是逐行批准一千多行状态地图。

#### 风险与制衡

- 过度限缩可能把真实冲突推迟到实现期。因此每个defer必须写明owner domain、触发reopen条件和当前fail-closed行为；
- D02可以引用domain exact enum用于对账，但引用不等于取得其所有权；
- “S06需要”不能成为无限扩张理由，必须证明是S06下一轮问题的直接前置。

#### Owner 问题

Owner是否接受：D02 v1只冻结“跨域所有权 + 跨域不变量 + domain cutoff + blocker/defer登记”四类内容；凡不能证明同时满足“跨domain、阻塞当前v1/S06、无需提前设计完整实现”的问题，一律退回owner domain或defer，不进入D02冻结范围？

#### 业主回答

业主接受D02作为共有域真相层和状态宪法，但对“D02只做cutoff/defer登记”的原推荐作出重要增强：

1. D02必须包含上层建筑的形状，并明确哪些行为在全局上非法；
2. 具体如何执行仍由下游相关domain通过自己的QNA/Spec深入讨论，D02不替代它们；
3. 一旦下游讨论命中D02范围，下游与D02必须完成共同校准；
4. 下游冻结的相关真值必须复制一份到D02对应位置，使D02成为可核查不同区域状态控制冲突和命名漂移的共同ledger；
5. 因此D02不是只读索引，也不是执行总Spec，而是“共有宪法 + 状态ledger”。

`accepted with owner amendment / frozen → T-O-86 / T-O-87`

### Q2 — v1是否只承认六个已有状态族，其余全部作为正交事实而非新状态

#### 单一裁决面

MKB v1中“什么才算拥有合法边的状态族”。此题不讨论状态的物理列、表数、API形状或新业务kind。

#### 已知事实

D02之所以显得状态很多，主要原因是status、phase、Outcome、readiness、pointer和cleanup evidence都在自然语言中被叫作“状态”。但accepted Truth实际只冻结了六个具有自身合法transition的状态族：

| 状态族 | Owner | 已冻结集合 |
|---|---|---|
| Task aggregate | S02 | `queued/running/cancelling/succeeded/failed/cancelled` |
| Execution control | S03 | `created/ready/running/waiting/succeeded/failed/cancelling/cancelled` |
| Process control | S03 | `ready/claimed/running/retry_wait/succeeded/failed/cancelling/cancelled` |
| IntakeItem lifecycle | S04 | `active/deactivated/deleted` |
| CandidateSet staging | S04/S05 contract | `open/sealed/accepted/abandoned` |
| ExecutionGate | S05 | `open/released/rejected/superseded` |

以下内容都有业务价值，但不拥有独立通用状态机：

- Execution `phase_key`与`waiting_reason`；
- ProcessOutcome、Acquisition result、PreflightOutcome、Membership decision；
- Snapshot completeness与Source admission fence；
- Task result readiness、TaskItem outcome与`action_required`；
- latest/serving/generation-current/index-active选择指针；
- cleanup intent、physical proof与publication proof。

#### 推荐执行方案

冻结一条最小v1状态宪法：

1. D02只把上表六组称为`StateFamily`；
2. 六组exact values和合法边继续由S02-S05拥有，D02只引用和检查跨域组合；
3. 其他生产事实必须使用自己的typed名称，不得统一改名为`status`；
4. v1禁止建立全局`production_status`、stage-specific status或组合状态，例如`running_reviewing`、`structurize_retrying`、`latest_unpublished`；
5. 新需求优先用`existing state + typed fact/ref + proof`表达；只有现有owner状态机无法表达合法控制边时，才能reopen对应domain，而不是直接扩D02。

#### Reasoning

- owner需要记忆的不是几十个“状态”，而是六个owner明确的状态族；其余都是查询时并列展示的事实；
- 它保留了human wait、partial scatter、no-change、latest-versus-serving等真实业务信息，同时避免笛卡尔积状态爆炸；
- 它不改变任何已accepted enum，因此不会扩大v1实现量；
- 后续S06只需说明使用哪个Execution/Process状态以及产出什么typed artifact/proof，不需要再发明generation状态机。

#### 风险与制衡

- CandidateSet和Gate虽然是supporting truth，仍具有合法边，不能降格为随意字符串；
- phase和Outcome不是状态，不代表它们可以写入`payload_extra`；它们仍需typed schema、owner和校验；
- 查询层可以组合展示，但组合结果只能是projection，不能反向驱动SSOT。

#### Owner 问题

Owner是否接受：v1只承认上述六个已有StateFamily，不新增全局或stage-specific状态；phase、reason、Outcome、readiness、pointer和proof全部按正交typed fact管理，任何新状态诉求必须回到其owner domain证明现有状态机确实无法表达？

#### 业主回答

业主在Q1共有域宪法和Truth镜像原则的基础上，接受本题关于六个既有StateFamily、正交typed facts、禁止global/stage-specific状态以及新状态必须回到owner domain证明必要性的全部定义和约束。

`accepted / frozen → T-O-88`

### Q3 — v1运行路由是否只由bound WorkflowRevision消费typed facts后决定

#### 单一裁决面

运行时“谁有权选择下一步”。此题不讨论具体Workflow图、每条route内容、S06 node kind或S08/S09工序数量。

#### 已知事实

1. S01/S02的`request_intent`只表达外部希望MKB做什么，不等于Process或route kind；
2. S03已经冻结关系型Workflow SSOT、typed route/guard和ProcessCommand/Outcome边界；
3. S04/S05产生Snapshot、Membership、ChangeSet、PreflightOutcome和Gate等typed facts；
4. leaf Process只执行capability并提交Outcome/proof，不拥有next-step选择权；
5. D02中的大量routing matrix若被实现成第二个global router，会与S03 Workflow产生双真相。

#### 推荐执行方案

冻结唯一的v1 route authority：

```text
RequestIntent
  → 选择内部注册的 Workflow purpose/revision
  → Execution锁定exact WorkflowRevision与domain bindings
  → Process提交typed Outcome/proof
  → S03 Engine读取immutable typed facts并评估bound route/guard
  → materialize next Process / wait / fan-out / join / terminal candidate
  → owner transition service校验后推进各自状态族
```

因此：

1. D02 routing matrix只是跨域contract、合法组合与验收lint，不是第二套路由引擎；
2. Process handler、queue adapter、API controller、projection和`payload_extra`均不得决定next step；
3. D02只冻结route输入必须是durable typed facts、route authority归S03、状态推进仍归各owner transition service；
4. v1不新增global route registry、通用policy engine、动态agent route authoring或`ProductionStateProjection`反向写面；
5. 若某个domain需要新增route输入，它先持久化为该domain拥有的typed fact，再由versioned Workflow引用，不能让handler返回自由字符串控制流程。

#### Reasoning

- 这直接继承legacy SMCP/dispatcher已经验证的“声明式workflow解耦process”优势，同时删除多dispatcher、callback和补丁式route债务；
- D02负责规定边界，S03负责执行路线，两者不会成为双SSOT；
- single/scatter、preflight/human gate、retry/cancel都可以在同一route authority下表达，无需建立全局生产状态机；
- S06后续只需冻结输入artifact、schema与typed Outcome，不必承担是否继续S07-S09的控制责任。

#### 风险与制衡

- Workflow不能读取mutable latest、日志或外部live I/O；route所需事实必须先durable并绑定exact version/digest；
- S03也不能越权修改Intake lifecycle或Gate状态，只能调用对应owner transition；
- D02仍需保留跨域route acceptance scenarios，避免“矩阵不进runtime”被误解为“不做验证”。

#### Owner 问题

Owner是否接受：MKB v1只有S03 bound WorkflowRevision拥有运行next-step选择权；D02 routing matrix只作为跨域contract和验收lint，Process/queue/API/projection不得路由，各domain先提交typed durable fact，再由S03选择next Process、wait、fan-out/join或terminal candidate？

#### 业主回答

业主不接受由D02裁决本题的具体运行路由权：

1. D02不负责某一业务域“具体如何运行、如何路由”的问题；
2. 相关下游真相层负责进一步讨论、提供服务并冻结具体执行Truth；
3. 下游冻结后，必须依照Q1回到D02完成相关状态Truth回填和一致性校准；
4. 因此本题原先关于“S03 bound WorkflowRevision是唯一route authority”的推荐不作为D02 Truth冻结；D02只冻结责任cutoff和回填义务；
5. S06冻结后，当前推进顺序跳过S07，先选择一个更高价值、涉及通用状态控制的节点；由Codex届时结合完整Truth向owner推荐，当前不提前指定。

`question ownership rejected / cutoff frozen → T-O-89`

## 3. ★ 中场评估 I（Round 1 → Round 2）

### 3.1 对Round 1的判定

| 问题 | 判定 | 核心影响 |
|---|---|---|
| Q1 | `accepted with owner amendment` | D02不仅做cutoff，还必须成为共有宪法和状态Truth镜像ledger。 |
| Q2 | `accepted` | 六StateFamily成为owner可记忆的最小状态宪法，其余生产信息全部分账。 |
| Q3 | `question ownership rejected / cutoff frozen` | 具体运行路由退回下游；D02只接收冻结结果并检查宪法一致性。 |

Q1是本轮最关键裁决。它同时避免两个极端：D02既不能膨胀成所有domain的执行总Spec，也不能退化为只含链接、无法核查冲突的空索引。

### 3.2 本轮已锁定真相

- `T-O-86`：共有域宪法与非法行为权威；
- `T-O-87`：下游Truth必须与D02双向校准并镜像；
- `T-O-88`：六StateFamily + 正交typed facts；
- `T-O-89`：具体执行/路由归下游，冻结后回填D02。

### 3.3 对Q3原推荐的处置

Q3中的S03/Workflow分析可以继续作为S03已有Truth的事实说明，但D02无权通过本题重新冻结它。以下内容从D02 active recommendation撤回：

- 由D02宣布某个WorkflowRevision是全局唯一route authority；
- 由D02设计Process、wait、fan-out/join的具体运行算法；
- 把D02 routing matrix直接实现成runtime router或policy engine。

D02只能在下游冻结后核对：是否出现新状态族、是否抢占其他owner、是否把typed fact混成status、是否发生命名漂移或非法边。

### 3.4 诚实反方与风险

1. “复制一份Truth”若没有固定粒度，可能把D02重新复制成所有Spec全文；
2. D02镜像与下游源Truth可能因后续修订发生版本漂移，必须有明确校准协议；
3. 如果冲突时简单采用“更新版本”或“D02永远覆盖”，会破坏owner裁决和domain专业责任；
4. 如果只靠人工记忆回填，D02仍可能漏记；但v1也不应因此立即建设generator、CI平台或数据库化治理系统。

### 3.5 为什么进入Round 2

Round 1已经冻结“D02是什么”，但尚未冻结“这份宪法ledger怎样保持短、怎样镜像、怎样发现并处理冲突”。因此Round 2只问三个ledger execution问题：

- Q4由`T-O-86/T-O-88`驱动，裁决D02的可读文档形状；
- Q5由`T-O-87/T-O-89`驱动，裁决下游Truth镜像的最小单元；
- Q6由`T-O-86/T-O-87`驱动，裁决冲突/命名漂移的校准协议。

## 4. Round 2 — Ledger Execution（Q4-Q6）

### Q4 — D02是否重组为“短宪法核心 + 分域ledger + 冲突册 + 非规范附录”

> **驱动真相**：`T-O-86 / T-O-88`

#### 单一裁决面

D02正式文档的阅读形状。此题不讨论任何下游状态如何执行，也不决定是否拆分物理文件。

#### 为什么必须确认

D02-v0.2同时铺开状态、路由、kind、端到端场景和S06草案矩阵，适合作为调查底稿，但不适合作为owner日常核对的共有宪法。Q1要求它既能表达上层形状和非法行为，又能作为状态ledger；如果没有层次，后续每次镜像都会继续增加阅读负担。

#### 推荐执行方案

保持D02为一份共有域权威文档，但把正文重组为四层：

1. **Constitution Core**：只保留D02角色、六StateFamily、状态/事实分账、控制向下/proof向上、共有非法行为；
2. **Domain State Ledger**：按Task、Execution、Process、Intake、Gate等owner分区，每区只镜像当前exact状态、合法边、正交事实和权威Truth引用；
3. **Conflict & Drift Register**：集中登记跨域冲突、命名漂移、未完成共同校准和owner-gate；
4. **Non-normative Appendix**：保留调查价值较高的组合矩阵、端到端例子和历史推理，但明确不能从appendix直接生成enum、route或DDL。

当前D02-v0.2中的kind大全、完整路由目录和S06候选矩阵先降为appendix；只有下游正式冻结并完成镜像后，相关精简Truth才进入ledger正文。v1不拆出多份新D02子Spec，也不建设单独管理系统。

#### Reasoning

- owner首先看到的是少量宪法和当前冲突，而不是全部推理材料；
- ledger仍保留exact真值副本，满足Q1的核查要求；
- appendix保存调查证据，避免为了“变短”丢掉未来复核上下文；
- 单文件在v1最简单，不产生新的文档发现、版本和冻结协调成本。

#### 风险与制衡

- appendix不得成为“没人维护的第二真相”，其中与ledger冲突时必须明确以最新owner-frozen ledger为准；
- Constitution Core只能保存跨域不变量，不能偷偷放入S06-S09业务算法；
- exact表格可以引用下游，但必须足以在不打开所有Spec时发现命名漂移。

#### Owner 问题

Owner是否接受把D02重组为“短Constitution Core + 分域State Ledger + Conflict/Drift Register + non-normative Appendix”的单文件结构，并将现有长篇kind/route/S06候选矩阵降为非规范附录，今后只有下游已冻结且完成共同校准的精简Truth才能进入ledger正文？

#### 业主回答

业主于2026-08-10要求直接收口并冻结D02，接受本题推荐的单文件四层结构。D02-v1.0据此将规范正文限制为Constitution Core、Domain State Ledger与Conflict/Drift Register，原调查矩阵统一降为non-normative Appendix。

`accepted / frozen → T-O-90`

### Q5 — 下游Truth回填D02时，是否只复制一个最小“状态契约镜像块”

> **驱动真相**：`T-O-87 / T-O-89`

#### 单一裁决面

每次下游冻结后，究竟复制什么到D02。此题不设计数据库schema、代码manifest或自动同步工具。

#### 为什么必须确认

Q1要求真值复制到D02，但“复制全文”会让D02无限膨胀，“只放链接”又无法独立核对状态冲突。必须冻结一个介于二者之间的最小镜像粒度。

#### 推荐执行方案

每个与D02相关的下游冻结点，在对应Domain State Ledger中追加或更新一个Markdown状态契约镜像块，只包含：

| 镜像内容 | v1最小要求 |
|---|---|
| 权威来源 | owner domain、Spec/QNA版本、Truth-ID和精确章节 |
| 状态所有权 | StateFamily或正交fact的唯一owner、允许的writer/transition service |
| exact状态 | 当前enum与合法边；若不是StateFamily则明确写`not a state machine` |
| 跨域输入输出 | 只列与其他domain接壤的typed fact/ref/proof和cutoff |
| 非法行为 | 禁止alias、抢权、非法back-edge、从projection/log/payload猜Truth |
| 校准影响 | 本次修改了D02哪一块，哪些consumer需要复核 |

镜像块是源Truth的规范化副本，不复制：完整业务schema、所有字段、算法、DDL、API示例、风险清单或实现计划。下游仍是具体执行细节的权威；D02是跨域形状、命名和状态控制核对权威。

触发回填的条件只限于：新增/删除/改名状态，改变合法边或owner，新增会影响route/control的正交fact，改变跨域cutoff，或发现原镜像错误。普通文字润色、实现优化和domain内部非状态字段不触发D02更新。

#### Reasoning

- 六项内容足以发现状态集合、owner、边和命名漂移；
- 通过Truth-ID和版本保持可追溯，不需要v1额外设计digest服务或自动同步平台；
- 明确触发条件能避免每次下游小修改都重写D02；
- “不是状态机”本身也需要镜像，防止phase/outcome/pointer日后被重新包装成status。

#### 风险与制衡

- 镜像是规范性副本，不能把D02摘要写成与源Truth不同的新解释；
- 如果精简后丢失关键guard，应扩充该镜像块，而不是把整个下游Spec复制进来；
- source version/Truth-ID变化但语义未变时，仍应更新引用，避免表面版本漂移。

#### Owner 问题

Owner是否接受上述六项Markdown“状态契约镜像块”作为v1唯一回填单元，并只在状态/合法边/owner/控制性typed fact/跨域cutoff变化时触发D02共同校准，而不复制下游完整schema、算法、DDL和实现细节？

#### 业主回答

业主于2026-08-10通过D02直接收口指令接受六项Markdown“状态契约镜像块”作为v1唯一回填单元。该选择冻结的是Truth治理粒度，不新增runtime对象、数据库表或公共契约。

`accepted / frozen → T-O-91`

### Q6 — 发现D02与下游冲突或命名漂移时，是否强制进入同一轮双文档校准

> **驱动真相**：`T-O-86 / T-O-87`

#### 单一裁决面

冲突和漂移的处理协议。此题不裁决任何一个现存开放冲突的业务答案。

#### 为什么必须确认

D02和下游都保存相关真值副本后，天然存在双边漂移风险。必须明确谁不能静默覆盖谁、什么情况下暂停推进，以及一次裁决怎样同时落回两边。

#### 推荐执行方案

冻结以下最小校准协议：

1. 发现状态集合、合法边、owner、typed fact分类、canonical name或非法行为不一致时，先登记一个D02 conflict/drift条目，引用双方精确版本和Truth；
2. 只改变source version/章节引用且语义完全相同的citation drift，可以在同一校准变更中机械修正，无需重新请求owner裁决；
3. 一旦涉及canonical name、owner、enum、合法边、state-vs-fact分类或非法行为变化，即属于semantic drift，必须进入owner-gate；
4. 不以文件更新时间、版本号更大或“实现已经这样写了”自动决定语义冲突；D02共有宪法约束跨域合法性，下游domain负责具体业务解释；
5. 裁决后在同一个校准工作单元内更新下游源Truth与D02镜像块，并分别写revision history；只改一边不算完成；
6. semantic conflict关闭前，受影响的新Spec不得把任一候选解释成frozen；实现若必须继续，只能采用现有最后一致Truth并对新分支fail-closed；
7. v1先采用QNA/Spec评审时的人工checklist与全文搜索完成对账，不建设自动同步器、schema generator、状态治理服务或新的CI平台。

#### Reasoning

- D02拥有宪法权威但不拥有全部业务解释，因此不存在简单的“D02永远覆盖下游”；
- 同轮双写和修订历史可以防止只修摘要、不修源头，或只改源头、ledger继续漂移；
- 最后一致Truth + fail-closed为冲突期间提供安全默认，不需要新增runtime状态；
- citation drift与semantic drift分级，避免无语义变化的版本引用修正反复占用owner gate；
- 人工协议足以支撑当前v1文档规模，自动化应等真实重复成本出现后再讨论。

#### 风险与制衡

- “同一轮”指同一个校准变更，不要求同一数据库事务或工具平台；
- D02 conflict条目不是新的业务状态机，只是Truth治理记录；
- 紧急修正也必须留下causation和后续补齐要求，不能以hotfix永久绕过宪法。

#### Owner 问题

Owner是否接受：D02/下游漂移必须先登记并在同一校准工作单元更新两边；纯citation drift可机械修正，涉及name/owner/enum/合法边/state-vs-fact的semantic drift必须进入owner-gate；版本新旧和现有实现不能自动决定语义权威，冲突未关闭前沿用最后一致Truth并对新分支fail-closed；v1只用人工checklist/搜索，不建设自动治理平台？

#### 业主回答

业主于2026-08-10通过D02直接收口指令接受本题最小漂移协议：citation drift机械修正，semantic drift显式gate，同一校准工作单元双向更新，冲突期间沿用最后一致Truth并对新分支fail-closed；v1不新增自动治理平台。

`accepted / frozen → T-O-92`
